#4
Are AI labs pelicanmaxxing?
⬆ 547 pts 💬 211 HN comments

Simon Willison's informal benchmark—asking LLMs to generate an SVG of a pelican riding a bicycle—has become a de facto test for model capability and a potential target for optimization. In this post, Dylan Castillo systematically tests the hypothesis that AI labs are 'pelicanmaxxing' by generating 1,008 SVGs across seven frontier models (including GPT-5.6 Terra, Claude Sonnet 5, Gemini 3.5 Flash) using an 8×6 grid of animals and vehicles. Each SVG is scored by an LLM judge on animal quality, vehicle quality, and action coherence. A fixed-effects regression adjusts for inherent difficulty of each combination, allowing isolation of model-specific boosts on pelicans, bicycles, or the specific combo. The methodology is rigorous, controlling for multiple comparisons and providing confidence intervals.

The findings are clear: no lab shows significant pelicanmaxxing. Pelicans rank 6th out of 8 animals, bicycles 2nd last out of 6 vehicles, and the pelican-bicycle combo is 42nd of 48. Only Gemini 3.5 Flash shows a marginal bicycle boost (p=0.022) that does not survive Bonferroni correction. The strongest cell effect is from GLM-5.2 but is insignificant. Interestingly, 100% of pelican-bicycle images face right, but this mirrors broader trends (60% of all images face right) and is explained by bicycle photography conventions. Comments from simonw and others praise the methodology, while some suggest labs may be 'svgmaxxing' generally. Skeptics argue benchmarks are inherently tainted, and others note subtle biases like the 'ottermaxxing' observed in plane scenes. The post remains a landmark in systematic evaluation of informal benchmarks.

No lab demonstrated significant pelicanmaxxing: the pelican-bicycle combo ranked 42nd out of 48, and all model-specific effects were within chance.

Key Highlights
  • The pelican-on-a-bicycle benchmark is a famous informal LLM test; this study systematically tests for optimization across 7 models and 48 animal-vehicle combos.
  • 1,008 SVGs were generated and scored by an LLM judge; regression analysis found no significant pelican, bicycle, or combo-specific boosts.
  • All 21 pelican-bicycle images face right, but this aligns with a general rightward bias (60% of all images) and bicycle photography conventions.
  • The strongest signal was GLM-5.2's non-significant cell effect (p=0.12); Gemini 3.5 Flash showed a marginal bicycle effect (p=0.022) that fails multiple comparison correction.
  • Commenters discussed broader 'svgmaxxing', potential training data contamination, and the need for out-of-distribution tests to truly evaluate generalization.

GigaToken: ~1000x faster Language model tokenization
⬆ 513 pts 💬 107 HN comments

GigaToken is a Rust-based tokenizer that achieves up to 1000x throughput improvements over HuggingFace's tokenizers and tiktoken by heavily optimizing pretokenization with SIMD, replacing regex engines with hand-tuned byte-level operations, and implementing a multi-level caching hierarchy for pretoken-to-token mappings. The library supports nearly all common BPE-based tokenizers (GPT-2, Llama, Qwen, DeepSeek, etc.) and offers both a native Rust API and compatibility layers for HuggingFace and tiktoken. Benchmarks on 144-core EPYC show sustained encoding rates of 20-25 GB/s for many models, while single-file end-to-end encoding of 11.9 GB OWT text completes in under half a second. The author, Marcel Rød, emphasizes that a majority of the code was hand-crafted without AI assistance, with AI used only for final polishing and porting. The project is MIT-licensed and available via pip.

The performance claims are striking: on an EPYC 9565, GPT-2 tokenization runs at 24.53 GB/s versus 24.8 MB/s for HuggingFace – a 989x speedup. On Apple M4 Max, gains exceed 1000x for some tokenizers. The author estimates that the entire Common Crawl corpus (~130 trillion tokens) could be tokenized in 6.5 hours using this approach. However, SentencePiece-based tokenizers see modest gains (7x–20x), indicating the optimization is BPE-specific. Compatibility mode, which preserves exact output with HuggingFace, still delivers ~200-300x speedup but is slower than the native API. The project has garnered 1.7k stars and 107 comments on Hacker News, with discussions spanning practical utility for training data preparation, skepticism about tokenization being a bottleneck, and broader implications for software optimization in the AI stack.

On an AMD EPYC 9565, GigaToken tokenizes GPT-2 at 24.53 GB/s – nearly 1000x faster than HuggingFace's 24.8 MB/s, and could process the entire Common Crawl in under 6.5 hours.

Key Highlights
  • SIMD-accelerated pretokenization and multi-level cache achieve ~1000x speedup over HuggingFace tokenizers for BPE-based models.
  • Native Rust API and compatibility layers for HuggingFace/tiktoken enable drop-in replacement with minimal code changes.
  • Benchmarks across diverse tokenizers and CPUs show consistent gains, especially on modern x86 and ARM (e.g., 989x on EPYC, 1268x on M4 Max).
  • SentencePiece-based tokenizers see smaller gains (7-20x), highlighting BPE-specific optimization.
  • Author claims majority of code hand-coded without AI, with AI used only for final stages; project is open-source under MIT.

Show HN: Cactus Hybrid: We taught Gemma 4 to know when it's wrong
⬆ 140 pts 💬 28 HN comments

Cactus Hybrid introduces a pragmatic hybrid inference architecture where small on-device models are post-trained with a confidence probe that scores each answer between 0 and 1 directly from hidden states—never parsed from text. The probe is trained on Gemma 4 E2B to detect correctness without modifying base weights, achieving an average AUROC of 0.814 across text, vision, and audio benchmarks, far outperforming token entropy (0.549). The method is modality-agnostic: the probe generalizes to audio tasks despite zero audio training data, indicating a deep correctness signal. The project provides integrations for multiple frameworks (Python, MLX, Transformers, llama.cpp) and is MIT-licensed with Gemma model terms.

By routing only 15–35% of queries to a larger model (Gemini 3.1 Flash-Lite), Cactus Hybrid matches its performance on benchmarks like MMLU-Pro and ChartQA while maintaining privacy and latency benefits of local inference. The community response has been cautiously optimistic: some commenters suggest improving calibration with conformal prediction or combining multiple confidence indicators, while others question the philosophical framing of “knowing when wrong.” The project’s transparency around strengths (freezing base weights, high AUROC on zero-shot audio) and limitations (degradation at higher quantization) invites practical experimentation. Developers are already integrating the system for voice transcription tasks, suggesting real utility beyond the lab.

The confidence probe achieves 0.814 mean AUROC vs 0.549 for token entropy, with zero audio training data yet reaching 0.79–0.88 on four audio benchmarks—revealing a modality-independent correctness signal.

Key Highlights
  • Post-trained probe outputs confidence from hidden states, not output text, enabling reliable handoff decisions.
  • AUROC of 0.814 across text, vision, audio, far exceeding token entropy (0.549).
  • Hybrid architecture routes only 15–35% of queries to larger model, matching Gemini 3.1 Flash-Lite on benchmarks.
  • Freezes base weights to avoid degradation; quantization degrades performance but still effective at 4-bit.
  • Open-source integrations for Python, MLX, Transformers, and llama.cpp; MIT-licensed.

Show HN: Bento - An entire PowerPoint in one HTML file (edit+view+data+collab)
⬆ 851 pts 💬 190 HN comments

Bento is a single-file HTML slide deck tool that has garnered significant attention on Hacker News (851 points, 190 comments) for its innovative architecture: the entire presentation—including editor, viewer, data, and collaborative features—is packed into one self-contained HTML file. The core design separates a plain JSON blob (slide data) near the top of the file from a base64-encoded, compressed application blob that deflates in the browser using DecompressionStream. This eliminates external runtime dependencies and enables offline use via the File System Access API for direct JSON writeback. The tool supports rich animations (Ken Burns, morph transitions, count-up numbers), charts, and real-time collaboration through Cloudflare Durable Objects, though the implementation is still maturing—some users noted performance issues under heavy concurrent editing and an unintended Cloudflare Insights beacon contradicting the 'nothing phones home' claim.

The HN community response reveals a deep appreciation for Bento's alignment with the single-file web app philosophy, reminiscent of TiddlyWiki or mdwiki. Many commenters highlighted the practical advantages for corporate environments tired of traditional slide software, with one noting that 'internal IT fiefdoms everywhere should be very afraid.' However, the discussion also surfaced legitimate concerns: accessibility (no alt text for images), naming confusion with BentoPDF, and the tension between self-contained simplicity and enterprise needs like SSO. Comparisons to existing tools—Reveal.js, Slidev, Marp, and impress.js—were common, with some favoring Bento's WYSIWYG editing over markdown-based workflows. The creator, starfallg, actively engaged, promising fixes for the phone-home issue and negative chart axis bug, and showing openness to feedback, which earned goodwill despite the rough edges.

"The file contains more or less two sections. There is a plain block of JSON near the top of the file which is the slide data... the app itself is in a base64 blob that loads through a small shim which deflates in the browser with DecompressionStream."

The author, relying heavily on LLM assistance (Opus 4.8), ported the Qualcomm TFE665 ISP driver from the existing TFE530 codebase, adapted the CSID and CSIPHY blocks, and fixed a subtle register mismatch (packer format) that caused all-zero frames. The OV13B10 sensor driver, previously x86/ACPI-only, was extended for device tree. After enabling libcamera's simple pipeline and adding a gain helper, the camera produced live, auto-exposed previews at ~30 fps, albeit with fixed focus and cropped field of view due to broken binned modes. The work highlights both the feasibility of mainlining modern smartphone cameras and the remaining gaps in power sequencing, autofocus, and image quality.

The article generated significant community discussion, with 125 points and 33 comments focusing on three main themes: the viability of LLMs for low-level driver development, the tension between security requirements (GrapheneOS) and Fairphone's repairability, and the ethics of AI-assisted writing. Several commenters noted the article's AI-influenced style (bolded filenames, enumerative structure), which the author's friend confirmed as LLM-assisted. Despite skepticism, the technical achievement is real: the author found that TFE665 is register-compatible with TFE530, differing only in write-bus offset and packer width. A single register change (0xa → 0x0) resolved a "Bad config violation"—a classic example of how obscure hardware details can derail bring-up. The project repository is public, inviting further contributions to fix binned modes and add proper power management.

Changing the RDI write-master packer from PLAIN64 (0xa) to 0x0 turned all-zero frames into real Bayer images, revealing that TFE665 uses a 128-bit bus while the mainline driver assumed 64-bit.

Key Highlights
  • TFE665 ISP is register-compatible with mainlined TFE530; only write-bus offset and packer format differ.
  • Missing CAM_CC_SOC_AHB_CLK caused silent register read failures—a common Qualcomm trap.
  • OV13B10 sensor driver extended for device tree and libcamera gain helper added.
  • Binned sensor modes produce garbled output; disabling them restricts preview to cropped full-res.
  • Fixed focus via DW9714 VCM driver; no autofocus algorithm in libcamera's software ISP yet.

Malleable Computing, Emacs, and You
⬆ 112 pts 💬 31 HN comments

The article by Charles Choi presents a concrete example of malleable computing using Emacs to build a custom GitHub issue management tool, `fj.el`, in just 400 lines of Elisp over a day. It demonstrates how Emacs allows users to compose external tools (e.g., `gh`, Pandoc) and existing packages (Transient, vtable) to create bespoke workflows without needing a full-featured client. The narrative emphasizes the empowerment of building for one's own needs, contrasting it with supply-driven software like Microsoft Office. The author argues that malleable environments enable combinatorial reuse, where desired behavior emerges by recombining building blocks, sidestepping the 90/90 rule and Pareto principle for personal tools.

Key technical details include the `fj-request-issues` function that shells out to `gh` and parses JSON into Elisp hash tables, using shell-command-to-string for synchronous calls. The tool covers listing issues, copying to Org, creating issues, and opening in browser, all via a Transient menu. The article touches on software scope: building for 1 vs. N, noting that malleability shifts product definition burden to the consumer. Comments reveal diverse perspectives: some celebrate Emacs' legacy of live coding and extensibility, others point to overlooked existing solutions (Magit Forge) or missing sync. The discussion reflects a deep appreciation for user agency but also recognizes the complexity of scaling such approaches.

400 lines of Elisp built in roughly 2.5 hours covers core functionality, illustrating how malleable computing enables rapid, personal tool creation.

Key Highlights
  • Malleable software lets users combine building blocks (gh, Pandoc, Elisp) to create bespoke tools without building from scratch.
  • Emacs' live coding environment (scratch buffer, REPL) eliminates the edit-compile-restart cycle, accelerating prototyping.
  • The 90/90 rule and Pareto principle apply less to personal tools where building for 1 is sufficient and fast.
  • Trade-offs: building for 1 vs. N involves error handling, documentation, and distribution overhead.
  • Historical precursors (Lisp machines, Smalltalk) offer similar malleability, but mainstream computing has moved away.
