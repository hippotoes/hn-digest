Claude-real-video － any LLM can watch a video
⬆ 137 pts 💬 43 HN comments

Claude-real-video is a Python tool that enables any LLM to meaningfully 'watch' a video by extracting scene-aware, deduplicated frames and transcripts, all processed locally. Unlike existing approaches—ChatGPT typically reads only the transcript, Claude rejects video files outright, and Gemini samples frames at a fixed 1 fps, missing fast cuts and oversampling static scenes—this tool uses ffmpeg for scene-change detection and a sliding-window pixel-difference dedup algorithm. It ensures each shot is represented only once, even after cutaways (A-B-A edits), and provides a density floor to guarantee at least one frame per N seconds. Audio transcription via Whisper or embedded subtitles, plus optional retention of the full audio track, adds a layer of multimodal context. The output is a folder of frames, a transcript, and a manifest that can be fed to any LLM locally or in the cloud.

The project has garnered 387 stars and sparked lively debate on Hacker News. Many commenters praised the technical execution—calling it 'clever' and 'useful'—while others questioned its token efficiency, noting that feeding many frames to Claude can be expensive. Some pointed out that Gemini already natively supports video analysis, and several shared alternative libraries (e.g., vlm-run). A recurring critique was that keyframes cannot convey motion or object permanence, limiting understanding of dynamic content. The author of a similar tool also contributed, highlighting the ongoing exploration of optimal video encoding for LLMs. The tool is MIT-licensed and designed for offline use, but as one commenter noted, frames still get sent to Anthropic if you use Claude; the tool itself runs locally. The community is actively debating the trade-offs between local preprocessing and native multimodal models.

Most AI tools don't really see a video—Claude won't accept video files, ChatGPT reads only the transcript, and Gemini samples at a fixed 1 fps. claude-real-video extracts frames at every scene change and deduplicates them, giving LLMs meaningful visual context without burning excessive tokens.

Key Highlights
  • Uses scene-change detection and pixel-difference dedup to select meaningful frames, not fixed intervals.
  • Runs entirely locally, no video upload; output can be fed to any LLM.
  • Supports audio transcription via Whisper or embedded subtitles, plus optional full audio retention.
  • Community debate centers on token cost vs. quality of understanding, and whether native multimodal models are superior.

Since Linux 6.9, LUKS suspend stopped wiping disk-encryption keys from memory
⬆ 481 pts 💬 206 HN comments

A kernel regression introduced in Linux 6.9 silently broke the LUKS key wiping functionality during suspend, a feature originally pioneered by Debian's cryptsetup-suspend add-on. The bug was discovered by Ingo Blechschmidt when his NixOS integration test failed, which verifies that LUKS keys are properly evicted from memory on luksSuspend. Git bisect traced the root cause to a single-line error in a refactoring of the dm-crypt key management code path. The flaw meant that from Linux 6.9 onward, the dm-crypt master key remained resident in RAM after suspend, potentially exposing it to cold boot attacks or physical memory extraction. Notably, the issue was invisible to normal operation: resume still worked because the key was already in memory, so no user-visible error occurred. The feature is not part of mainline cryptsetup but is widely ported across distributions that adopted Debian's approach, including Ubuntu, Fedora, and Arch Linux via community packages.

The community response highlights a spectrum of security priorities. Some commenters dismiss the impact, noting that most stock Linux distributions do not wipe keys on suspend anyway, and that hardware memory encryption (e.g., Intel TME) or full hibernation render the attack moot. Others stress that the regression exemplifies a recurring systemic weakness: security invariants in C codebases are fragile under refactoring, and even well-intentioned patches can introduce subtle vulnerabilities. The discoverer's use of a NixOS integration test to catch the bug is praised as a model for proactive security validation. The episode also rekindles debate about the Linux kernel's testing culture, with some calling for automated regression tests for security features. A few outlier comments speculate about intentional backdoors, but the consensus leans toward this being an unintended oversight, albeit one that persisted for over two years undetected.

The LUKS key-wiping regression went unnoticed for over two years because it caused no visible failures—a silent security bug that only a dedicated integration test could catch.

Key Highlights
  • Linux kernel regression in 6.9 broke LUKS key wiping on suspend, leaving encryption keys in memory.
  • Feature originated from Debian's cryptsetup-suspend, now ported to multiple distros.
  • Bug was found via a NixOS integration test and traced to a single-line C refactoring error.
  • Attack vector is cold boot or DMA with physical access, but mitigations like TME exist.
  • Debate over severity: stock distros don't wipe keys anyway, but security-conscious setups were silently weakened.
