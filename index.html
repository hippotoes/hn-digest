Claude Code sends your email address to websites
⬆ 1408 pts 💬 441 HN comments

Claude Code shipped a design decision that turned a mundane context-engineering shortcut into an outbound privacy leak. To stop the model hallucinating attribution handles (@author tags), Anthropic injected the signed-in account's email address into the model's system context. The side effect: when the agent autonomously composed HTTP requests — curl invocations, Python fetch scripts, geocoding and paper-search API calls — it folded that address into User-Agent strings, sometimes alongside a project name, client identifier, repository slug and the actual query text. Issue #107757 drew 1,408 points, 588 thumbs-up reactions and 441 comments within a day, with the reporter claiming "dozens of scam emails per day" and announcing a migration to Pi with OpenRouter. Anthropic's first response was a built-in plugin, cc-plugin-privacy, enabled by default from v2.1.317, which deterministically refuses shell input naming the account address; a staffer (lydia_hallie) later committed to removing the email from model context entirely in the next release.

The remediation arc exposes the gap between hook-level pattern matching and genuine data-flow control. Commenters immediately found trivial bypasses: mkubenka showed that a model-written script executed as `python3 fetch.py` never surfaces the address in checked shell input, and that `<project-name>-site-build/1.0 (<email>)`-style tokens fail the address-only match while still leaking project and client names linkable by IP. llama052 pasted real headers such as `company-helm-research/1.0 (Claude Code agent run by <my name>, <company> platform team; docs lookup)` — the model volunteered name, team and repo. The original trigger was partly legitimate: SEC EDGAR's documentation requires a contact email in the User-Agent and rejects default clients, a behaviour varenc demonstrated with curl and jessriedel reframed sharply: "It's not an alignment problem. The SEC can reject your request if it lacks an email address, but it can't order you to provide it here." Others noted the address also leaks via git config, and that Anthropic reportedly cannot change an account email without cancel-and-resubscribe.

The fix that shipped was a plugin matching one string, not removal of the capability — and users caught that distinction immediately.

Anthropic initially patched a user-email exfiltration path by shipping an opt-out-able built-in plugin that matches the literal account address, while a commenter demonstrated the same header getting through whenever the model writes the script itself — 588 users reacted with a thumbs-up to the bug report, and Opus 5.5's system prompt reportedly already contained "don't send the user's email".

Key Highlights
  • Claude Code put the signed-in account email in model context to prevent hallucinated @author handles; the agent then reused it in self-composed curl/HTTP User-Agent headers
  • The first fix was a built-in mod (cc-plugin-privacy, v2.1.317+) that pattern-matches the literal address rather than removing it from context — bypassable when the model writes and executes a script
  • Beyond the email, agents invent descriptive UA tokens leaking project names, client names, teams and repo slugs, tieable to an IP
  • The behaviour is partly induced by services like SEC EDGAR whose documentation demands a contact email in the User-Agent or rejects the request
  • Practical fallout: spam anecdote, no supported way to change an Anthropic account email, and third-party tooling that strips the account block, saving 10k–20k tokens per context

#1
sshole
⬆ 2847 pts 💬 691 HN comments

sshole documents a decade-long latent authentication bug at the intersection of three separate design decisions. musl libc's sha512crypt implementation caps keys at 256 bytes to prevent a DoS-by-slow-hash attack, and on failure returns the literal string "*". Separately, Unix convention — dating to Bill Joy's 1980 /etc/passwd entry for the daemon account — uses "*" in the password field as an impossible hash meaning 'this account can never take a password'. OpenSSH, hardened against a CVE-2016-6210 user-enumeration timing oracle, hashes against a borrowed salt anyway and then compares the result to the stored field. On musl without PAM, a 257–1024 character password hashes to "*", which string-compares equal to a "*" shadow entry, so key-only accounts — root on Alpine cloud images, LDAP users, deploy users — accept that password.

The bug requires no memory corruption: it is a pure type-confusion of value with error signal, first introduced in musl commits b3c4cc12 and 88bf5a8a (August 2012), which replaced the POSIX-specified NULL return precisely to stop callers from segfaulting. The kicker is the second attempt: OpenSSH's timing-equalization path requires a warm-up, a detail multiple commenters reported missing during reproduction. Debian asked glibc to adopt musl's '*' convention in 2013 and was refused; libxcrypt later chose "*0", one character away from disaster. The write-up was produced by fuzzing 17,600 malformed logins across glibc/musl, PAM/no-PAM, shadow/no-shadow builds using agent swarms, and is fixed in OpenSSH 10.6p2; mitigations are `apk upgrade` or setting PasswordAuthentication no. Alpine cloud images ship a passwordless-doas 'alpine' user, giving root to anyone who types 257 A's twice.

For a 2,847-point, 691-comment thread, the reaction is notable for treating a devastating auth bypass as a pedagogy problem rather than an emergency: the dominant response is API-design outrage, not incident response.

Two independent subsystems chose '*' as their sentinel — Unix for 'no password can ever match' and musl's crypt() for 'hashing failed' — so a 257-character password hashes into a valid locked account.

Key Highlights
  • musl's crypt_sha512 refuses keys over 256 bytes (DoS mitigation) and signals failure by returning '*', the exact sentinel /etc/shadow uses for locked accounts.
  • OpenSSH's CVE-2016-6210 fix hashes against a borrowed salt even when the target's hash is not real, making the '*' comparison reachable — but only on musl builds without PAM.
  • The trigger requires two attempts (OpenSSH's timing-equalization path), which slowed both discovery and reproduction by readers.
  • Fixed in OpenSSH 10.6p2; Alpine backported to even EOL releases, frustrating readers who tried to reproduce on current images.
  • Worst-case exposure: Alpine AWS/Azure cloud images where the default 'alpine' user has a '*' hash and passwordless doas — a 257-character password yields root.

MS Paint Remote Code Execution Vulnerability
⬆ 643 pts 💬 242 HN comments

Microsoft's Paint — long the canonical example of a harmless, offline, single-purpose app — is at the center of CVE-2026-83844, an out-of-bounds weakness rated AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H and affecting Paint versions 11.0.0.0 through 11.2605.91.0, with a fix landing in 11.2609.401.0. What turned a routine memory-safety bug into a 643-point HN story is the score itself: network attack vector, no privileges, no user interaction. For a program most users believe does nothing but move bitmaps around, the implication that a specially crafted packet could achieve code execution — with Paint merely installed, possibly not even running — reads as absurd on its face. The CVE record itself is nearly information-free, and the linked MSRC guidance is largely Microsoft's standard 'unauthenticated attacker could send a specially crafted packet to an affected service' template, which is exactly the phrase the community seized on.

The most plausible technical reading, advanced early by commenters, is that the vulnerable surface is Paint's image-decoding path rather than any listening socket: modern Paint ships as a Store app whose codecs, thumbnail providers and preview handlers are invoked by the shell and indexer automatically, so 'no user interaction' means a malformed image merely needs to exist on disk for the decoder to run in-process. Others point at the newer generative-erase/AI plumbing as the likeliest source of a networked or model-loading code path, and the fact that the fix was only obtainable through the Microsoft Store — not Windows Update — reinforces how far the app has drifted from a static system binary. Threads also surfaced practical fallout: users reporting Windows Update showed nothing, admins forced to unblock the Store in firewalls to patch, and version-numbering confusion (11.2605.x vs. legacy mspaint.exe) leaving people unsure whether they were exposed. The comment section is less a security analysis than a referendum on what Paint has become.

Commenter 6thbit noted that 57 of 59 wormable CVEs in one October batch carried the identical 'unauthenticated attacker could send a specially crafted packet' boilerplate — raising the real possibility that Paint's 'remote' rating is mis-scoped template text, not a listening port.

Key Highlights
  • CVE-2026-83844 affects Paint 11.0.0.0 up to (not including) 11.2605.91.0; fixed in 11.2609.401.0.
  • CVSS vector shows AV:N/UI:N/PR:N — 'remote' and 'no user interaction' — which users found hard to reconcile with a drawing app.
  • Leading theory: the shell's thumbnail/preview/indexing pipeline invokes Paint's image decoder automatically, so a malformed file on disk is enough to trigger it.
  • The patch is distributed via the Microsoft Store rather than Windows Update, forcing some admins to unblock the Store in their firewalls.
  • Commenters suspect Microsoft's generic CVE boilerplate was copy-pasted across dozens of unrelated vulnerabilities, muddying the disclosed scope.

Motorola Signature 27 with GrapheneOS support
⬆ 548 pts 💬 389 HN comments

Motorola’s Signature 27 is the first Motorola handset to officially support GrapheneOS, shifting the hardened Android distribution beyond its long-standing Pixel-only hardware base. The significance is not just software availability: Motorola says it meets GrapheneOS’s demanding hardware and firmware requirements, including a performant ARM Memory Tagging Extension implementation, better secure-element integration, and a commitment to provide driver/firmware code and help port and maintain the OS. That matters because GrapheneOS depends on verified boot, timely firmware updates, and low-level platform support that AOSP alone does not guarantee. The device is also a conventional flagship: Snapdragon 8 Elite Extreme Gen 6, a tandem AMOLED rated up to 12,000 nits peak, a 7000mAh battery, 90W wired charging, and a 200MP periscope camera. But the launch couples hardened privacy with Google’s Gemini Intelligence and Motorola’s Lenovo-owned supply chain, creating immediate tension in the HN discussion.

The headline number is $1,599, and it dominates the comment thread. Users compare it with second-hand Pixel 8s bought for a tenth of the price, predict Motorola’s usual rapid discounting, and worry that weak sales will be misread as lack of demand for GrapheneOS rather than price sensitivity. GrapheneOS representatives reply that this will not be the only supported Motorola device, that Qualcomm currently offers MTE only on flagship SoCs, that camera-app support is planned after launch, and that bootloader details will come later. Other threads raise deeper concerns: Chinese ownership and opaque baseband/firmware blobs, the coexistence of Gemini and a privacy OS, Play Integrity attestation, missing features such as UWB or a headphone jack, and whether the 6.8-inch form factor underserves users who want a compact, long-lived secure phone. The outcome will test whether OEM-backed hardened Android can become a durable product line rather than a costly enthusiast experiment.

The first Motorola with official GrapheneOS support costs $1,599—roughly ten times the used Pixel 8 cited by skeptics—so the real test is whether OEM-backed hardened Android can escape the flagship privacy tax.

Window Sweaters
⬆ 409 pts 💬 120 HN comments

Window Sweaters is a macOS menu-bar utility, written in Objective-C, that draws procedurally generated knitted borders around application windows — a purely aesthetic skeuomorph layered on top of the window server. Architecturally it is a fork-lineage descendant of Felix Kratz's JankyBorders, which means it does what most window-decoration tools on macOS do: attach to windows via private CoreGraphics/CGS window-server APIs, harvest the focused-window list, and paint an overlay rather than modify the app itself. That approach explains the app's two structural costs. It must request Accessibility permission to know which window is focused and which apps to dress, and it inherits fragility — the README concedes that system updates "may affect how it works," that borders vanish during live resize, and, per commenters, that Stage Manager's window-capture model is fundamentally incompatible with ghost-border overlays. Border art is driven by replaceable PNG stitch charts plus a plain-text apps.conf, so the styling layer is deliberately hackable outside the binary.

The project's numbers are modest but telling: 409 Hacker News points, 120 comments, roughly 1.2k GitHub stars, 37 forks, and only 25 commits — a first open-source release from a product designer, released under GPL-3.0 with attribution to JankyBorders. Thirty-seven apps ship hand-picked colourways (Claude's #D58561, Terminal, Figma, Ghostty); everything else gets icon colours sampled locally in the background and softened into "yarn," with a deterministic name-hash fallback when an icon yields no usable colour. Distribution is where the design collides with engineering culture: the README's headline install path is "send this repo to your coding agent," the Homebrew cask requires `brew trust`, and the app is unnotarized. That single editorial choice — cute UX over conventional trust signalling — generated more friction than the knitting did, and it is the sharpest lens on how the HN audience receives whimsy wrapped around privileged system access.

A designer's first open-source project — 25 commits, 1.2k stars — built on JankyBorders and private macOS window APIs, whose most controversial decision wasn't the knitted borders but telling users to hand the repo to a coding agent to install.

Key Highlights
  • Objective-C menu-bar agent derived from JankyBorders, decorating windows via private macOS window-server APIs rather than modifying target apps
  • Accessibility permission required to track focused windows; known limitations include borders hiding during live resize and incompatibility with Stage Manager
  • 37 hand-curated app colourways plus runtime icon colour sampling with a deterministic name-hash fallback, all user-overridable via apps.conf and custom PNG stitch charts
  • Distribution friction dominates criticism: an 'ask your coding agent to install it' headline, `brew trust` requirement, and no Apple notarization
  • Community reaction splits between delight/nostalgia for skeuomorphic desktop theming and skepticism about granting Accessibility access to an unvetted binary

The Hackintosh Reborn
⬆ 371 pts 💬 211 HN comments

For roughly three decades the Hackintosh was a story about x86: patching kernels, faking SMBIOS tables, coaxing kexts onto commodity Intel boards, and later using OpenCore to make an unofficial PC impersonate a genuine Mac. Apple's 2021 ARM transition was widely read as the closing chapter — the M-series chips were faster and more efficient than anything Intel could ship, and macOS 27 'Golden Gate' finally dropped x86 entirely. The author's own history tracks that arc: a KVM/PCI-passthrough guide for macOS 10.14 nearly a decade ago, then a smooth macOS 26 install on a spare ThinkPad T490, purely because Xcode 26 was needed to build a first iOS app. The interesting twist is what happened once AI coding assistants entered that workflow — the author shipped a functional iOS app in a day 'without touching a single line of code.'

That same agentic tooling — Claude Code driving Ghidra-class disassembly and binary analysis — is now being pointed at the platform bring-up problem itself, and the results are startling: macOS 27 booting on a Snapdragon laptop, macOS 27.2 beta on an RK3588 ARM SBC with Mali GPU drivers, iOS 17 on a Nintendo Switch OLED, and emergent support for Nvidia 50-series GPUs via a project called nullmoth, plus work on AirDrop, hardware video decode, and even translated macOS 27 on x86. The technical foundation is unchanged — device trees, driver stubs, reverse-engineered firmware contracts — but the labour cost of each port has collapsed. The comments show the community splitting accordingly: some see a genuine hardware-ownership revival, others note that x86 virtualization via QEMU/KVM was always the saner route, and a vocal plurality admit they now want the inverse: Linux on Apple silicon, and the bootloader freedom Apple still refuses to grant.

"This is the power of Claude Code with Ghidra on steroids" — the author's summary of why reverse-engineered platform bring-up, from Snapdragon laptops to a Switch OLED running iOS 17, suddenly accelerated after years of dormancy.

Key Highlights
  • macOS 27 (Golden Gate) drops x86, which was expected to end the Hackintosh era entirely
  • AI-assisted reverse engineering (Claude Code + Ghidra-style tooling) has collapsed the effort required for new platform ports
  • Recent ports include macOS 27 on Snapdragon laptops, macOS 27.2 beta on an RK3588 SBC, and iOS 17 on a Switch OLED
  • The author's own trigger was pragmatic: Xcode 26 on a ThinkPad T490 to build an iOS app, shipped in a day with AI assistance
  • Commenters largely argue Apple's real value is hardware, not software — many would rather run Linux or Asahi on Macs than macOS elsewhere

Show HN: Firenook – Firebase emulators in Rust: 40× faster writes, 10× less RAM
⬆ 157 pts 💬 22 HN comments

Firenook is an independent, Apache-2.0 reimplementation of the Firebase Local Emulator Suite, shipping native service engines inside a single npm package rather than the JVM-based Java processes the official suite spins up. It is a genuine drop-in: it parses firebase.json and .firebaserc the way firebase-tools does, binds the canonical ports (Firestore 8080, Auth 9099, Storage 9199, Functions/Extensions 5001, Pub/Sub 8085, Cloud Tasks 9499, Eventarc 9299), honours FIRESTORE_EMULATOR_HOST and the rest of the SDK environment variables, and imports/exports the official data format in both directions — so migration is literally one word in a package.json script, with firebase-tools retained for deploy and login. Coverage spans eight emulators including Security Rules evaluated natively, gRPC and HTTP/JSON Pub/Sub RPCs, and every Functions trigger class. Two harder-to-copy pieces surround the core: a `--keep-data` mode that persists Firestore, Auth and Storage into a local state directory and restarts in ~half a second without export/import round-trips, and an MCP server exposing 54 tools so a coding agent can interrogate function call logs, replay failures, and ask Security Rules why a request was denied. Notably absent: Realtime Database, Hosting, App Hosting and Data Connect.

The headline benchmarks come from replaying two hours of a production app's traffic (211,205 Firestore documents, 6.7 GB of Storage) against each emulator alternately: 5.1 ms median writes versus 208.2 ms, 11 ms versus 209 ms for listener updates, 12.0 ms versus 96.3 ms for orderBy+limit queries, 61% less CPU, 2.11 GiB peak RSS versus 22.57 GiB, and a 0.59 s restart against 30.8 s — 25 of 26 query shapes faster, one tied. The caveats are stated honestly: 0.2.x is the first public release, every release is gated on conformance replays against the official emulator and packed installs across five platforms, and unsupported services merely warn rather than block startup. Zero Hour: Telling time was a matter of survival and strategy during WWI (2014)
⬆ 24 pts 💬 0 HN comments

The article treats WWI as a distributed-systems problem: once armies were dug in across hundreds of miles, time became command-and-control infrastructure. Shouting, horns, and visible formations no longer worked; gas releases, artillery barrages, and infantry advances required officers to share a common clock. The phrase “synchronize watches” and the term “zero hour” emerge from that operational need. Technically, the pocket watch was fragile and slow to access under fire, so the wristwatch was redesigned around military constraints: one-handed readability, luminous dials, unbreakable glass, integrated cases, and chronometric certification. Rolex’s Hans Wilsdorf pursued precision certificates and branding to convert the “wristlet” from feminine jewelry into masculine military equipment.

Specific details make the adoption story concrete. A 1915 New York Times item records a “zero” hour for a gas attack; a 1916 field manual lists a “luminous wristwatch with unbreakable glass” ahead of a gun and water bottle in an officer’s kit. British official issue remained a double-cased “trench watch,” while U.S. Signal Corps officers received Zenith wristwatches in 1917. Advertising by Waltham, Bulova, and others sexualized and militarized the device; the 1918 Stars and Stripes piece “The Wrist Watch Speaks” calls it “the mark of the woman and the she-man” turned “military tyrant.” The 11/11 11 a.m. armistice, signed after 5 a.m., imposed symbolic symmetry while an estimated 10,000 men were killed or wounded that day.

The armistice was signed a little after 5 a.m. but took effect at 11 a.m. on 11/11/1918 for symbolic symmetry; an estimated 10,000 men were killed or wounded on November 11, including over 3,000 American casualties.
