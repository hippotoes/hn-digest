Show HN: My $300 embroidery machine needed a subscription, so I built my own app
⬆ 659 pts 💬 218 HN comments

ZigZag is an open-source embroidery editor written in Rust by a solo developer (simpsoka) after discovering that a $300 Brother Skitch PP1 required paid companion software to be useful. The repository, at 526 stars and climbing after 659 HN points, is not a toy: it implements SVG import via usvg, a boolean/offset geometry layer (i_overlay), a planner that removes hidden overlaps, orders caps center-out and routes travel stitches invisibly through fills and under later-sewn objects, plus twelve stitch primitives — tatami fill with pull compensation and underlay, two-rail satin with auto-satin and short stitching on tight curves, contour, meander, ripple, cross-stitch, tartan, appliqué and blanket E-stitch. It writes and reads PES/PEC, DST, EXP, JEF and VP3, and speaks the Brother Skitch's Bluetooth (PEN) protocol directly via btleplug.

The architectural bet is MCP. The studio ships an embedded Model Context Protocol server (with a stdio↔HTTP bridge), so Claude Code or Codex can drive the same document model the GUI uses — the Agent panel runs the agent sandboxed to design tools only, with no shell or file access, and animates on-canvas outlines labelled Drawing, Placing, Restyling. The surrounding ecosystem is thin and expensive: commenters cite Hatch at over $1,000 and Embrilliance's à-la-carte module pricing, with UIs "straight out of Windows 95." ZigZag's honest README caveat — "Not yet run against a real Skitch" — sits alongside Ink/Stitch as the free incumbent, which several users defend on results, if not ergonomics.

"I likely wouldn't have approached the project if I had to write it all by hand. But it was fairly easy with AI... The days of personalized software are here." — simpsoka, whose six-commit Rust app replaces four-figure digitizing suites with ZWSP ZWSP a 300-word GUI, a CLI, five machine formats and an MCP server.

Key Highlights
  • Built in Rust with a full digitizing engine: tatami fill, auto-satin, contour, meander, ripple, cross-stitch, tartan, appliqué, plus overlap removal and invisible travel routing
  • Exports PES, DST, EXP, JEF and VP3; imports SVG (usvg) and even traces raster logos; speaks Brother Skitch PP1 Bluetooth directly
  • Ships an embedded MCP server so Claude Code or Codex can author designs in a sandboxed tool-only scope, with live on-canvas agent feedback
  • Competing against Ink/Stitch (Inkscape plugin, free) and Hatch/Embrilliance (four figures, dated UX, HWID-locked trials)
  • README admits the Bluetooth path has not been validated against physical hardware, drawing fair skepticism

Gemini 4 Hydrogen and Orchestrator
⬆ 467 pts 💬 144 HN comments

Google's Antigravity team has shipped Gemini 4 Hydrogen — a fast, standalone coding model — alongside a new model-selector mode called Orchestrator, which dynamically hands work back and forth between Hydrogen and the frontier Gemini 4 Carbon model inside a single agent trajectory. The architectural claim is a rejection of the static "model router" pattern that guesses task difficulty from the first prompt and pins the entire run to one model. Orchestrator is bidirectional: Carbon opens in a read-only reconnaissance phase to map dependencies, resolve ambiguity, and build a plan with explicit re-planning triggers; Hydrogen then takes the write path — edits, package upgrades, test runs — and escalates back to Carbon when it hits friction. Google positions this as the fix for long-horizon agents whose complexity profile changes mid-run, and exposes the same primitive programmatically through the Antigravity SDK for hand-wired multi-model pipelines (their demo pairs Hydrogen triage/coding agents with a Carbon agent for refactors and security review).

The numbers are the interesting part. Hydrogen scores 51 on the Artificial Analysis Intelligence Index (54 at its highest setting) and 57% on Terminal-Bench 4.1 — more than triple 3.8 Flash's 18.2% — with four reasoning tiers (low, medium, high default, and a new xhigh). Orchestrator, on the same benchmark, reaches near-Carbon success while consuming 24% less quota and finishing 19% faster, which is a modest win for co-trained models and bespoke harness support. Availability is tiered: Hydrogen for paid AI Pro and Ultra subscribers, Orchestrator (Carbon) and (Argon) for Ultra, Orchestrator (Argon) only for Pro, plus Gemini for business. The HN thread (467 points, 144 comments) barely debates the routing design; it fixates on chemistry-themed naming, subscription lock-in to Google's harness, and whether delegating model-selection authority to a model is wise.

Orchestrator claims near-Carbon task success on Terminal-Bench 4.1 while using 24% less quota and completing 19% faster — a 57% score for Hydrogen versus 3.8 Flash's 18.2%.

Key Highlights
  • Orchestrator replaces static prompt-time model routing with dynamic, bidirectional Carbon↔Hydrogen handoffs inside a single trajectory, with explicit re-planning triggers
  • Hydrogen hits 51 on the Artificial Analysis Intelligence Index (54 at max) and 57% on Terminal-Bench 4.1 vs 3.8 Flash's 18.2%
  • Orchestrator delivers near-Carbon success at 24% lower quota and 19% faster completion on Terminal-Bench 4.1
  • The Antigravity SDK exposes explicit multi-model pipelines; the demo splits issue triage/coding (Hydrogen) from refactors and security checks (Carbon)
  • Rollout is tier-gated: Hydrogen for paid Pro/Ultra, Orchestrator (Carbon) Ultra-only, Orchestrator (Argon) for Pro, plus enterprise via Gemini for business

#6
I'm making LLMs work on small and old devices
⬆ 433 pts 💬 165 HN comments

smolmaxxing is a llama.cpp fork and patch set that treats memory-constrained consumer hardware — a Xiaomi TV Box S, a jailbroken 2013 iPad Air, a OnePlus Nord CE 2 — as a legitimate inference target rather than a joke. The project's premise is that idle CPUs, undersized RAM and flash storage sitting in TV boxes, routers and old tablets can host far larger models than their RAM would suggest, provided you attack the problem at three layers simultaneously: hand-written kernels for the specific core (a 1-bit lookup-table kernel needing only baseline NEON, repacked 2-bit and ternary formats for Cortex-A55, and dot-product-free variants for the Apple A7), aggressive memory reduction by pruning rarely-used vocabulary rows from the output head and even suspending Android's launcher and Google services during inference, and finally expert paging — keeping hot MoE experts resident and streaming cold ones from flash with next-layer prefetch. Because MoE decoders activate only a few experts per token, the memory-bandwidth cost becomes a paging problem rather than a capacity problem.

The measured results are genuinely unusual. The TV box runs a 16B Ling-mini-2.0 at 5.1 tok/s on roughly 1 GB of usable RAM; the iPad Air manages a 1-bit Bonsai-1.7B at 24–26 tok/s and the same 16B model at 2.6–4.5 tok/s; the phone pushes to Qwen3.6-35B-A3B at 4.9–5.7 tok/s and an 80B-A3B at 2.6–3.1 tok/s from ~3 GB free. Everything is reproducible: patches, GGUF-rewriting tools, benchmark JSONL, vocabulary lists and a 165-experiment lab notebook are in the repo, with weights on Hugging Face. The author is explicit that this is currently novelty — the useful path today is fine-tuned narrow models on modest hardware — and explicitly frames the work as search over kernels and configurations rather than a single clever trick, noting the results took 107 plus roughly 50 further experiments to find.

A 16B mixture-of-experts model running at ~5 tok/s on a TV box with about 1 GB of usable RAM — because only a few experts fire per token, the rest stream from flash on demand.

Key Highlights
  • Expert paging keeps popular MoE experts in RAM, streams the rest from flash, and prefetches the next layer — decoupling model size from RAM size
  • Custom quantized kernels: 1-bit LUT, repacked 2-bit and ternary formats for Cortex-A55, plus A7 variants avoiding dot-product instructions
  • Vocab-head pruning plus a 'headless' Android mode that kills the launcher and Google services buys back scarce memory
  • Every figure is device-measured with published patches, GGUF rewriting tools, raw benchmark logs and checksums
  • The author concedes current value is novelty unless models are fine-tuned for narrow domains on the same hardware

Foundation Models framework
⬆ 247 pts 💬 33 HN comments

Apple's Foundation Models framework has quietly evolved from a thin Swift wrapper around the on-device Apple Intelligence model into something closer to a provider-agnostic inference substrate. The architecture hinges on the Language Model protocol: any vendor — Anthropic's Claude, Google's Gemini, Apple's own Core AI and MLX-converted open-weight models, or Private Cloud Compute — can ship a Swift package conforming to it, and the app code above it stays unchanged. The framework bundles guided generation (constrained decoding), tool calling, multimodal prompts with Vision-backed OCR and barcode extraction running on-device, and a new Dynamic Profiles API that lets a session hot-swap model, temperature, reasoning level, and toolset mid-conversation while preserving a shared transcript — effectively a declarative primitive for composing agents and multi-step skills rather than a single fixed session.

The pricing mechanics are the sharpest edge. Apple grants Private Cloud Compute access at no cloud API cost to App Store Small Business Program members with fewer than two million first-time downloads — 'frontier-level intelligence with unparalleled privacy protections' — but the fine print reserves daily usage limits that vary by 'request complexity, system demand, system policies,' and promises paid expansion later. Alongside it Apple shipped an Evaluations framework for hill-climbing prompt quality beyond unit tests, a preinstalled `fm` CLI in macOS 27, and open-source utilities plus a Python SDK. Discussants note the entitlement requires an Organization developer account, that the PCC model still fumbled a side-scrolling platformer test, and that ChatGPT's conspicuous absence from the provider list looks like more than an oversight.

Apple is giving small developers free Private Cloud Compute inference — gated by 'daily usage limits' that may vary by 'request complexity, system demand, system policies,' and explicitly slated to become paid. As one commenter put it: 'free tokens with unspecified daily limits is doing a lot of heavy lifting here.'

Key Highlights
  • The Language Model protocol turns the framework into a vendor-neutral abstraction — Claude, Gemini, Core AI, and MLX models plug in behind the same Swift API with tool calling and guided generation intact.
  • Dynamic Profiles allow mid-session swapping of model, temperature, reasoning level, and toolsets over a shared transcript, positioning the framework as an agent-construction primitive rather than a one-shot completion API.
  • Private Cloud Compute is free for Small Business Program developers under 2M first-time downloads, but requires an Organization account and carries vague, adjustable daily limits with a future paid tier.
  • Vision integration gives on-device OCR and barcode reading directly inside multimodal prompts, keeping image understanding local and offline.
  • New developer tooling includes an Evaluations framework for validating prompts under dynamic conditions, the `fm` CLI in macOS 27, and open-source utilities plus a Python SDK.

#2
Service degradation on Microsoft 365
⬆ 1080 pts 💬 910 HN comments

A global Microsoft 365 outage took Exchange Online mailbox access offline for hours across multiple regions, with the failure concentrated in the mail and identity-adjacent substrate rather than in Azure compute: commenters running cloud workloads reported their Azure infrastructure as healthy while Teams chat and meetings kept working, narrowing the blast radius to M365's own deployment pipeline and Exchange-based data layer. Microsoft's own remediation narrative traced a metastable failure loop — an initial trigger (an unvalidated "alternative health check" and a traffic management imbalance) causing servers to fail health checks, be pulled from rotation, push load onto survivors, and then die again on reconnection as every dropped client performed a fresh secure handshake. Notably, the status page itself degraded under load, so engineers relied on the RSS feed ("like getting transmissions from Cassini") for updates.

The timeline is damning: roughly eight hours in, organizations with 15,000+ and even 100,000+ employees still had no mail, with one commenter calling it "the worst 365 outage our org has seen since starting with M365 in 2019" — worse than the all-day September 2018 incident. Microsoft's later updates grew progressively less hopeful: "our actions taken thus far have not provided the anticipated relief," then the key admission that returned servers "can become unresponsive again once they begin receiving traffic," followed by an automated restart-and-detect loop to hold capacity. Microsoft stated it had "no evidence of malicious activity." The thread also captured blast radius through coupling — SSO via Entra, Intune enrollment, and Defender EDR dragging down ostensibly unrelated SaaS — while the community repeatedly flagged Downdetector's survey bias as panicked users marked Gmail, AWS, and Cloudflare as down.

"While the servers we've returned to service initially remain healthy, we've observed that they can become unresponsive again once they begin receiving traffic" — Microsoft's own confirmation that the outage had become self-sustaining, a textbook metastable failure where recovery traffic is itself the load.

Key Highlights
  • Failure isolated to M365/Exchange Online substrate — Azure compute, Teams chat, and GitHub (largely separate infra) stayed up, narrowing the fault domain
  • Self-sustaining metastable failure: restarted servers died on receiving traffic as reconnect handshakes saturated front ends, forcing staged reintroduction and automated restart loops
  • Microsoft's status page degraded under its own incident, with RSS and third-party sources (ThousandEyes, Reddit r/sysadmin) filling the observability gap
  • Blast radius extended through coupling — Entra SSO, Intune, and Defender EDR failures pulled down nominally unrelated third-party SaaS
  • Community reaction split between cascading-failure analysis, a broader narrative of Microsoft quality decline, and calls for on-prem/self-hosted fallbacks

Rust 1.100.0 is nominally just a round-numbered minor release, but it lands three long-running stabilization efforts simultaneously. Two smaller APIs deserve attention. `core::mem::DropGuard` runs a closure on every exit path — `return`, `?`, or panic — with a `dismiss()` escape, turning rollback-style transactional code (truncating a `Vec` when a parse fails) into a three-line idiom instead of a bespoke guard type. `std::mem::conjure_zst` replaces `transmute(())` incantations for constructing zero-sized types, yet stays `unsafe` precisely because tokens like PyO3's `Python<'py>` GIL marker encode safety invariants. Mehmet Ince's six-part series on systemic risk in managed PostgreSQL reaches its most consequential installment: a type-confusion primitive in PostgreSQL core that survived roughly 22 years, tracked as CVE-2026-6460. The path is instructive. While exploiting a memory-corruption chain in pg_clickhouse, Ince was forced to internalize PostgreSQL's Datum abstraction: an 8-byte untyped carrier that knows nothing about what it represents, paired with a separate type OID resolved through pg_type into typlen, typbyval and typinput/typoutput. Because int4 is byval while text is a pointer, the same bytes mean radically different things depending on a type identifier stored outside the value — a design with no runtime tag to verify the pairing. Ince's insight was a TOCTOU analogue from web security: if a value can be constructed under one type and consumed under another, every output function becomes an attacker-controlled interpreter.

The primitive itself needs no superuser and no extension. Create a composite type with a single uuid attribute, PREPARE a query that stores a sixteen-byte UUID beginning 0x01 0x02, ALTER TYPE ... ALTER ATTRIBUTE key TYPE bytea CASCADE, then EXECUTE. The stored Datum is never rewritten, so record_out() trusts the new schema, dispatches to byteaout(), and the leading bytes are parsed as a varlena header — 0x01 marking an external expanded-object reference with 0x02 as the tag, the remainder read as an ExpandedObjectHeader pointer, yielding signal 11. Ince calls the uuid-to-bytea pairing 'one of the most reliable memory-corruption exploit[s] I have seen,' reachable 'as a lowest-privileged login role on any PostgreSQL instance' — and, by implication, on Postgres-compatible managed offerings where tenants already hold credentials. The HN crowd is divided less on severity than on nomenclature.

Ince's one-liner: 'I gave PostgreSQL a value inside a composite type, changed the type of one of its fields, and asked it to read the value back' — 16 attacker-controlled UUID bytes, re-read as a bytea varlena header whose 0x01 0x02 prefix becomes an expanded-object pointer, and a segfault from a lowest-privilege role.

Key Highlights
  • Datum carries no type tag; the OID lives beside it in the query tree, so any mechanism that mutates the schema between PREPARE and EXECUTE decouples value from interpretation.
  • The exploit chain is pure SQL: composite type → PREPARE with a crafted UUID → ALTER TYPE ATTRIBUTE to bytea → EXECUTE, crashing through byteaout() on a forged varlena external-expanded header.
  • Reachability is the story: unlike the earlier LANGUAGE internal trick, this requires only an ordinary unprivileged login role, making multi-tenant managed Postgres the natural blast radius.
  • CVE-2026-6460 is presented as a class, not a singleton — a general type-confusion pattern arising wherever PostgreSQL trusts cached schema metadata over stored bytes.
  • Community reaction splits on classification (RCE vs. ACE vs. privilege escalation) rather than on whether the bug is real, with a secondary thread on whether the Datum design is 'code reek' or unavoidable high-performance low-level optimization.
