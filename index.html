#2
Ollaya – Ollama for open-source, Jev-style decision models
⬆ 489 pts 💬 122 HN comments

Ollaya is an independent, open-source local runtime for what it calls decision models—specialized, non-generative models that answer typed questions such as choice, score, and yes/no in a single forward pass rather than token-by-token generation. It deliberately mirrors TypeSafe's Jev API, serving /v1/systemone and /v1/models with the same request and response shapes, so the official TypeSafe Python SDK works unchanged against a local server. The project is not affiliated with Ollama, despite the name and CLI conventions. Under the hood it uses ONNX Runtime on CPU or NVIDIA GPU, pulls open weights from Hugging Face pinned to commits and checked against sha256, and ships an Apache-2.0 runtime with a desktop app, CLI, and Docker. Models include laya, decider, nli, gliclass, qwen3guard, decision, kev, and von. This positions calibrated, low-latency classification as private local infrastructure rather than a metered cloud API.

The headline benchmark is latency: Ollaya reports Laya answering five questions in 8–10 ms end-to-end through the HTTP API on an RTX 4090, versus 236–276 ms for TypeSafe's hosted Jev API including network. decider:2b runs at roughly 190 ms and scores 0.591 on typed decisions; smaller models trade accuracy for speed. In the HN thread, developer 'cobanov' concedes Laya is 'a lot weaker than Jev' on harder queries and that bigger open models are coming. Commenters split sharply. Some dismiss the category as repackaged classification—'decision model = classifier,' says hbrn—while others welcome local-first utility: one user replaced Jev API calls with Laya on a GTX 970 with 4 GB VRAM. The naming and API compatibility also raise questions about whether Ollama will simply absorb the feature, and whether open weights can commoditize TypeSafe's moat within weeks.

Ollaya claims a five-question decision request at 8–10 ms on an RTX 4090, an order of magnitude below TypeSafe's 236–276 ms hosted Jev median—yet its own developer admits the featured Laya model is 'a lot weaker than Jev' on harder queries.

Key Highlights
  • Ollaya is an independent open-source runtime for Jev-style decision models, not affiliated with Ollama, with TypeSafe /v1/systemone API compatibility.
  • It targets single-forward-pass typed decisions (choice, score, yes/no) with calibrated probabilities, using ONNX Runtime on CPU or NVIDIA GPU.
  • The article claims 8–10 ms for five Laya questions on an RTX 4090 versus 236–276 ms for TypeSafe's hosted Jev API.
  • Models include laya, decider, nli, gliclass, qwen3guard, decision, kev, and von; the developer concedes small models are weaker than Jev on hard queries.
  • HN debate centers on whether this is trivial classification commoditizing TypeSafe, the accuracy/latency trade-off, local privacy and use cases, and Ollama potentially adding support.

#3
Plan mode is dead
⬆ 375 pts 💬 336 HN comments

Ayman Nadeem, formerly a senior engineer at GitHub and founder of the AI coding app Nuanced, argues that the plan mode primitive he built an entire product around has become obsolete. His thesis splits plan mode's historical function in two: (1) producing instructions precise enough for an agent to execute, and (2) giving humans a coherent mental model of the system being built. He contends the first is collapsing as context-window improvements and repo-level memory let models explore codebases and make reasonable assumptions autonomously, while the second remains unsolved but demands an entirely different abstraction. Nuanced's failure taught him that 'planning' and 'a plan' are not the same thing: by turning the plan into a persistent, AI-generated artifact, the product forced users to prematurely 'finish thinking,' bolted on a 'Spec Tour' to make unreadable generated prose digestible, and split an inherently interleaved process into a waterfall that users could not walk back up once implementation began.

The comment thread (375 points, 336 comments) sharply disputes whether plan mode is dead or merely unfashionable. Boris Cherny, who works on Claude Code, concedes the article's thrust and reveals that Claude Code's plan mode is literally a per-message reminder — 'you're in plan mode, please don't code yet' — that was never allowed to alter the toolset because doing so 'would break the prompt cache, and so would be expensive.' Countering, commenters like loveparade argue the mode's real value is orthogonal to the plan text: it 'forces models to gather as much context as possible before implementing' and stays read-only, enabling parallel planning without worktrees. taurath describes the wider anxiety — 'understanding slip away from developers, code review getting paired down to no comment checkmarks' — while pcblues asks whether anyone would ship code no human had read. The unsettled frontier, several note, is keeping humans oriented as hundreds of parallel agents mutate one system.

Claude Code's own maintainer confirms plan mode "has always been a prompt — it has never changed the toolset because doing so would break the prompt cache, and so would be expensive," validating the article's core claim that the mode is a harness convention rather than a real architectural boundary.

Key Highlights
  • The author argues plan mode conflated two jobs — specifying precise agent instructions vs. building human understanding — and only the first is being obsoleted by model capability.
  • Nuanced failed because it made the plan a persistent artifact rather than a process, forcing users to prematurely 'finish thinking' before implementation and creating a one-way waterfall.
  • Claude Code's plan mode is disclosed as a prompt-only reminder, deliberately not changing the toolset to preserve prompt caching economics.
  • The proposed replacement loop is understand → act → inspect → clarify → adjust → act again, with planning implicit inside iteration rather than surfaced as a document.
  • The unsolved problem is orientation: as parallel agent count scales from five to hundreds, interfaces must surface the fewest high-leverage points for human attention.

#4
First Principles Thinking
⬆ 267 pts 💬 117 HN comments

Sunil Sadasivan's essay is a direct rejoinder to Sunil Pai's widely circulated 'the senior engineer death spiral,' and it reframes the senior-engineer malaise as a cognitive failure mode rather than a skills gap. His thesis: the engineers who stay effective across paradigm shifts share a habit of reasoning from first principles — asking what is actually being built, what it does for the user, and how the pieces connect — which in practice means deliberately quarantining accumulated experience long enough to re-derive the problem. Sadasivan calls this 'put it in a box,' and links it to Pai's momentum-over-outcomes heuristic: shrink the work to the smallest thing you can actually accomplish, then let the resulting learning loop orient you. The agentic era is the stress test that makes this habit load-bearing, because the engineers 'vibing' with agents are the ones willing to suspend old technical constraints before assuming they still apply.

The specific claims are small but sharp. Sadasivan attributes senior excellence to an unteachable-looking intuition — 'they seemed to know what needed to be done' — and traces it to non-traditional paths: customer support, services, design, self-taught coding, all of which force contact with the problem's exterior rather than the codebase's interior. He concedes the emotional cost openly ('This is the hard part for me'), and closes that tighter agent feedback loops constitute 'the new flow state.' The 267-point, 117-comment thread splits predictably along HN's fault lines: dkarl argues 'first principles are an illusion' and that good engineers merely choose which principles to apply; nicbou reduces the practice to treating humans as 'spherical cows'; trwhite and Joe_Boogz describe architecture deferral and on-call losses of mental map; and airstrike dismisses the phrase as 'the latest expression ruined by SFBA posers like orthogonal and non-trivial before it.'

"Take your experience, what you've learned, and what you currently believe is true, and set it aside long enough to look at the problem again." — the essay's central prescription, which commenters split between praising as a discipline and dismissing as an ungrounded Silicon Valley cliché.

Key Highlights
  • Sadasivan responds to Sunil Pai's 'senior engineer death spiral,' arguing first-principles reasoning is what distinguishes engineers who survive paradigm shifts.
  • The proposed mechanism is 'put it in a box': suspend accumulated experience long enough to re-derive what the problem actually is before applying known constraints.
  • Pai's momentum-over-outcomes heuristic and first-principles thinking are framed as mutually reinforcing — smallest viable step generates the learning loop.
  • Commenters contest the term itself: dkarl calls first principles 'an illusion,' nicbou invokes 'spherical cows,' and airstrike calls it an SFBA-ruined phrase alongside 'orthogonal.'
  • The strongest practical objection is architectural: trwhite, ripvanwinkle, and Joe_Boogz report agents producing unsustainable designs and eroding engineers' ability to reason unassisted or debug their own on-call incidents.

#6
What even is an OS now?
⬆ 215 pts 💬 302 HN comments

In "What Even Is an OS Now?", Thomas Ptacek announces his departure from Fly.io to build a phone with Kurt, staking the thesis on a claim that AI has dissolved the boundary between programmers and users. His framing is architectural: the modern OS exists chiefly to "partition different applications off from each other, and carefully control how they can communicate" — a design predicated on importing prefabricated, fixed-function software "from strangers." If most software is instead conjured locally by its user via natural language, that threat model weakens, and so does the rationale for heavyweight app isolation. Ptacek traces a lineage from BASIC-booting 8-bit machines through Egghead shelves, CD-ROMs, and the web's distribution collapse, arguing the next casualty is the prefabricated application itself, with strangers shipping "just their building blocks."

The post drew 215 points and 302 comments, and the community supplied sharp counterweights. utopiah argued most OS think-pieces "have no idea what an OS is": "If your OS doesn't change how a computer allocates resources, then you are talking about higher level." chroma_zone pressed the security gap — an LLM-written app should still be sandboxed "as if written by a stranger." Xirdus reframed the thesis: "it's not the idea of the OS that's outdated - it's the idea of apps," predicting a single assistant rather than thousands of bespoke ones. Diffusion skeptics cited HyperCard and BASIC's history: meredithbloom said "You were the exception," while II2II noted most users "don't think of computers as programmable machines." Ptacek himself appeared repeatedly, calling the transition-post genre "deeply cursed."

Ptacek's core bet: "What I did on my computer, any power user can do on theirs. Will do on theirs. It's fucking inevitable." The sharpest rebuttal came from chroma_zone — if an LLM wrote the app, "I would still want my OS to treat it as if written by a stranger."

Key Highlights
  • Ptacek frames the OS's core job as partitioning mutually-distrusting applications, a design premised on importing software from strangers — and argues AI-generated local software erodes that premise.
  • The announcement is a platform play: a phone (plus Kurt) explicitly not optimized for fixed-function, AAA, or short-form-video workloads but for on-device app generation.
  • Critics dispute definitions: utopiah and sollewitt argue that without dynamic hardware allocation and resource arbitration, you're describing a runtime, window manager, or package manager — not an OS.
  • Security proponents (chroma_zone, fennecbutt) insist LLM-authored code still warrants sandboxing, noting that provenance does not equal trust and that naive users grant broad permissions anyway.
  • Diffusion skeptics (II2II, meredithbloom, trinari, Zaraif13) invoke BASIC, HyperCard, and the early web to argue most users never program, have narrow needs, and are overwhelmed rather than empowered by more tools.

Excel now supports multiple values in a single cell
⬆ 204 pts 💬 148 HN comments

Microsoft has begun rolling out the most structurally significant change to Excel's data model in its 40-year history: lists, arrays-in-cells, and nested arrays, initially to Beta Channel builds on Windows (Version 2610, build 20520.20000+) and Mac (16.114). Historically one value per cell; a value is now a first-class scalar-or-array, of any shape and arbitrary depth. Lists (Insert > List, or Ctrl+J) hold delimiter-separated items in a single cell while remaining individually filterable and referenceable — referencing =B2 spills the constituent values into separate cells. Wrapping any formula body in braces creates a 1x1 array that suppresses spilling, and ={{1,2,3};{4,5,6}} produces genuine nested arrays, where previously Excel truncated the output or threw #CALC!. Four new functions — FLATTEN, HAS, HASANY, HASALL — plus a new Compatibility Version 3 calculation engine gate the behavior.

The reaction among the 204-point, 148-comment thread is notably warmer than typical Microsoft-feature reception. thunderbong calls Excel 'a godsend for manipulating reams of data for non-programmers who can think analytically,' while tombert concedes 'even as a programmer I find Excel pretty useful for anything involving numbers... everything is reactive.' amanzi reports a concrete use case — a per-user comma-separated list of software apps that was 'a bit of a nightmare to parse.' Skeptics are unpersuaded: herbst argues the feature 'seems to break the whole concept' of flat tabular data, arbirk calls it 'a band aid' for not separating calculation from position, and ducktoysleftout flatly declares 'Excel is a fractal of bad design.' Others flag the sharp edges: conditional formatting, data validation, charts, PivotTables and Power Query still cannot read array contents, Havoc wonders whether legacy functions 'assume one value,' and gcanyon mocks the coexistence of nested arrays with Excel's 1900 leap-year bug.

"Throughout Excel's 40-year history, you've only been able to put one value per cell" — a claim Microsoft has now inverted with nested arrays, while requiring Compatibility Version 3 to make most nested calculations work at all.

Key Highlights
  • Lists let a single cell hold multiple individually filterable, referenceable values (Insert > List or Ctrl+J), with =B2 spilling them into adjacent cells.
  • Wrapping a formula in braces creates a 1x1 array, suppressing spill; ={{1,2,3};{4,5,6}} produces real nested arrays where Excel previously truncated or returned #CALC!.
  • Four new functions ship alongside: FLATTEN(array, [pad_value], [levels]), HAS, HASANY, and HASALL for set membership testing.
  • Compatibility Version 3 is required for most nested-array calculations and can change results of existing workbooks; users can stay on Version 1 or 2.
  • Documented limitations are broad: conditional formatting, data validation, charts, PivotTables, Power Query, and Find & Replace still do not understand array-valued cells.

#9
Ask HN: Who's still keeping a DOS machine up because the business depends on it?
⬆ 149 pts 💬 142 HN comments

The Ask HN thread exposes a persistent layer of production computing that never migrated: MS-DOS, Windows 3.11/9x/NT, SCO UNIX, and bespoke 16-bit applications still run industrial machinery, point-of-sale, lab analyzers, rail signalling, radio programming, and CNC equipment. The technical substrate is not nostalgia. These systems rely on real-mode DOS, direct port I/O, ISA bus DMA, serial/parallel timing, GPIB, EPROM burners, Novell Btrieve, dBase/Clipper databases, and proprietary interface cards that modern OSes cannot address without a hypervisor trap. The common pattern is a business-critical process whose software was never rewritten because the cost of recertification, validation, or hardware re-engineering dwarfs the cost of keeping a 386/486 alive. Comments cite a nuclear plant Windows NT 4.0 machine reporting control-rod position long after its AmigaOS origin, an airline stack certified by the FAA, and Deutsche Bahn ICE trains still on DOS and Windows 3.11.

Concrete data points show both longevity and fragility. A Fortune 100 facility maintains mandatory DOS machines, struggling to integrate them via VMs where 'faster hardware' creates timing issues for serial links. A Juki pick-and-place line runs DOS 6.22 on a 486, with file transfer solved only flakily by a GOTEK floppy emulator and ESP32 USB emulation. A 1993 SCO UNIX box on a FTSE 100 network is '100% airgapped' but has a classful IP stack and is called 'a ticking time bomb nobody seems to want to address.' The pragmatic counterpunch is emulation: vDos for Clipper/dBase, DOSBox, DOSEMU serving a dozen VNC seats since 2008, qemu for dBase with a REST bridge, 86box for cycle accuracy, and VMs for DOS apps. The impact is a hidden dependency on deprecated hardware across critical infrastructure, kept alive by spare parts, source code, and virtualization.

One commenter reports a nuclear power plant ran Windows NT 4.0 until 2007—'reporting only, NOT control'—to report control-rod status after its original AmigaOS software outlived the Amiga hardware.

Key Highlights
  • DOS and legacy OSes survive in industrial control, point-of-sale, lab analyzers, rail, radio programming, and CNC because the software is certified or tied to custom ISA/serial hardware.
  • The practical migration path is usually emulation or virtualization—DOSBox, vDos, DOSEMU, qemu, 86box, and VMs—rather than a full rewrite.
  • Physical I/O is the hardest part: ISA DMA and timing, serial ports in VMs, floppy transfer, Sound Blaster tape backups, EPROM burners, and GPIB adapters.
  • Regulatory and certification costs (FAA, nuclear, medical) make rewriting software prohibitively expensive, so end-of-life hardware is scrounged or cloned.
  • Commenters split between 'if it ain't broke' continuity and recognizing airgapped legacy systems as ticking time bombs; source code and emulation are seen as long-term insurance.

Lab on a Contact Lens Can Measure Stress Through Serotonin
⬆ 49 pts 💬 16 HN comments

Researchers at the Terasaki Institute for Biomedical Innovation have demonstrated a "lab on a contact lens": a soft, reusable hydrogel lens encapsulating flexible graphene and silver electrodes printed in serpentine geometries that tolerate repeated folding, stretching, and twisting. The sensing chemistry hinges on ferrocene covalently bonded to the graphene, which gives a strong, repeatable electrochemical response to serotonin — a molecule present in tears at vanishingly low concentrations. The device is fundamentally an electrochemical aptamer/mediator-style biosensor miniaturized onto a curved, oxygen-permeable substrate, and it reflects a broader shift in wearables from physical signals (heart rate, temperature) toward continuous molecular readouts of body chemistry.

The headline number is the limit of detection: 72 picomolar, roughly 200× below the ~15 nanomolar average serotonin concentration in human tears. The team validated across three tiers — artificial tears spiked with serotonin, tear samples from 10 volunteers before, immediately after, and 30 minutes after public-speaking and mental-math stressors (serotonin fell as expected), and a five-minute in vivo trial on an anesthetized pig eye with no infection or irritation, detecting 50 and 100 nM spiked levels. Durability exceeded 28 days of mechanical abuse, and readout in the lab/pig work used soft nickel wires. A proof-of-concept wireless variant adds an NFC chip and stretchable antenna for battery-free, phone-based transmission. Parallel mouse studies showed tear and blood serotonin dropping in tandem, hinting tears may window blood chemistry. Peer review: Science Translational Medicine, 16 September.
