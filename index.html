How to setup a local coding agent on macOS
⬆ 376 pts 💬 94 HN comments

The article by Kyle Howells provides a hands-on guide for setting up a local coding agent on macOS using llama.cpp with speculative decoding (MTP) and the Pi agent framework. Howells benchmarks Gemma 4 26B-A4B and Qwen3.6 35B-A3B models, achieving 72.2 tokens/s with MTP acceleration on an M1 Max 64GB machine. The setup aims to replicate cloud-like coding agent capabilities—including multimodal support—entirely offline, addressing internet outages that previously stranded the author. The post is a deep dive into practical inference optimizations, with detailed commands and configuration files.

Key findings include a 24% speedup from MTP (58.2 to 72.2 t/s) and that llama.cpp outperforms MLX on Apple Silicon for these specific models (72.2 vs 45.8 t/s). Howells also provides a secondary setup for Qwen3.6 (55 t/s), noting it's a better coder but slower. The HN community largely appreciates the thoroughness but raises concerns: benchmark length (128 tokens may be insufficient for MTP effects), the necessity of 64GB RAM, and whether the observed speedups translate to real-world coding tasks. Some question the complexity, suggesting simpler alternatives like LM Studio or Ollama, while others defend the manual approach for maximum performance.

Twenty One Zero-Days in FFmpeg
⬆ 212 pts 💬 128 HN comments

Depthfirst, a security startup, deployed an autonomous AI security agent that uncovered 21 zero-day vulnerabilities in FFmpeg, a widely used multimedia library. The agent, built on publicly available LLMs (unlike Anthropic's proprietary Mythos), conducted deep threat modeling and code analysis across FFmpeg's 1.5 million lines of C code. It identified bugs in components such as the TS demuxer, RTP depacketizers, and VP9 decoder, many introduced between 2003 and 2025. Notably, the agent produced concrete, reproducible proof-of-concept inputs, confirming exploitability without false positives. The total compute cost was approximately $1,000—a tenth of Anthropic's reported expense for similar work. One standout finding is a heap buffer overflow in the AV1 RTP depacketizer, reachable via a simple RTSP stream, where a single 183-byte packet can achieve remote code execution by corrupting a freed pointer.

The findings underscore the persistent security challenges of legacy C codebases that have withstood decades of fuzzing and manual audits. Several bugs lay dormant for 15–23 years, including a stack buffer overflow from FFmpeg's original SDT implementation (2003) and a heap underflow in the CAF demuxer (2009). Eight issues received CVEs, while the remaining await assignment. The community response on Hacker News reflects a mix of admiration for the AI's capability and skepticism about the term 'zero-day,' given these were responsibly disclosed (and patched) before publication. Commenters stress that FFmpeg's complexity and C heritage make sandboxing essential; many already run it in VMs or gVisor. The research also raises ethical questions about holding back exploits and the growing asymmetry between bug-finding speed and patching resources.

Depthfirst's autonomous agent found 21 zero-days in FFmpeg for $1k, uncovering bugs that had lain latent for over two decades and achieving proof-of-concept RCE via a single 183-byte RTP packet.

Slightly reducing the sloppiness of AI generated front end

This aligns with the observation that Qt is heavily represented in training data (from thousands of tutorials, screenshots, and source repos), giving the model a coherent 'named distribution' to latch onto. The experiment used a simple electoral-college map app and compared styles (Apple, Win11, Material, Qt); only Qt broke the pattern of identical-feeling outputs. The post resonates because it addresses a real pain point for developers building personal tools with AI: the models tend to generate visually noisy, inconsistent pages that scream 'machine-made'.

CRISPR tech selectively shreds cancer cells, including "undruggable" cancers
⬆ 828 pts 💬 190 HN comments

Researchers at the Innovative Genomics Institute (IGI) have unveiled a CRISPR-based technique that selectively destroys cancer cells by targeting mutations in the p53 tumor suppressor gene, present in nearly half of all cancers and up to 70–90% of hard-to-treat cases like ovarian, pancreatic, and non-small cell lung cancer. Unlike traditional CRISPR editing that fixes genes, this approach leverages Cas12a2—an enzyme that, upon detecting a specific mutant RNA transcript, shreds the entire chromatin within the cell, causing rapid cell death. The system is programmable via a guide RNA, making it adaptable to new mutations quickly. This 'chromatin shredding' method reimagines CRISPR's natural role as a destroyer, not a fixer, and offers a path to target so-called 'undruggable' cancers that lack conventional drug binding sites.

In cell culture experiments, the system distinguished cells with a single nucleotide difference, leaving healthy cells unharmed. Co-author Jennifer Doudna called it 'an exciting development for cancer therapies,' while first author Jingkun Zeng emphasized the speed of adaptation: 'When there’s a new mutation, we can easily make a new guide RNA.' However, delivery remains a critical hurdle, as the large Cas12a2 enzyme must reach every cancer cell—a challenge echoed by commenters who note that surviving 1% of tumors can regrow. The paper, published in Nature, has sparked intense discussion about delivery mechanisms, resistance evolution, and the gap between lab success and clinical reality, with many pointing to the decades-long journey from proof-of-concept to approved therapy.

The system can detect a single nucleotide change between healthy and cancerous cells, triggering chromatin shredding only in the mutant cells.

Key Highlights
  • Uses Cas12a2 to shred chromatin upon detecting cancer-specific mutant RNA, not DNA editing.
  • Targets p53 mutations found in ~50% of all cancers, including undruggable types.
  • Programmable guide RNA allows rapid adaptation to new mutations.
  • Precision: distinguishes a single nucleotide difference between mutant and wild-type cells.
  • Main challenge: in vivo delivery to all cancer cells without harming healthy tissue.

Swift at Apple: Migrating the TrueType hinting interpreter
⬆ 202 pts 💬 90 HN comments

Apple has rewritten the TrueType hinting interpreter from C to Swift, shipping it in Fall 2025 releases for security and performance. The interpreter is a bytecode virtual machine embedded in font rendering, a historically attack-prone component due to untrusted font data. By adopting Swift, Apple eliminated entire classes of memory safety bugs while maintaining pixel-identical rendering to the C version. The team employed advanced Swift features like ~Copyable types, Span (from Swift 6.2), and projection types to achieve safe zero-cost abstractions. A rigorous testing strategy included a 99.7% code-coverage unit suite and a fuzzer-minimized corpus of 4,200 PDFs from 10 million, ensuring correctness across 27 million glyphs. This migration is part of a broader Apple initiative to adopt Swift across macOS, including kernel and system software.

The Swift interpreter runs 13% faster on average than its C predecessor, measured across all hinted fonts on macOS and non-system fonts. Performance gains came from minimizing runtime overhead (e.g., avoiding ARC for hot paths), using Span for efficient data access without copying, and replacing allocation-heavy patterns with continuation-passing. The team also distilled lessons into prompts for LLM coding assistants, using models for later code transformations. The open-sourced reference implementation (MIT license) demonstrates how memory-safe languages can outperform C in performance-critical, security-sensitive system software. This project highlights that careful language choice, combined with thorough testing and optimization, can yield both safety and speed, challenging assumptions that only C or C++ are viable for low-level systems programming.

The Swift TrueType hinting interpreter not only eliminates memory safety bugs but also runs 13% faster than the C implementation it replaced, with zero bugs reported since shipping.

Key Highlights
