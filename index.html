TorchTPU: Running PyTorch Natively on TPUs at Google Scale
⬆ 137 pts 💬 9 HN comments

Google's TorchTPU represents a significant leap in bridging PyTorch with TPU hardware, addressing years of friction where developers had to resort to forks or cumbersome wrappers. By deeply integrating via PyTorch's "PrivateUse1" interface, TorchTPU enables native tensor operations without subclassing, supporting eager execution (Debug, Strict, and Fused Eager modes) that automatically fuses operations for 50-100% performance gains. For peak performance, it integrates with torch.compile and XLA, translating PyTorch ops to StableHLO to exploit TPU's TensorCores and SparseCores. The stack also handles MPMD workloads—a pain point in predecessor PyTorch/XLA—allowing divergent rank behavior without sacrificing XLA's global optimization of communication/computation overlap across the ICI torus topology. This is not merely a port but a re-architected system designed for clusters of O(100,000) chips.

The engineering team emphasizes usability ("change initialization to 'tpu' and run"), but comments on HN reflect both hope and caution. One user notes that PrivateUse1 makes adding hardware support convenient, citing a WebGPU plugin. Another shares war stories from PyTorch/XLA—"a mess of undocumented behavior and bugs (silently hanging after 8 hours)"—highlighting the trust deficit TorchTPU must overcome. The "one line change" pitch is met with skepticism; yet if realized at 100k-chip scale, it could democratize TPU access. A commenter from a Google session confirms a GitHub release in 1-2 months, though not all ops will be supported initially. The hardware availability critique—servers can't buy TPUs—underscores that TorchTPU benefits only Google Cloud customers, limiting broader impact. The roadmap includes dynamic shape support, Helion DSL integration, and partnerships with vLLM and TorchTitan, aiming for linear scaling to full pods.

TorchTPU's Fused Eager mode delivers a 50% to 100+% performance increase over Strict Eager with zero user setup, using automated fusion of operations before dispatching to TPU TensorCores.

Key Highlights
  • TorchTPU uses PyTorch's PrivateUse1 interface for deep, out-of-tree integration without subclassing.
  • Offers three eager modes (Debug, Strict, Fused) with Fused Eager showing 50-100% throughput gains.
  • Static compilation via torch.compile → XLA → StableHLO for maximum hardware utilization.
  • Supports distributed training with DDP, FSDPv2, DTensor, and handles MPMD code patterns gracefully.
  • Roadmap includes dynamic shape support, custom kernels (Pallas, JAX, Helion), and open-source release in 2026.

Show HN: Honker – Postgres NOTIFY/LISTEN Semantics for SQLite
⬆ 259 pts 💬 63 HN comments

Honker is a SQLite extension that brings Postgres-style NOTIFY/LISTEN semantics to SQLite, enabling cross-process pub/sub, task queues, and event streams without a separate broker or daemon. It uses a clever trick: instead of polling the database with periodic queries, it stat(2)-polls the SQLite WAL file every 1 ms for size or mtime changes, then fans out notifications to subscribers. This achieves single-digit millisecond reaction times while keeping idle CPU cost at ~0.1% (as one commenter noted, one stat call takes under a microsecond). The key architectural insight is treating the WAL file as a monotonic change signal and using SQLite's transactional outbox pattern—any enqueue, notify, or publish can be atomically committed alongside business writes within the same database transaction, rolling back everything on failure. Honker ships as a Rust core with bindings for Python, Node, Go, Ruby, and more, making it a cross-language solution for the growing number of applications using SQLite as their primary datastore on a single VPS.

The project intentionally avoids features like task pipelines or multi-writer replication, focusing instead on a minimal, correct foundation. The comment thread reveals both excitement and deep technical scrutiny. The author, russellthehippo, defends the choice of stat(2) polling over platform-specific APIs like inotify or FSEvents, citing Darwin's silent dropping of same-process notifications as a dealbreaker. Several commenters probe edge cases: how does the poller handle WAL checkpoints that shrink the file? The author admits this needs testing. Others debate whether fstat with a kept file descriptor would be faster, or whether PRAGMA data_version is a better signal. The scalability question arises—can 10k listeners coexist? The author acknowledges a thundering herd issue at that scale. Despite these concerns, the sentiment is largely positive, with many developers recognizing the pain point Honker solves: avoiding the operational complexity of adding Redis or Postgres just for pub/sub when SQLite is already in use. The atomic commit with business logic is widely praised as the killer feature.
