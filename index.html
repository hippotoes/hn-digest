Show HN: Getting GLM 5.2 running on my slow computer
⬆ 706 pts 💬 169 HN comments

Colibri is a groundbreaking, dependency-free C engine that runs GLM-5.2, a 744B-parameter mixture-of-experts model, on consumer hardware with as little as 25GB of RAM. The key innovation is streaming experts from disk: only the dense ~17B parameters (9.9 GB at int4) reside in RAM, while the 21,504 routed experts (~370 GB on disk) are loaded on demand per token using an LRU cache, OS page cache, and optional pinned hot-store. This enables running a frontier-class model—normally requiring multiple high-end GPUs—on a standard PC with a fast NVMe SSD. The engine implements faithful GLM-5.2 forward pass including MLA attention, sigmoid routing, MTP speculative decoding, and DSA sparse attention, all validated token-exact. Quantization uses int4 for experts and int8 for the MTP head, with custom AVX2 kernels. The project is openly available on GitHub under Apache-2.0 license.

Measured performance on modest hardware (WSL2, 12 cores, 25 GB RAM, NVMe via VHDX) shows cold decode at ~0.05–0.1 tok/s due to ~11 GB disk reads per token, but warm cache and MTP speculation push useful response latency down to 2.2–2.8 tokens/forward. The author notes: 'This is not fast. It is a 744B frontier-class model answering correctly on a machine that costs less than one H100 fan.' The project includes an OpenAI-compatible API server, a web UI, and an offline FP8-to-int4 converter that never requires the full 756 GB checkpoint on disk. While performance is limited by SSD bandwidth, colibri represents a significant step toward democratizing access to large language models, sparking discussions about trade-offs between speed, cost, and practicality for local AI inference.

This is a 744B frontier-class model answering correctly on a machine that costs less than one H100 fan.

Postgres rewritten in Rust, now passing 100% of the Postgres regression tests
⬆ 686 pts 💬 578 HN comments

pgrust is a complete rewrite of PostgreSQL 18.3 in Rust, now passing 100% of the official regression suite (over 46,000 queries) and maintaining disk compatibility with existing Postgres data directories. The project, driven by LLM-assisted programming (using c2rust for the parser and AI for the majority of the port), aims to modernize Postgres internals without breaking existing behavior. According to the author, a newer unpublished version achieves a thread-per-connection model (replacing Postgres's traditional process-per-connection), delivering a 50% performance improvement on transaction workloads and a remarkable ~300x speedup on analytical workloads (currently 2x slower than Clickhouse but with potential to surpass it). The codebase, however, contains ~2,664 occurrences of 'unsafe {' and ~1,835 unsafe functions, primarily from the mechanically translated bison-based parser.

The HN community response is sharply divided. Many commenters express fatigue with 'rewritten in Rust' projects, especially those heavily reliant on AI, questioning the lack of human reviewable commit history, the AGPL license switch from PostgreSQL's permissive license, and the long-term maintainability of code that few humans can understand. Others defend the project as a valuable proof-of-concept and experimentation platform, noting that the author explicitly states it is not production-ready. The author's claims of large performance gains (e.g., 300x on analytical workloads) are met with skepticism, with commenters calling for independent verification via benchmarks like Jepsen. A central debate concerns the threading model: while thread-per-connection is widely considered more efficient, it risks isolation properties that Postgres's process-per-connection model guarantees for extensions. Overall, the story exemplifies the growing tension between AI-accelerated reimplementation and the trust required for production database software.

The author claims a new version of pgrust is 300x faster than PostgreSQL on analytical workloads and 50% faster on transactional workloads, achieved through a thread-per-connection model and architectural changes.

⬆ 91 pts 💬 164 HN comments

This decouples generation from execution, enabling sub-second first-action latency. They also employ an asynchronous planner agent that reviews the child's progress while the child is thinking, pre-generating responses to likely answers via branched trajectories. A safety classifier runs in parallel with generation, blocking execution on flagged turns without incurring latency. These innovations aim to mimic a real teacher's ability to anticipate and adapt in real time, but the article acknowledges trade-offs in cost, instruction-following, and error handling.

The article underscores that pedagogical quality cannot be sacrificed for speed: earlier experiments with smaller models were faster but constantly gave away answers, undermining learning. The system's safety measures, while technically novel, raise concerns: the safety classifier uses an LLM that can false-positive on transcription errors, and the reflexive mirroring response must be overridden when the child mentions sensitive topics like bullying. The broader societal context is a US literacy crisis (40% of fourth graders below basic level) and teacher shortages, which the Ello team cites as motivation.
