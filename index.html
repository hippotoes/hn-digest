Cache-to-Cache: Direct Semantic Communication Between LLMs (2025)
⬆ 95 pts 💬 14 HN comments

Multi-LLM systems have until now communicated the way humans do: by serializing internal state into text. Published in ICLR'26, "Cache-to-Cache" (C2C) argues that this is a lossy bottleneck — transforming rich hidden representations into token sequences discards semantics and imposes token-by-token generation latency. The authors' oracle experiments first establish the key premise: enriching a model's KV-cache semantics improves response quality *without* increasing cache size, validating the KV-cache itself as a viable inter-model communication medium. C2C then operationalizes this with a learned neural projection that fuses the source model's KV-cache into the target model's, plus a learnable gating mechanism that selects which target layers actually benefit from the injected cache. The result is direct semantic transfer — no intermediate text generation — leveraging the deep, specialized representations each model already holds internally.

The numbers are the story: C2C delivers 6.4–14.2% higher average accuracy than the individual constituent models, and beats the conventional text-communication paradigm by roughly 3.1–5.4%, while clocking an average 2.5x latency reduction — the speedup falls out naturally from skipping autoregressive token emission between agents. The work sits at the intersection of the KV-cache-as-shared-state line of research that HN readers immediately mapped to adjacent efforts (a "Universal Weight Subspace Hypothesis" paper, latent-state handoff from cloud "big brain" models to smaller local ones, and Ramp's "Latent Briefing" for multi-agent coordination). It also lands squarely in an ongoing community debate about whether non-textual "thought layers" are a genuine capability unlock or an observability catastrophe for alignment and monitoring.

C2C beats text-based inter-model communication by 3.1–5.4% accuracy while cutting latency ~2.5x — the strongest evidence yet that token serialization between LLMs is a lossy, expensive bottleneck rather than a neutral interface.

Key Highlights
  • C2C fuses a source LLM's KV-cache directly into a target LLM via a learned neural projection, with a gating mechanism choosing which target layers receive the injected semantics.
  • Oracle experiments show cache semantic enrichment improves response quality at constant cache size — the empirical justification for using KV-cache as the inter-model channel.
  • Reported gains: 6.4–14.2% over individual models, 3.1–5.4% over text communication, and ~2.5x average latency reduction by avoiding explicit intermediate token generation.
  • The paper implies partial representational compatibility between independently trained models, which commenters extrapolate toward "KV-aligned" model families where an expensive reasoner plans and cheap models execute.
  • Community reaction flagged the alignment cost: non-textual Neuralese in inter-agent channels undermines monitorability, echoing concern about latent CoT traces in recent frontier models.

OpenJev
⬆ 638 pts 💬 270 HN comments

SemIf, formerly branded OpenJev, is an independent browser-only laboratory reproducing TypeSafe's Jev interface pattern with open-weight models rather than Jev's undisclosed model. Everything runs client-side through wllama with pinned GGUF builds pulled from Hugging Face and cached locally; no backend, no waitlist, inputs never leaving the page. The core experiment is a controlled A/B on the same loaded checkpoint and the same prompt: one path reads the model's choice logits directly and normalizes a softmax only across the displayed option tokens ('no decoding'), while the other asks the model to write the same distribution as JSON, token by token, with first-token and total wall-clock timings captured via performance.now(). Three tiers are offered — Qwen3 0.6B (639 MB, phone), MiniCPM5 2B (1.56 GB, desktop default), Qwen3.5 4B (3.01 GB, high-memory) — with balanced accuracy on native checkpoints reported at 44.0%, 68.6%, and 81.3% respectively against Jev's published 88.3%. The site is candid about methodological limits: direct scores are conditional probabilities over supplied options, not calibrated confidence, and quantization can shift both quality and speed.

The framing is deliberately deflationary, and that is precisely what the 270-comment thread seized on. TypeSafe's Jev is a non-generative, confidence-aware classifier optimized for zero-shot decisions ('BERT on crack' per orbital-decay), so a demo built from instruction-tuned chat models can only approximate the interface, not the behavior — the README concedes it 'does not reproduce Jev's undisclosed model or training.' Commenters ran their own probes and found the seams: ludicrousskill's trolley-style 'cross the road?' test yielded 0.985/0.015 from Qwen3 direct readout, 0.5/0.5 from the same model's generation path, and 0.878 for MiniCPM5, concluding 'we're just getting coinflip answer faster.' paulluuk's 1d6 die roll gave 76% on a single face, versus 84% at 83% confidence in 62ms from 'real' Jev. Meanwhile mmastrac pointed to a vLLM PR turning DiffusionGemma into a Jev-like evaluator, and cmrdporcupine summarized the trick bluntly: 'skip decode, just do prefill' — prefill being dramatically cheaper on GPUs. The thread also detoured into Jev's Terms of Use barring published benchmarks and the trademark scrub that renamed OpenJev.

Jev's published 88.3% balanced accuracy against SemIf's best locally-runnable 81.3% (Qwen3.5 4B) — with the project itself conceding 'None is claimed to match Jev.'

Key Highlights
  • SemIf/OpenJev is a fully client-side (wllama + GGUF) reimplementation of TypeSafe's Jev interface pattern using open models, explicitly unaffiliated with TypeSafe.
  • Two methods run sequentially on the same loaded model: direct logit softmax over displayed option tokens, versus token-by-token JSON probability generation.
  • Reported balanced accuracies: Qwen3 0.6B 44.0%, MiniCPM5 2B 68.6%, Qwen3.5 4B 81.3%, versus Jev's published 88.3%.
  • Community replications and adjacent work abound: a vLLM DiffusionGemma Jev patch (PR 57250), jevlike, Laya, and prior art from DeepMostInnovations.
  • Sharpest critique is behavioral: generation paths collapse to 0.5/0.5 on binary choices while direct readout is overconfident, undermining claims of calibrated decision probabilities.

Inside ZCode: Silently uploading your Git history to the cloud
⬆ 310 pts 💬 102 HN comments

A reverse-engineering teardown of ZCode — Zhipu (z.ai)'s AI coding desktop app — has surfaced a background pipeline that silently tars, encrypts, and uploads the user's entire workspace, including full .git history. The author, ferstar, began with a disk-space audit: ~/.zcode had ballooned past 700MB, with ~303MB sitting in v2/checkpoints/ as a 313MB .enc blob plus a state manifest recording encryptedSizeBytes 313070842 and a failureCount of 564. Cracking open the bundled app.asar revealed a two-stage flow: the client POSTs to https://zcode.z.ai/api/v1/snapshot/upload-credential, receives an RSA public key, a dynamic OSS object key, size limits and Aliyun form signatures, then archives and streams streaming-encrypted data directly to Aliyun OSS via a browser-style form POST, bypassing Zhipu's application servers entirely.

The encryption is textbook envelope encryption — AES-256-CTR for the payload, RSA-OAEP-SHA256 to wrap the ephemeral key — except the wrapping key is delivered by the server and its private half never touches the client. The author confirmed locally that no private key on the machine can unwrap it: neither the user nor the ZCode client can decrypt the ciphertext stored on their own disk, only Zhipu's backend can. A plaintext manifest shows 42,411 files packed, of which .git accounted for 86.6% — 196.1MB of LFS cache, 102.2MB of object store, 0.6MB of reflogs — meaning deleted API keys, unpushed branch names, and internal GitLab hostnames in .git/config all travel with the snapshot. Both UI switches (optimizeAgentExperienceEnabled, repoSnapshotIndexingEnabled) are inert against capture and upload, and the privacy policy never mentions workspace or history exfiltration. Zhipu has since issued an apology blaming a 'codebase indexing' feature.

That 313MB ciphertext on your drive cannot be opened by you or by the ZCode client — only by Zhipu's servers, because the RSA private key never leaves the cloud. The .git directory alone was 86.6% of the payload.

Key Highlights
  • ZCode packages the full workspace (tar.gz), AES-256-CTR encrypts it, wraps the ephemeral key with an RSA-OAEP public key fetched from zcode.z.ai, and POSTs the result directly to Aliyun OSS with a server callback registering the snapshot.
  • The decryption private key exists only server-side, so the 313MB .enc file on disk is unreadable by the user and by the client itself — evidence of collection rather than user-facing backup or sync.
  • A local plaintext manifest shows 42,411 files captured, 86.6% of the bytes being .git (LFS cache 196.1MB, objects 102.2MB, reflogs 0.6MB), exposing deleted secrets, unpushed branches, and internal hostnames.
  • Both relevant UI toggles are cosmetic against this pipeline: optimizeAgentExperienceEnabled only gates model-training authorization and repoSnapshotIndexingEnabled only gates server-side indexing; capture is instantiated unconditionally at startup with no preference checks.
  • Deleting the pending archive triggers immediate re-capture (failureCount 564 → 565), so the effective mitigation is filesystem immutability — chflags uchg (macOS) or chattr +i (Linux) on ~/.zcode/v2/checkpoints.

Show HN: Cactus Needle 3: 8-29MB automation models can match DeepSeek V4 Flash
⬆ 202 pts 💬 89 HN comments

Cactus Compute released Needle 3, an 8–29 MB on-device foundation model built on what it calls a Laddered Simple Attention Network: a 121M-parameter, 20-layer stack (70.8M of which lives in hashed engram tables) that can be sliced at inference into smaller sub-networks from 2 to 20 layers, each individually fine-tunable. The architecture is deliberately non-standard: mHC residual lanes with Sinkhorn-normalized routing, engram fusion injecting hashed 2- and 3-gram memory at layers 3/7/11/15/19, 3-tap causal convolutions per channel, 12:2 GQA with QK-norm and RoPE over a 1024-token window with global attention only at layers 4/9/14/19, and a Monarch–Hadamard FFN with Kronecker-factored matrices. The company claims >2x fewer MFLOPs per token than a same-config transformer, with 400–4k tok/s decode and 1–10k tok/s prefill on a Raspberry Pi 5 at CQ2 2-bit quantization.

The product thesis is narrow by design: trade general chat capacity for exact structured output — tool calls with ordered multi-call support, schema-constrained extraction with a byte-level grammar that guarantees parseability, and sentence embeddings for local routing and dedup. The headline claim is aggressive: a 4-layer sub-network fine-tuned for one epoch on downstream data supposedly matches DeepSeek V4 Flash, with fine-tuning on DroidCall lifting every sub-network 18–36 points and the crossover starting around 29M parameters. Deployment targets span macOS, Linux (x86_64, ARMv7, RISC-V64, MIPSEL), Windows, Android, iOS, watchOS, WASM and WASI, each shipping a sub-1MB engine. The comment thread, however, is a live stress test: the founder answers nearly every critic within minutes, patching demo presets in real time while Scaevolus posts a 90.9% vs 32.2% FunctionGemma comparison that undercuts the central benchmark narrative.

"Turn the kitchen to 230°C" was executed with confidence 0.9015 — a one-line demonstration of why a calibrated confidence head and a grammar-constrained decoder are not the same thing as world knowledge or common sense.

Key Highlights
  • Laddered architecture: one weight set slices from 2 to 20 layers (8MB to 29MB), each sub-network independently fine-tunable for a specific device and task.
  • Non-transformer internals — engram hashed n-gram memory, mHC lanes, 3-tap causal conv, Monarch-Hadamard FFN — claimed at >2x fewer MFLOPs/token than equivalent transformers.
  • Fully local structured output: ordered multi-tool calls, Pydantic-typed extraction, embeddings, with a decode grammar that guarantees valid JSON and returns empty call lists instead of guessing.
  • The 'matches DeepSeek V4 Flash from 4 layers up' claim rests on one-epoch fine-tuning on narrow suites (DroidCall 200 rows, Mobile Actions 961 rows), a methodology commenters found unpersuasive.
  • Broad deployment surface (ARMv7, RISC-V, MIPSEL, WASM/WASI, watchOS) with a sub-1MB prebuilt engine and Rust/C/JS bindings makes it genuinely interesting for silicon that cannot host an 8B model.

How OpenAI Used Its Own LLMs to Design Its Jalapeño Chip
⬆ 136 pts 💬 96 HN comments

OpenAI's Jalapeño, unveiled 25 August, is a 13.4-petaflop (4-bit) inference accelerator with 232 GB of HBM4 linked at 15.4 TB/s, deployed in 2,048-chip pods and benchmarked at up to 3.6x lower end-to-end latency than Nvidia's GB300 at lower power. The architecturally interesting part is the design pipeline: concept to first silicon in under 20 months, first RTL to tape-out in nine, with a team averaging fewer than 100 people and Broadcom handling physical design 'from the gates onward.' OpenAI's front end was built on XLS, Google's open-source high-level synthesis chain (DSLX/C++ to Verilog), deliberately chosen because LLMs are strongest in software-shaped, linguistic domains where synthesis tools provide fast, machine-checkable iteration loops. The model stack itself drifted during the project, from o3-era models to GPT-6 Astra precursors that write Verilog directly without an HLS translation layer, plus internal fine-tunes not released publicly.

The hard numbers are the story: pointed at DeepSeek's multi-head latent attention kernel, internal models moved performance from 0.31 percent of the theoretical bandwidth ceiling to 88.94 percent in roughly 40 hours, and AI-guided physical design cut matrix-multiply-unit area by 10 percent against an optimized human baseline (Hot Chips 2026). Richard Ho frames the human role carefully: 'The models are giving superpowers to our engineers... They're still the final arbiter.' Chris Leary admits XLS 'looks like software, so it got that benefit.' External reaction is split: Verkor's founders call the schedule 'quite credible' but attribute much of it to Broadcom; Andrew Kahng calls it 'best in class today.' Societally, the implications run toward IP exposure, verification bottlenecks, and whether design moats erode while foundry and lithography moats hold.

OpenAI's internal models lifted a DeepSeek MLA kernel from 0.31 percent to 88.94 percent of the chip's theoretical compute/memory ceiling in roughly 40 hours of automated tuning — a repeatable result the team now builds all its post-silicon schedules around.

  • Under 20 months concept-to-silicon and 9 months RTL-to-tape-out with a team averaging under 100 people; Broadcom owned physical design from gates onward
  • Front end built on Google's open-source XLS high-level synthesis chain because LLMs perform better on software-shaped DSLX/C++ than raw Verilog
  • Internal models tuned a DeepSeek MLA kernel from 0.31% to 88.94% of theoretical ceiling in ~40 hours, and cut matmul unit area 10% vs a human baseline

Android 17 is the first since 3.x to add new APIs without releasing to the AOSP
⬆ 878 pts 💬 458 HN comments

GrapheneOS disclosed that Android 17 QPR1 is the first Android release since Honeycomb (3.x) to introduce new application-facing APIs without simultaneously publishing them to AOSP. The mechanism is subtle but structural: beginning with Android 16, quarterly releases QPR1 and QPR3 became Pixel-exclusive builds, leaving only QPR2 and the annual platform drop as public AOSP artifacts. Consequently, any API added in a QPR1 or QPR3 branch exists first only in Google's commercial Pixel SDK, documentation, and system images. GrapheneOS frames this as a break in a fifteen-year covenant—new APIs for third-party developers have historically been open source and available to every OEM, not gated behind a single vendor's hardware. The change is not a license revocation but a cadence artifact, which makes it harder to contest and easier to extend.

The practical blast radius is bounded but real. As bri3d notes, OEMs receive backported security patches and internal source with a small delay, so the exposure is mainly SDK-level: Pixel-exclusive app features appearing months before December 2026's QPR2 fold-in. Developers are unlikely to target APIs available on a fraction of devices, so the immediate app-ecosystem impact is muted. The precedent matters more: GrapheneOS's own clarification—'There hasn't been a case of new APIs for apps not being open source or not being available to every OEM since Android Honeycomb'—frames this as the thin end of a wedge toward the macOS/Darwin model, where AOSP remains free but rots into a reference codebase while the shipped experience diverges. Commenters paired this with the unpatched CVE-2026-43499 root LPE ('ghostlock') allegedly weaponized for months across Pixels, arguing Google is degrading both openness and security simultaneously.

GrapheneOS: 'There hasn't been a case of new APIs for apps not being open source or not being available to every OEM since Android Honeycomb.' Android 17 QPR1 is the first regression in roughly fifteen years—new APIs are Pixel-exclusive until QPR2 in December 2026.

Key Highlights

#4
Saving another 100TB of RAM
⬆ 379 pts 💬 83 HN comments

Cloudflare's engineering blog details how a single load-balancing service, the Pingora Backend Router (PBR), was consuming far more memory than warranted because of its use of pingora-ketama, its open-source consistent-hashing library. The article spends considerable effort building the case from first principles: hashing maps both servers and tasks onto a shared 32-bit number line, and tasks are assigned to the first server to their left. The math matters because hash output is effectively random, so the fraction of traffic each server receives is a random variable with expected value 1/N and standard deviation (1/N)·sqrt((N-1)/(N+1)); the coefficient of variation, sqrt((N-1)/(N+1)), reaches roughly 99% for 100 servers, meaning some nodes may handle double the load of others. Adding hashes per server shrinks this error — 160 virtual nodes, the NGINX default that Pingora inherited, drops CV to about 8%.

The real memory cost came from a second axis: because compliance rules and caching features mean only subsets of servers can handle certain requests, every feature combination needs its own distinct ring. Cloudflare weighted hashes by disk space via ketama, then multiplied ring counts combinatorially, inflating hash structures dramatically. The fix was partly algorithmic — culling unnecessary hashes without degrading balance — and partly mundane: packing hash structs into tighter representations, where shaving a couple of bytes per entry compounds across millions of core-hours of data. The result was over 100TB of RAM reclaimed globally, on top of the 100TB the DNS team shed the previous month. The piece lands as a case study in how at Cloudflare's scale, a 1% optimization is worth celebrating and a well-profiled data-structure change can free resources equivalent to an entire fleet of servers.

Reducing hash counts and packing hash structs a few bytes tighter reclaimed more than 100TB of RAM globally — building on the 100TB the DNS team freed the month before.

Key Highlights
  • pingora-ketama's consistent-hashing structures in Pingora Backend Router used far more memory than expected
  • Coefficient of variation for 100 servers is ~99% with one hash each, dropping to ~8% with 160 virtual nodes per server
  • Feature combinations (compliance, caching) require separate rings, multiplying hash memory combinatorially
  • Ketama weights hash counts by disk space so request share is proportional to storage
  • Fixes were algorithmic (culling hashes) plus tight struct packing, reclaiming 100TB+ of RAM globally

Photon-Emission-Guided Laser Fault Injection Enables RP2350 Secure Debug
⬆ 195 pts 💬 73 HN comments

Ledger Donjon's disclosure against the Raspberry Pi RP2350 A4 is notable less for the end result than for the methodology used to get there. The attack chain begins with differential photon-emission microscopy: because switching transistors leak faint near-infrared photons correlated with activity, the team toggled individual DEBUGEN bits in a loop, averaged hundreds of frames, and subtracted mean stacks acquired in interleaved order to cancel sensor noise, thermal emission, and drift. That narrowed a needle-in-a-haystack targeting problem — finding the storage of one register bit on a die — down to a few micrometres, something impossible with the instruction-skip faults typical of laser fault injection, where any disturbed pipeline flip-flop produces the same effect. A 980 nm pulsed laser at ~1.2 W through a 50x objective then set PROC1 and PROC1_SECURE, producing DEBUGEN=0xc and Secure-attributed Mem-AP access.

The second half of the chain is architectural rather than physical. Setting DEBUGEN bits is necessary but not sufficient: the challenge's page-48 runtime lock (otp_hw->sw_lock[48] = 0b1111) blocks even Secure debug reads after firmware runs. The team exploited the RP-AP, which remains always accessible, to trigger CTRL.RESCUE_RESTART — a reset that halts the boot ROM before user firmware executes, so the runtime lock never tightens and reverts to the permissive persistent value derived from PAGE48_LOCK1 (LOCK_S = READ_WRITE). Halting core 1 via DHCSR then permitted reading OTP rows 0xc08–0xc0f directly. Critically, DEBUGEN_LOCK does not block laser-induced changes: pulses set DEBUGEN bits even with the corresponding lock bit at 1, and lock bits themselves became permanently set, preventing firmware from restoring DEBUGEN=0. The documented $250,000 lab cost, destructive backside decapsulation, and redundant OTP voting on CRIT1 flags did not protect the overriding mutable control register — a reminder that enforcement-path completeness, not per-mechanism hardening, is what security actually rests on.

"DEBUGEN can override the effect of the OTP-encoded debug-disable flags and has no equivalent protection documented in the datasheet" — a single unprotected mutable register undid redundant three-of-eight OTP voting and permanent debug-disable.

Key Highlights
  • Differential photon-emission microscopy localized DEBUGEN bit activity, reducing a blind die-wide scan to a few-micrometre search area.
  • Two laser positions a few micrometres apart set PROC1 and PROC1_SECURE (DEBUGEN=0xc), enabling Secure-attributed Mem-AP access; a 20x objective could not reproduce this because the wider spot hit both set and clear regions.
  • RP-AP CTRL.RESCUE_RESTART halts the chip in boot-ROM wait loops, so firmware never applies otp_hw->sw_lock[48]=0b1111 and the page reverts to permissive persistent LOCK_S=READ_WRITE.
  • DEBUGEN_LOCK is ineffective against faults: pulses set DEBUGEN bits with lock=1 and permanently set lock bits, preventing software from restoring the disabled state.
  • Mitigations like ACCESSCTRL debugger-manager filtering and periodic DEBUGEN checks are best-effort; ACCESSCTRL returns to all-open defaults after rescue reset, before firmware can reconfigure it.
