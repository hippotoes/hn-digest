Rio de Janeiro's "homegrown" LLM appears to be a merge of an existing model
⬆ 374 pts 💬 196 HN comments

The controversy surrounding Rio-3.5-Open-397B, released by Rio de Janeiro’s municipal IT company IplanRIO as a homegrown large language model, centers on a GitHub issue alleging that the model is merely a weighted merge of two existing models: Nex-N2 Pro (approximately 60%) and Qwen3.5-397B-A17B (approximately 40%). The accuser, nex-agi, demonstrates through two independent methods—prompt analysis revealing the model self-identifies as Nex, and weight tensor analysis showing a consistent linear interpolation across all 60 layers—that no additional training occurred. This practice, known as model merging, has gained traction as a cost-effective way to combine strengths of different finetunes, but the lack of disclosure undermines claims of original development. The incident highlights the challenges of provenance tracking in open-weight AI, where merges can be mistaken for novel training efforts, especially when the model outperforms benchmarks due to the combination of complementary finetunes.

Community reactions span technical fascination and ethical concern. Commenters note that merging only works reliably when models share a base architecture, as Nex itself is a finetune of Qwen 3.5, making interpolation plausible. One commenter observed that 'a simple linear combination of every weight did not degrade performance, but enhanced it,' referencing the Model Merging paper (arxiv 2203.05482). Others criticized the misrepresentation: 'Lying about your lab's capabilities is the relevant part.' Some defended the initiative, noting that a municipal IT department attempting AI work is admirable even if underfunded. The Hugging Face page for Rio-3.5-Open-397B was later updated to acknowledge the merge and claim additional on-policy distillation was intended but accidentally omitted. This incident underscores the need for transparent disclosure in model releases and the ease with which merges can be disguised as original work, especially when government entities are involved.

Every weight tensor in Rio is, to thousands of standard deviations, the same 0.6/0.4 blend of Nex and Qwen across all 60 layers.

Key Highlights
  • Rio-3.5-Open-397B is shown to be a linear merge of 60% Nex-N2 Pro and 40% Qwen3.5-397B-A17B, not an original finetune.
  • Evidence includes self-identification as 'Nex' in 79% of queries and identical weight interpolation across all layers.
  • Model merging is feasible and effective only between models with the same base architecture, as both Nex and Qwen derive from Qwen3.5.
  • IplanRIO updated the model card to acknowledge the merge, claiming the final distilled version was accidentally replaced by the merge.
  • The incident highlights growing concerns over provenance and transparency in open-source AI model releases.

Your ePub Is fine
⬆ 751 pts 💬 246 HN comments

The article exposes a fundamental disconnect between the EPUB standard as validated by tools like epubcheck and the real-world rendering on Kobo devices, which rely on Adobe's RMSDK renderer. The author, an indie author and publisher, has meticulously crafted EPUBs that pass all validation checks, only to find them rendered poorly on Kobo e-readers—text overflow, missing images, broken layouts. The culprit is RMSDK's CSS support, which remains stuck at around 2013 capabilities, lacking features like 'max-width' and modern layout modules. This is not a case of non-compliant files but a broken renderer that Adobe has neglected, focusing instead on DRM. The author argues that the EPUB standard is robust, but its implementation by Adobe has been disastrous for indie publishers and readers alike.

Commenters overwhelmingly confirm the issue, with many sharing workarounds: converting EPUBs to Kobo's proprietary KEPUB format (using Calibre or kepubify), installing the open-source KOreader alternative, or even running Linux on Kobo devices. A striking comment notes that 'Adobe has always been like this'—citing Flash's decline due to poor QA and DRM obsession. Another highlights that 'EPUB: the open standard where "valid" and "will render correctly" are two separate hobbies.' The irony is that Kobo's own devices perform better with a non-standard format (KEPUB) than with the standard EPUB. This saga underscores the broader problem of standards fragmentation and vendor lock-in, even in ostensibly open ecosystems, and points to the need for independent renderers like KOreader to ensure true portability.

“EPUB: the open standard where 'valid' and 'will render correctly' are two separate hobbies.”

Key Highlights
  • EPUB validation via epubcheck does not guarantee correct rendering on Kobo due to Adobe's outdated RMSDK CSS engine (circa 2013).
  • Kobo's proprietary KEPUB format offers superior rendering, highlighting the failure of the standard EPUB implementation.
  • Open-source alternatives like KOreader and Calibre's converter provide practical solutions for users.
  • Adobe's historical pattern of poor QA and DRM prioritization (e.g., Flash) is seen as the root cause.
  • The situation reflects a broader issue: standards are only as good as their least capable implementation.

Show HN: Kage – Shadow any website to a single binary for offline viewing
⬆ 611 pts 💬 120 HN comments

Kage (影, 'shadow') is a Go-based CLI tool that clones websites into self-contained offline archives by driving a real headless Chrome instance, capturing the final DOM after JavaScript execution, then stripping all scripts and localizing assets. Unlike traditional mirroring tools like wget --mirror or httrack, which fail on JavaScript-heavy single-page applications, Kage renders each page in a headless browser, waits for the page to settle (including lazy-loaded content via optional auto-scroll), snapshots the rendered DOM, removes all <script> tags, inline event handlers, and javascript: URLs, then rewrites CSS, images, and fonts to local relative paths. The output is a folder of static HTML files that can be served via a built-in HTTP server (or Python's http.server) and further packed into a single ZIM archive (standard Kiwix-compatible format) or a self-contained executable binary (with or without native window via webview tag). The crawl is polite (reads robots.txt, uses sitemap.xml, respects breadth-first order with configurable depth, page limits, and subdomain scope), idempotent (resumes on interrupt), and deterministic for packs.

The project, with 1.3k GitHub stars and 5 releases, addresses a growing need for reliable web archiving in an era of ephemeral, JavaScript-dependent sites. The author, tamnd, emphasizes portability: a cloned mirror can be packed into a ZIM file (text zstd-compressed, media stored as-is) that works with any Kiwix reader, or into a binary that serves itself without dependencies. A notable feature is the ability to create platform-specific viewers via --base flag, e.g., building a Windows executable from macOS. The README also hints at an upcoming WARC export (via separate ccrawl-cli) and Markdown conversion. However, concerns raised in HN comments include the use of --no-sandbox Chrome flag (needed for Docker but risky otherwise), the fact that the output's static nature still requires a server (due to same-origin and CORS restrictions when opening files directly), and comparisons to SingleFile for single-page saves or gwtar for self-extracting HTML archives. The highlight: the tool's tagline 'No tracking, no network calls, no surprises' encapsulates its core promise of a future-proof, JavaScript-free offline copy.

"The page was never really yours. It was a thin client for someone else's JavaScript." — This line from the README crystallizes the motivation behind Kage's approach of rendering then stripping JS.

Key Highlights
  • Renders pages via headless Chrome, strips all JavaScript post-render.
  • Outputs a folder of static HTML with localised assets; can pack into ZIM or self-contained binary.
  • Respects robots.txt, sitemap.xml, and supports resume, scope-prefix, subdomain, and auto-scroll.
  • ZIM archives are portable across Kiwix ecosystem; binary mode includes embedded viewer.
  • Deterministic packing and platform-cross compilation for offline distribution.
