#1
Multiple vulnerabilities in Regexp and String case conversion
⬆ 318 pts 💬 122 HN comments

On 18 November 2026 the Ruby core team disclosed seven memory-safety flaws spanning the Onigmo regular-expression engine and the C-level string case-conversion routines, shipping fixes in Ruby 4.0.10, 3.4.13 and 3.3.14. The advisory is unusually blunt: proof-of-concept code exists showing that several of these bugs reach remote code execution, not merely denial of service. The underlying defects are classic C arithmetic failures reached through Unicode semantics — a one-byte heap overflow when upcasing Windows-1252 strings (German ß normalises to "SS", growing the output one byte beyond what the per-character headroom check anticipates), an integer overflow in Shift_JIS downcasing where a 2**32+4-byte string wraps a length calculation, a double free during regexp compilation, and out-of-bounds reads in case-insensitive matching and backreference handling. Ruby 3.2 and earlier are end-of-life and will receive nothing.

The credits are the story's second act: four of the seven advisories are attributed to Stephan Lipp of Ada Logics "and Anthropic" — a clear signal that LLM-assisted code review and fuzzing now produces exploitable memory-corruption findings in mature, heavily audited codebases. HN's 318 points and 122 comments quickly forked into familiar territory. tptacek reverse-engineered the ß overflow from the advisory text alone ("if the last character of a string you upcase is ß, it looks like you get a one-byte overflow (of 'S')"), while pentestercrab posted a Shift_JIS repro that prints a 4.29 GB bytesize before crashing. Practically, exposure requires attacker-controlled regexps or multi-gigabyte crafted strings, which softens the blast radius for a typical Rails app — but the deeper lesson stands: a nominally memory-safe language is only as safe as the C it delegates to.

Four of seven advisories are credited to "Stephan Lipp (Ada Logics) and Anthropic" — and one bug is triggered simply by upcasing a string ending in ß, where "SS" needs one byte more than the Windows-1252 buffer allows.

Key Highlights
  • Seven GHSA-tracked vulnerabilities in Ruby's regexp engine and String case conversion, all C-level memory-safety bugs; patches in 4.0.10, 3.4.13 and 3.3.14.
  • PoCs demonstrate remote code execution for at least four of the issues, including a heap overflow in case conversion and a double free in regexp compilation.
  • The ß→"SS" case-expansion path in Windows-1252 (and an integer overflow with a 2**32+4-byte Shift_JIS string) show Unicode case folding breaking C buffer-length assumptions.
  • Four advisories were reported by Stephan Lipp (Ada Logics) and Anthropic, underscoring AI-assisted vulnerability discovery against production-grade C.
  • Ruby 3.2 and earlier are EOL and unpatched; the community split over real-world exploitability versus the broader memory-safety indictment.

#2
Nintendo takes Picofly firmware down from GitHub [video]
⬆ 162 pts 💬 57 HN comments

Nintendo has filed a DMCA takedown against a GitHub fork of Picofly, the RP2040-based modchip firmware that lets a Switch — including patched and Mariko units, and reportedly Switch 2 hardware — boot unsigned payloads. The technically interesting part is what Picofly actually is: a clean-room firmware targeting a Raspberry Pi RP2040 microcontroller, not Nintendo silicon. It ships no copyrighted assets, no leaked keys, no Nintendo code. Its only 'offense' is that it enables the console's boot ROM to accept an unsigned payload, which is precisely the conduct anti-circumvention law was written to reach — a hardware-agnostic general-purpose unlock whose legality hinges on whether a console's signature checks are legally a technological protection measure under 17 U.S.C. §1201 rather than §512.

The comment thread immediately split on that distinction. judge2020 notes Nintendo cites only §1201, and asks whether a §512 takedown mechanism is even a valid vehicle for an anti-circumvention claim, then self-replies with Universal City Studios v. Reimerdes (S.D.N.Y. 2000), which held §512(c) shields only copyright infringement liability. ndiddy counters that GitHub processes §1201 claims voluntarily, since the DMCA's anti-trafficking clause has no safe harbor and GitHub could itself be named. haunter supplies the sharpest fact: the canonical repo, up since 2023, is untouched — Nintendo hit a fork 'which had a lot more than the firmware itself.' piltdownman frames the stakes as a coming collision between physical-equipment rights and IP rights across all hardware vendors.

"The main repo is still untouched and available on Github and it's up since 2023. They took down a fork which had a lot more than the firmware itself" — the takedown may be less a legal victory than a chokepoint strike on the most complete mirror.

Key Highlights
  • Picofly is clean-room firmware for a generic RP2040 MCU, containing no Nintendo code or assets — its sole function is allowing unsigned payload execution on Switch hardware
  • Nintendo's notice invokes only §1201 anti-circumvention, raising the unresolved question of whether §512 takedown machinery is a valid vehicle for such claims (cf. Reimerdes, 82 F. Supp. 2d 211)
  • The canonical repository survived; the target was a fork containing additional material, undercutting any clean 'firmware is illegal' narrative
  • GitHub processes §1201 claims voluntarily as risk mitigation, because anti-trafficking liability has no statutory safe harbor protecting the host
  • Discussion quickly shifted to archival resilience — Radicle, local + cloud backups, and the observation that 'anyone who cloned it is a mirror'

#3
We taught robots to carve marble sculptures
⬆ 94 pts 💬 74 HN comments

Monumental Labs, a Greenpoint, Brooklyn shop that has spent years carving landmarked New York stonework with conventional CNC, presented at Embodied AI NYC what it calls the first end-to-end autonomous stone-carving pipeline: a 3D model and a marble block in, a finished sculpture out, with no human programming toolpaths. The novelty is not machining but the removal of the CAM programmer. Their manual baseline — Villard Houses balconies, 100+ limestone modillions for the Frick, a life-size Feynman — consumed weeks to months each in Autodesk PowerMill, software designed for injection molds where one toolpath is reused thousands of times. The autonomous system instead builds a sparse voxel grid from arbitrary meshes, derives a signed distance field with normals and gradients for constructive-solid-geometry subtraction, plans isoplanar bulk roughing, then fine and off-axis passes for overhangs, then solves finishing as a sequence of offset layers via voxel dilation and mesh-intersection cuts.

The finishing stage is the technically interesting part: point-cloud segmentation partitions each layer into machinable regions, iso-geodesic isolines replace Euclidean paths that would cut through the stone, an optimizer stitches isolines into continuous non-lifting toolpaths, and a kinematics solver produces collision-free tool orientations and joint angles for a KUKA KR240 — all simulated and visualized in an in-house app called Hilbert before a million-dollar arm ever moves. Compute, they argue, is now the only ceiling on sculptures per day. The framing is deliberately economic: 'de-extinction, not displacement,' targeting Baumol-style cost disease in ornament rather than displacing artisans, with human hand-finishing retained for final surface quality. The demo, a Stanford bunny pulled from a carved top hat, earned both admiration and the obvious rebuttal that three decades of graphics research made that particular mesh easy.

"Each of these pieces took our digital fabrication team weeks to months of manually programming toolpaths in CAM software like Autodesk PowerMill... Available compute is now the only limit to the number of sculptures that could be programmed each day."

Key Highlights
  • The claimed advance is autonomous toolpath generation, not machining: replacing weeks-to-months of manual PowerMill programming with an unsupervised pipeline.
  • Technical stack: sparse voxels → signed distance fields → CSG subtraction, isoplanar and off-axis roughing, voxel-dilation finishing layers, geodesic isolines, and full kinematic simulation.
  • Monumental Labs positions automation as cost-disease relief for architectural ornament, not artisan replacement, retaining human hand-finishing for final surfaces.
  • The Stanford bunny demo was widely criticized as a poor showcase: a smoothed 1994 scan with under-sampled detail and no crisp features to test against real marble sculpture.
  • Commenters split between 'this is just normal CAM' skeptics and those excited about cheap, Gaudi-scale ornament and scan-driven restoration of old buildings.

Exponential Behavior in Magic: The Gathering
⬆ 56 pts 💬 33 HN comments

Levi Neuwirth's essay uses Magic: The Gathering as a case study in why exponential blowup defeats naive software design. Building his own Rust rules engine, Arcana, after concluding that Forge could not be rehabilitated into an RL experimentation platform, he traces the failure mode to the game's ability structure: card interactions compound, and the rules checks required to confirm no further triggers must be placed on the stack grow exponentially with board size. His canonical examples are Scute Swarm, which doubles copies on each land drop—eight landfalls with two Wardens and token/life doublers yield 6,561 Scutes and 26,240 life—and Liliana, the Last Hope's emblem, whose zombie recursion follows Z_{n+1} = 2Z_n + 2, giving Z_n = 2^{n+1} − 2 and, crucially, restarting from zero even after a full board wipe. Scute Swarm can be removed; an emblem cannot.

The empirical payoff came from fuzzing: 64 Pioneer decks, 2,016 pairs, 4,032 games replayed across 100 seeds—403,200 randomized matches on an HPC cluster. Nine jobs hit the two-hour wall, all involving the four Liliana decks. A laptop replay showed emblem resolutions costing 1.72, 7.78, and 35.15 seconds as the zombie count doubled, since each entering token walks the battlefield to check evolve—quadratic work per doubling. Worse, Arcana's combat enumerator, capped at 1,024 declarations, fills its budget on single-creature attacks (56 attackers × 4 defenders + pass = 229 on turn 44), so the all-in loop never executes; by turn 58 the largest offered attack sends one zombie against 7,258. The fix was crude but effective: cap total permanents at 500 and yield 'board_cap'.

Neuwirth's real contribution is framing the halting-adjacent problem as an engineering one: expressive rules plus combinatorial state explosion means correctness and tractability must be traded explicitly, not discovered by timeout.

By turn 58 the opponent sat at 31 life facing 7,256 Zombies—yet the largest attack Arcana's 1,024-declaration budget offered sent exactly one 2/2 Zombie at a planeswalker, because the single-attack loop exhausted the enumerator before the all-in loop ever ran.

Key Highlights
  • Liliana's emblem recursion Z_n = 2^{n+1} − 2 restarts from zero after board wipes, unlike removable Scute Swarm copies
  • 403,200 randomized HPC games exposed nine two-hour timeouts, all from four Liliana-containing decks
  • Per-token evolve checks make emblem resolution roughly quadratic per zombie doubling: 1.72s → 7.78s → 35.15s
  • A 1,024-declaration combat cap silently starved the all-in attack loop, leaving 7,234 zombies unable to attack
  • Neuwirth's mitigation is a blunt 500-permanent board cap, trading fidelity for tractability

C's designated initializers give us named arguments
⬆ 50 pts 💬 37 HN comments

Arthur O'Dwyer's post resurrects a preprocessor idiom from Ben Klemens' 2014 book *21st Century C*: wrap a function in a variadic macro that splats `__VA_ARGS__` into a compound literal of an argument struct, letting callers write `ideal_volume(.kelvin = 373.15)`. The trick exploits two properties of C's designated initializers that C++20 deliberately declined to adopt — designators may appear in any order, and later designators silently override earlier ones with the same field name. Defaults live in the macro body; user-supplied designators come last and win. The payoff is named, defaultable, order-independent arguments with ordinary call syntax, and the guarantee that adding a new field to the args struct is not an API break: every existing call site recompiles unchanged with identical behavior. It is, however, still an ABI break, since the compound literal is passed by value and the struct layout changed.

The article is candid about the cost-benefit, noting that callers merely need recompilation, not rewriting, and that the pattern is 'heavyweight and cute' compared to a plain `double ideal_volume(double atm, double moles, double kelvin)`. O'Dwyer points to real deployments: Epic's `raddebugger` uses it for `ui_anim(key, target, .initial = x)` with a default animation rate baked into the macro, and `gab462/hof-flecs-raylib` for `send_message(..., .from_id = name)`. He also documents the warts — Clang warns `-Winitializer-overrides` by default while GCC only emits `-Woverride-init` under `-Wextra`, meaning the override behavior that makes the idiom work is exactly what a linter is trying to flag. That tension, plus struct-by-value calling convention overhead, frames the discussion: an elegant language-lawyer exploit that trades diagnostics and ABI stability for ergonomics.

The idiom's load-bearing mechanism is the one compilers warn about: the same designator appearing twice, with only the last one sticking — Clang flags it by default, GCC only under `-Wextra`.

Key Highlights
  • Designated initializers in C allow arbitrary ordering and duplicate designators (last wins), both rejected by C++20's restricted form — that difference is what enables defaultable named arguments
  • Adding a field to the args struct is not an API break for callers but is an ABI break, requiring recompilation against the new header
  • Clang emits -Winitializer-overrides by default, GCC only emits -Woverride-init under -Wextra, so the idiom fights default diagnostics
  • Real-world users include EpicGames/raddebugger and gab462/hof-flecs-raylib, though the author explicitly says not to adopt it broadly
  • The core trade-off is macro-based call syntax plus struct-by-value calling convention in exchange for named, order-independent, defaultable parameters
