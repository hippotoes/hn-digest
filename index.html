Show HN: Whiteboard (YC W26) – An open-source IDE for thoughtful software design
⬆ 339 pts 💬 123 HN comments

As coding agents shift the bottleneck from writing code to comprehending it, Whiteboard (YC W26) proposes that the missing artifact is a shared visual workspace where humans and agents architect together. The MIT-licensed desktop app vendors a full Code OSS fork rather than maintaining patches — a deliberate choice justified by the observation that '~45% of the codebase is Copilot these days' and that agents struggle with patch-based forks — and layers on three technical bets: an AST-aware semantic diff viewer written in Rust that collapses unit tests and docs and summarizes large added functions as pseudocode, a WASM-based plugin system for customizing that view, and a local stdio MCP server that gives Claude Code or Codex an SDK to stream sequence diagrams, ER diagrams, and decision traces onto an in-app canvas. Diagrams are wired bidirectionally to source, so clicking a node performs go-to-definition against VS Code's LSP, with the stated goal of preventing specs from drifting from implementation by treating diagram nodes as code 'forge comments'.

The reception numbers are substantial for a Show HN: 339 points, 123 comments, 994 GitHub stars, 36 forks, and 439 commits. But the thread surfaced real friction. The README's 'Known limitations' concedes 'You cannot currently edit files in Whiteboard,' and the launch is macOS plus Fedora only — the author promises 'windows is on our roadmap (fingers crossed launching tomorrow!)' but no web viewer or multiplayer. Codex itself warned users that 'Whiteboard requires uploading/exposing repository data to its authoring server,' which the team clarified is just the local stdio MCP process, conceding 'we should clarify that nomenclature.' Most damaging was a hallucination catch: commenter 8organicbits identified a 'wait for release' transition in the lease-broker demo that didn't exist in the diff; the author admitted 'that gif is a notional one we were using for design, and we forgot to update it.'

Codex flagged the tool itself: "Whiteboard requires uploading/exposing repository data to its authoring server" — prompting the team to admit the local stdio MCP server's naming 'needs clarifying' and that hallucinated diagram labels appeared in a launch demo.

Key Highlights
  • Whiteboard is an MIT-licensed desktop IDE that vendors Code OSS instead of maintaining patches, arguing agents handle patch forks poorly and that ~45% of stock VS Code is Copilot code they don't need
  • Its Rust AST-aware semantic diff viewer hides tests and docs by default and summarizes large added functions as pseudocode, extensible via a WASM plugin system
  • A local stdio MCP server gives coding agents (Claude Code, Codex) an SDK to stream diagrams onto a canvas, with diagram nodes linked to code via LSP go-to-definition

Opus 5.5 is good at explainer videos
⬆ 313 pts 💬 168 HN comments

LaunchVideo (launchvideo.io) is a demo, built by the Digger team on OpenComputer, showing that Claude Opus 5.5 can author a complete explainer video from nothing more than a URL or a one-line prompt. The interesting engineering claim is that no video model is involved. Opus writes an HTML/CSS/JS film; a serverless agent then loads that document in a fresh arm64 microVM (Amazon Linux 2023, 4 vCPU, 8 GB, Node 22) with headless Playwright Chromium and a static ffmpeg, and renders it deterministically. The trick is clock virtualisation: requestAnimationFrame, setTimeout, Date, CSS animations and Web Animations are all replaced by a synthetic clock, so every frame is an exact seek rather than a real-time screen capture. Frames are 1920x1080 at 30 fps, JPEG-piped into libx264 at crf 18, then uploaded to Vercel Blob. The whole product is described as one agent file, three defineTool functions (web_fetch, check_scene, render_video) and a form.

The economics are the real headline: roughly 90k input and 15k output tokens per film — mostly the HTML itself — and about four minutes of wall time, with the first tool call spending ~60 seconds installing Chromium and ffmpeg before the VM is discarded. The control plane is the same session API the CLI uses: create a session, send one turn, poll tool.started/tool.completed/turn.completed events. Seeded by Deedy's post on Opus 5.5 and instructional video, the demo triggered 168 comments that split sharply. Cynics called it \"flashy slide decks\" and \"the next level of PowerPoint presentations,\" or pointed at explainer videos as \"dark patterns that replaced written howto documents in order to serve ads.\" Practitioners — videozero.ai, screenci.com, videowright, ndemo, a $4 Reddit recreation — were far more enthusiastic, and one commenter noted the local fork runs \"just as well with claude-code -p and a local copy of ffmpeg,\" puncturing the platform lock-in.

~100k tokens and four minutes per video, with no video model at all: Opus 5.5 writes the film as HTML/CSS/JS, and a virtual-clock Chromium seek renders every 1080p30 frame deterministically into libx264.

Key Highlights
  • No video model: Opus 5.5 authors HTML/CSS/JS, and headless Chromium plus ffmpeg renders it — the 'model writes code, code renders identically every time' thesis.
  • Determinism comes from clock virtualisation — rAF, timers, Date, CSS and Web Animations are replaced with a virtual clock so each frame is an exact seek.
  • Cost/throughput: ~90k input + 15k output tokens and ~4 minutes per film, including a ~60s one-time Chromium/ffmpeg install in an ephemeral arm64 microVM.
  • The whole product is one agent file, three tools (web_fetch, check_scene, render_video) and a form; jobs run via the same session API the CLI uses, with MP4s landing in Vercel Blob.
  • Community reaction split between 'flashy slide decks / dark-pattern ads' and a cluster of practitioners (videozero.ai, screenci.com, videowright, ndemo) who say they've shipped the same thing already.

Using LLMs to trace alchemical knowledge and decode 17th century letters
⬆ 145 pts 💬 31 HN comments

The article, by historian Benjamin Breen on his Res Obscura Substack, argues that AI labs should fund historical research, using LLMs to decode 17th-century alchemical letters and trace the transmission of esoteric knowledge. Technically, this involves handwritten text recognition (HTR) on early modern scripts, entity resolution across multilingual correspondence, and semantic search over digitized archives. Alchemical texts are especially challenging: they mix Latin, vernacular, symbols, and ciphers. Breen demonstrates that LLMs can surface connections between practitioners and map intellectual networks across Europe. The piece is both a proof-of-concept and a policy proposal: historical corpora are low-resource, high-value testbeds for reasoning, retrieval, and multimodal parsing. The call for funding is framed as mutually beneficial: labs get novel evaluation data, historians get computational tools, and the public gets open knowledge. It sits within a broader digital humanities trend of leveraging AI for transcription, translation, and knowledge graph construction.

On Hacker News (145 points, 31 comments), the reception is largely enthusiastic but critical. Users report decoding handwritten vital records 'one shot' (apaprocki), translating 800 pages of German mission records (thomasfromcdnjs), and correcting genealogical errors buried in consensus trees. dr_dshiv's SourceLibrary.org offers tens of thousands of alchemy and magic books as agent-accessible translations via MCP and embeddings. Skeptics, however, question ROI: charcircuit asks whether old texts improve benchmark scores; wartywhoa23 doubts LLMs can grasp hermetic metaphors. Others pilot claim audits against primary sources, finding that two of six claims contradicted their own sources. The debate underscores both the promise of LLMs for historical scholarship and the need for verification, sustainable funding, and open infrastructure.

'Current models are amazing at one shot decoding hand written vital records. I thought there might be some friction, but if there is, I haven’t found any.' — HN commenter apaprocki, capturing the practical success driving enthusiasm.

  • Open infrastructure like SourceLibrary.org provides agent-accessible translations, MCP endpoints, and embeddings for alchemy/magic corpora.

F-Droid 2.0
⬆ 1313 pts 💬 374 HN comments

F-Droid 2.0 lands after more than a year of development and 14 test releases, billed by the project as its largest update in a decade. The Android client was rewritten in Kotlin and Jetpack Compose, collapsing navigation into three areas — Discover, Search, My Apps — while categories, search (now covering descriptions, categories, translated content, and markedly better CJK tokenisation) and combinable filters were reworked to address a repository that has grown to thousands of apps. The technically consequential change is installer plumbing: F-Droid now uses Android's session installer plus the newer pre-approval API for a unified install path, letting users confirm before download on supported devices — a capability the post explicitly credits to EU DMA pressure and global antitrust action. The Privileged Extension is unsupported in 2.0, Tor auto-detection has given way to generic proxy settings with TorVPN recommended, and the panic-triggered app-wiping feature is temporarily gone.

The comment thread (1,313 points, 374 comments) reads as a referendum on a decade of accumulated UX debt. comex noticed a broken 'Syncthing-For / k' line break in the first screenshot, which tadfisher diagnosed as Compose's omitted per-Text line-break flag; idle_zealot attacked the 'now-standard design convention of categorically refusing to draw lines between things', while doginasuit defended proximity grouping over separator lines. epihelix used droid-ify to 'uninstall F-droid and roll back to v1', objecting to clicking through updates app-by-app; landdate migrated the other way from Neo Store. Rollout confusion is real — m4rtink found the download page still serving 1.23.2. A deeper debate pits meredithbloom's distrust of repository binaries against potamic's reproducibility argument ('actually safer than downloading directly'), with yjftsjthsd-h insisting on F-Droid's due diligence given past supply-chain incidents, and maintainer eighthave engaging directly.

F-Droid's own release notes advise a subset of users not to upgrade at all: 'Users who rely on the current app-wiping implementation may opt to postpone updating to F-Droid 2.0 while we evaluate bringing the feature back.'

Key Highlights
  • F-Droid 2.0 is the project's largest release in a decade: a Kotlin/Jetpack Compose rewrite, three-tab navigation (Discover, Search, My Apps), and 14 pre-release cycles before rollout.
  • The overhaul replaces the Privileged Extension with Android's session installer and a new pre-approval API, which F-Droid credits directly to EU DMA pressure and worldwide antitrust action.
  • Default behaviour changed materially: automatic background update checks, pull-to-refresh repurposed for scrolling only (manual checks moved to an overflow menu), and Tor auto-detection replaced by generic proxy settings.
  • Privacy features narrowed — panic-triggered app wiping is temporarily removed and icon masking no longer disguises F-Droid as a calculator, prompting the maintainers' own advice to postpone updating.
  • Discovery work spans expanded specialised categories (including 17 game genres), search across descriptions and CJK content, stackable filters, and a security audit by OTF's Security Lab with Convocation.

Two-tier encryption in the UK
⬆ 476 pts 💬 427 HN comments

The story turns on a distinction most 'encryption' coverage blurs: all iCloud data is encrypted, but only some of it is end-to-end encrypted. Fourteen categories — Keychain, Health, Messages in iCloud — are E2EE by default; Apple holds no keys and cannot produce plaintext under warrant. Advanced Data Protection (ADP) extends that to 23 categories, moving iCloud Backup, Photos, Notes and Drive into a regime where keys derive from the user's trusted devices and Apple's servers are architecturally barred from rolling the setting back. That design choice is exactly why the UK's January 2025 Technical Capability Notice, issued under the Investigatory Powers Act 2016, could not simply be satisfied by handing over keys: there were none to hand over. Apple's response was to withdraw ADP for new UK users in February 2025 rather than build the capability the notice demanded. Because the setting can only be changed from a trusted device, Apple could not disable ADP for existing UK users — producing the titular two-tier outcome, where identical hardware in the same jurisdiction gets materially different cryptographic guarantees based purely on whether ADP was switched on before the cutoff.

The numbers and the paper trail matter here. The HN thread drew 476 points and 427 comments, deep into a dispute now running through the Investigatory Powers Tribunal: Apple filed a fresh complaint in July 2026, and on 17 September 2026 the Daily Telegraph reported Apple asking the IPT to lift gag restrictions so 'facts [could] be deployed in the open' — Daniel Beard KC for Apple. Liberty and Privacy International called the gag 'farcical'; Ben Jaffey KC likened it to the emperor's new clothes, arguing it 'brings the administration of justice into disrepute.' US Senator Ron Wyden and Representative Warren Davidson pressed the tribunal on 11 September, framing foreign non-disclosure orders as an obstacle to congressional oversight. The original global demand was narrowed to UK persons in late 2025 after US pressure — but the precedent generalises: WhatsApp, Signal (whose Meredith Whittaker has said the Foundation would leave a jurisdiction rather than backdoor), cloud storage, password managers. Apple picked the least-bad third option; the asymmetry is the government's gift to UK users.

"Alice enabled ADP on her iPhone in 2024. Bill can't turn the feature on. Both are UK residents. Both use iCloud. Both are subject to the same UK legal regime." — two identical iPhones, two different cryptographic realities, decided entirely by whether a checkbox was ticked before February 2025, because Apple's servers are designed so they cannot roll ADP back on a user's behalf.

Key Highlights
  • ADP raises E2EE coverage from 14 to 23 iCloud categories; Apple holds no keys for those, so the TCN could only be satisfied by rebuilding the security architecture, not by handing over data.
  • Apple withdrew ADP for new UK users in February 2025 rather than comply — but by design the setting can only be modified from a user's trusted devices, so existing UK users retain it, creating a permanent two-tier split.
  • The original Technical Capability Notice was reportedly global in scope, narrowed to UK persons in late 2025 after Trump administration pressure over US users' exposure.
  • Marching through the IPT: Apple's July 2026 complaint, the September 2026 Telegraph report, and the Wyden/Davidson letter arguing foreign gag orders obstruct US congressional oversight.
  • TCNs are issued in secret with recipients gagged; the Home Office generally neither confirms nor denies their existence, which critics like Jaffey KC call 'farcical' and damaging to the administration of justice.
