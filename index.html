Os8088: A powerful Mac-like OS for the IBM XT, 286, 386
⬆ 153 pts 💬 77 HN comments

os8088 is a complete graphical operating system for the original IBM PC/XT class machines, built for the Intel 8086/8088 and booted entirely from floppy. It delivers a Macintosh System 1-style desktop—overlapping windows, pull-down menus, dock tiles—on machines with just 256K of RAM. The kernel is 78,950 bytes and the boot sector is exactly 512; all 112,792 lines of assembly were written in real mode with the aid of Anthropic's Claude. It provides genuine pre-emptive multitasking at the PC's 18.2 Hz timer tick, a feature the 1984 Mac never had. The system probes VGA, Hercules, or CGA adapters, drives a serial mouse, and can load multiple applications into separate memory segments. Because the 8086 has no memory protection, context switches are cheap but any program can crash the system. The entire project is open source and the website documents every detail, including a host machine running five programs simultaneously.

The HN thread attracted 153 points and 77 comments, with reactions split between astonishment and AI-authenticity backlash. The author, jggonz, openly acknowledged that Claude wrote the code, admitting "many millions" of tokens were used. Some commenters called it a "hand-prompted" rather than hand-written effort, while others like RachelF called it the most compelling AI coding demonstration yet. The project was verified on a real IBM 5150, Toshiba T1100 Plus, and a 286, with photos on the site. Beyond the visual nostalgia, os8088 includes a four-channel MOD player, a bitmap editor, a Mandelbrot explorer, and even a ported Markdown writer. Commenters drew comparisons to Visi On, GEM, GeoWorks, and Atari GOS, framing the project as a rebuilt alternate history of PC GUI. Whether dismissed as "AI slop" or celebrated as the best ad for Claude, it has clearly reinvigorated interest in retro-hardware hacking.

A 78,950-byte kernel and 512-byte boot sector give an IBM XT pre-emptive multitasking, overlapping windows, and loadable apps—written entirely in AI-generated 8086 assembly.

Key Highlights
  • os8088 is a Macintosh System 1-style GUI OS for Intel 8086/8088, written in real-mode assembly with AI (Claude), booting from a single 512-byte sector.
  • It runs in 256K, supports VGA/Hercules/CGA, pre-emptive multitasking at 18.2 Hz, loadable apps, serial mouse, and fits a 78,950-byte kernel.
  • The project is open source on GitHub, with 112,792 lines of NASM, no C or linker, and verified booting on real 5150/T1100 Plus/286 hardware.
  • HN discussion centers on AI authorship: many discount the accomplishment as hand-prompted, while others view it as the best argument for Claude's abilities.
  • Historical context: commenters compare it to Visi On, GEM, GeoWorks, and Atari GOS, positioning os8088 as a 'what could have been' alternate-history artifact.

#10
Message your other Claude Code sessions
⬆ 123 pts 💬 47 HN comments

Claude Code's new cross-session messaging turns multiple agent instances into a loosely-coupled mesh. Built on two tools—ListAgents for discovery and SendMessage for delivery—it lets a Claude in one terminal warn, coordinate, or hand findings to a sibling session. Under the hood, same-machine sessions register in the filesystem and bind a per-session Unix socket, restricted to the OS user. Remote replies travel through Anthropic's servers, but only as responses, preventing cold contacts from the outside. Each receiving session applies crossSessionInbound controls (accept, hold, refuse), and Claude Code hardens the boundary: an incoming message cannot approve a permission prompt, change configuration, or execute slash commands like /compact. It is, as the docs say, 'a piece of text one Claude writes to another, never conversation history or files.'

The feature lands just as many HN developers are already building their own inter-agent plumbing. One commenter praised the approach as like 'shared specialist subagents who source and derive important shared knowledge from separate threads'; another ran Telegram-coordinated Codex and Claude bots that 'diagnosed some alerts while I was on a plane.' A skeptical voice called it 'another attack surface where you can ask a remote agent to do things by default,' comparing it with RCE. Others saw it as a first-party clone of tmux send-keys, while still others redirected to the larger problem of context compression, with simonw lamenting he is 'fed up with compaction'—wanting a compacted agent to retain searchable access to prior conversations. The feature is clearly positioned for multi-agent workflows, but the community is split between 'why didn't this exist earlier' and 'what just sent me that message?'

When a change in one session breaks what another is building on, Claude can warn that session before you notice.

Key Highlights
  • Cross-session messaging arrives in Claude Code v2.1.224+ on macOS/Linux, with support for subagents, agent-team teammates, and independent sessions.
  • Sessions discover each other via /list-agents and the ListAgents tool; SendMessage delivers text-only messages, never conversation history or files.
  • Same-machine delivery uses per-session Unix sockets; cross-machine replies use Anthropic servers and require an inbound message first.
  • Admins can control inbound traffic with crossSessionInbound (accept/hold/refuse) and block sending/listening by denying SendMessage and ListAgents.
  • Security guardrails: incoming messages cannot approve permissions, change configuration, or execute commands; same-machine sockets are restricted to the OS user.

Fastmail offers EU data region
⬆ 403 pts 💬 204 HN comments

Fastmail, the Australian email provider known for its privacy-focused infrastructure, has announced an EU data region with self-managed servers in Amsterdam. Previously all user data was stored exclusively in the US. The new option lets account holders choose where their primary copy of email and files resides, with EU-region accounts reading and writing directly to Amsterdam. However, the company is candid about the limits: geographically separate replicas and encrypted emergency backups for all accounts remain in US locations, as do system logs and certain shared metadata. Fastmail emphasizes that it built the EU facility itself rather than renting from a hyperscaler, and that all data remains encrypted at rest in locked racks. This is not a zero-knowledge service; the announcement is more about regulatory compliance and latency than absolute privacy.

Fastmail automatically pre-selected users with European billing addresses and migrated an encrypted copy to Amsterdam ahead of the announcement; they can opt out. New users can choose their region in settings at no additional cost. The decision surfaces a deeper geopolitical tension: as a Five Eyes company, Fastmail remains subject to Australian law, including mutual legal assistance treaties and national-security directives. The HN discussion reflects that concern, with many commenters arguing that the EU region offers false comfort and suggesting genuinely EU-based providers like Tuta or Mailbox instead. Others appreciate the transparency and incrementalism, but the prevailing sentiment is that until an EU-based company with EU-only data centers offers a comparable service, data sovereignty remains elusive.

"If what you need is a guarantee that your data remains only in the EU, we don’t have that, and we’d rather tell you directly than let you assume otherwise."

_for-sale DNS records
⬆ 393 pts 💬 143 HN comments

The story centers on a proposed DNS convention, RFC 10023 (Informational, July 2026), defining a reserved _for-sale leaf node. A domain owner can publish TXT records like `_for-sale.example.com IN TXT "v=FORSALE1;furi=https://example.com/fs"` to signal that a live, actively-used domain is available for purchase. Unlike parking, this doesn't replace the site; it sits unseen in DNS, aimed at brokers and automated availability services. The spec mandates a case-sensitive version tag, allows at most one tag=value pair per record, recommends TTL ≤3600, and warns to remove the record when the domain is no longer for sale. It explicitly states absence is the only way to signal 'not for sale.' The convention is positioned as filling a gap between WHOIS/RDAP registration status and actual willingness to transact.

Community reaction reveals deep unease alongside adoption. Several commenters worry that publicly declaring a domain for sale could weaken legal position in trademark disputes or UDRP proceedings; one described receiving a FedEx legal package from Sony after refusing an offer. Others condemn the spec as another tool for domain squatters/campers, with calls for bans, caps on ownership, or a 'Georgist' annual tax to force productive use. Skeptics note the article reads oddly—one commenter thanked a link to the actual RFC because they suspected AI-generated content—and question the lack of concrete users. There are also positive data points: one user implemented it for a portfolio, another cited SIDN's .nl as prior art, and a bulk buyer confirmed root-level TXT for-sale records already exist in the wild. The technical design is solid, but the incentive alignment remains hotly contested.

The convention has no 'not for sale' value; absence is the only way to say no.

Key Highlights
  • RFC 10023 defines _for-sale TXT records with mandatory `v=FORSALE1;` version tag and at most one tag=value pair per record.
  • It explicitly keeps the domain live and untouched; browsers never see the record.
  • TTL must be ≤3600, records should be removed when no longer for sale, and absence is the only negative signal.
  • Commenters raise legal/trademark exposure, squatting acceleration, and unclear real-world demand.
  • Existing precedents like SIDN .nl and root TXT records suggest the problem is real, but the spec's implementation details and trust model are contested.

My server is a phone now
⬆ 309 pts 💬 116 HN comments

Seg6, a self-hosting developer, replaced a Hetzner VPS with a CMF Phone 1 that had been sitting in a drawer. The trigger was Surf, a remote-browser backend that needs real CPU: shared VPS instances felt starved and dedicated CPU machines cost too much. After a failed postmarketOS flash left the phone with broken Wi-Fi, GPU, and a soft-brick scare, he kept stock Android and turned Termux into the host environment. Termux provides SSH, runit, Caddy, Cloudflared, and Tailscale, while Android keeps every hardware driver working. PRoot initially ran Debian OCI images, but Chrome’s latency-sensitive workload suffered from userspace syscall translation, so he rooted the phone and switched to real chroot inside private mount namespaces. The result is a quiet, battery-backed 8-core/8GB/128GB server reachable via Tailscale and Cloudflare Tunnel, running Surf, a finance tracker, a screen-sharing service, and an operations dashboard.

The build is deliberately reproducible: Ansible definitions with digest-pinned images, versioned releases behind atomic current symlinks, runit services, health checks, no Git checkout, and no plaintext secrets on the device. Public traffic flows through Cloudflare Tunnel for ordinary apps, while a WebSocket-wrapped TLS stream keeps Surf’s old iPad client working without pinning the whole tunnel. The author also documents the fight against Android’s power optimization, applying wake locks, exempting Termux and Tailscale, and limiting charge to 80% because the phone lacks bypass charging. Commenters praised the infrastructure discipline, debated whether the title should be “My phone is a server now,” recommended cheap SFF PCs or old desktops instead, and questioned battery/fire safety. The piece is a practical case study in repurposing consumer hardware: it avoids e-waste and recurring VPS costs, but accepts Android kernel trust trade-offs and unusual software constraints.

“I started this trying to save money on a VPS. I ended up with a rooted phone running my personal infrastructure, and somehow that is much more satisfying. :)” The eight ARM cores, 8GB RAM, and Ansible-driven reproducibility quietly replaced a paid cloud server.

#5
Shopify replaced Redis with MySQL for inventory reservations–and it scaled
⬆ 180 pts 💬 101 HN comments

Shopify's engineering team replaced Redis with MySQL for checkout inventory reservations, a critical path that must prevent overselling and underselling under peak traffic. The previous Redis-based system stored quantity counters and handled concurrency well, but reservations lived outside the inventory ledger, making atomic claim operations impossible and causing consistency bugs. The new design uses MySQL 8's SKIP LOCKED with one row per sellable unit instead of a quantity column. To avoid unbounded table growth, they maintain a bounded pool of up to 1,000 available rows per item/location, replenished from the inventory ledger when needed. Supporting decisions include composite primary keys to reduce row locks, READ COMMITTED isolation to avoid gap locks, consistent lock ordering to prevent deadlocks, and UNION ALL batching to cut round trips. This keeps reservations and the ledger in one database, giving ACID guarantees end to end.

The hardest lesson was that the real bottleneck was not query performance or CPU but connections. Even after optimizing MySQL locking, throughput ceilings persisted with queuing and ProxySQL connection exhaustion. They added SQL comment tags like /* conn_tag:checkout_completion */ and aggregate connection hold time at the proxy, revealing that other parts of the checkout path were holding database connections far too long. Cleaning that up removed 50% of reads and 33% of transactions from the primary database, and raising InnoDB thread concurrency removed the remaining ceiling. During flash sales, writer CPU stayed under 50% and reader CPU under 16%. The cutover used shadow mode: dual-write to Redis and MySQL with Redis as source of truth, then a gradual pod-by-pod switch with a kill switch. The post's explicit takeaway—"if the numbers don't add up, instrument the full path"—is a useful reminder that systemic bottlenecks often hide in plumbing, not the engine.

The real ceiling wasn't the database engine—it was finite connections being held by code we weren't even looking at; cleaning up the checkout path removed 50% of reads and 33% of transactions on the primary database.

Key Highlights
  • Migrated from Redis to MySQL using one row per sellable unit and SKIP LOCKED to avoid contended quantity counters.
  • Bounded reservation pools (cap 1,000 per item/location) with inline replenishment and a lock prevent thundering herds.

Triton: DirectX 11 Driver for QEMU
⬆ 177 pts 💬 35 HN comments

The article introduces Triton, a new DirectX 11 driver for QEMU Windows guests, built on the Neptune protocol. Triton implements the Direct3D 11 Device Driver Interface (DDI) as a user-mode driver (UMD) and kernel-mode driver (KMD), rather than replacing system d3d11.dll/dxgi.dll. This avoids anti-cheat detection and enables smooth desktop compositing through DWM. The key architectural choice is to transform DDI calls back into Direct3D API calls, reusing Neptune's serialization and avoiding VirtualBox's intermediate bytecode approach. The hardest part is reconstructing DXContainer metadata from raw DXBC shader bytecode, since d3d11.dll passes only the bytecode to the UMD, while the host renderer expects the full container. This synthesis was described as the 'weakest and most error prone part' of the implementation.

The post details host-rendering challenges, especially on macOS. They forked DXMT to translate D3D11 to Metal, as DXVK+MoltenVK proved unstable. Shared textures across virglrenderer's multi-process model required a shm_open() + MTLBuffer approach leveraging Apple Silicon's unified memory, while shared fences were emulated with CPU-side waits at frame boundaries. They also moved swapchain logic into the guest Neptune driver to align with Venus design. The community response is largely positive, with excitement about practical Windows VM graphics acceleration, but also questions about older DirectX support, VirtualBox availability, and why DX12 wasn't targeted. The project represents a major milestone for open-source virtualized GPU drivers.

In the end we still pass through the bytecode unmodified but since we don’t see the original DXContainer file, we have to synthesize fields that the host DirectX renderer expects. Dithered QR Codes
⬆ 170 pts 💬 15 HN comments

The article presents a practical technique for embedding images inside QR codes using error-diffusion dithering. It starts with the basics: a QR code consists of rigid function patterns—finder patterns, timing, etc.—needed for reliable localization, and data modules that encode the payload and can tolerate modification. The author describes a common approach of subdividing each module into a 3x3 grid, reserving the center pixel for data and surrounding pixels for a one-bit image. Plain thresholding produces crude salt-and-pepper artifacts, so he introduces Floyd–Steinberg error diffusion. The core innovation is a two-pass algorithm: first, forced data-module colors are diffused into neighboring pixels, masking the QR pattern; second, regular error diffusion renders the target image. This substantially cleans up the visual noise while retaining scannability, trading aesthetics against robustness.

Implementation details matter: when a forced data module contradicts the desired image, the error can reach 95%, far above the usual 50% bound, making error diffusion essential rather than optional. The generator also lets users rotate, tweak QR encoding parameters, or deliberately flip a few high-error modules within the error-correction budget. The author cautions that such codes are best for large screens or posters; crumpled printouts on poor phone cameras require more redundancy. Margins must be considered, and inverted codes need black quiet zones. The write-up is notably clear—as one commenter puts it, 'The first section is super clear about what QR code is in ~200 words.' The HN thread expands the idea with color QR variants, animated QR codes, and even jokes about running Doom or Bad Apple inside a QR code, showing the idea's creative appeal.

Normally we get to choose the colour so the error can never be more than 50%, but here we might have to make a pixel in a dark area pure white and end up creating 95% error.

Key Highlights
  • QR codes separate function patterns from data modules; only data modules can be aesthetically modified.
  • Subdividing modules into 3x3 grids enables embedding one-bit images but adds salt-and-pepper noise.
  • Two-pass error diffusion first masks forced data-module errors, then dithers the actual image.
  • QR error-correction allows flipping a few high-error data modules without breaking scanning.
  • Scannability trade-offs and margin requirements matter for real-world print use.
