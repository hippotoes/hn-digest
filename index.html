Claude: System Prompts
⬆ 643 pts 💬 254 HN comments

Anthropic published the system prompts used by claude.ai and its mobile apps, effectively opening the hood on how the company steers flagship models. The docs read as a layered changelog: early Claude Sonnet 3.5 prompts were roughly 300 words, while the latest Opus 5 prompt exceeds 3,000 words and contains not just style rules (no emojis, avoid 'genuinely/honestly'), but also operational state such as the current date, Markdown formatting requirements, and instructions for handling edge cases like a user forgetting to upload an image. Starting with Claude 4.6, each model ID is a fixed snapshot, so every model version has one canonical prompt. The most striking addition, spotted by Simon Willison's diff, is a passage explaining that a user may have intended to query Claude Fable 5 but was redirected to Opus 5 by a 'safeguards routing mechanism'.

The HN community immediately treated the page as a spec to reverse-engineer. Commenters extracted prompts into git repositories to track changes, compared word counts, and debated the philosophy of prompt-versus-weights. Critics argued that gigantic system prompts contradict Anthropic's own guidance on concise AGENTS.md files and that many behaviors should be baked into the model via RL rather than appended on every call. Others noted these prompts are consumer-chat only—the API does not include them—and that prefix caching mitigates token cost. The exercise reveals how much of Claude's apparent 'personality' is actually maintained through prose that is patched frequently, sometimes within days, and how a frontier AI company relies on prompt engineering as a fast, reversible layer of control.

"Wow AGI looks way more hardcoded than I expected" — a commenter's reaction to discovering the elaborate, surgical system prompts behind Claude Opus 5.

Key Highlights
  • System prompts are versioned per model; Claude 4.6+ models are fixed snapshots with a single dated prompt.
  • Prompt length grew from ~300 words in early Sonnet 3.5 to 3,000+ words in Opus 5.
  • Opus 5's prompt includes a fallback explanation for queries redirected from Claude Fable 5 due to a 'safeguards routing mechanism'.
  • These system prompts apply only to consumer chat products (claude.ai, iOS/Android apps), not the Claude API.
  • Community members (Simon Willison, Piebald-AI, asgeirtj) are mirroring prompts to GitHub, enabling diff-based analysis of Anthropic's behavioral adjustments.

The AI Credit Resale Economy
⬆ 277 pts 💬 113 HN comments

"The AI Credit Resale Economy" describes how an informal practice of swapping unused OpenAI/Anthropic credits among startups has transformed into a commercialized gray market of "token brokers." The author, Matt Lenhard, found brokers buying credits at steep discounts and reselling through transparent marketplaces such as AI Credits and AICreditMart, plus "bulk discount routers" like CheapCredits, Tokvana, and Neokens. Rather than passing along provider keys, these brokers act as API proxies that forward requests from a pool of accounts. The article estimates "tens of millions" of dollars' worth of credits are being offered, and the author corrects in comments that this is dollar-based, not token-based. Technical concerns emerge: the proxy layer can terminate TLS and inspect or modify prompts, making the arrangement both a bargain and a security hazard.

Lenhard's outreach uncovered a seller claiming $100,000 per day in available spend, and sites advertising flat 40% discounts "at every model" which the author finds implausible through bulk pricing alone. He documents listings on Telegram channels, Reddit threads (including YC Startup School credits), and Chinese forums like linux.do. Commenters highlight that in China, where Western models are blocked, resold tokens may be the only access, but kay_o asserts these resellers simultaneously "sell all the prompts and responses to labs." Others like Aurornis suggest distillation is a primary purpose of the resale economy, while RALaBarge claims much supply comes from botnet account takeovers and carding. The post leaves an open question: is this market simply efficient arbitrage, or a fraud-enabled drain on AI providers' economics?

"Tokens have become a pseudo-currency, and there is enough liquidity in the market to allow for a lot of abuse."

Key Highlights
  • Token brokers buy unused AI credits from startups and resell them via proxied API access, often at 30-80% off list price.
  • Several marketplaces (AI Credits, AICreditMart, CheapCredits) and Chinese forums (linux.do) facilitate the trade.
  • The proxy architecture introduces MITM risks, including prompt/session logging and tool-call manipulation.
  • A plausible major buyer of resold tokens is AI labs seeking cheap data for distillation.
  • Fraud is mixed with legitimate arbitrage; sources include account takeovers, stolen cards, and YC Startup School credits; the economics of subsidized subscriptions may be unsustainable.

Anthropic's 'watermark' text adulteration in Claude is a perversion of writing
⬆ 222 pts 💬 205 HN comments

Anthropic's plan to watermark all Claude text outputs has ignited a fierce technical and philosophical debate. Contrary to earlier claims of invisible metadata, the implementation is a semantic steganography scheme: at each token generation, words are pseudorandomly partitioned into 'green' and 'red' sets based on a secret key, and the model biases sampling toward green tokens. Detection compares observed green/red ratio against the unwatermarked distribution, gaining statistical confidence over longer texts. For Gruber, this is a perversion: synonyms never carry identical nuance, so biasing word choice sacrifices communicative precision for provenance signaling. He also attacks the EU's Code of Practice as red-tape that punishes honest users while paraphrasing tools easily strip watermarks. The piece has become a Rorschach test for how developers, writers, and policy commentators view the tradeoff between machine text quality and AI accountability.

Commenters on Hacker News sharply split. Technical users point out that LLMs are already stochastic—temperature sampling means there is no 'single best next token'—and that gumbel-softmax watermarking can, in principle, leave the probability distribution provably unchanged; 'It does not affect writing quality at all, provably,' one commenter argues. Others dismiss Gruber's premise with 'Then write your own damn text' and accuse him of anti-EU knee-jerk bias, citing his history with Apple regulation. A third camp focuses on practical harm: terms-of-service forbidding watermark removal, false positives when Claude proofreads human prose, and the resemblance to printer tracking dots. A recurring insight from both sides is that the debate is less about cryptography than about whether the craft of writing can be separated from the statistical mechanics of autocomplete.

"Translation: Specific words do not matter and we don’t think anyone reads anything closely." — John Gruber, on Anthropic’s claim that watermarking has no practical impact.

Key Highlights
  • Anthropic will use semantic steganography (green/red token lists) rather than hidden characters, sacrificing optimal token choice for a secret-key watermark.
  • Watermark confidence scales with text length; only Anthropic can detect its own marks, raising interoperability concerns under the EU Code of Practice.
  • Gruber argues no two synonyms are truly equivalent, so any bias toward 'green-list' words degrades meaning and quality, contradicting Anthropic's 'imperceptible' claim.
  • Technical commenters counter that LLMs already sample stochastically, and gumbel-softmax watermarking can provably preserve the output distribution.
  • Practical concerns dominate: ToS restrictions, false positives for proofreaders, and potential migration to open-weight models.

Red queen hypothesis – A new way forward for self-improving AI
⬆ 56 pts 💬 10 HN comments

Recursive self-improving AI agents typically edit their own code, test variants, and keep the best performers. As the Cambridge-led team notes, this process is bounded by a fixed evaluator: 'A self-improving agent can only get as good as the test that scores it.' The Red Queen Gödel Machine breaks this ceiling by co-evolving the agent and its evaluator. Instead of a static benchmark, the evaluator is periodically upgraded at checkpoints whenever it outperforms its predecessor on trusted ground-truth examples. This creates a bootstrapped loop where a stronger agent demands a harder evaluator, which in turn pushes the agent further. The work, led by Alex Iacob and Prof Nic Lane, includes collaborators from NVIDIA, Flower Labs, MBZUAI, and Inria, and extends the Gödel Machine lineage popularised by Huxley/Darwin-Gödel tree-search algorithms.

The paper reports concrete gains: co-evolved scientific paper writers reach 1.78×–1.86× higher acceptance rates under a diverse agent-as-a-judge panel, and co-evolved graders achieve 9% higher ground-truth accuracy on Olympiad-level proofs. A notable efficiency result is that a hybrid setup using the open-weight NVIDIA Nemotron 3 Ultra alongside ChatGPT-5.5 approximated the performance of ChatGPT alone while cutting search-token costs by around 13×. The authors stress the work is preliminary and need longer search horizons to assess scalability, but they point toward a new class of self-improving systems that recursively bootstrap agents and evaluators. The method is slated to be open-sourced, and the team plans to scale experiments across a broader range of tasks.

“Instead of improving an agent against a fixed test, we let the evaluation evolve alongside the agent. As the agent gets better, the evaluation also gets harder, and the bar keeps rising.” — Alex Iacob

Key Highlights
  • Fixed evaluators create a ceiling on self-improvement; co-evolving the evaluator removes that bound.
  • The Red Queen Gödel Machine alternates fixed-evaluator phases and checkpoints where a stronger evaluator replaces the old one.
  • Scientific-paper writers co-evolved with reviewers reached 1.78×–1.86× higher acceptance rates; co-evolved proof graders gained 9% accuracy.
  • Using open-weight models for search cut token costs ~13× while preserving performance.
  • Method will be open-sourced; scope remains preliminary and scaling is still under investigation.

Qwen 3.8 27B is excellent, but it defaults to overthinking things
⬆ 428 pts 💬 189 HN comments

Qwen 3.8 27B, Alibaba’s Apache-2.0-licensed 27B vision-language model, arrived Friday as a 17GB Q4_K_M quantized file that runs on high-end laptops and small workstations. Simon Willison tested it on an M5 Max MacBook Pro and an NVIDIA DGX Spark, using LM Studio and llama-server. The striking finding: the official default reasoning_effort is xhigh, producing spectacular overthinking. A pelican SVG took 21 minutes and 22,276 reasoning tokens, versus 137 seconds with reasoning disabled. The same “draw an SVG of a circle” prompt turned into an elaborate animated geometric study. Willison calls the default a “bad place to start,” recommending low or no reasoning. Despite this, the model is remarkably capable: excellent bounding boxes in 0-1000 coordinates, one-shot HTML tool generation, and solid coding-agent behavior with Pi. The release demonstrates how much open-weight capability now fits in a single consumer-grade file.

The model’s 15–30 tok/s throughput feels slow against hosted APIs like OpenAI's Sol (74 tok/s) or Luna (184 tok/s), but a Multi-Token Prediction layer—enabled in llama.cpp via --spec-type draft-mtp—reportedly improved throughput by around 72% on the Spark. Commenters largely echo Willison’s mixture of awe and frustration: many call consumer-hardware local models a “miracle,” while others criticize RL incentives that reward over-verification. Deeper context: the MTP trick lets a cheap draft model guess several tokens ahead, which materially changes the cost equation for dense models. The bigger narrative is a forward-looking one: a 17GB open-weight model now offers long context, tool calling, vision, and competent code generation, eroding the need for datacenter-class hardware. This sparks debate about defaults, electricity costs, and whether visible “thinking” helps or wastes tokens in real-world use.

“We don’t need to spend half a million dollars on datacenter-class hardware just to run a competent model.” — Simon Willison, on Qwen 3.8 27B

Key Highlights
  • Qwen 3.8 27B defaults to xhigh reasoning effort, producing wildly verbose thinking traces that consume context and time.
  • A pelican-riding-a-bicycle SVG took 21 minutes and 22,276 reasoning tokens with default settings; the same prompt with reasoning off took 137 seconds.
  • The model excels at vision tasks like bounding-box annotation and can one-shot build tools (e.g., a bounding-box visualizer) when given clear prompts.
  • Multi-Token Prediction (MTP) support in llama.cpp improves throughput by ~72%, a promising optimization for dense local models.

MathCode, Mathematical Coding Agent
⬆ 90 pts 💬 28 HN comments

MathCode is a terminal-first AI coding assistant that aims to close the gap between natural-language mathematics and machine-checked proof. Given a plain-language problem, it invokes an LLM-based planner and a Lean 4 prover to generate formal theorem statements and search for proofs. Built on the AUTOLEAN pipeline, it adds a persistent Lean language server that drops typical compile checks from ~30 seconds to ~0.4 seconds after warmup, plus a theorem library that auto-names and stores proven results for reuse, an axiom library for compile-checked assumptions, and integrations with leansearch.net and Loogle for retrieving Mathlib lemmas. A tree-of-subgoals mechanism decomposes hard theorems into parallel subproofs, and multiple planners can race diverse proof strategies. Outputs land in LeanFormalizations/, and an Obsidian vault visualizes theorem-to-lemma dependencies, turning the assistant into something closer to a knowledge-base builder than a one-shot code generator.

Hacker News greeted MathCode with curiosity and a strong demand for proof by example. Several commenters asked for a practical demonstration—'wish these project always start with an example'—while others zeroed in on the hardest part: correctly capturing informal English as a Lean theorem. One commenter called this 'tricky,' with another defending that good abstraction and composable primitives make it overcomable. A licensing thread highlighted the repo's missing license, with one reply dismissing enforceability because 'It's AI generated,' while another questioned the need for a theorem-proving agent in commercial settings. More skeptical voices warned about 'hooking up slop to slop' in auto-research and insisted the field must move from 'it compiles' to 'it is correct.' Overall, the project appears technically impressive but still in need of concrete case studies, legal hygiene, and a clearer demonstration of mathematical value beyond infrastructure.

MathCode's persistent Lean REPL drops compile-check latency from ~30 seconds to ~0.4 seconds after warmup—a 75x speedup that makes agentic proving loops practical.

Key Highlights
  • MathCode autoformalizes plain-language math problems into Lean 4 theorems and attempts proofs via an agentic loop.

  • Reusable theorem/axiom libraries and an Obsidian knowledge graph turn formal proofs into a growing knowledge base.

#11
An open-source, candle-only crypto pump detector–looking for ML contributors
⬆ 3 pts 💬 0 HN comments

This open-source TypeScript monorepo, created by aleks-ent, is a complete pipeline for detecting pump-and-dump regimes in crypto markets using only OHLCV candles from Binance and Bybit. It downloads historical 1m and 5m klines from public bulk archives and REST endpoints, runs a configurable rule-based scan (e.g., minScore 80, optional calm pre-pump period), persists pump episodes to a Turso SQLite-compatible database, and sends Telegram alerts with 'Pump | Dump | None' classification buttons. The project is MIT-licensed and designed for self-hosting with PM2, which runs three processes: pump-monitor (download→scan→persist→alert), pump-bot (interactive Telegram bot), and pump-web (simple HTML page). While the detection logic is currently heuristic, the author explicitly asks for ML contributors, hinting that the project is an early-stage attempt to apply modern anomaly detection to an inherently noisy market.

What stands out is the operational maturity mixed with glaring inefficiencies. The pipeline re-discovers the symbol universe every four days, uses worker threads for scanning, and supports an incremental tail rescan for new 5m bars. It also includes a human-in-the-loop review UI with keyboard shortcuts to label events as wick spike, weak pump, sustained move, volume only, illiquid noise, or unclear; annotations are stored separately from detector output, enabling dataset creation for supervised ML. However, the tool writes several GB/day of debug output that no code path reads, and on a long-lived VDS the data directory can exceed 100 GB within months. The README recommends a cron-driven pruning script. With only 5 stars and 3 HN points, the project is far from proven, but the combination of public data access, Telegram integration, and a labeled dataset pipeline makes it an interesting foundation for community-led ML experimentation.
