The Twelve-Factor App
⬆ 148 pts 💬 79 HN comments

The Twelve-Factor App is a 2011 methodology by Adam Wiggins and the Heroku team for building software-as-a-service applications. It prescribes twelve principles: one codebase tracked in revision control with many deploys; explicit dependency isolation; storing config in the environment; treating backing services as attached resources; strict separation of build, release, and run stages; execution as stateless processes; exporting services via port binding; concurrency via the process model; disposability with fast startup and graceful shutdown; dev/prod parity; treating logs as event streams; and running admin tasks as one-off processes. The document is deliberately language-agnostic and focuses on portability, continuous deployment, and scalability for cloud deployments. It emerged from patterns seen across hundreds of thousands of apps on Heroku and has since become a canonical reference for cloud-native architecture, influencing Docker, Kubernetes, and platform-as-a-service design.

The Hacker News thread shows the document still resonates deeply, though the community debates specific factors. Most commenters agree the principles are foundational—one calls it a 'certified classic,' another half-jokes that it's their religion. The strongest controversy centers on Factor III (Config): critics argue environment variables are a poor mechanism for secrets, being introspectable via /proc, size-limited, and flat. Some point to the unwritten assumption that production environments are secure, while others recommend modern tools like dotenv, varlock, or ephemeral filesystem mounts. Another thread of nostalgia flows toward Heroku's simplicity versus today's complex clouds, with Fly.io and Cloud Run cited as successors. The overall tone is respect for the text's historical impact, coupled with a recognition that 'state' and organizational incentives remain unsolved. As one commenter notes, few junior engineers have even heard of it, making this repost a repeated reminder of a generation gap.

The twelve-factor methodology can be applied to apps written in any programming language, and which use any combination of backing services.

Key Highlights
  • Codebase: one codebase tracked in revision control, many deploys
  • Dependencies: explicitly declare and isolate dependencies
  • Config: store configuration in the environment (controversial for secrets)
  • Processes: app runs as one or more stateless processes, exporting via port binding
  • Dev/prod parity: keep development, staging, and production as similar as possible
