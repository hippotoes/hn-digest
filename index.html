#7
An incoherent Rust
⬆ 184 pts 💬 90 HN comments

The article 'An Incoherent Rust' delves into a fundamental tension in Rust's trait system between soundness and ecosystem flexibility. Coherence ensures that for any type and trait, there is at most one implementation, enforced by orphan rules that restrict implementations to crates owning either the trait or the type. This design prevents type system unsoundness, such as conflicting associated types leading to safe transmutations, and aids composition by avoiding overlapping impls in dependencies. However, it stifles innovation by making it artificially difficult to replace foundational crates like serde; if a new serialization library emerges, every dependent crate must add support, creating a high barrier to ecosystem evolution. The article argues this is not a fault of library authors but a language-imposed constraint that prioritizes correctness over adaptability.

Specific examples illustrate the problem: serde's Serialize trait must be implemented by all crates using it, and alternatives like nextserde require extensive forking or patching. The article reviews proposals to mitigate this, such as binary crate exemption or coherence domains, but notes all have trade-offs like harming library evolution or introducing composition issues. It then proposes a radical solution: introducing incoherent traits that opt out of coherence, coupled with named implementations and trait bound parameters to allow explicit selection of impls, akin to dictionary-passing in type theory. This change could enable overlapping implementations for traits like Serialize, fostering competition but adding complexity to the language. Societally, this impacts open-source sustainability, as Rust's design decisions influence how communities collaborate on library maintenance and innovation.

Coherence and orphan rules, while ensuring soundness, create artificial barriers to ecosystem evolution by making it difficult to replace foundational libraries like serde, as highlighted in the article: 'If someone publishes an alternative to serde (say, nextserde) then all crates which have added support for serde also need to add support for nextserde.'

Key Highlights
  • Coherence ensures unique trait implementations for type system soundness and composition.
  • Orphan rules enforce coherence but hinder ecosystem flexibility by restricting impls to crates owning trait or type.
  • Foundational crates like serde become entrenched, making it hard for alternatives to emerge.
  • Existing proposals (e.g., binary crate exemption) have trade-offs and don't fully solve ecosystem evolution.
  • The article proposes incoherent traits with named impls to allow overlapping implementations, increasing flexibility but adding complexity.
