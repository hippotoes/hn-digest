The article explores a provocative organizational strategy: under pressure to maximize development speed via LLMs, teams might legitimately stop reading generated code, akin to treating high-level source as machine code. The author, Facundo Olano, frames this not as advocacy but as a thought experiment in response to actual mandates. On The <dl> (2021)
⬆ 397 pts 💬 112 HN comments

The article champions the underused HTML `<dl>` (description list) element, which semantically represents name-value pairs. It traces the element's evolution from HTML's early days as a 'definition list' to its current broader role in HTML5, using examples like book metadata and a Dungeons & Dragons statblock to demonstrate versatility. The author argues that semantics matter: screen readers can announce list length, current position, and allow skipping the list as a block, turning `<div>` soup into an accessible structure. However, the piece acknowledges that browser/screen reader support is not yet universal, and developers may need to weigh benefits against fallback experiences. The D&D example cleverly shows how multiple `<dl>`s can structure diverse data—from ability scores to weapon attacks—proving the pattern's adaptability beyond simple glossaries.

Comments reveal a deep technical community split: while some praise the element's history (with theodpHN noting DL-DT-DD existed in 1985 IBM GML, predating the web), others echo frustrations over its inflexibility. A key accessibility researcher (simonw) links to a 2025 analysis showing inconsistent screen reader support—an ongoing issue since at least 2018. The most contentious technical point comes from chrismorgan, who corrects the article's use of `aria-label` on `<dl>`, citing W3C specs that only allow it when the element has an implicit role like `group` (which `<dl>` lacks, requiring explicit `role="group"`). This sparks a side debate on whether to add `role="listitem"` to wrapper `<div>`s. Meanwhile, users like kqp and miki123211 (a screen reader daily-driver) argue the semantic-idealism fails real-world needs: 'every time I’ve reached for a <dl> I’ve eventually regretted it' because the pattern cannot accommodate dividers, headings spanning pairs, or icons. The tension between spec purity and practical flexibility dominates the thread.

DL-DT-DD have been a thing since before the web — they appear in IBM’s 1985 DCF/GML manual for generalized markup.

Key Highlights
  • The `<dl>` (description list) element semantically represents name-value pairs, with `<dt>` for terms and `<dd>` for details.
  • Proper use of `<dl>` can improve screen reader accessibility by announcing list context (e.g., count, position).
  • HTML spec allows only `<div>` as a wrapper for groups of `<dt>`/`<dd>` elements for styling purposes.
  • The `<dl>` element dates back to IBM's Generalized Markup Language (1969) and was present in early HTML.
  • Practical drawbacks include inability to handle dividers, headings spanning multiple pairs, or custom icons without hacks.

80386 microcode disassembled
⬆ 251 pts 💬 49 HN comments

A collaborative effort by Reenigne, GloriousCow, Smartest Blob, and Ken Shirriff has successfully disassembled the microcode of the Intel 80386 processor from high-resolution die images. The microcode ROM contains 94,720 bits (versus 10,752 bits for the 8086), encoding 215 entry points—a dramatic increase from the 60 of its predecessor. The team methodically decoded the binary blob by identifying patterns, field boundaries, and sequencing, aided by tracing physical connections on the die. Notably, they uncovered a potential security flaw in the IO permission bitmap handling: a 4-byte port access at a boundary may fail to check the fourth byte's permission, a bug that could have remained undetected for four decades. The disassembly reveals that the 80386 uses hardware accelerators (multiply, divide, barrel shifter, protection test unit) with microcode primarily orchestrating these units, unlike the 8086's algorithmic microcode.

The open-source release (github.com/reenigne/x86-microcode) includes a plain-text disassembly and field definitions. Early analysis indicates the die is from a B0 or B1 stepping (post-XBTS/IBTS instructions, but before later revisions). A Verilog implementation by nand2mario, built from the extracted microcode, currently runs DOOM but struggles with full protected-mode operating systems. Comments highlight the sheer effort: GloriousCow describes the bit extraction process (marking row/column intersections, classifying bits visually). The community is both awed by the reverse engineering feat and concerned about the historical context—knowing the exact stepping is critical for accuracy. The work opens avenues for fully open-source x86 implementations and deeper understanding of 386 bugs, though it remains a hobbyist effort lacking Intel archival support.

The microcode disassembly reveals a potential 40-year-old bug: the IO permission bitmap only checks three of four addresses for 4-byte port accesses, which could allow unauthorized hardware access in protected-mode operating systems.

Key Highlights
  • Microcode extracted from die photos with 94,720 bits, disassembled through collaborative pattern recognition and die tracing.
  • 215 microcode entry points exist, compared to 60 in the 8086, reflecting added instructions and mode-specific handling.
  • A potential IO permission bitmap bug was found: 4-byte access at a boundary may skip checking the last byte, a flaw unnoticed since the 80386's release.
  • No hidden opcodes or Easter eggs were found, but some unused microcode (0x849-0x856) exists, possibly a paging-related routine.
  • The disassembly has enabled a Verilog implementation (z386) that can run DOOM, but full OS boot requires further debugging.

Air France and Airbus found guilty of manslaughter over 2009 plane crash
⬆ 93 pts 💬 64 HN comments

Air France and Airbus have been found guilty of involuntary manslaughter for the 2009 crash of Flight AF447, which killed all 228 people on board. The Paris Appeals Court overturned a previous acquittal, attributing sole and entire responsibility to the companies. The accident occurred when the Airbus A330 encountered icing conditions that led to unreliable airspeed readings. The co-pilots, lacking adequate training, mishandled the stall by pulling the nose up—exactly the wrong action—causing the aircraft to plummet into the Atlantic from 38,000 feet. Investigators had earlier identified the combination of technical failure (blocked pitot tubes) and pilot error as the cause, but this ruling places legal blame on the corporate entities for systemic failures in training and sensor replacement.

The verdict comes after a lengthy legal battle, with charges initially dropped in 2019 before being reinstated on appeal. Both companies face maximum fines of €225,000 each—a sum many victims' families decry as a token penalty. The crash spurred industry-wide changes, including improved pilot training and mandatory replacement of the faulty pitot probes. Notably, the captain was on a break during the critical phase, highlighting issues with cockpit resource management. The HN community debates the balance of blame, with some arguing the pilots' inexplicable actions outweigh corporate neglect, while others emphasize that known problems were ignored for cost reasons. This case underscores the tension between individual and systemic accountability in complex engineered systems.

The court found Air France and Airbus 'solely and entirely responsible' for the crash, but the maximum fine of €225,000 each was called a token penalty by victims' families.

My I3-Emacs Integration
⬆ 74 pts 💬 19 HN comments

The author details a personal project to unify keyboard-driven window management between i3 and Emacs, motivated by the shortcomings of EXWM (Emacs X Window Manager) when handling graphical applications like Steam. EXWM's input methods falter with 'dodgy programs,' so the author sought a deeper integration that preserves Emacs's keybindings while leveraging i3's robust handling of non-text windows. Initial attempts using xdotool and emacsclient proved too slow—exhibiting latencies up to a second—prompting a radical solution: patching i3 itself. The patch adds a --passthrough flag to i3's bindsym/bindcode commands, allowing specific keybindings to be forwarded to the focused window if its X11 class matches a target (e.g., 'Emacs'). This approach sidesteps the need for a complete window manager replacement, retaining i3's stability for standard applications while extending Emacs's influence over window navigation.

The implementation required modifying i3's binding struct, parser specification, and keypress handler. In the patched handle_key_press(), if a binding has a non-null passthrough class, the function checks the focused window's class; on match, it re-emits the XCB key event directly to that window (via xcb_send_event() with owner_events disabled) instead of running the i3 command. On the Emacs side, elisp functions like nausicaa/emacs-i3-windmove attempt an internal window movement before falling back to i3-msg commands for external windows. Terminal launching is also integrated: $super+Return fires a script that either creates a new muxtty frame inside Emacs or launches Alacritty in the current working directory. The patch (available for i3 4.25.1) is intentionally minimal—hardcoded to match 'Emacs'—but the author invites feedback on refinement, particularly regarding focus retention and the re-emission mechanism.

"It'll be too slow," they told me — but the author achieved sub-100ms latency by patching i3 instead of using external scripts.

Key Highlights
  • Patches i3's key-grabbing code to conditionally pass key events to Emacs based on window class (hardcoded to 'Emacs').
  • Uses XCB xcb_send_event() to re-emit the original keypress to the focused Emacs window.
  • Modifies i3's parser and binding struct to add a --passthrough flag for bindsym/bindcode.
  • Emacs-side elisp integrates windmove with i3-msg for seamless navigation between Emacs splits and i3 windows.
  • Automated terminal spawning: inside Emacs, creates muxtty frames; otherwise launches Alacritty in the current directory.
