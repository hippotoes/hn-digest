I burned all my tokens researching how to save tokens
⬆ 135 pts 💬 183 HN comments

The article chronicles the author's journey building a cost-efficient deep research pipeline after burning through an entire Claude Max 5x plan in 30 minutes. The core insight is that naive use of frontier models for everything leads to token waste and incomplete results. The solution is a multi-agent orchestration system that uses cheaper models (Sonnet, Opus, Haiku, GPT-5.5, Gemini 3.1 Pro) as subagents for specific roles—finding, verifying, judging—while reserving the most expensive model (Fable) only for planning and dispute resolution. By leveraging three existing subscriptions (Claude, Codex, Antigravity) with shared memory via an extended claude-mem plugin, the author extended continuous research from 30 minutes to several hours without extra cost. The pipeline also incorporates automatic fallback when a service hits usage limits, ensuring research continuity.

Trust was the second major challenge: hallucinations were reduced by enforcing that whoever finds a claim never verifies it, and that every finding must include a URL and direct quote from the primary source. Human oversight remains critical, as shown when a rule silently rejected the popular project Headroom (56k stars) because its savings numbers weren't quality-controlled—highlighting that agent rules can themselves be bugs. Key findings from the resulting knowledge base include: same model shows up to 66x token spread across different harnesses, context compaction can double bills instead of saving, and mid-session tool changes silently invalidate cache prefixes. The author concludes with a recommendation to reverse the typical research order: cheap models find, accurate models verify, deep research goes last.

Your token counter is not your invoice. In one documented case a calculated $3.60/month landed as a $25-40/month invoice, a 7-11x gap coming from context accumulation, retry amplification, framework overhead, and evaluation calls.

Grok-iOS – remote Grok Build from your iPhone over ACP
⬆ 10 pts 💬 0 HN comments

Grok-iOS is an open-source iOS client that transforms an iPhone into a remote pager for Grok Build, an AI coding agent developed by xAI. The architecture separates the agent runtime (Mac) from the user interface (iPhone), communicating via the Agent Client Protocol (ACP) over WebSocket. The Mac runs the official `grok agent serve` command, while the iOS app—built with SwiftUI and requiring iOS 17+—connects to it using a secret printed by the agent. This design offloads the heavy compute of running a large language model to a Mac while leveraging the portability of an iPhone as a lightweight UI. The project is not on the App Store; it must be sideloaded or run in the Xcode simulator. Author Pedro Shakour licenses it under Apache-2.0 and pins a specific upstream commit of xai-org/grok-build.

The repository includes a SwiftUI app under `ios/GrokApp/`, a legacy TCP/TLS bridge under `companion/`, and shared themes from upstream. The default connection uses the official ACP over WebSocket (port 2419), with an optional legacy LAN bridge with TLS and Bonjour for experimentation. Development scripts provide a stub mode for testing without an API key. The project underscores a growing trend of decoupling AI agents from their interfaces, enabling mobile-first interactions with powerful desktop-hosted agents. However, it introduces network security considerations: the agent’s WebSocket server is bound to localhost by default, but for physical iPhones on the same Wi-Fi, users must expose the agent to the LAN. This trade-off between convenience and security is a classic tension in remote-control tools, likely to spark debate among HN readers.

"Your Mac runs the agent; your iPhone is the remote pager." — The project elegantly separates compute from interface, turning any iPhone into a portable terminal for a powerful AI coding assistant.

Key Highlights
  • iOS client communicates with macOS agent via ACP over WebSocket, using the official `grok agent serve` command.
  • Requires Xcode 16+, iOS 17+, and an xAI API key; not on App Store — sideload or simulator only.
  • Default connection uses port 2419; physical devices need the Mac’s LAN IP, raising security trade-offs.
  • Includes optional legacy LAN bridge with TLS and Bonjour under `companion/` for experimental setups.
  • Repository structure shares SwiftUI app, upstream submodule, scripts, and docs; licensed Apache-2.0.

Claude Code uses Bun written in Rust now
⬆ 532 pts 💬 707 HN comments

Claude Code, Anthropic's AI-powered coding assistant, now silently ships with a Rust port of Bun, the JavaScript runtime originally written in Zig. Developer Simon Willison confirmed the change by examining the binary: `strings ~/.local/bin/claude | grep -m1 'Bun v1'` returned an unreleased version 1.4.0, and a list of 563 `.rs` source files (e.g., `src/runtime/bake/dev_server/mod.rs`) proved the Rust migration. Jarred Sumner, Bun's creator, revealed the port was performed using an AI agent that transpiled the entire codebase—a process that took under a month for a 1M+ line pull request. The rationale: Rust's memory safety eliminates an entire class of bugs that plagued the Zig version, where manual lifecycle tracking led to a long list of issues. While the change only yielded a 10% startup speed improvement on Linux, the real benefit is reduced cognitive overhead for developers. This incident underscores the growing intersection of AI-assisted development and runtime infrastructure—where even internal tooling becomes a showcase for AI's ability to rewrite mission-critical systems at scale.

The transition has sparked intense debate within the developer community. On one hand, it demonstrates the feasibility of using AI to mechanically port large codebases with minimal disruption. Simon Willison's investigation found that Claude Code users were largely unaware of the change, validating Sumner's remark: 'Boring is good.' However, the process has drawn criticism for its opacity. One commenter noted that the entire affair was handled poorly from a communication standpoint, with a '1mil+ PR merged in less than month' catching the Zig community off guard, especially given prior tensions between the Bun and Zig teams. Others questioned why a TUI application needs a full JavaScript runtime at all, especially when performance and stability issues—such as segfaults and rendering glitches reported by users—persist. The incident also raises governance questions: if a company can silently replace a project's core runtime using AI, what does that mean for open-source trust and fork viability? Ultimately, the Bun-in-Rust story serves as a litmus test for how the industry will navigate AI-driven rewrites: as a powerful tool for modernization when done transparently, or as a force that erodes community confidence when decisions are made behind closed doors.

"Claude Code v2.1.181 uses the Rust port of Bun. Startup got 10% faster on Linux but otherwise, barely anyone noticed. Boring is good." — Jarred Sumner

His experience challenges the common wisdom that hardware is inherently difficult, suggesting instead that it scales with product ambition.

Weinberger's practical recommendations include maintaining at least 70% gross margins, partnering with Chinese assembly houses, and implementing strong anti-counterfeit measures. He hand-assembled the first 500 units in four days without issues, and has had zero field failures. Yet the article resonates with many engineers who see hardware as an attainable frontier, especially in a post-LLM world where software development feels less rewarding.

Community reactions are mixed—some praise SDL3's API design, others worry about regressions. The switch reinforces Minecraft's evolution into a game engine, with its data-driven systems (e.g., loot tables, environment attributes) enabling unprecedented moddability. This snapshot exemplifies how a legacy game can modernize its tech stack while preserving backward compatibility.

SDL3 adoption ends GLFW's long tenure in Minecraft, bringing native Wayland support and potential latency improvements, though exclusive fullscreen crashes on Windows and Wayland remain blocking issues.
