Bonsai 2 27B: Near-Lossless Compression in a 9x Smaller Footprint
⬆ 483 pts 💬 149 HN comments

PrismML—a Caltech-spinout backed by Khosla Ventures, Cerberus, Google, and Samsung—has shipped Ternary Bonsai 2 27B, the successor to July's Bonsai 27B and the first serious attempt to turn extreme weight quantization into a deployment unlock rather than a parlor trick. The model is built on Qwen3.8 27B and stores every weight in a ternary alphabet of {−1, 0, +1} with FP16 group-wise scaling, yielding 1.76 effective bits per weight and a 5.9GB total on-disk footprint—roughly 1/9th the size of its full-precision parent—while keeping a 262K-token context, multimodal text-and-image input, and an Apache 2.0 license. The technical foundation matters more than the headline number: commenters familiar with the method note this is not "round Qwen weights to {-1,0,+1}." The weights are first rotated into a quantization-friendly basis, then ternarized with per-group scales in a QAT-adjacent pipeline whose exact recipe Prism has kept proprietary. The framing is intelligence density—useful capability per gigabyte, per bit, per watt—and Bonsai 2 is a direct bet that this, not raw parameter count, becomes the deployment metric that matters.

The headline claim is 98.2% aggregate benchmark retention against full-precision Qwen3.8 27B (83.9 vs 85.4), up from roughly 95% in the first Bonsai generation, which Prism argues makes the release practically lossless. Per-category, coding lands at 81.58 (vs 82.17), agentic/tool-calling at 77.57 (vs 79.74), math at 96.57, instruction-following at 82.66, and vision at 78.59 (vs 81.64)—with vision and agentic loops being exactly where compounded small errors hurt most. Runtime numbers are equally aggressive: up to 143 tok/s on an RTX 5090, 46.8 tok/s on an M5 Max, and 0.714 mWh/token on an RTX 4090, which Prism claims makes it 40% more energy-efficient than a full-precision 8B model. The fine print is that this requires Prism's own llama.cpp fork with custom low-bit kernels; the community reports a mixed bag on the ground—7–8 tok/s on a 16GB M2 Mac Mini, 34 tok/s on a DGX Spark, no SYCL path for Intel Arc, no optimized MMQ path for AMD/HIP, and WebGPU deployments that loop.

Ternary Bonsai 2 27B packs a 27B-class multimodal model into 5.9GB at 1.76 effective bits per weight—98.2% of full-precision aggregate performance, and 0.714 mWh/token on an RTX 4090, claimed to be 40% more energy-efficient than a full-precision 8B.

HN reaction splits cleanly: genuine excitement about 27B-class capability landing on 16GB consumer GPUs versus a loud chorus insisting "near-lossless" collapses under real agentic workloads, compounded by tooling friction (custom llama.cpp fork, CUDA/CPU/Vulkan-only kernels) and a side-thread nitpicking "9x smaller" as mathematically incoherent.

The compression is real and technically sophisticated—ternary weights with group-wise scaling plus a basis-rotation step, not naive rounding—but the community's live-fire tests show the retention gap is widest exactly where it counts: multi-step agentic loops, vision, and computer use.

Deployment is gated by custom kernels: Prism's llama.cpp fork handles CUDA, CPU, and Vulkan only, leaving AMD/HIP without an optimized PTQ1_0 MMQ path and Intel XPU/SYCL unsupported entirely, which several commenters hit immediately.

Reported real-world throughput varies wildly by platform—~143 tok/s on RTX 5090, 46.8 tok/s on M5 Max, 7–8 tok/s on a 16GB M2 Mac Mini, and an unexplained 34 tok/s on DGX Spark—suggesting kernel tuning, not memory bandwidth, is the current bottleneck.

Commenters question the comparison baseline: the blog benchmarks against full-precision Qwen3.8 27B rather than standard 2–4 bit quants, so the real differentiator lives in a Hugging Face dropdown table claiming parity with UD-Q4_K_XL except on OCR.

The strategic subtext is that low-bit compression plus open weights erodes any assumed moat for frontier labs—commenters extrapolate the 1/9th ratio to 126B MoE models fitting on consumer hardware, while others counter that cloud economics and top-end coding performance still differentiate the big labs.

Astra for Law
⬆ 521 pts 💬 611 HN comments

OpenAI's Astra for Law is a verticalized packaging play rather than a new model release: GPT‑6 Astra wrapped in a licensed-plus-open legal retrieval stack, legal-analysis and legal-writing prompt scaffolding, and enterprise governance controls. The retrieval core is a search index spanning 230M+ URLs of U.S. case law, statutes, regulations, court rules and administrative decisions, refreshed daily, with case-law coverage drawn substantially from Free Law Project's CourtListener corpus (claimed >99.9% of published precedential U.S. case law). Distribution is deliberately indirect: an initial Trusted Access Program in ChatGPT and Codex with Zero Data Retention on the API, a model picker entry of 'GPT‑6 Astra Law' and gpt-6-astra-law in the API, 26 partner-built plugins (iManage, Intapp, DeepJudge, Relativity, Clio, Thomson Reuters HighQ/CoCounsel), plus custom firm-built applications at Sullivan & Cromwell, Ropes & Gray, Cooley and Wachtell. The strategic subtext, which HN readers caught immediately, is that OpenAI is courting rather than cannibalizing Harvey, Legora and the legal-tech layer.

The quantitative claims deserve scrutiny. On 200 questions from the private validation set of Vals AI's Legal Research Bench, Astra for Law passed the overall correctness check on 54.0% of questions versus 38.7% for GPT‑6 Astra with plain web search — a 40% relative gain — plus 24% more reference cases found and up to 54% more correct target passages retrieved at matched reasoning effort. Commenters were quick to note that 54.0% places the system slightly below the ~55.29% all-pass top tier occupied by Claude Opus 5 and Fable 5.1 on the same public leaderboard, so the headline improvement is mostly a retrieval-configuration delta, not a frontier capability lead. Privacy language was thin — ZDR on API, Enterprise excluded from human review by default — and practitioners flagged hallucination, PDF/OCR brittleness, and the fact that the model is explicitly non-advisory, leaving liability squarely with the licensed attorney.

Astra for Law scores 54.0% on Vals AI's Legal Research Bench — a 40% relative lift over the same model with web search alone, yet still behind Claude Opus 5's 55.29% all-pass top score.

Key Highlights
  • Astra for Law is GPT‑6 Astra plus a 230M-URL legal search index, legal writing/analysis instructions, and enterprise governance — not a new foundation model.
  • Benchmark gain is real but narrow: 54.0% vs 38.7% overall correctness on the Vals AI Legal Research Bench, with 24% more reference cases and up to 54% more correct passages retrieved.
  • Distribution is deliberately ecosystem-friendly: Harvey, Legora, Thomson Reuters, 26 plugins, and an explicit 'building on OpenAI should mean getting more from the ecosystem, not replacing it' framing.
  • Privacy/governance is thin beyond Zero Data Retention on API and default exclusion from human review for ChatGPT Enterprise, plus a design partnership with Latham & Watkins on ethical walls and client instructions.
  • Practitioner comments split on impact: AI helps with discrete verifiable tasks (doc extraction, first-pass research) but remains unusable for judgment-heavy work, and one commenter reported real-world advice diverging sharply from model output.

#3
Bend – A language that blocks AI mistakes via proof, on CPU and GPU
⬆ 511 pts 💬 243 HN comments

Bend 2, released by Victor Taelin (LightMachine) after roughly a year of near-full-time work, is a from-scratch language whose pitch is explicitly post-AGI: humans will stop reading code, so intent must be expressed unambiguously and machine-verified. Technically it is an affine dependent type theory (BendTT) with Python-like surface syntax whose type checker doubles as a proof checker; a companion runtime (BendRT) compiles the same source to native CPU code via clang and to Metal or CUDA kernels, so a `!` annotation runs identical code on host or device. The workflow centres on LAWS.bend — invariants the human, not the agent, owns — plus PROOF.bend, with a snippet for AGENTS.md instructing coding agents to run `bend guide`, preserve laws, and run `bend PROOF.bend` before committing.

The claims are aggressive: single-core performance near C, up to ~100x via 16 cores or GPU, and proof checking in under a second where Lean or Rocq take minutes on mid-sized codebases. The community response — 511 points, 243 comments — was as much sociological as architectural. Taelin noted this Bend shares only a name with the HVM/interaction-combinator predecessor; commenter mccoyb confirmed 'this Bend doesn't really have anything to do with interaction combinators,' calling it a QTT with an affinity change tuned for GPU performance. Others flagged 20K stars against 500 forks and a squashed commit history, prompting Taelin to restore it. Meanwhile, users report agents burning half a million tokens looping on 'laws broken,' and Claude itself complaining that Base ships exactly one arithmetic law, U32.add_comm.

The landing page asserts 'Merging a bug is mathematically impossible: it is a theorem' — yet testers watched an agent burn ~500k tokens in a 'laws broken' loop just to add walls to a demo game, and Claude complained the stdlib ships one arithmetic law (U32.add_comm) and nothing resembling order theory.

Key Highlights
  • Bend 2 is a ground-up rewrite unrelated to the original Bend/HVM interaction-combinator project, recycling only the name — a deliberate pivot that confused long-time followers.
  • Its core is BendTT, an affine dependent type theory whose proof checker runs in ~1 second, positioned against Lean/Rocq checking times measured in minutes.
  • One source compiles to both CPU (clang) and GPU (Metal, CUDA), with automatic parallelism and no kernels, threads or locks written by the user.
  • LAWS.bend + PROOF.bend are marketed as 'AGENTS.md backed by proof', but critics note the agent can edit the laws themselves unless a human locks and reviews that file.
  • Adoption friction is real: a nearly empty standard library, missing lemmas like cmp_refl and le_max_l, and agents looping on proof failures until API rate limits break the cycle.

#6
How to Write with an LLM
⬆ 208 pts 💬 137 HN comments

Thomas Ptacek's "How to Write with an LLM" argues that the tooling most writers want—a ghostwriter—is precisely the wrong abstraction, because frontier models are optimized to produce pleasing, headline-grade prose at every sentence. The proposed method inverts the workflow: you write the piece first, then hand it to a model strictly as a copyeditor that surfaces flaws. Two rules enforce the boundary. Rule One forbids adopting any phrase the model suggests, on the theory that LLM turns of phrase are individually seductive and collectively detectable—"readers can detect LLM words in the parts per trillion." Rule Two forbids soliciting encouragement, since models default to praising structure, transitions, and metaphor, nudging authors to double down on first-draft impulses rather than perform the rethinks that constitute authentic voice.

The mechanical payoff is concrete: models never fatigue, so they reliably flag passive-voice overuse, nominalized verbs, repeated diction, filler adverbs ("very," "actually," "unfortunately"), and paragraphs that improve instantly when relocated. Ptacek points programmers to Joseph Williams' "Style: Lessons in Clarity and Grace" as the prose analogue of Hanson's "C Interfaces and Implementations"—copyediting as a repeatable, near-algorithmic pass—and describes prompting a local Python/HTMX/SQLite workshopping tool with Genius-style margin annotations, running each edit through Codex, Claude, or Antigravity CLIs. Critically, A/B comparisons of rewrites must be judged by a model lacking context, since a model that saw you rewrite will flatter the revision. He even declines GPT-5's verdict that the essay is 20% too long.

"Do not let an LLM pick your words" — frontier models are wedged in a mode where everything they write is a magazine headline, and readers can detect LLM diction "in the parts per trillion," so every suggested phrase is disqualified on principle.

Key Highlights
  • Rule One: never adopt a word an LLM suggests, even if you prefer it—model phrasing is individually pleasing but collectively detectable
  • Rule Two: forbid encouragement, because praise about structure and transitions causes writers to double down on first-draft impulses instead of load-bearing rethinks
  • LLMs excel at fatigue-free mechanical proofing: passive voice, nominalizations, filler adverbs, repeated diction, and paragraph reordering
  • "Style: Lessons in Clarity and Grace" is pitched as the programmer's schematic for prose, making copyediting as rote as Java coding
  • A/B rewrite comparisons must go to a context-free model, and even then the author may reject the advice—Ptacek ignores GPT-5's '20% too long' verdict

Hister: A private search engine for the pages you visit and the files you keep
⬆ 646 pts 💬 173 HN comments

Hister, by asciimoo — the developer behind the privacy metasearch engine Searx — is a self-hosted personal search engine that inverts the metasearch model entirely. Rather than proxying queries out to third-party providers, Hister builds a local inverted index from the full text of pages you visit, browser history, bookmarks, crawled sites, and local files, storing extracted content and offline previews so results survive link rot and page mutation. The stack is a Go server (CGO-dependent, AGPLv3, ~2,125 commits, 4.7k stars, 197 forks) with a web UI, TUI, CLI, multi-user separation on a shared host, and an MCP server for AI-assistant access. Query language supports field filters, phrases, wildcards, negation, aliases and priority weighting, with optional semantic search delegated to a user-configured embeddings endpoint. The author explicitly frames it as a response to 'the limitations of the metasearch concept' after a decade of Searx.

The reception reveals a mature appetite for what is essentially a regression-recovery tool: commenters note Google shipped full-text history search in 2008 and removed it around 2013, and as TeMPOraL puts it, 'now we have no browser capable of searching in anything — not even Firefox.' Practitioners describe months of production use — jjice indexes Obsidian notes and a work machine; Yehoshaphat runs Hister as his default engine, falling back to Kagi via a '!!' escape prefix. Flet 1.0 – Build cross-platform apps in Python
⬆ 136 pts 💬 69 HN comments

Flet 1.0 marks the stabilization of a Python-first UI framework that compiles down to Flutter, letting developers ship a single Python codebase to iOS, Android, Windows, macOS, Linux, and the web. The architectural bet is layered: a Python runtime host sits alongside Flutter's rendering engine, so controls are expressed as Python objects (Text, FloatingActionButton, Container) that are serialized into Flutter widgets over an IPC/protocol bridge. Flet exposes 150-plus controls and services, both imperative and declarative styles, a flet build packaging pipeline targeting app stores, Pyodide/WASM browser execution, pytest-driven UI testing with iOS/Android screenshot diffs, and an MCP server that feeds version-specific API context to coding assistants. The stated ambition is to erase the frontend barrier for Python developers without asking them to learn Dart.

The release leans heavily on distribution ergonomics rather than novel rendering: prebuilt NumPy, pandas, Pillow, and cryptography wheels for mobile remove the cross-compilation tax that has historically crippled Python-on-iOS projects like BeeWare and Kivy. Flet Studio offers a zero-install browser IDE, and extensions let teams wrap arbitrary Flutter packages or compose custom controls. The public numbers are modest but telling: 136 points and 69 comments, with no visible upvote differential on individual comments. The community debate split along three fault lines — whether abstraction stacks (Flutter-over-Python) are worth debugging versus native/WASM, whether Python belongs in more or fewer places, and whether web targets should emit DOM or canvas, since Flet's web export renders into a single canvas element.

Flet 1.0 ships a single Python codebase to six platforms by running a full Python interpreter on top of Flutter — one commenter's app APK already weighs 140MB before custom extensions push it toward 300MB.

Key Highlights
  • Flet 1.0 wraps Flutter in a Python API layer, exposing 150+ controls and services across desktop, mobile, and web from one codebase.
  • Prebuilt mobile wheels for NumPy, pandas, Pillow, and cryptography target the long-standing pain of cross-compiling Python dependencies for iOS/Android.
  • Packaging (flet build), pytest UI testing with screenshot diffs, and an MCP server for AI coding assistants round out the shipping story.
  • The web target renders mostly into a single <canvas> element, surprising developers who expected DOM/HTML output.
  • Community reaction is polarized: production users praise stability, while skeptics prefer native, Tauri, or plain Flutter and flag missing services like Bluetooth.
