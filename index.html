Lore – Open source version control system designed for scalability
⬆ 1163 pts 💬 619 HN comments

Lore is an open-source version control system developed by Epic Games, designed to address the scalability challenges of managing large binary assets alongside code—a pain point in game development and other media-rich industries. Unlike Git, which struggles with binary files, Lore uses a centralized, content-addressed architecture built on Merkle trees and an immutable revision chain, ensuring integrity and deduplication. Its chunked storage splits large files into reusable chunks, enabling on-demand hydration so workspaces stay lightweight. A service-backed architecture with caching scales to large teams, while lightweight branches and fast switching support iterative workflows. Licensed under MIT, Lore is already used internally at Epic for Unreal Editor for Fortnite, replacing traditional storage layers to reduce file transfers and publish times. The system supports multiple languages via SDKs and provides a CLI, with a desktop client promised open-source later.

The HN community largely recognizes Lore's niche as a competitor to Perforce, the long-standing standard in game development, rather than Git. Comments highlight Perforce’s dominance for binary asset management, permissions, and file locking—features Git lacks. Many express cautious optimism, appreciating Epic's open-source move and architectural choices like Rust and Merkle trees. However, skepticism remains about Epic's long-term commitment, given their history with projects like Unreal Engine’s drama and ‘vibe-coding’ accusations. Some users note missing features like a local-only mode and GUI for non-programmers, while others compare it to existing tools like PlasticSCM (now owned by Unity) and data versioning systems like LakeFS. The reaction is mixed: excited for a modern Perforce alternative but wary of adoption risks without proven enterprise track record.

Lore is a content-addressed, Merkle-tree-based VCS that promises to replace Perforce for game development, already powering UEFN and reducing publish times by eliminating redundant file transfers.

Key Highlights
  • Content-addressed storage using Merkle trees ensures integrity and deduplication.
  • Chunked storage and on-demand hydration handle large binary files efficiently.
  • Centralized with caching for scalable throughput and team collaboration.
  • Lightweight branches and free branching enable fast experimentation.
  • Full open source under MIT with SDKs for C/C++, C#, Rust, Go, Python, JavaScript.

RFC 10008: The new HTTP Query Method
⬆ 384 pts 💬 159 HN comments

RFC 10008 defines the HTTP QUERY method, a new request method that bridges the gap between GET and POST for safe, idempotent query operations. Unlike GET, which encodes query parameters in the URI and suffers from size limits, logging exposure, and lack of request body semantics, QUERY allows the query content to be sent in the request body while retaining the safety and idempotency guarantees of GET. This makes it suitable for complex queries that exceed URI length constraints or involve sensitive data that should not appear in logs or bookmarks. The method leverages existing HTTP mechanisms like content negotiation, caching (with the request body as part of the cache key), and conditional requests. Servers can optionally assign URIs to query results via Content-Location or Location headers, enabling subsequent GET requests. The specification also introduces the Accept-Query response header for indicating supported query formats.

The community response is mixed but engaged. Many developers welcome the formalization of a pattern already in use (e.g., POST for search endpoints), noting that QUERY eliminates ambiguity about safety and idempotency. However, concerns center on caching complexity: including an unbounded user-controlled request body in the cache key could lead to performance issues or cache-busting attacks. Commenters also debate whether a simpler approach—like standardizing GET with a body—would have been preferable, but acknowledge historical interop issues with proxies. The naming 'QUERY' is criticized as confusing given the existing use of 'query' for HTTP requests generally. Adoption remains a challenge, as infrastructure (CDNs, proxies, browsers) must explicitly support the new method. Overall, the RFC is seen as a pragmatic evolution of HTTP for modern API patterns, with potential to reduce reliance on POST for queries.

"The QUERY method spans the gap between GET and POST, being explicitly safe and idempotent while using a request body—a pattern already widely needed in practice."

Key Highlights
  • QUERY is safe and idempotent, like GET, but uses a request body for query content.
  • Caches must incorporate the request body into the cache key, which could be unbounded and user-controlled.
  • Servers can assign URIs to query results via Content-Location or Location headers for later GET requests.
  • The method formalizes existing patterns (e.g., POST for search) but avoids ambiguity about side effects.
  • Adoption requires updates to proxies, CDNs, and browsers, which may slow rollout.

Clojure Hosted on Go
⬆ 154 pts 💬 17 HN comments

Glojure is a Clojure interpreter hosted on Go, aiming to provide the same seamless interoperability with Go libraries as Clojure does with Java. It is a tree-walk interpreter, currently in early development (v0.6.5) and not yet performance-optimized. Its hosted nature means all Go values are valid Glojure values and vice versa, enabling direct access to the Go ecosystem. The project supports standard library packages out of the box, with extensible interop via generated package maps. It offers a full-featured REPL with vi/emacs modes, multiline editing, and tab completion, plus a Go embedding API for scripting and plugins.

The project has garnered 633 stars and 22 releases since its inception, indicating steady but early adoption. Key technical differences from Clojure include mapping of numeric types to Go's native types (e.g., long→int64, double→float64) and handling of runes as tagged chars. The README explicitly compares it to other Go Clojure ports like Joker and let-go, emphasizing its hosted interop as a differentiator. Commenters noted its promising interop model but raised concerns about performance given the tree-walk approach, and questions about sandboxing. The community also discussed alternative dialects such as Lisette, Carp, and Jank, highlighting the growing interest in Lisp-like languages on Go.

Glojure is a tree-walk interpreter that provides full interop with Go, making it unique among Clojure-on-Go implementations.
