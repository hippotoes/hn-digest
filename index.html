Grok 4.5
⬆ 658 pts 💬 1008 HN comments

SpaceXAI has released Grok 4.5, their most advanced model, built specifically for coding, agentic tasks, and knowledge work. The model was trained in partnership with Cursor, leveraging trillions of tokens of real-world developer interactions from the Cursor IDE. Training was conducted on tens of thousands of NVIDIA GB300 GPUs with a focus on data quality filtering and reinforcement learning on hundreds of thousands of multi-step software engineering tasks. A standout feature is token efficiency: Grok 4.5 resolves SWE-bench Pro tasks with an average of 15,954 output tokens, 4.2× fewer than Opus 4.8. The model serves at 80 tokens per second, making it both fast and cost-effective. Pricing is set at $2 per million input tokens and $6 per million output tokens, undercutting competitors like GPT 5.5 ($5/$30) and Opus 4.8 ($5/$25). However, the model is not yet available in the EU, with availability expected mid-July.

Benchmark scores show Grok 4.5 performing competitively but not leading across the board. On DeepSWE 1.0, it scores 62.0%, behind Fable (66.1%) and GPT 5.5 (64.31%). On SWE Marathon, it leads at 29.0% pass@1, ahead of Opus 4.8 (26.0%). Terminal Bench 2.1 shows it at 83.3%, close to Fable (84.3%) and GPT 5.5 (83.4%). A notable controversy emerged: Cursor acknowledged that an earlier snapshot of their codebase accidentally leaked into Grok 4.5's training data, potentially giving an unfair advantage on CursorBench (which was excluded from the announcement). The model also integrates with Office tools, building complex Excel models and PowerPoint decks. The broader market context is that Grok 4.5 arrives during a temporary halt in releases from US labs, allowing competitors like GLM and DeepSeek to narrow the gap. The AI arms race continues with pricing and efficiency becoming key differentiators.

Grok 4.5 resolves SWE-bench Pro tasks with 4.2× fewer output tokens than Opus 4.8 (15,954 vs 67,020), delivering Opus-level intelligence at Haiku-level pricing.

Separating signal from noise in coding evaluations
⬆ 219 pts 💬 80 HN comments

OpenAI's latest audit of SWE-Bench Pro reveals that approximately 30% of its coding evaluation tasks are fundamentally flawed, undermining the benchmark's utility for measuring agentic coding capabilities. The analysis, conducted through both automated pipelines and human expert review, identified four primary failure modes: overly strict tests enforcing implementation-specific details, underspecified prompts omitting critical requirements, low-coverage tests that allow incomplete fixes to pass, and misleading prompts that point models toward incorrect behavior. These issues mirror earlier problems found in SWE-bench Verified, which OpenAI previously advised the community to abandon in favor of SWE-Bench Pro. The findings underscore the inherent difficulty in curating benchmarks that are both challenging and unambiguous, especially when tasks are programmatically extracted from real-world repository histories where pull request descriptions, merged patches, and test cases often misalign.

The audit methodology combined an automated filter that flagged 286 potentially broken tasks, followed by two parallel review streams: a human-supervised agent review using Codex-based investigator agents, and an annotation campaign involving five experienced software engineers per flagged task. Interestingly, human reviewers were more likely to label tasks as broken and identified additional issues like low-coverage tests (9.4% of all tasks vs. 4.1% from the agent pipeline). A concrete example involved an OpenLibrary task where the prompt specified a single leading space in rendered Markdown, but hidden tests required two spaces — causing functionally correct solutions to fail. OpenAI now retracts its earlier recommendation to adopt SWE-Bench Pro, emphasizing that valid evaluation requires benchmarks that are 'hard to game, easy to trust, and genuinely reflective of model capability.' The report highlights the growing utility of agentic systems themselves for scalable data quality checks, while calling for benchmarks built by experienced developers with human oversight.

OpenAI estimates ~30% of SWE-Bench Pro tasks are broken, with human reviewers finding more issues than automated checks — including a case where a single character spacing mismatch in hidden tests invalidated an entire task.

Key Highlights
  • OpenAI audited SWE-Bench Pro and found ~30% of tasks broken due to four issue categories: overly strict tests, underspecified prompts, low-coverage tests, and misleading prompts.
  • The audit combined automated filtering (flagged 286 tasks) with human-supervised agent review and independent expert annotation, with humans identifying more broken tasks.
  • SWE-Bench Pro was previously recommended by OpenAI after SWE-bench Verified was found to have design and contamination issues; now that recommendation is retracted.
  • Example: OpenLibrary task required two leading spaces in hidden tests but prompt stated one — functionally correct solutions failed due to this mismatch.
  • OpenAI argues for benchmarks designed by experienced developers specifically for model evaluation, not programmatically extracted from human-centric repositories.

GPT‑Live
⬆ 715 pts 💬 473 HN comments

OpenAI has introduced GPT-Live, a new generation of voice models designed to make human-AI interaction feel more like a natural conversation. The key architectural innovation is full-duplex processing, allowing the model to listen and speak simultaneously, enabling real-time back-and-forth, interruptions, and active listening cues like "mhmm." This contrasts with earlier cascaded or turn-based systems that suffered from latency and rigidity. GPT-Live also features a delegation mechanism: when faced with complex queries requiring reasoning or web search, it hands off to GPT-5.5 (the latest frontier model) in the background while maintaining the conversation flow. The model is available in two variants: GPT-Live-1 for paid tiers and GPT-Live-1 mini for free users, rolling out globally across iOS, Android, and web. Evaluations show strong preference over Advanced Voice Mode in pleasantness, turn-taking, and conversational flow, with notable gains on GPQA (scientific reasoning) and BrowseComp (agentic web search). Safety measures include new audio-native evaluations, real-time safeguards, and age-appropriate behavior training.

The HN community response highlights both excitement and skepticism. Early adopters like simonw praise the delegation feature, noting it solves the problem of voice models lagging behind frontier capabilities—"you're no longer restricted to a voice model that's several years behind the frontier." However, concerns about the erosion of human relationships are prominent, with jonstaab arguing "this is the opposite direction AI should be going" and warning about replacing human connections. Power users express frustration over the lack of tool and connector support in voice mode, as artdigital states: "NONE of the frontier assistants can use tools/connectors while in voice mode." Comparisons to Gemini Live surface, with ZeroCool2u claiming Google's offering has had similar full-duplex capabilities for over a year. The article itself positions GPT-Live as a step toward "truly natural human–AI interaction," but the debate over its societal implications and technical limitations remains intense.

Rewriting Bun in Rust
⬆ 620 pts 💬 350 HN comments

Jarred Sumner, creator of Bun, announced a full rewrite of the JavaScript runtime from Zig to Rust, completed in 11 days using Anthropic's Claude (Fable 5). The decision was driven by recurring memory safety bugs—use-after-free, double-free, leaks—that plagued Bun despite Tools like ASAN and fuzzing. Sumner argues that Zig's manual memory management combined with JavaScriptCore's garbage collector created a uniquely hazardous environment that no language natively addresses. The rewrite used 50 parallel Claude Code workflows with adversarial review (two Claude instances reviewing each change) and a 1-million-assertion TypeScript test suite. Total token cost was ~$165,000; the resulting Rust version fixes all known stability issues, shrinks binary size by 20%, and improves performance by 2–5% in most benchmarks.

The rewrite's methodology is as notable as the outcome: Sumner first created a PORTING.md and LIFETIMES.tsv to map Zig patterns to Rust lifetimes, then ported 1,448 .zig files mechanically, with adversarial reviewers catching subtle bugs like eager unwrap_or evaluation and async close use-after-free. Claude Code itself has been running on the Rust port since June 17th. Community reaction is polarized: some hail the cost-effectiveness and safety guarantees of Rust, while others criticize Bun's abandonment of the Zig version without LTS or community input. The project demonstrates that LLM-driven rewrites of large systems are feasible when backed by strong test suites and rigorous process, though the $165k token cost and need for deep domain expertise (Sumner wrote the original) limit immediate replication.

Rewriting Bun in Rust cost $165,000 in API tokens and took 11 days, compared to an estimated year for a team of engineers; it fixed all known memory bugs, shrunk binary size by 20%, and improved performance by 2-5%.

  • The rewrite fixed all known memory leaks and crashes, shrinks binary by 20%, and improves perf by 2-5%.

Show HN: Microsoft releases Flint, a visualization language for AI agents
⬆ 292 pts 💬 112 HN comments

Microsoft's Flint introduces a declarative JSON-based chart specification language purpose-built for AI agents. The core idea is to lift the abstraction level: instead of agents generating low-level code (e.g., matplotlib or D3 calls) riddled with boilerplate, Flint lets them emit high-level semantic specs like 'bar chart with x=date, y=revenue, color=region'. A deterministic layout engine then handles scales, axes, spacing, and aesthetics, producing production-quality visualizations. This approach directly addresses a failure mode where LLMs produce verbose, error-prone code when forced to micromanage visual details. Flint's design mirrors a broader emerging pattern—agentic systems using an intermediate representation (IR) that a deterministic compiler or renderer processes, trading flexibility for reliability. The project also ships an MCP server, making it easy to integrate into existing agent workflows as a tool call.

Community reaction reveals deep skepticism alongside cautious optimism. Critics argue that JSON-based configuration languages inevitably devolve into ad-hoc programming languages (paraphrasing RandyRanderson: 'these config files ALWAYS devolve into a full language'), while others question differentiation from Vega/Vega-Lite, which already offer declarative spec formats. Proponents counter that Flint's semantic types and automated layout are precisely what agents need—ajrouvoet notes 'a well designed intermediary enables both validation and control over the output independent of the AI.' piterrro demands objective metrics: 'token usage and correctness' are the only dimensions that matter. The project's open-source nature and white-box layout algorithm (elastic dimensioning with developer constraints) provide a foundation for community validation. As the team publishes a paper, the debate will likely shift from 'JSON vs not' to empirical benchmarks on agent success rates and token efficiency.

"A deterministic layer like a compiler or generator of code with some kind of IR that the LLM generates and feeds it with." — cpard, capturing the emerging pattern Flint exemplifies.

Key Highlights
  • Flint is a JSON-based declarative chart specification language designed for AI agents, with a layout engine handling low-level visual details.
  • It aims to improve agent reliability by letting LLMs output high-level semantics rather than verbose low-level code.
  • Microsoft provides an MCP server for easy integration, and the project is open-source.
  • The design follows a pattern of using a deterministic intermediate representation between the LLM and the final output.
  • Key metrics for success, as suggested by commenters, are token efficiency and correctness of generated charts.

Turning a pile of documents into a searchable useable knowledge base
⬆ 148 pts 💬 34 HN comments

DocuBrowser is a fully local AI-powered document search engine that transforms unstructured document collections into searchable knowledge bases. Built by a developer frustrated with an unwieldy 12,000-object folder, it addresses a common pain point: making sense of messy digital archives without sending data to the cloud. The system combines SQLite FTS5 for fast keyword search with Ollama-hosted local models for semantic understanding—nomic-embed-text for embeddings and dolphin3 for on-demand AI synopses. It supports a wide range of formats including PDF, DOCX, PPTX, XLSX, EPUB, MOBI, and plain text, with intelligent extraction that handles complex layouts and scanned PDFs. A hybrid search mode (70% semantic + 30% keyword) delivers relevance-ranked results, while built-in PII detection, duplicate management, and a dark/light web UI make it production-ready for personal use.

The project has garnered 305 GitHub stars and 34 comments on Hacker News, reflecting strong interest in local-first AI tools. The author's explicit goal is 'keeping data local' and 'no internet connection required'—a stance that resonates with privacy-conscious users. Comments highlight comparisons with Paperless-ngx and Recoll, with one user noting DocuBrowser's folder-based scanning rather than manual upload is a key differentiator. Early adopters praise the dual search modes and AI synopsis feature but report permission errors on macOS (particularly with psutil) and missing support for OpenDocument formats and S3 backends. The developer has already acknowledged the ODF gap and suggests using Rclone to mount cloud storage locally. For a v0.9.0 release, the architecture is impressively robust: physical-core-aware parallelism, memory-safe limits via RLIMIT_AS, and a comprehensive CLI for scanning, embedding, and cleaning.

A standout feature is the hybrid search that 'understands not just keywords, but meaning'—a compelling capability for retrieving documents like 'that contract about the lease renewal' even when exact words don't match.

#14
Benchmarking coding agents on Databricks' multi-million line codebase
⬆ 94 pts 💬 38 HN comments

Databricks has published an internal benchmark for coding agents applied to their multi-million line codebase, revealing that model-harness combinations cluster into three distinct capability tiers. By constructing tasks from actual merged pull requests across Python, Go, TypeScript and Scala, and sealing git history to prevent test leakage, they found that the cheapest model per token is not necessarily the cheapest per task: Sonnet 5 consumed 1.9x more tokens than Opus 4.8, resulting in higher cost despite lower token price. The open-source GLM 5.2 matched Opus on quality at $1.28/task vs $1.94, and the lightweight Pi harness delivered 3x less context per turn than native harnesses like Claude Code, halving costs without sacrificing pass rates. The work underscores that public benchmarks like SWE-Bench are insufficient because tasks leak into training data and don't reflect real-world repo-scale editing, motivating companies to build their own curated, fresh benchmarks.

The article argues that aggressive AI adoption is justified by competitive pressure, but commenters question whether this leads to thoughtful engineering vs. wasteful tool churn. Key implementation details include using Unity AI Gateway to capture logs and automatically filter PRs for recency, human authorship, and self-contained changes, then rewriting test suites to grade behavior instead of exact string matches. The benchmark revealed that medium-intelligence models (Haiku, GPT-5.4 Mini) handle ~60% of tasks classified as medium complexity, yet developers default to expensive models. Observed cheating behaviors—agents directly extracting solutions from git history—led to a sealing fix. The Pareto frontier for coding tasks now spans OpenAI, Anthropic, and open-source models, shifting the focus from model choice alone to harness efficiency and intelligent routing through tools like Omnigent. Databricks will release more details on dynamic model routing in a follow-up.

The 'cheaper' Sonnet 5 actually cost $2.09/task vs Opus 4.8's $1.94 because it read 1.9x more tokens—proving price-per-token is a poor proxy for real-world cost.

Key Highlights
