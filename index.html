HERMES.md in commit messages causes requests to route to extra usage billing
⬆ 1133 pts 💬 480 HN comments

A critical bug in Claude Code v2.1.119 caused API requests to be billed to 'extra usage' credits instead of the subscriber's Max plan quota when a git repository's recent commit history contained the case-sensitive string 'HERMES.md'. The bug was discovered via systematic binary search: the user cloned affected repos, tested orphan branches, and isolated individual commit message strings until identifying the trigger. Notably, the mere presence of 'HERMES.md' in a commit message—not a file on disk—rerouted billing server-side. The error message, 'You're out of extra usage...', gave no indication that content-based routing was the cause, making diagnosis extremely difficult. The user burned $200.98 in extra credits while their Max 20x plan showed 86%+ remaining capacity. Anthropic later confirmed the root cause was an 'overactive anti-abuse system' that has since been fixed.

The incident sparked intense community backlash, particularly after the initial support response stated, 'we are unable to issue compensation for degraded service or technical errors that result in incorrect billing routing.' Many commenters noted this response appeared AI-generated, with one Anthropic employee confirming via a throwaway account that 'the response... was, as you imagined, generated by Claude.' Thariq from the Claude Code team later intervened, promising full refunds and an extra grant of usage credits equal to a monthly subscription for all affected users. The broader conversation revealed a pattern of billing irregularities and opaque customer support at Anthropic, with multiple users reporting double charges, unresolved tickets, and forced chargebacks. This incident underscores the dangers of relying on LLM-generated customer service for complex technical issues and raises questions about the opacity of AI company infrastructure.

#3
Copy Fail
⬆ 978 pts 💬 360 HN comments

Copy Fail (CVE-2026-31431) is a 732-byte Python exploit that provides 100% reliable local privilege escalation on every Linux distribution shipped since 2017. The vulnerability lies in the authencesn algorithm within the kernel's crypto API, chained through AF_ALG sockets and splice() to achieve a 4-byte page-cache write. This overwrites the code of a setuid binary (e.g., /usr/bin/su) with shellcode, yielding a root shell. Unlike most Linux LPEs, it requires no race window, kernel-specific offset, or network access—just an unprivileged local account. The bug was introduced in 2017 via an in-place optimization commit and exists in nearly every distro's default kernel config. The exploit was discovered by Xint Code's AI-driven audit tool and reported to the kernel security team in March 2026, with a patch committed April 1. Major distros are now shipping the fix, but many remain unpatched.

The disclosure timeline saw friction: Red Hat initially rated it 'Moderate' and deferred it, later upgrading to 'Important' after pressure. Debian and Ubuntu trackers show similar delays, with some commenters noting the patch was public for weeks before coordinated disclosure. The vulnerability's impact is highest on multi-tenant hosts (shared dev boxes, Kubernetes nodes, CI runners) where any unprivileged user can become root. Mitigations include disabling the algif_aead module (via modprobe blacklist) or blocking AF_ALG socket creation via seccomp. The exploit page itself, hosted at copy.fail, is a slick marketing piece for Xint Code, which drew mixed reactions—some praised the technical achievement and helpful write-up, others criticized the AI-generated tone and minor errors like citing 'RHEL 14.3'. Despite the marketing gloss, the underlying bug is severe: a single Python one-liner (curl | python3) can root nearly any Linux system built in the last nine years.

A single 732-byte Python script roots every Linux distribution shipped since 2017—no race condition, no kernel offset, 100% reliable.

Key Highlights
  • CVE-2026-31431 is a container escape/LPE affecting all Linux kernels since 2017 via AF_ALG and splice().
  • Exploit is 732 bytes and 100% reliable—no race window or kernel-specific offsets needed.
  • Vulnerability overwrites page-cache of setuid binaries (e.g., /usr/bin/su) to execute arbitrary shellcode.
  • Primary mitigation: disable algif_aead module; kernel patch is commit a664bf3d603d.
  • Highest impact on multi-tenant environments (Kubernetes, CI runners, shared hosts); lower on single-user systems.

#5
FastCGI: 30 years old and still the better protocol for reverse proxies
⬆ 340 pts 💬 78 HN comments

Andrew Ayer's 2026 retrospective argues that FastCGI, despite its 30-year age, remains superior to HTTP for reverse proxy-to-backend communication due to its inherent security properties. The core thesis is that HTTP/1.1's lack of explicit framing enables desync attacks (request smuggling), a vulnerability class that continues to plague modern infrastructure—exemplified by a recent Discord media proxy flaw. FastCGI, by contrast, uses a binary protocol with clear message boundaries, eliminating parsing ambiguities. More critically, it provides structural domain separation: trusted metadata (e.g., REMOTE_ADDR) is transmitted as dedicated parameters, while client headers are namespaced with an HTTP_ prefix. This prevents proxy-injected headers like X-Real-IP from being spoofed by attackers, a persistent issue with HTTP even when using HTTP/2. The article includes concrete configuration examples for nginx, Apache, Caddy, and HAProxy, and notes that Go's standard library makes switching trivial.

Ayer acknowledges FastCGI's limitations: no WebSocket support, suboptimal tooling (curl lacks a FastCGI client), and occasionally lower throughput compared to HTTP/1.1 or HTTP/2 under heavy load. However, he argues these are not inherent protocol flaws but reflections of less optimized code paths. The broader industry problem, he contends, is awareness—desync attacks were documented by Watchfire in 2005 but largely ignored for over a decade. HN commenters largely agree with the security analysis, with several highlighting alternative binary protocols like WAS and uWSGI. Historical debate resurfaces: HTTP's simplicity won adoption, but at the cost of increasing complexity in parsers and security middleware. Some commenters note that HTTP/2 fixes framing but not untrusted headers, reinforcing FastCGI's advantage. The community also discusses practical workarounds for WebSockets and streaming, but consensus leans toward Ayer's conclusion that for most internal services, FastCGI's safety outweighs its vintage feel.

FastCGI completely avoids untrusted header problems by providing domain separation: HTTP header names are prefixed with 'HTTP_', making it structurally impossible for clients to send a header that would be interpreted as trusted data.

Key Highlights
  • FastCGI's binary framing eliminates HTTP/1.1 desync attacks.
  • Domain separation (HTTP_ prefix) prevents trusted header spoofing.
  • Go's standard library makes switching from HTTP to FastCGI trivial.
  • Practical downsides: no WebSockets, less tooling (e.g., curl), sometimes lower throughput.
  • Historical commenters argue HTTP's simplicity won adoption despite security costs.
