Inkling: Our Open-Weights Model
⬆ 983 pts 💬 247 HN comments

Thinking Machines Lab has released Inkling, a Mixture-of-Experts transformer with 975B total parameters and 41B active, trained on 45 trillion tokens of text, images, audio, and video. The model supports a 1M token context window and features controllable thinking effort, enabling developers to balance performance with token cost. Rather than chasing leaderboard supremacy, Inkling is positioned as a versatile, multimodal foundation model optimized for fine-tuning. Its design prioritizes breadth across agentic, reasoning, coding, instruction-following, and multimodal tasks. The release also includes Inkling-Small, a 276B-parameter variant with 12B active parameters, for lower-latency applications. Crucially, Inkling is available on the Tinker platform, allowing users to fine-tune the model via a simple API—a strategy that aligns the company's business model with open-weight distribution.

The article includes a striking demonstration of self-fine-tuning, where Inkling writes its own fine-tuning job to become a lipogram model (avoiding the letter 'e'), runs it on Tinker, and updates its weights autonomously. Benchmark results show competitive performance: Inkling matches Nemotron 3 Ultra on Terminal Bench 2.1 while using only one-third the tokens. Community reactions highlight Inkling as potentially the first competitive American open-weights model since Llama 3, with some seeing it as a counter to Chinese open models. However, skepticism exists about benchmark comparisons, and the distinction between 'open-weights' and 'open-source' draws pointed criticism. The fine-tuning API and cost-efficiency are widely praised, positioning Inkling as a practical choice for enterprise customization at scale.

Inkling spends one third as many tokens to achieve the same performance as Nemotron 3 Ultra on Terminal Bench.

Key Highlights
  • Inkling is a 975B-parameter MoE transformer with 41B active parameters, trained on 45T tokens of multimodal data.
  • It supports up to 1M tokens context window and controllable thinking effort for efficiency.
  • The model is designed as a strong base for fine-tuning, available on the Tinker platform with a simple API.
  • Inkling is competitive on benchmarks like Terminal Bench, using far fewer tokens than comparable models.
  • A demo shows Inkling self-fine-tuning via Tinker to become a lipogram model, completing the loop autonomously.

Running Gemma 4 26B at 5 tokens/sec on a 13-year-old Xeon with no GPU
⬆ 289 pts 💬 187 HN comments

In a remarkable feat of low-resource inference, Ryan Findley got Google's Gemma 4 26B mixture-of-experts model running at ~5 tokens/sec on a repurposed HP StoreVirtual server with dual Xeon E5-2690 v2 (Ivy Bridge, 2013) and no GPU—hardware that predates AVX2 and FMA3 instruction sets. The journey began after a viral post demonstrated similar results on a 2016 Broadwell Xeon using ik_llama.cpp, a fork of llama.cpp optimized for Gemma 4's MoE architecture. However, Findley's older chips lacked the required CPU extensions, causing build failures and, more insidiously, a silent runtime bug where two MoE graph operations had no dispatch case on non-AVX2 builds, resulting in uninitialized memory passed through 240 expert tensors per forward pass. The fix, submitted as PR #2138, involved patching the graph builder to fall back to split matmuls and a fused silu-and-multiply, preserving correctness while sacrificing only the fused kernel's AVX2-only speed.

The concrete result: ~5.2 tok/s decode, ~16 tok/s prompt eval, on a $300 server from 2013. While this is dwarfed by cloud GPU performance, Findley emphasizes the skill of understanding a model deeply enough to debug silent failures—work he partially outsourced to Claude, which diagnosed the deterministic gibberish by instrumenting logits. The HN community engaged vigorously: some celebrated the technical ingenuity, others debated cost-effectiveness (pointing out that cloud inference at ~$0.30/million tokens can be cheaper than the server's 300W+ power draw). A notable undercurrent of skepticism emerged regarding the article's AI-generated prose, with several commenters questioning the authenticity of the human effort. Others shared their own numbers on similar old iron, and predictions surfaced that by 2027, 200B+ MoE models will run on consumer hardware—a trend this hack exemplifies.

5.2 tokens/sec on 13-year-old silicon for borderline free—proof that a basement server can rival cloud APIs for certain workloads.

Key Highlights
  • Dual Xeon E5-2690 v2 (Ivy Bridge, 2013), no GPU, 384GB DDR3, cost <$300.
  • Model: Gemma 4 26B-A4B (MoE) quantized to Q8_0, using a patched ik_llama.cpp.
  • Silent bug: missing dispatch cases for fused MoE ops caused uninitialized memory, producing deterministic gibberish.
  • Fix: split fused ops into separate matmuls and a silu+multiply, enabled via build flag GGML_USE_IQK_MULMAT=off.
  • Performance: ~5.2 tok/s decode, ~16 tok/s prompt eval; limited by memory bandwidth, not compute.

High-Bandwidth Flash offers efficient storage for model weights
⬆ 46 pts 💬 17 HN comments

High-Bandwidth Flash (HBF) is an emerging memory technology that applies the stacking techniques of High-Bandwidth Memory (HBM) to NAND flash, targeting AI inference workloads where read performance is critical and writes are rare. By vertically stacking up to 16 NAND dies, Sandisk projects first-generation HBF will deliver 512 GB capacity per stack with read bandwidth reaching 1.6 TB/s, far exceeding standard flash interfaces (~4.8 GB/s per die) but still below HBM4E's 3.6 TB/s. The key insight is that inference demands massive, read-heavy storage for frozen model weights and KV caches, making flash's slow writes tolerable while benefiting from its density and non-volatility. SK Hynix and Sandisk have launched a standardization effort under the Open Compute Project, aiming to complement rather than replace HBM.

The technology exploits NAND's inherent parallelism, which is typically not exposed outside the die. HBF leverages advanced 3D packaging to expose that parallelism, achieving bandwidth improvements that make it viable as a caching tier in inference accelerators. Jim Handy of Objective Analysis notes that while flash is notoriously slow for writes, 'for reads, it can be coaxed to go pretty fast.' The road map includes second and third generations targeting 2 TB/s and 3.2 TB/s reads. By offloading static model weights to HBF, HBM can be reserved as a high-speed scratchpad, potentially reducing the number of accelerators needed for large-scale inference. However, HBF is at least a year from production, and standardization is ongoing. Its success hinges on cost competitiveness relative to DRAM-based solutions and the continued growth of inference workloads.

“In an inference environment massive, read-heavy data, such as the static multi-billion parameter model weights or the precomputed KV cache, can be securely housed in the HBF tier,” says Hoshik Kim, freeing HBM to work as a “high-speed scratchpad.”

Key Highlights
  • HBF stacks NAND flash dies using HBM-like 3D packaging to achieve high read bandwidth (1.6–3.2 TB/s) while preserving flash's density and non-volatility.
  • Targeted at AI inference where model weights and KV caches are read-intensive and write-rare, making flash's slow writes acceptable.
  • Standardization efforts are underway via the Open Compute Project, with SK Hynix and Sandisk collaborating to position HBF as complementary to HBM, not a replacement.
  • First-generation HBF is expected to deliver 512 GB per stack, with read bandwidth 1.6 TB/s, scaling to 3.2 TB/s in future generations.
  • HBF could reduce the number of GPUs/accelerators needed for large-scale inference by offloading static data from expensive HBM.

Grok Build is open source
⬆ 452 pts 💬 496 HN comments

xAI has open-sourced Grok Build, its terminal-based AI coding agent, under the Apache 2.0 license. The codebase, written in Rust, provides a full-screen TUI that understands codebases, edits files, executes shell commands, searches the web, and manages long-running tasks. It supports interactive use, headless mode for CI, and integration via the Agent Client Protocol (ACP). Notably, the repository includes a self-contained terminal renderer for Mermaid diagrams that uses Unicode box-drawing—a surprisingly sophisticated component that developer Simon Willison ported to WebAssembly via Fable 5. The open-sourcing follows controversy around the tool exfiltrating entire user repositories to cloud storage, which xAI claimed to stop after backlash, though independent certification of data deletion remains absent.

The release has sparked a flurry of activity: within hours, forks appeared stripping telemetry and locking auto-update (e.g., gork-build, dgrok), highlighting distrust in xAI's privacy practices. The codebase itself is massive—over 1.3 million lines of Rust with 182 top-level external dependencies—prompting criticism that it's over-engineered 'tokenmaxxed slop' rather than a lean agent harness. Yet some developers report Grok Build feels faster than Claude Code or Cursor, attributing this to near-instant responses before telemetry removal allegedly slowed it. The strategic move is seen as a tactical play by a trailing AI company (xAI) to open-source its moat, potentially undermining incumbents like OpenAI and Anthropic while rebuilding trust after the data scandal. The community remains divided on whether this is genuine openness or damage control.

Within hours of open-sourcing, privacy-hardened forks like 'gork-build' appeared that strip vendor telemetry, opt-out data retention, and block auto-update—essentially a VSCodium-style fork for a coding agent.

Key Highlights

  • Controversy: previously uploaded entire user repositories to cloud storage without consent.

  • Critics highlight the 1.3M+ lines of Rust and 182 deps as excessive for what it does.

LLM Networking with MikroTik
⬆ 88 pts 💬 40 HN comments

The article chronicles the author's experience using large language models (LLMs) to configure MikroTik networking equipment, a task traditionally hampered by the platform's notoriously complex UI and CLI. The author, a self-described amateur networker, found LLMs to be a chaotic but effective force multiplier, enabling rapid setup of small networks through the REST/JSON API rather than SSH, which suffers from incremental failures. Key recommendations include dumping full configs before changes, using CAPsMAN for multi-AP setups, and implementing MAC-Telnet for out-of-band L2 access when IP conflicts arise. The author emphasizes a step-by-step, test-after-every-change approach, cautioning that LLMs hallucinate and must be tightly controlled, akin to coding assistants.

The post highlights a pragmatic, hands-on methodology where the author leverages multiple LLMs (Antigravity, Codex, Opus, Fable) to cross-check configurations and generate idempotent scripts. Notably, the community response underscores a broader shift: MikroTik's updated Docusaurus documentation now offers AI-friendly Markdown via URL suffix .md, and a dedicated llms.txt TOC simplifies agent prompting. Comments reveal divergent experiences—some praise LLMs for automating VLANs and static IPs, while others flag severe WiFi6 bugs, version-syntax mismatches, and the risk of exposing credentials to external models. The article concludes with a call for automated backup runbooks and version-controlled configs, reflecting a maturing practice of LLM-assisted infrastructure management.

The best tool for this is L2 MAC-Telnet—it will come in handy at the worst time, i.e., when IP addresses don’t work!

Key Highlights
