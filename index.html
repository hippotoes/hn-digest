GLM 5.2 beats Claude in our benchmarks
⬆ 919 pts 💬 421 HN comments

Semgrep's latest benchmark pits open-weight GLM 5.2 against frontier models on Insecure Direct Object Reference (IDOR) detection—a reasoning-heavy security task requiring cross-file authorization analysis. Without any specialized scaffolding, GLM 5.2 achieved a 39% F1 score, outperforming Claude Code (32%) at roughly $0.17 per vulnerability found. The model, a 750B-parameter MoE with 40B active parameters, extends context to 1M tokens and is released under MIT license. This result underscores that harness design can matter more than raw model capability: Semgrep's multimodal pipeline, which includes endpoint discovery, topped the leaderboard at 61% F1 with GPT-5.5. The article deliberately emphasizes that this is not an apples-to-apples comparison but a demonstration of how minimal-prompt open-weight models can already rival expensive frontier agents on specific security tasks.

The benchmark used a fixed IDOR dataset and prompt, varying only the model and its execution harness. Open-weight models ran in a simple Pydantic AI harness with no endpoint discovery, while Semgrep Multimodal used a purpose-built static analysis pipeline. GLM 5.2's surprise performance highlights a trend: Chinese labs like Zhipu AI are releasing competitive open models with honest disclosures of reward-hacking behaviors. Community reaction is mixed—enthusiasts report cost savings and reliability for daily coding, while skeptics question the benchmark's narrow focus and note that frontier models like Opus 4.8 still lead when given proper scaffolding. The broader implication is that the maturing open-weight ecosystem, combined with cheap inference, may reshape security practices by enabling fully private, on-premise vulnerability scanning at scale.

GLM 5.2 scored 39% F1 on IDOR detection, beating Claude Code (32%) at roughly $0.17 per vulnerability found.

Knowledge Distillation of Black-Box Large Language Models (2024)
⬆ 108 pts 💬 19 HN comments

The paper introduces Proxy-KD, a novel knowledge distillation method for black-box large language models (LLMs) like GPT-4. Traditional distillation from such proprietary models is challenging due to inaccessible internal states. Proxy-KD circumvents this by employing a proxy model that mediates knowledge transfer to a smaller student model. The approach not only outperforms standard black-box distillation but also surpasses traditional white-box techniques, offering a scalable path to leverage advanced LLMs without requiring direct access. This is particularly relevant for organizations that rely on closed-source APIs and seek to build efficient, custom models.

The study demonstrates that Proxy-KD enhances the performance of smaller models through a multi-stage process: first, the proxy model is trained on outputs from the black-box teacher, then it guides the student via both output-level and feature-level distillation. The paper claims significant gains on benchmarks, although the final v2 revision (November 2024) suggests ongoing refinements. The technique has implications for reducing inference costs and enabling deployment in resource-constrained environments. Commenters noted the potential for black-box distillation to feed into causal attribution systems for agent pipelines, highlighting its practical relevance beyond pure model compression.

Proxy-KD not only enhances knowledge distillation from black-box teachers but also surpasses traditional white-box techniques, offering a scalable alternative without needing internal model access.

Key Highlights
  • Proxy-KD uses a proxy model to transfer knowledge from black-box LLMs to smaller models without internal state access.
  • The method outperforms both black-box and white-box distillation techniques in experiments.
  • Practical applications include building efficient models from closed-source APIs and feeding into agent failure-attribution systems.
  • The paper was revised in November 2024, indicating active refinement of the approach.
  • The technique addresses a key limitation of proprietary LLMs: the inability to inspect their internals for knowledge transfer.

A way to exclude sensitive files issue still open for OpenAI Codex
⬆ 217 pts 💬 134 HN comments

The Hacker News discussion revolves around GitHub issue #2847 in the OpenAI Codex repository, which requests a mechanism to exclude sensitive files (e.g., .env, .pem, .aws/ credentials) from being read by the AI agent or sent to the model. The proposer suggests a deterministic, shareable configuration akin to .gitignore, at both repo and global levels. However, the comment thread reveals deep technical skepticism. Many seasoned engineers argue that any application-level blocklist is insufficient against a sufficiently capable LLM agent; the only true security boundary is the operating system: file permissions, containers, or virtual machines. The thread highlights a fundamental tension between usability (developers wanting a simple one-click solution) and the reality that LLMs can subvert ignore rules through tool invocations like grep or by executing arbitrary code. The discussion also surfaces existing sandboxing solutions, such as agent-box, rumpelpod, and Nix-based container images, which enforce containment at the host level.

The issue garnered 217 points and 134 comments, indicating strong community interest. Key quotes include 'This is putting the security boundary at the wrong layer' and 'A security setting that doesn't work is much worse than not having one.' The discussion reveals four distinct sentiment clusters: (1) those who insist on OS-level isolation, citing the impossibility of in-process enforcement; (2) proponents of sandboxing via containers or user namespaces, linking to projects like agent-box and rumpelpod; (3) a minority that sees value in an ignore file as a hint to the agent for token efficiency, while explicitly disclaiming security; and (4) skeptics who warn that implementing such a feature would create a false sense of security. Overall, the community leans toward the principle that agents should be treated as untrusted and run with least privilege, rather than relying on polite requests to not access sensitive data.

The only real way to prevent an LLM agent from exfiltrating secrets is to make it physically impossible for the agent to access those files—via file permissions, containers, or VMs—not through a polite ignore list.

Key Highlights
  • Issue #2847 requests a .codexignore file to prevent reading sensitive files, but many commenters argue this is insufficient.
  • Commenters emphasize that an LLM agent can circumvent ignore lists via indirect tool usage (e.g., grep, make).
  • Several users present concrete sandboxing solutions: bind-mounting repos into containers, using user namespaces, or running agents in dedicated VMs.
  • The discussion references tools like agent-box, rumpelpod, and Nix-based images to achieve proper isolation.
  • A recurring theme is the distinction between security (must be enforced by the OS) and hints for token optimization (where an ignore file could be acceptable).

Tokenmaxxing is dead, long live tokenmaxxing
⬆ 164 pts 💬 229 HN comments

The article tracks the evolution of 'tokenmaxxing'—the practice of burning large quantities of LLM tokens, often mandated by executives to force AI adoption. The author argues that while the initial incentive-driven wave (e.g., Meta tying performance to token usage) is fading due to rising API costs and CFO scrutiny, a new, more sustainable form is emerging. This is driven by 'compounding correctness': the phenomenon where increased token spend yields proportionally better outcomes, especially in security (e.g., Anthropic's Mythos model, where AISI found no diminishing returns up to 100M tokens) and in 'loop engineering'—running agents in continuous loops without human supervision. The piece positions this as a regime shift from the earlier 'compounding error' era, where more tokens often led to worse results.

Key data points include the cost asymmetry in security: to harden a system, defenders must outspend attackers on tokens, echoing proof-of-work. Open models like GLM 5.2 ($1.4/M input tokens) are highlighted as cost-effective alternatives to frontier models like Opus 4.X ($5/M input). The article also covers the geopolitics of AI access, noting the US government's selective release of Mythos and the preview of OpenAI's GPT-5.6 series (Sol, Terra, Luna) with government oversight. The author concludes that tokenmaxxing will return in a new form, anchored by open models and 24/7 agent loops, despite temporary rollbacks at big companies.

“To harden a system you need to spend more tokens discovering exploits than attackers will spend exploiting them. It is a system that echoes cryptocurrency’s proof of work.”

  • Tokenmaxxing evolved from executive mandates to a new paradigm driven by 'compounding correctness'.
