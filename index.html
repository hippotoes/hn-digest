#2
GLM-5.3 is now open-weight
⬆ 732 pts 💬 244 HN comments

Z.ai has released GLM-5.3 as an open-weight model on Hugging Face, a ~753B-parameter mixture-of-experts text-generation model stored in FP8. The safetensors files total roughly 755GB, about half the size of GLM-5.2's 1.51TB BF16 checkpoint, thanks to FP8 experts. Despite the compression, the model posts strong benchmark numbers: 88.2 on Terminal-Bench 2.1, 66.9 on Deep Swe, and 62.5 on HLE with tools. Community insiders note that GLM-5.3 reuses the same base model as 5.2, implying the gains come primarily from post-training—better verifiers, environments, and training trajectories. The model is available immediately on Together, Fireworks, Baseten, and zai-org's own endpoint, with tool calling enabled and a customizable reasoning-effort chat template.

The HN reaction is unusually enthusiastic: developers describe it as 'feels like Opus 4.8, in the best possible way,' and many report using it as their primary coding model. The Flash variant draws particular praise for value, though cost and speed complaints persist—some see $0.30+ runs vs DeepSeek's $0.08 and inconsistent token rates. Locally, a 512GB M5 Ultra could run a 4-bit quant, but commenters question the tokens-per-dollar math vs cloud APIs. There is also unease about safety ('less touchy' around exploits) and geopolitics: some celebrate the competitive pressure from Chinese open weights, while others anticipate regulatory clampdowns. Overall, GLM-5.3 marks a moment where open-weight models are no longer a generation behind the frontier—at least for coding and agentic tasks.

'Feels like Opus 4.8, in the best possible way' — and with 88.2 on Terminal-Bench 2.1, GLM-5.3 is the first open-weight model many HN devs trust as their primary coder.

Key Highlights
  • Open-weight release of ~753B-parameter MoE model in FP8, ~755GB, half the size of GLM-5.2.
  • Scores 88.2 on Terminal-Bench 2.1, 66.9 on Deep Swe, and 62.5 on HLE with tools.
  • Same base as GLM-5.2; gains attributed to post-training, verifiers, and environments.
  • Multiple inference providers live (Together, Fireworks, Baseten, zai-org); DeepInfra first on OpenRouter.
  • Debates around local hardware, pricing/speed, safety, and US-China open-weight competition.

#9
I accidentally turned LLM memory into program analysis
⬆ 189 pts 💬 52 HN comments

Jordy Zomer's essay describes an accidental convergence: trying to give LLMs longer-term memory for vulnerability research led him to build a Datalog engine, Lemmalog. The core frustration is not that models forget facts, but that invalidation doesn't propagate - when an observation is disproved, every conclusion derived from it should become invalid. Zomer reframes this as program analysis: LLMs extract messy observations into structured facts, and a deterministic Datalog-style engine maintains derived facts, tracks provenance, supports retractions, and even records validity intervals. This lets an investigator ask 'why is this believed?' and automatically avoids the classic failure where a model confidently asserts something that was already ruled out. 'You can almost think of the whole system as a slightly strange compiler' - the LLM is the front-end, Lemmalog is the analysis engine.

Benchmarks give substance to the idea. On LongMemEval, Lemmalog reaches 0.463 F1, under PropMem and SimpleMem but more than double GPT-4.1 full-context (0.197) while using ~38x fewer tokens per question (2,700 vs 104,000). On LoCoMo, it lands at 0.533 F1, third among memory systems behind PropMem and OpenClaw. The most striking category wins are Knowledge Update (0.579 vs PropMem's 0.528 and full-context's 0.202) and adversarial false-premise questions (0.707 vs 0.509 full context) - a structured store can simply say 'no' when no supporting fact exists. Zomer also shares hard-won lessons: aggressive 'don't answer unless supported' prompts caused 32 refusals, and a plural stemmer bug silently killed counting questions. The takeaway is that memory involves two separate problems - relevance retrieval and truth maintenance - and only the first should be left to vector search.

On knowledge-update questions, Lemmalog scored 0.579 versus 0.202 for full-context GPT-4.1, while using 38x fewer tokens per question.

Key Highlights
  • LLM memory fails because invalidating derived conclusions doesn't propagate; Datalog's provenance tracking solves this.
  • Lemmalog splits the problem: LLM extracts fuzzy facts, deterministic engine maintains them.
  • Retractions, support counting, and validity intervals allow maintaining current truth vs history.
  • Benchmarks: LongMemEval 0.463 F1 (2x full context with 38x less context), LoCoMo 0.533 F1; tops knowledge-update and adversarial questions.
  • Two problems under 'memory': relevance retrieval (vector DB) vs truth maintenance (Datalog).

#6
Just the rumour of a bug is enough to find an exploit these days
⬆ 347 pts 💬 115 HN comments

Anil Madhavapeddy's cohttp 6.3.0 security fix for a path traversal vulnerability was barely opened as a public PR before his live server began fielding percent-encoded probe requests. That observation underpins the post's central claim: conventional OSS embargoes are obsolete because agentic LLMs need only a rumor of a bug to autonomously discover and weaponize it. Citing Fang et al., Madhavapeddy notes that GPT-4 agents exploited 87% of a 15-vulnerability benchmark when given a CVE description, versus 7% without; two years later, the mean time to exploit has gone negative at -7 days, meaning exploitation now precedes the patch. He also demonstrates that his own agent could produce a working exploit in under a minute from just a hint—turning the traditional secrecy-based disclosure model on its head.

The consequences are concrete: rclone's maintainer Nick Craig-Wood reports a surge from ~20 security disclosures in a decade to 40 in the past month, many machine-generated. A May 2026 paper on 'bugonomics' argues the bottleneck is defender remediation throughput, not exploit generation. Madhavapeddy proposes three responses: (1) truly private patch development, though GitHub's temporary private forks break CI and only allow one PR; (2) continuous, rapid shipping with better packaging and scanning—citing Chrome's twice-weekly security updates and the Linux kernel's 7-day deferral; (3) protocol-layer virtual patching, e.g., normalizing percent-encoded paths, distributed outside commercial CDNs. He also calls for a web-of-trust for OSS contributors. The underlying tension: infrastructure that once relied on obscurity must now assume the attacker has a compatible reasoning engine.

Mean time to exploit is -7 days—exploitation now precedes the patch, and a public PR can attract live probes within ten minutes.

  • Opening a public fix PR attracted live exploit probes within ~10 minutes; an agent locally produced an exploit in under a minute.
  • LLM agents given a CVE description compromised 87% of vulnerabilities vs 7% without; mean time to exploit is now -7 days.
  • Security embargoes are obsolete: just a rumor supplies enough search direction for automated attackers.
  • Maintainer capacity is the bottleneck: rclone went from ~20 disclosures in a decade to 40 in one month.
  • Proposed countermeasures: private patch workflows, continuous shipping, virtual patching at the protocol layer, and a web-of-trust for OSS.

GUIs should be fully keyboard-driven
⬆ 888 pts 💬 440 HN comments

The article directly challenges a recurring HN argument that TUI (terminal user interface) applications should be preferred because they are keyboard-driven. The author, Charalampos Kardaris, argues this confuses a current inadequacy with an inherent limitation: there is nothing about GUI frameworks that prevents full keyboard navigation. He cites the GNOME Human Interface Guidelines, which explicitly state that every action possible with a pointing device must also be possible with the keyboard. He also notes that keyboard support is a matter of developer will, not feasibility—he implemented comprehensive keyboard shortcuts in his own first GUI app, Klisi. The deeper technical context is that keyboard-driven interaction is an accessibility baseline and a usability multiplier, and while TUIs have historically been better at it, GUI toolkits offer equal or greater potential when properly used.

Some terminal loyalists, like jolmg, highlight TUIs' inherent text-selection advantages, but orbital-decay counters that many modern TUIs break even basic copying—a sign neither side has a monopoly on keyboard ergonomics.

#3
Htmx 4.0
⬆ 715 pts 💬 177 HN comments

Htmx 4.0.0 marks a significant but careful evolution of the hypermedia-oriented library. Released after eight months, it keeps the 2.x API mostly intact but makes three major changes: attribute inheritance becomes explicit via the `:inherited` suffix, event names are normalized to the `htmx:phase:action` pattern, and history restoration no longer relies on localStorage, instead re-fetching pages on back-navigation or using the opt-in `hx-history-cache` extension. Internally, htmx replaces XMLHttpRequest with the fetch() API, a change that enables modern streaming extensions for SSE, WebSockets, and multipart responses. The new `<hx-partial>` tag and built-in morph swaps (idiomorph) expand server-driven UI updates without writing client-side JavaScript. Despite being a major version, the team intentionally keeps 2.x as the NPM `latest` until early 2027 to avoid breaking unspecified CDN users, and they symbolically skipped v3 entirely—a joke stemming from their earlier promise never to release a breaking version 3.

The release includes practical upgrade tooling—`npx htmx.org@4.0.0 upgrade-check`—to flag code needing `:inherited`, renamed attributes like `hx-ignore`, and old event names. It also ships LLM-oriented 'skills files' for guidance, debugging, extension authoring, and upgrades, reflecting the project’s willingness to meet the agentic-coding era head-on. Comment sentiment is largely enthusiastic: users on Go+SQLite and Rails stacks describe replacing Turbo/Hotwire, while one commenter notes htmx pairs well with agent-driven development because 'coding agents are exactly as good as your test coverage.' Skeptics from Angular/.NET backgrounds counter that htmx forces a return to server-side presentation concerns, and the project’s creator, Carson Gross, openly concedes that LLMs may hurt adoption of small libraries. The broader HN reaction is a mix of genuine appreciation, CEO-of-HTMX jokes, and debate over htmx’s role in a frontend landscape increasingly shaped by AI code generation.

Htmx 2.x stays `latest` on NPM even as 4.0 ships, because the team doesn't want to force-upgrade users relying on non-versioned CDN URLs—a rare act of upgrade empathy.

Key Highlights
  • Attribute inheritance becomes explicit via `:inherited` suffix; `hx-disinherit` is no longer needed.
  • Internal migration from XMLHttpRequest to fetch() enables new streaming extensions (hx-sse, hx-ws, hx-multipart) and hx-download.
  • History now avoids localStorage by default; opt-in `hx-history-cache` extension restores sessionStorage caching.
  • New built-in morph swaps via idiomorph and `<hx-partial>` tag make multi-target HTML updates easier.
  • 4.0 ships an upgrade checker and LLM skills files; 2.x stays NPM `latest` until early 2027.

Inception-style curved map for turn-by-turn directions
⬆ 540 pts 💬 181 HN comments

Orbify's demo presents a navigation interface that warps the map into an Inception-style curved perspective, aiming to combine the contextual overview of a top-down map with the spatial immediacy of a first-person view. Built on the PlayCanvas engine and protected by a pending European patent (PCT/EP2026/058725), the concept garners fascination for its clever fusion of 2D and 3D cartography. However, the Hacker News discussion quickly pivots from novelty to critical scrutiny: many commenters point out that the core visual metaphor predates both the film and the startup—citing Berg London's 2009 'Here and There' poster, Saul Steinberg's 1976 New Yorker cover, and even Animal Crossing's rolling-log effect. The fundamental challenge highlighted is cognitive: while the projection elegantly bends road geometry to show the next turn, it sacrifices distance estimation and forward visibility, especially after sharp turns, and induces motion sickness in a significant fraction of users.

The community response is strongly polarized. Advocates like krm01 call it 'surprisingly useful' and pmkary praises it as 'Bret-Victorian magic,' while detractors joke about 'Nausea as a Service' and report immediate physical discomfort: rootusrootus wrote, 'the constant feeling of going downhill would be off-putting to me.' Technical suggestions abound—orienting the camera toward a point '10 seconds from now' (albrewer), reducing the spherical distortion to one-third (vessenes), or elevating the camera slightly (dwd). Patent concerns dominate another thread, with users citing prior art and questioning the validity of software patents in Europe. The demo itself proved fragile under load, with several users reporting crashes at 90% loading; developer Orbify_Karsten acknowledged '200 people trying the demo at the same time.' Despite 540 points and 181 comments, the consensus remains unresolved: a brilliant idea that may not be ready for real-world driving.

One HN commenter summarized a widespread reaction: “I'm not normally prone to motion sickness, but the change of perspective during a turn is quite unpleasant.”

#8
Migrating to HTTPX2
⬆ 204 pts 💬 92 HN comments

OpenAI's Python SDK has migrated its HTTP client layer from httpx to HTTPX2, a fork created in response to the original library's stagnated development and looming 1.0 breaking changes. The migration affects default clients, custom transports, TLS trust stores, and type annotations. While the SDK maintains backward compatibility for simple API calls, applications using custom auth, event hooks, or request mocking must adopt HTTPX2 objects. Anthropic made the same move weeks earlier, signaling an industry trend among AI vendors to decouple from httpx's governance risks. The change also shifts TLS certificate validation from certifi to the operating system's trust store, a subtle but potentially breaking alteration for containerized and corporate environments.

The migration guide provides an explicit escape hatch: legacy httpx clients remain supported at runtime, but require cast(Any, ...) because public type annotations now expect httpx2. That type-level break forces integration libraries like RESPX to update.
