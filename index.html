Attention Residuals
⬆ 171 pts 💬 22 HN comments

Attention Residuals (AttnRes) propose a novel drop-in replacement for standard residual connections in Transformers, addressing a critical flaw in deep models: uniform accumulation of layer outputs with fixed weights in PreNorm architectures leads to unbounded hidden-state growth and progressive dilution of layer contributions. By replacing this with softmax attention over preceding layer outputs, AttnRes enables each layer to selectively aggregate earlier representations via learned, input-dependent weights, using a single pseudo-query per layer. This content-aware mechanism enhances gradient flow and mitigates the vanishing signal issue, foundational for scaling Transformer depth without performance degradation, drawing parallels to adaptive gating in recurrent networks.

Implementation-wise, Block AttnRes partitions layers into groups (e.g., ~8 blocks) to reduce memory overhead from O(Ld) to O(Nd), making it practical for large-scale training. Results show consistent outperformance: it matches baseline loss with 1.25x less compute and achieves gains like +7.5 on GPQA-Diamond for reasoning and +3.1 on HumanEval for code generation. Training dynamics improve with bounded output magnitudes and uniform gradient distribution. Societally, this advances efficient AI development, potentially lowering barriers for consumer hardware inference and accelerating research iterations, as highlighted by the article's emphasis on 'drop-in replacement' and scalability.

Block AttnRes recovers most of Full AttnRes's gains while serving as a practical drop-in replacement with marginal overhead, reducing memory from O(Ld) to O(Nd) and enabling up to 20% compute savings in equivalent performance.

Key Highlights
  • Standard residual connections in Transformers cause hidden-state growth and layer dilution with depth
  • AttnRes replaces fixed accumulation with attention over previous outputs for selective, content-aware aggregation
  • Block AttnRes reduces memory complexity for scalability while retaining performance benefits
  • Demonstrates improvements on benchmarks including +7.5 on GPQA-Diamond and +3.1 on HumanEval
  • Mitigates PreNorm issues by bounding outputs and distributing gradients more uniformly across layers

We rewrote our Rust WASM parser in TypeScript and it got faster
⬆ 193 pts 💬 110 HN comments

The article details a performance optimization journey where the OpenUI team migrated their Rust-based WebAssembly (WASM) parser to TypeScript, achieving significant speedups. Initially, the parser—designed to convert an LLM-generated DSL into React components—faced latency issues due to the WASM-JS boundary tax. The core problem wasn't computational; Rust's parsing was efficient, but each call incurred overhead from serializing data to JSON strings and copying them across runtime boundaries. This boundary crossing, involving allocations and memory copies, dominated execution time, highlighting a common pitfall in web performance where interop costs outweigh language-level optimizations. The pipeline included six stages like lexing and AST resolution, but the focus shifted to data transfer inefficiencies rather than raw parsing speed.

Benchmark data revealed that the TypeScript rewrite eliminated boundary overhead, reducing per-call latency from 20-61µs to 9-19µs, a 2.2-4.6x improvement. However, a deeper algorithmic issue persisted: streaming parsing had O(N²) complexity due to re-parsing entire accumulated strings per chunk. The fix implemented statement-level incremental caching, which cached completed ASTs and only re-parsed in-progress statements, reducing full-stream costs by 2.6-3.3x. Key quotes like 'The overhead was entirely in the boundary' and insights on WASM's ideal use cases—such as compute-bound tasks with minimal interop—underscore broader implications: this case study cautions against premature WASM adoption and emphasizes profiling-driven optimization in modern web development, where JIT-compiled JS can outpace WASM for frequent, small data exchanges.

Rewriting from Rust WASM to TypeScript eliminated the WASM-JS boundary tax, reducing per-call parsing latency by 2.2-4.6x, while an algorithmic fix for streaming lowered total costs by 2.6-3.3x.

Key Highlights
  • WASM-JS boundary serialization costs dominated performance, not Rust's parsing speed.
  • Direct object passing via serde-wasm-bindgen increased latency due to fine-grained runtime conversions.
  • TypeScript elimination of boundary overhead achieved 2.2-4.6x faster per-call parsing.
  • Algorithmic fix from O(N²) to O(N) via statement-level caching reduced streaming costs by 2.6-3.3x.
  • WASM is best for compute-heavy tasks with rare interop, not frequent small data exchanges.
