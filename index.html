#4
The end of Microsoft Research's AI Frontiers group
⬆ 477 pts 💬 290 HN comments

John Langford, creator of Vowpal Wabbit and a founding lead of Microsoft Research's AI Frontiers (AIF) group, published a post-mortem on its dissolution. AIF was formed in 2023 in the wake of ChatGPT on an explicit premise: single-investigator research had become structurally uncompetitive, because one person could neither assemble strong-enough baselines nor move fast enough to demonstrate an idea's value against well-resourced groups. The ~50-person org deliberately sat in the "messy middle" between top-down and bottom-up, producing agent infrastructure (AutoGen orchestration, the Fara computer-use agent) alongside fundamental work in NYC on the Next Latent objective, Dion3 (an improved Muon optimizer), and the Full Bandwidth Transformer, which exploits recursion for efficiency. AIF also built a default-shared monorepo containing an edge-scale pretraining codebase — Langford notes at least four parallel, non-shared pipeline efforts inside MSR, a concrete instance of duplicated infrastructure cost. In early September the group was reorged into Microsoft AI (MAI).

The failure mode Langford describes is philosophical, not merely budgetary: MAI's ex-Inflection leadership treats scale as the primary axis, with data engineering as the core discipline, because returns to scaling are far more predictable than returns to research. Langford's counter-argument is quantitative — ByteDance experiments suggest a Full Bandwidth Transformer variant may match a model of twice the size, and halving training and inference cost against an industry capex approaching a trillion dollars is an enormous expected value. AIF's leadership team largely departed. Langford declines to return to MSR for two stated reasons: research with no path to deployment, and a perceived collapse of MSR's implicit contract — "do good work and good things happen" — since good work was non-consensually reorged away. The commentariat generalizes this beyond one group: multiple threads assert MSR as an institution is being parted out, with the Kevin Scott-era division quietly dissolved and research placed under Azure Security leadership.

"The core philosophy there is scaling, and aggressively not research" — Langford's diagnosis of MAI, paired with his ROI argument that a Full Bandwidth Transformer variant matching 2x model size could halve training and inference costs across an industry deploying close to a trillion dollars.

Key Highlights
  • AI Frontiers (~50 people) was reorged into Microsoft AI in September, whose ex-Inflection leadership prioritizes scaling and data over exploratory research.
  • AIF produced AutoGen and the Fara computer-use agent, plus fundamental work on the Next Latent objective, Dion3, and the Full Bandwidth Transformer.
  • Langford left rather than return to MSR, citing research with no path to use and a broken implicit contract of 'do good work and good things happen'.
  • Commenters allege this is part of a broader dismantling of MSR, including the quiet dissolution of the T&R division under Kevin Scott.
  • A visible counter-argument holds that predictable returns to scale make research funding irrational in a race, and that AIF had years to 'show the money'.

#5
Claude Code's "Don't Ask Again" exposes passwords in 1,122 public GitHub files
⬆ 470 pts 💬 330 HN comments

Apiiro's researchers crawled public GitHub for `.claude/settings.local.json` and `.claude/settings.json` files and found 1,122 files across roughly 1,105 repositories in which a persisted permission rule itself contained a live credential. The mechanism is mundane and instructive: agentic permission systems implement "Don't Ask Again" by serializing the exact approved command string into a project-scoped allowlist. If the human approved `curl -H "Authorization: Bearer sk-..."`, or a `psql`/`mysql` invocation with an inline password, that literal command — secret and all — lands on disk in a JSON file. Anthropic documents that this file is not meant to be committed, and Claude Code auto-gitignores it when the agent creates it, but git enforces no such convention. The result converts what was designed as a private, ephemeral approval into a durable, replicable artifact that travels with every clone and fork and becomes public the moment the repository does.

The most damning data point is provenance: in 539 of the 1,105 repos containing a genuine secret, the leaking file was touched by a commit co-authored by Claude, naming models from Sonnet 4.5 through Opus 5.5 — the agent itself staged and committed the credential store that recorded its own permissions. Anthropic's Boris Cherny responded directly, conceding Claude Code has historically not done secret scrubbing ("there are many good tools for that") but that the team is investigating, and noting the affected files were manually created and checked in rather than machine-gitignored. A GitHub issue (13106) had reportedly been filed Dec 5, 2025 and auto-closed. The story's real payload is architectural: shell-command allowlists are a lossy, plaintext encoding of intent, and any approval UI that captures secrets into committed config is a secret leak with a delay of one `git add .`.

In 539 of the 1,105 affected repositories, the file containing the credential was modified by a commit co-authored by Claude itself — the agent helped publish the record of the permissions it was granted.

Key Highlights
  • "Don't Ask Again" persists the full approved command string — including any inline token or password — into `.claude/settings.local.json`, a file Claude auto-gitignores only when it creates it itself
  • Apiiro found 1,122 such files in public repos; 539 of the ~1,105 repos with a real secret had the file changed by a Claude-co-authored commit
  • Anthropic's Boris Cherny confirmed Claude Code does no secret scrubbing today but said the team is looking into prevention
  • Critics note the headline overstates causality: the leak requires a user to commit local settings containing secrets, i.e. pre-existing bad OPSEC
  • Proposed mitigations span pre-commit scanning (gitleaks), secret-manager CLIs with biometric approval, API proxies, and per-task ephemeral VMs with `--dangerously-skip-permissions`

#1
Need for Speed Underground 2 online in the browser
⬆ 1050 pts 💬 265 HN comments

Need for Speed Underground 2, EA's 2004 street-racing blockbuster that sold some 11 million copies, now runs in Chrome and Firefox courtesy of a fan project at nfsu2.xyz. The technical foundation is a static recompilation pipeline: the game's original x86 machine code is translated ahead-of-time into C, which is then compiled to WebAssembly and rendered through WebGPU — a lineage the authors trace through Talha Müderrisoğlu's NFSU2Recomp, itself descended from N64: Recompiled and XenonRecomp. The fork pins to the MIT-licensed version of 16 October 2026, and the shipped bundle is reportedly under 10 MB of wasm. The project advertises up to 120 fps widescreen, controller, wheel and touch support, cloud saves keyed to a username, and — crucially — reconstructed online free roam and races, features EA shut down years ago.

What elevates this above a demo is the social layer rebuilt on top of dead infrastructure: persistent crews (up to four players, colour-coded and mutually visible), friend world-joining, quick chat, and ghost mode. Community reports describe hundreds of cars spawning simultaneously, burning out and honking — emergent chaos in a mode that never had it. Translations are bundled via KyoriAsh's Multi 13 languages mod; the site is explicit about funding (Ko-fi, Discord role only, no microtransactions). The friction points are real: Linux users need --enable-unsafe-webgpu and Vulkan/ANGLE flags, and commenters note the sandbox trade-off. Meanwhile the hosted assets raise an unresolved legal question that dominates discussion, since the game remains commercially unavailable.

The PC game's x86 code is statically recompiled to C, then to WebAssembly — shipping an entire 2004 AAA racer in under 10 MB of wasm, with EA's long-dead online free roam rebuilt from scratch.

  • Linux users must enable unsafe WebGPU flags; commenters document sandbox-preserving workarounds
  • Hosting original game assets plus accepting Ko-fi donations is widely seen as legal exposure
  • Commentary frames abandonware as a cultural-preservation failure and asks why comparable modern racers don't emulate the formula

#3
What I run on my $10 USD OpenStick homelab
⬆ 662 pts 💬 121 HN comments

The OpenStick is a $10 (shipped) repurposed MSM8916-class 4G LTE dongle that turns out to be a complete, passively cooled Linux server: four ARM Cortex-A53 cores at 1 GHz, 512 MB of RAM (~450 MB usable after firmware reservations), 4 GB eMMC, Wi-Fi 4, GPS, and a programmable LED. The author flashes Debian onto it — the vendor image is a Linux/Android hybrid, but the kernel is mainline — and gets systemd and rootless Podman, i.e. a silent, sub-watt home server. The post's real contribution is not the hardware novelty but the discipline it forces: every service is documented with its resident-set-size, and the whole article reads as an exercise in memory budgeting where a 20 MB observability stack is a design decision, not an afterthought. It is a useful counterweight to the assumption that self-hosting begins at 16 GB and a hypervisor.

The service ledger is the substance: CastSponsorSkip at 5–10 MB strips sponsor segments from Google Cast sessions; a custom AdGuard Home fork holds memory constant (~40 MB) regardless of blocklist size and blocks roughly 60% of DNS queries; Zeroclaw, an LLM agent harness, idles at ~3 MB RSS versus the 1 GB+ the author's previous OpenClaw setup consumed on Kubernetes; Cloudflare Tunnel, Beszel (10 MB agent + 10 MB server), Dozzle, Gatus, Fusion RSS, Shiori (which archives bookmarks before link rot kills them), and Diun round it out. Backups go to Backblaze via restic nightly. The author grants Zeroclaw a root shell over the stick — deliberately bounded blast radius — and monitors it over Telegram from the mountains, which is precisely where the comment thread's sharpest dispute begins.

A quad-core 1 GHz / 512 MB server hosted hundreds of concurrent LAMP users in the Pentium-II era — today the same spec sheet fits in a $10 USB dongle that draws almost nothing and makes no sound.

Key Highlights
  • A $10 LTE dongle (MSM8916, 4× Cortex-A53 @1GHz, ~450MB usable RAM, 4GB eMMC) runs mainline-kernel Debian with systemd and Podman, passively cooled and silent.
  • The article is structured as a per-service RSS budget: CastSponsorSkip 5–10MB, AdGuard Home fork 40MB (constant regardless of blocklist size), Zeroclaw ~3MB idle, Cloudflare Tunnel 8–20MB, Beszel 20MB, Gatus 10MB, Fusion 22MB, Diun 9MB.
  • Zeroclaw replaces a 1GB+ OpenClaw-on-Kubernetes deployment; the author grants it root on the stick, arguing the limited blast radius justifies the convenience of Telegram-based ops monitoring.
  • Commenters argue the 'limited blast radius' premise is wrong: the device is the DNS resolver and the Cloudflare ingress point, so agent compromise reaches the whole network.
  • Sourcing is fragile — the writer admits the price is now ~$20, the hardware repo is four years stale, and one commenter claims to hold ~300 units plus IMEI-preserving reflash tooling.

#6
Every Windows 11 app should kill Electron, and Discord just showed why
⬆ 378 pts 💬 377 HN comments

Discord is using its unreleased “Phoenix” client to make a public argument against Electron. In a widely shared cold-start clip, CTO Stanislav Vishnevskiy shows the Rust build reaching a loaded friends list while the Electron client is still stuck on its dark loading window and “Starting” modal. The technical significance is that Discord did not choose a Tauri-style HTML wrapper around WebView2. It chose GPUI, Zed’s GPU-accelerated hybrid immediate/retained-mode Rust UI framework, so the interface is drawn without HTML. Electron’s bundled Chromium and Node.js multi-process runtime is replaced by Rust’s non-garbage-collected memory model, with the native webview retained only for YouTube embeds and Activities. Mobile is also moving off React Native toward shared Rust, while the web app keeps HTML but moves logic to WebAssembly. The bet is code reuse without shipping a browser engine in every app.

The headline numbers are aggressive but early: 290.2MB of RAM with two accounts signed in, roughly 70% below Discord’s stated sub-1GB normal usage and far below the 1–2GB idle footprint the article reports for Electron. Discord had already tried incremental fixes: its Electron 42 upgrade cut median CPU by about 17% but regressed p50 memory by roughly 4%. The new client also eliminates the “Starting” update modal by auto-updating in the background, which attacks a major cold-start pain point. Access and security are still being worked out: the client keeps login tokens in the system keyring, and Discord says accessibility and security matter as much as performance. The broader impact is pressure on WhatsApp and Teams, whose WebView2 wrappers have been measured near 1GB idle, and a memory-price squeeze that makes Electron’s overhead newly expensive. HN’s reaction is far less triumphant than the article: commenters question the benchmark, defend Electron’s team economics, and warn that GPUI’s accessibility and IME story may not match the web stack.

Discord’s Rust client reportedly idles at 290.2MB with two accounts signed in—about 70% below its sub-1GB norm—and loads the friends list before the Electron client finishes its “Starting” screen.

#8
Show HN: Coldframe, a honeypot that poses as a supermarket fridge controller
⬆ 258 pts 💬 62 HN comments

Coldframe is a single-file, standard-library-only Python honeypot that impersonates two classes of supermarket refrigeration supervisor — the Danfoss AK-SM 800A and the Copeland/Dixell XWEB 500 — devices that were compromised in 2026 by attackers using factory-default credentials and stale firmware to trigger defrost cycles against internet-facing estate. Its novelty is not the interaction depth (it is deliberately shallow) but fingerprint fidelity: the Danfoss persona replays the nginx Server header and header ordering observed on real units, the StoreView page title, TLS 1.2-only negotiation, and a per-build self-signed certificate for CN=DanfossSM800A; the Dixell persona suppresses the Server header entirely and mirrors XWEB EVO's security-header set, asset paths and page size. Each persona accepts the documented weak logins (Supervisor/12345, Admin/Admin) plus a correct CVE-2025-41450 code-of-the-day, then hands the attacker a fabricated dashboard of refrigerated cases with defrost buttons — logging every control action as an event rather than executing anything.

Detection is the point: requests matching known public exploits get tagged in the JSONL log — CVE-2023-25914 get_file path traversal, CVE-2023-25915 load_cert command injection, CVE-2025-41452 nginx header overwrite, CVE-2021-45420 XWEB upload paths and CVE-2026-25085 auth_mode bypass — with CVE-2025-41450 additionally noting whether the attacker computed the correct code. An optional Modbus TCP listener serves fake case temperatures, setpoints and a defrost register, off by default because real AK-SM units only speak Modbus to their own case controllers. Deployment is a cloud-init one-liner onto a $4 droplet, running rootless with --userns=auto, read-only root, --cap-drop=ALL, pids and memory caps, and log rotation; the README is candid that public code is fingerprintable and that static paths and some XML response shapes are plausible fabrications where real units were not observable.

The community split three ways. Practitioners questioned whether Shodan-derived fingerprints and cloud-hosting WHOIS defeat the disguise before an attacker ever connects — 'i think it would be pretty trivial to determine the box is a pot from whois' — and argued honeypots pay off for mass-exploited targets, not targeted intrusions. A loud faction flagged the README and submission as LLM-written prose ('That text is Claude', 'their prose still sucks balls') alongside a Hacker-News-badge complaint. A third group pushed the institutional argument the author himself raised: a supermarket has no security team, so patching, VPNs and strong passwords must ship as vendor defaults or insured risk, not as an expensive maintenance contract.

Coldframe doesn't just log failed logins — it validates whether an attacker actually computed the correct CVE-2025-41450 'code of the day' after completing a getauth with eds_only or quantum_only, turning the honeypot into an exploit-proficiency sensor rather than a connection counter.

GitHub New pull request overview page in public preview
⬆ 159 pts 💬 108 HN comments

GitHub has shipped an opt-in public preview of a redesigned pull request Overview page, its first substantive rethink of the PR surface in years. The changelog frames the problem narrowly: on long PRs, determining what blocks a merge requires scrolling past dozens of timeline events to reach the merge box, and then reasoning about the next action yourself. The new page hoists a compact "readiness summary" to the top — checks, approvals, unresolved comments — and re-engineers the merge box to convey the same signals in under half the space, with drill-down affordances routing to failing checks, pending reviewers, or the relevant threads. GitHub also adds catch-up mechanics: filtering to unresolved conversations or comments you authored, newest-first comment sorting, an upper-right activity summary, and header actions to mark a draft ready or close the PR, permission-gated. Rollout is gradual, opt-in via a header button, with a one-click return to the classic view.

The strategic context matters more than the diff. GitHub is responding to a decade of stagnant PR UX and to competitive pressure from Graphite, Gerrit-style review flows, and a proliferating class of CLI/agent review tooling — while simultaneously absorbing a volume shock from AI-generated pull requests. The community response (159 points, 108 comments) splits sharply along that fault line rather than on the redesign itself. One commenter describes "staring at the raw diff of 35 PRs" and "being called the bottleneck" while "agents are hammering PRs out left and right"; another reports "Merge when ready" succeeding only "60-70%" of the time, and a third migrated to an external merge queue where "P90 of merge queue entry started dropped from up to 40 minutes to 16 seconds." GitHub's own framing — "The merge box, distilled" — drew derision as LLM-flavored marketing copy, and skeptics noted the demand for long-PR navigation is itself generated by tooling, not by humans.

"Agents are hammering PRs out left and right, and yet here I am still staring at the raw diff of 35 PRs and end up being called the bottleneck." — the review bottleneck GitHub's redesign doesn't claim to solve.

Key Highlights
  • GitHub's new PR Overview page is an opt-in public preview that promotes a compact, redesigned merge box (checks, approvals, comments) into a readiness summary at the top of the page.
  • Added catch-up features include filtering to unresolved threads or your own comments, newest-first sort, an activity summary, and header actions for marking drafts ready or closing PRs.
  • Commenters report GitHub reliability regressions — 'Merge when ready' landing in the merge queue only 60-70% of the time, unreliable sidebar file links — which undermines any UX gain.
  • Critics argue the PR review model is structurally broken: comments drift from ground truth after later commits, 'load more' and collapsed threads break timeline reconstruction, and large diffs hide modified files.
  • Third-party and CLI/agent workflows (Graphite, trunk.io, CodeApprove, gh/tea plus agent review passes) are cited as already better organized than GitHub's PR page.

Making any integer with four 2s (2025)
Eli Bendersky's post revisits a recreational mathematics puzzle with genuine pedagogical depth: given exactly four instances of the digit 2, produce any target natural number using only permitted mathematical operations. The progression the article traces mirrors mathematical education itself — elementary arithmetic yields 1 through 6, exponents and factorials unlock 18, 28, 256 and 65,536, concatenation (treating '22' as two 2s) produces 26 and 444, and the notoriously stubborn 7 falls to the Gamma function via Γ(2)+2+2+2. Each escalation of allowed operations expands the reachable set, which is precisely the puzzle's appeal: it is less a single problem than a family of problems parameterised by what counts as a legal operator. The article's centerpiece is Dirac's general solution, which collapses the puzzle entirely. Nested square roots generate 2^(2^-n), and two successive base-2 logarithms yield -n, giving n = -log₂(log₂(√√…√2)). This uses three 2s, remedied by substituting 2 = √(2+2) in the logarithm's base. As Bendersky notes, 'the entity n doesn't actually appear anywhere — it's just a helper to count the number of repeated square roots.' The construction is a striking demon...
Roots Spend a Digit The most substantive objection holds that square root is not a free operator like + or ! because it carries an implicit 2 — 'you could also take the cube root or fourth root,' as hahajk puts it, so the index is a hidden digit. JumpCrisscross counters by analogy: 'Squaring is to multiplication as is the latter to addition. If roots are invalid then so should be multiplications,' arguing the objection proves too much and would unravel arithmetic itself. This cluster treats the puzzle as a formal-language question about what belongs in the operator alphabet, and disagreement centres on where the boundary of 'free' operations legitimately lies. (~10 users)
Peano Successor Trivialises A rival camp bypasses analysis entirely by invoking Peano arithmetic. shoo notes 'a direct trivial solution for any natural number using the successor function S(a) = a + 1' after encoding zero as 2+2-2-2, requiring 'no need for construction of rationals, irrationals, logarithms.' Another commenter nests seven S-applications around zero, and rav improves it to use the four 2s as S(S(S(S(S(S(S(2+2-2+2))))))). The shared insight — that the successor operator 'doesn't spend any numbers' — echoes Dirac's own trick, reducing the puzzle to counting rather than arithmetic. (~8 users)
Base-10 Concatenation Cheat bajard attacks a different loophole: writing 22 is 'cheating because 22 = 2*10+2 is arbitrary in base 10.' Under this reading, concatenation smuggles in a base, and 'if you write 22 in some base, you have to write the base, and that's an extra number.' This is a sharper critique than the square-root complaint because it identifies a hidden parameter rather than a hidden digit. It also implicitly indicts the article's own 26 = 22+2+2 and 444 = 222·2 examples, suggesting the puzzle's folk solutions are less principled than they appear. (~5 users)
