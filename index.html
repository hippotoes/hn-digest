Liquid AI reveals 8B-A1B MoE trained on 38T
⬆ 189 pts 💬 74 HN comments

Liquid AI released LFM2.5-8B-A1B, a Mixture-of-Experts model with 8B total parameters and 1B active, trained on 38 trillion tokens—a dramatic scale-up from its predecessor's 12T. The model extends the context window to 128K tokens and doubles vocabulary size to 128K for better tokenization of non-Latin languages, achieving compression gains of up to 238% for Thai. Architecturally, it retains the MoE, GQA, and gated short convolution blocks but adopts explicit chain-of-thought reasoning, leveraging the efficiency of few active parameters to boost quality without speed loss. Key innovations include a tokenizer expansion method that avoids full retraining, a doom-loop mitigation stage via preference optimization, and an avg@k-based RL reward to reduce hallucinations by sharpening the model's knowledge boundary. The result is a model that, despite its small footprint, matches or exceeds much larger models on instruction following and agentic tasks.

Benchmarks show LFM2.5-8B-A1B leading its size class: 91.84 IFEval (vs. 82.23 for Granite-4.0-H-Tiny), 88.76 MATH500, and 64.79 BFCLv3. On the AA-Omniscience Index, it scores -24.70, a dramatic improvement from -78.42, with a non-hallucination rate of 63.47% vs. 6.38% for its predecessor. Most striking is its inference speed: 253 tokens/s on an M5 Max laptop, 146 on AMD Ryzen AI Max+ 395, and 18.5K output tokens/s on a single H100 GPU. The model supports llama.cpp, MLX, vLLM, and SGLang from day one, enabling private on-device agents via the open-source LocalCowork demo, which chains 67 tools across 13 MCP servers on a single laptop with no cloud dependency. This release signals a shift toward capable, private, edge-hosted AI that can handle complex tool-use tasks interactively.

Show HN: Tiny-vLLM – high performance LLM inference engine in C++ and CUDA
⬆ 149 pts 💬 13 HN comments

The 'tiny-vLLM' project by jmaczan is a high-performance LLM inference engine implemented in C++ and CUDA, designed as a smaller, educational sibling of the popular vLLM. The engine loads a real Llama 3.2 1B Instruct model from Safetensors and executes a complete forward pass (prefill + decode) using custom CUDA kernels. Key features include KV cache, static and continuous batching, online softmax, FlashAttention-like computation, and PagedAttention. The project is unique in that its README serves as a full, lesson-based course—covering topics from floating-point representation (bfloat16) and Safetensors parsing to CUDA kernel engineering for RMSNorm, RoPE, and attention. The author intentionally derives ideas and math from scratch, positioning the repository as a resource for learners and educators. This approach demystifies the engineering behind LLM serving, which is often glossed over in favor of high-level frameworks.

The community response has been overwhelmingly positive, with many commenters highlighting the pedagogical value of the README. yu3zhou4 (the author) notes that the README is designed to help others build a mental model without needing to read the code directly. janalsncm says they 'clicked in to see how safetensors are loaded and just kept reading,' while tom-wal feels they 'learned twice as much in 10 minutes' compared to other resources. The project implements a full stack: tokenization, embeddings, 16 transformer layers with grouped-query attention, SiLU activation, and argmax decoding. A notable highlight is the author's statement: 'Physically, LLM is a file which contains a lot of float numbers,' encapsulating the demystification ethos. Despite the praise, one commenter (einpoklum) criticizes the lack of CUDA API return value checks, suggesting a trade-off between minimalism and robustness. Overall, the project resonates with engineers seeking a hands-on understanding of LLM inference internals.

Physically, LLM is a file which contains a lot of float numbers.

The author posits that AI coding tools are doing the same to programming at large—turning a craft into a commodity. The piece draws parallels to the Bauhaus movement, which embraced industrialization while preserving core material understanding, suggesting that developers must retain a deep grasp of fundamentals to avoid producing low-quality, inaccessible, or poorly performing software.

The article's highlight is the analogy of LLMs being an extension of Stack Overflow copy-paste, where fuzzy retrieval replaces deep understanding. It notes that businesses often tolerate poor quality because market success rarely correlates with software quality, citing slow websites and cookie banners as examples. The author warns that AI's leaky, non-deterministic abstractions require new skills to evaluate outputs. The community reaction is deeply divided: some celebrate reduced accidental complexity, others mourn the erosion of craft, and many debate whether this is a natural evolution or a crisis. The piece calls for a conscious integration of AI tools while maintaining a commitment to quality and user-centered design.

The best analogy for using LLMs is how Google search used to behave: a fuzzy lookup that requires skill to prompt effectively, but often yields results that work without deep understanding—until the abstraction leaks.

MCP is dead?
⬆ 236 pts 💬 208 HN comments

The article 'MCP is dead?' by Quandri challenges the prevailing hype around the Model Context Protocol (MCP), arguing that for day-to-day developer workflows, MCP introduces unnecessary overhead compared to existing CLI/API patterns. The core technical critique centers on context window consumption: with four MCP servers connected (Linear, Notion, Slack, Postgres), tool definitions alone consume 10.5% of a Claude 200K context window (16.5% for GPT-4o), with Linear's 42 tools accounting for ~12,800 tokens always loaded. This 'spreading all menus on the table upfront' analogy, combined with reliability issues like init failures, mid-session crashes, and per-call slowness (3x slower than direct REST API per Jira benchmark), suggests MCP is over-engineered for many use cases. The article proposes a CLI-first strategy and a 'Skills' pattern where tool usage instructions are loaded on-demand, embedding CLI commands directly. For example, a Linear issue lookup via MCP costs ~65x more tokens than a simple curl command (~12,957 vs ~200 tokens).

The community response reveals deep divisions. OpenAI's mxstbr counters that MCP's value lies not in the protocol itself but in its widespread adoption—practically every company is building MCP servers, including those without CLIs or external APIs. However, others like forloop note that MCP is just a branding for 'APIs LLMs can use,' potentially accelerating API creation. Several commenters highlight that the article's core complaint about context bloat is already addressed by Claude Code's deferred tool loading (85%+ reduction) rolled out months ago, deeming the analysis outdated. Sentiments range from 'MCP-as-marketing-box' cynicism to pragmatic acceptance for non-CLI services. The Skills pattern garners interest but faces sandbox limitations in Co-Work, while enterprise identity and OAuth evolution may define MCP's future. The debate underscores a tension between simplicity (CLI) and interoperability (MCP), with token economics looming as providers shift to metered billing.

MCP consumes ~65x more tokens than the CLI approach for a Linear issue lookup (12,957 vs. 200 tokens), illustrating unnecessary context waste.

Bijou64: A variable-length integer encoding
⬆ 228 pts 💬 79 HN comments

Bijou64 is a variable-length integer encoding designed primarily for security and performance, developed by Ink & Switch for the Subduction CRDT sync protocol. Its core innovation is achieving canonical representation by construction, eliminating the possibility of multiple byte sequences for the same integer. This is critical in signed protocols where an adversary could exploit non-canonical encodings (e.g., overlong LEB128) to bypass signature verification. The encoding uses the first byte as a tag: values 0–247 encode directly, while 248–255 indicate the number of additional bytes. An offset mechanism ensures a unique representation: for example, the two-byte encoding starts at 248, so 0xF8 0x00 represents 248, not 0. This removes the need for runtime canonicality checks, a common source of security bugs. Benchmarks show bijou64 decodes 2–10× faster than LEB128 on both ARM and x86, with near-vertical CDF curves indicating consistent latency, while encoding is generally faster except for certain small-value cases.

The performance advantage stems from three design choices: the first byte provides the total length in O(1), enabling immediate memory allocation; the payload is a single big-endian integer easily handled with CPU byte-swap instructions; and branch prediction is stable due to fixed tiers. For a uniform u64 distribution, bijou64 decodes 4096 values in ~3 µs vs. LEB128's ~30 µs. However, the encoding is slightly less compact for mid-range numbers (e.g., 0–247 is 1 byte, 248–503 is 2 bytes, while LEB128 uses 1 byte for 0–127 and 2 for 128–16383). The article argues that for most workloads, wire sizes are within a few percent. Community comments highlight trade-offs: SIMD performance concerns (kstenerud), the utility of non-canonical encodings for linkers (i2talics), the need for range checks on the 255 tag (dzaima), and comparisons with other varints like QUIC's length-prefixed scheme (raphlinus). The project is published on crates.io and provides a Wasm wrapper, targeting scenarios where canonicality and speed are paramount, such as in distributed systems and secure protocols.
