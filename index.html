Show HN: Are You in the Weights?
⬆ 366 pts 💬 215 HN comments

The site 'intheweights.com' allows users to input a name and receive a composite report from multiple large language models (LLMs) on whether and how they are represented in the models' training data. By querying models like GPT-4, Claude, Gemini, and Llama variants, it aggregates responses, classifies them by confidence, and surfaces both accurate recalls and clear hallucinations. Technically, the tool performs a linear combination of model self-reported confidence plus a cluster bonus, then ranks results. The operator notes cost optimizations such as using Kimi K2 for final clustering, indicating a non-trivial orchestration layer. This toy effectively turns a black-box knowledge probe into a public introspection tool, revealing how LLMs store and distort information about individuals, especially those with low internet footprints.

Community reaction is polarized: some users are delighted to be recognized (e.g., open-source contributors, HN regulars), while many more are alarmed by confident falsehoods. One comment reports being misidentified as a 'terrorist on the US sanction list'—a dangerous hallucination. Another notes that nearly all models incorrectly tag common names as football players or actors, revealing training data biases. The scoring and 'Strength' metric are criticized as opaque and potentially misleading. Amidst the fun, a deeper tension emerges: the site demonstrates both the impressive reach of LLMs and their propensity to generate plausible but fictional biographies, raising questions about identity, privacy, and the reliability of AI-sourced information.

“The false positives are extremely scary… I don't want to be bombed based on an LLM query.” — commenter amdivia, highlighting the real-world risk of confident hallucinations.

Key Highlights
  • Tool queries multiple LLMs to check if a person is mentioned in training data, using confidence aggregation and clustering.
  • Many users report accurate identification, especially in tech/open-source bubbles, reinforcing that LLMs reflect internet prominence.
  • Hallucinations are rampant: common false identities include football players, actors, and security researchers.
  • Privacy concerns emerge from false positives (e.g., being labeled a terrorist) and the implicit scraping of personal data.
  • Scoring methodology is questioned: strength and top % are based on uncalibrated model confidence, not true prevalence.

Zero-Touch OAuth for MCP
⬆ 207 pts 💬 75 HN comments

The Model Context Protocol (MCP) community has stabilized the Enterprise-Managed Authorization (EMA) extension, which shifts MCP server authentication from per-user OAuth flows to centralized identity provider (IdP) governance. Under the hood, EMA leverages the Identity Assertion JWT Authorization Grant (ID-JAG) token format — an IETF draft — to allow clients to obtain a short-lived access token without per-server consent screens. During single sign-on, the client acquires an ID-JAG from the IdP, then exchanges it for an access token from the MCP server's authorization server. This eliminates the friction of each employee manually authorizing every server, enforces consistent policy via group membership and conditional access rules, and prevents personal-enterprise account mixups. Early adopters include Okta (as the first IdP), Anthropic's Claude clients, Visual Studio Code, and major SaaS providers like Asana, Atlassian, and Figma.

The extension addresses a critical pain point in enterprise AI deployment: one commenter from C1 noted that MCP auth has been a 'huge pain point', while another implementing Entra ID described feeling 'like an idiot' due to the lack of Dynamic Client Registration support. The EMA flow is intentionally not MCP-specific—as anthropic maintainer 'dend' pointed out, ID-JAG can work for any workload. Okta's Aaron Parecki called identity 'a centralized governance plane' for the AI workforce. However, some commenters expressed unease about automatic authorization without user awareness, and others questioned the necessity of OAuth for CLI tools. The adoption by Okta, Microsoft, and others signals a shift toward enterprise-grade AI tool connectivity, though challenges remain for IdPs that don't yet support the required protocols.

"Authorize once, inherit everywhere: admins enable a server for the org. Users get it automatically, scoped to the groups and roles they already have."

Key Highlights
  • EMA centralizes MCP authorization through the organization's IdP, removing per-user OAuth consent screens.
  • Uses the ID-JAG token format (IETF draft), which is not MCP-specific and can be reused across other protocols.
  • Early adopters include Okta, Anthropic (Claude), Microsoft (VS Code), and several SaaS providers.
  • Addresses security gaps like inconsistent policy enforcement and personal-enterprise account mixing.
  • Commenters note significant friction with current OAuth implementations (e.g., Entra ID's lack of DCR), leading to workarounds like proxying OAuth flows.

I found 10k GitHub repositories distributing Trojan malware
⬆ 824 pts 💬 214 HN comments

A security researcher discovered over 10,000 GitHub repositories distributing Trojan malware. The repos are not forks but exact clones of legitimate projects, with all commits and contributors copied to appear authentic. Every few hours, a new commit deletes the previous one and adds a link to a zip archive containing a loader executable and a Lua DLL. VirusTotal detects the trojan only when the zip file is uploaded directly, not when scanning the link. The researcher built a script using GitHub Archive data to find repos updated 1–24 times daily, identifying 40,000 candidates, of which 10,000 matched the malicious pattern. These repos have existed for months, and GitHub only deletes those specifically reported.

The scale of this campaign—spanning at least 1.5 years—reveals a failure in GitHub's automated abuse detection. The malware, linked to the Disco trojan family, targets cryptocurrency wallets via Polygon RPC calls and screenshots exfiltration. Commenters note that attackers likely exploit SEO by cloning new repos that rank high for low-competition search terms. The pattern of frequent updates may also be designed to stay ahead of security algorithms and appear in 'trending' feeds. A commenter who reversed the binaries (overloadedop) found C2 infrastructure hosted in Latvia. The article's updates show GitHub only deleted repos from an initial list, not subsequent findings, underscoring a reactive, report-based moderation model.

25% of the 40,000 frequently updated repositories found by the script exactly matched the pattern, totaling 10,000 trojan-distributing repos.

Key Highlights
  • Over 10,000 GitHub repos distribute trojan malware via cloned projects with malicious README links.

.gitignore Isn't the only way to ignore files in Git
⬆ 439 pts 💬 137 HN comments

This article demystifies Git's file-ignoring capabilities beyond the ubiquitous `.gitignore`, revealing a hierarchical system that addresses different scopes: per-repository (`.gitignore`), per-repo local (`.git/info/exclude`), and per-user global (`~/.config/git/ignore`). The author emphasizes that while `.gitignore` is committed and shared, the other two files remain private, making them ideal for personal workflow files (e.g., editor configurations, local notes) or environment-specific artifacts (e.g., `.DS_Store` on macOS). The `git check-ignore -v` command is highlighted as a diagnostic tool to trace which ignore file is suppressing a given path, offering transparency in complex setups. This hierarchy allows teams to maintain a clean, project-specific ignore file while accommodating individual developer needs without polluting the shared repository.

The community response underscores a mix of revelation and debate. Many seasoned developers expressed surprise at discovering `.git/info/exclude` and the global ignore file, with one commenter stating, 'Wtf. I've always wanted this, and it was right there.' However, the comments also surface deeper tensions: the proper use of `.gitignore` for IDE files (should they be in the repo or globally ignored?), the role of `.gitattributes` for diff suppression, and the distinction between 'global' (per-user) vs. 'machine-wide' ignore patterns. Practical tips abound, such as using a `scratch` directory with a local `.gitignore` containing `*` to ignore temporary files, or leveraging `git update-index --assume-unchanged` for tracked files. The article serves as a catalyst for rethinking Git hygiene, urging engineers to adopt a more nuanced approach to ignoring files that balances collaboration with personal efficiency.

The three levels of git ignore—`.gitignore`, `.git/info/exclude`, and `~/.config/git/ignore`—let you control what gets tracked at the project, local, and global scope, respectively, a distinction many developers discover only after years of use.

Key Highlights
  • Git supports three ignore files: `.gitignore` (committed, shared), `.git/info/exclude` (per-repo, private), and `~/.config/git/ignore` (per-user, global).
  • `git check-ignore -v` reveals exactly which ignore file is blocking a path, aiding debugging.
  • `.git/info/exclude` is ideal for personal workflow files that shouldn't be in the shared `.gitignore`.
  • The global ignore file should be used for editor/OS artifacts like `.DS_Store` or `.idea/`, avoiding polluting every project's `.gitignore`.
  • Alternatives include `.gitattributes` for diff suppression, `git update-index --assume-unchanged` for tracked files, and creating a `scratch` directory with a local `.gitignore` containing `*`.

Show HN: Talos – Open-source WASM interpreter for Lean
⬆ 60 pts 💬 8 HN comments

Talos is a WebAssembly interpreter written in Lean 4 that doubles as a formal verification object. Unlike traditional interpreters where evaluation semantics and proof semantics are separate, Talos unifies them: the same definitions that execute a program are used for reasoning. It employs weakest precondition (WP) calculus, a predicate transformer semantics that enables compositional verification of loops, branches, and function calls without re-unfolding the interpreter. The interpreter is deliberately optimized for clarity over speed, targeting the subset of Wasm features common in non-optimized compiled code from Rust or C. This design aims to make Talos a practical tool for verifying real-world programs at the binary level, with the long-term goal of full Wasm coverage.

The project is organized as a monorepo with three Lake packages: Interpreter (Wasm AST, semantics, WP tactics), CodeLib (lifting lemmas and reasoning helpers), and Programs (Rust-to-Wasm verification tasks). Quick-start examples show running a .wat module with a fuel cap and proving factorial correctness. Dependencies include Lean 4 (pinned toolchain) and wasm-tools for binary decoding and test suite execution. The repository has 73 stars, 8 forks, and active development. A team member (lukerj00) explains the core bet: Wasm is a good verification target due to many languages targeting it, and Lean provides a powerful proof environment. The community raises practical concerns about handling dynamic memory and non-terminating programs, and notes naming collisions with existing projects (Siderolabs Talos, Raptor TALOS II).

The same definitions that execute a Wasm program are the ones you reason about — evaluation and proof share a single codebase.
