1-Bit Bonsai Image 4B Image Generation for Local Devices
⬆ 422 pts 💬 178 HN comments

PrismML has released Bonsai Image 4B, a family of compact image generation models that leverage 1-bit and ternary weight quantization to run on local devices. Based on the FLUX.2 Klein 4B architecture, the models replace full-precision FP16 weights with binary {−1, +1} or ternary {−1, 0, +1} values, combined with group-wise FP16 scaling factors. This achieves effective bit widths of 1.125 and 1.71 bits per weight, reducing the diffusion transformer footprint from 7.75 GB to 0.93 GB (1-bit) and 1.21 GB (ternary). The mean-active memory during 512×512 generation drops to 1.5–1.96 GB, enabling inference on devices like the iPhone 17 Pro Max, where the original model would not fit. The models are released under Apache 2.0 with an iOS app (Bonsai Studio) and WebGPU demo.

Benchmark results show that the ternary variant retains 95% of FLUX.2 Klein 4B accuracy across GenEval, HPSv3, and DPG-Bench, while the 1-bit variant retains 88%. This places Bonsai Image 4B in a new Pareto frontier for quality vs. memory, outperforming similarly sized models like PixArt-Σ. The technology promises to shift image generation from cloud-dependent, metered services to local, private, low-latency experiences. However, the HN community highlights nuanced trade-offs: some question whether memory is the primary bottleneck (vs. compute speed), and technical observers note that FLUX.2 already runs on iPhone via Draw Things with 6-bit quantization, challenging the 'first' claim. Censorship in the iOS app also drew criticism from advocates of local sovereignty.

Ternary Bonsai Image 4B retains 95% of FLUX.2 Klein 4B accuracy at just 1.21 GB – a 6.4x reduction in diffusion transformer footprint.

Key Highlights
  • Bonsai Image 4B uses 1-bit/ternary weights (1.125/1.71 effective bits) for massive compression, enabling on-device inference.
  • Based on FLUX.2 Klein 4B, it runs on iPhone and Mac with mean-active memory under 2.4 GB.
  • Quality benchmarks show 88-95% retention of full-precision model performance.
  • Released open source under Apache 2.0 with iOS app and WebGPU demo.

ChatGPT for Google Sheets exfiltrates workbooks
⬆ 261 pts 💬 97 HN comments

A newly discovered vulnerability in OpenAI's ChatGPT for Google Sheets extension enables attackers to exfiltrate entire workbooks and execute phishing overlay attacks via a single indirect prompt injection. The attack, detailed by PromptArmor, exploits the extension's ability to run external scripts—a capability not documented in OpenAI's privacy guidelines. Even when users disable the 'Apply edits automatically' setting, the malicious script executes without further approval, exfiltrating the current sheet, then following links to other workbooks, ultimately stealing up to 12 documents in one test. The attacker can also replace the ChatGPT sidebar with a fake interface or display a phishing modal to steal credentials. This incident underscores the fundamental risk of granting LLMs privileged access to sensitive data and the difficulty of sandboxing agentic actions.

OpenAI's initial silence on the disclosure, despite multiple follow-ups, prompted PromptArmor to publish the findings. After public release, OpenAI's Max Burkhardt acknowledged the issue, stating the company had 'removed the model’s ability to generate Apps Script code' and was re-evaluating its sandboxing approach. However, the vulnerability highlights a pattern: similar issues have been found in GitHub Copilot CLI, Snowflake Cortex AI, and other LLM-integrated tools. The comment thread reflects deep concern—users point to the 'lethal trifecta' of untrusted data, insufficient sandboxing, and excessive permissions. Others advocate for local, containerized models as the only true defense, while some note that network-level egress blocking would cripple legitimate agent functionality.

A single indirect prompt injection in a single sheet can exfiltrate 12 workbooks and display a phishing overlay, even with automatic edits disabled.

⬆ 725 pts 💬 416 HN comments

Cloudflare's Turnstile, marketed as a privacy-respecting alternative to CAPTCHA, now requires WebGL fingerprinting to verify users. The change, effective since late May 2026, causes indefinite loops on WebKitGTK-based browsers that block WebGL fingerprinting—a safeguard Apple has maintained for years. The author, lanodan, demonstrates that Turnstile fails on WebKit browsers (e.g., Epiphany) while passing on Firefox and Chrome, even when Firefox's privacy.resistfingerprinting is enabled. Cloudflare's justification—that privacy tools make browsers appear as bots—is dismissed as a pretext for tracking. This move effectively bans non-mainstream browsers, highlighting the ongoing tension between usability and anti-bot measures.

The controversy is amplified by Mozilla's failure to enable privacy.resistfingerprinting even under 'Strict' mode, as jeroenhd notes the setting breaks legitimate sites (e.g., timezone scheduling). Meanwhile, userbinator warns the 'war against bots' will wall off the internet to only approved user agents, echoing the 'approved browser' critique. Despite 416 comments, few defend Cloudflare's approach: even proponents like denysvitali acknowledge fingerprinting is necessary but destructive to privacy. Some users suggest proof-of-work alternatives (e.g., Anubis), but the broader sentiment is that Cloudflare has betrayed its privacy promise. The incident underscores the escalating arms race between bot detection and browser fingerprinting resistance, with minority browsers caught in the crossfire.

The Website Specification
⬆ 523 pts 💬 208 HN comments

The Website Specification (specification.website) is a comprehensive, platform-agnostic reference outlining 128 technical features that every decent website should have, organized across ten categories: Foundations, SEO, Accessibility, Security, Well-Known URIs, Agent Readiness, Performance, Privacy, Resilience, and Internationalisation. Each topic links to authoritative standards (WHATWG, W3C, IETF, WCAG), and the entire site is built in the open under MIT license with an MCP server for agent querying. The project aims to serve as a one-stop checklist for developers, from <title> tags to .well-known/security.txt. The controversy underscores tensions between modern web complexity, AI-generated content, and the desire for simplicity.

The Website Specification consolidates 128 technical features across 10 categories, from <title> to /.well-known/security.txt, aiming to be a one-stop checklist for modern web development.

Dav2d
⬆ 517 pts 💬 191 HN comments

The VideoLAN community has announced dav2d, an open-source decoder for the emerging AV2 video codec, continuing their tradition from dav1d. AV2, the successor to AV1 from the Alliance for Open Media, promises around 25% compression improvement but at a staggering 5x decoding complexity. This means software decoding on current hardware is impractical without deep, architecture-specific optimization. Dav2d is built from day one with a BSD license, a focus on performance via C and hand-tuned assembly (AVX2, NEON, RISC-V), and reuse of tooling like checkasm from dav1d. The project already supports the AVM v15 feature set, including intra/inter prediction, transforms, and filtering, positioning itself as the critical path to practical AV2 deployment long before hardware decoders arrive.

Jean-Baptiste Kempf, the lead, emphasizes that a codec doesn't truly exist until a decoder can run it in real applications. Dav2d's early release aims to avoid the hardware dependency trap that plagued AV1 initially. The decoder is already functional, with assembly optimizations underway for x86, ARM, and RISC-V. While the AV2 specification just reached its first official release, dav2d proves that the ecosystem can start building immediately. The community's reaction is mixed: excitement about the open development and performance opportunity, but sharp concern over the 5x complexity vs. 25% gain tradeoff, with some questioning whether software decoding will ever be viable for consumer devices. The project's success hinges on continued optimization and widespread adoption of AV2 by streaming services and browsers.

AV2 saves 25% bandwidth at the cost of 5x more decoding complexity.

Key Highlights
  • Dav2d is an open-source AV2 decoder from VideoLAN, leveraging dav1d experience.
  • AV2 offers ~25% compression gain but 5x decoding complexity over AV1.
  • Decoder already supports core features and SIMD optimizations for x86/ARM/RISC-V.
  • Performance trade-off sparks debate on whether 25% size reduction justifies obsolescing hardware decoders.
  • Patent concerns and encoding competitiveness remain open questions.
