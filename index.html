Holy shit holy shit holy shit holy shit: The magnitude of what’s now happening
⬆ 1889 pts 💬 1733 HN comments

Scott Aaronson's post — a deliberately unhinged-titled dispatch dated November 2026, written as speculative future-history rather than reported news — argues that the 'Mathocalypse' has crossed from picking off problems 'in the convex hull of existing techniques' to genuinely climbing the mountain toward P≠NP. The technical payload is a wave of claimed lower bounds, which is what makes the piece more than hype: OpenAI allegedly pinned ω, the matrix-multiplication exponent, at exactly 9/4 with a matching lower bound, settling a question open since Strassen's ω<3 in the late 1960s and — shockingly — landing on a rational answer. Paired claims include a tight N(log N)^{1/2+o(1)} linear-gate count for the Fourier transform, VP≠VNP, a Riemann Hypothesis proof, superlinear Boolean circuit lower bounds for element distinctness, and QIP(2)=PSPACE. Lower bounds, not upper bounds, are the tell: they were long presumed nearly as hard as P≠NP.

The trust substrate is Lean: Aaronson's working assumption is that 'any proof that comes directly from OpenAI or Anthropic is correct barring information to the contrary,' and he preemptively calls bad-faith nitpickers 'raging doofuses' — a jab at Gary Marcus signal-boosting claims that unused Lean sections invalidated a proof. The post drew 1,889 points and 1,733 comments, a ratio suggesting argument rather than applause. He also gestures at unverified cryptography 'bombshells,' while warning readers not to let 'your Bitcoin wallet' overshadow the intellectual event. HN commenters supply the grounded counterweights: galactic O(n^{9/4}) algorithms with unusable constants, $70B of 'evidence' that ECDSA still holds, and the observation that these breakthroughs may simply be RL training byproducts on verifiable, leakage-free open problems.

"Yes, I do now think that AI is climbing the mountain that leads to P≠NP" — and the decisive clue was not an upper bound but a matching lower bound: ω = 9/4 exactly, a rational answer to a question open since the 1960s.

  • Claimed matching lower bound ω = 9/4 settles the matrix multiplication exponent as a rational number, a result presumed nearly as hard as P≠NP

#2
1Password Security Incident
⬆ 1603 pts 💬 696 HN comments

On November 25, 2026, 1Password disclosed that an attacker had gained access to an employee's corporate GitHub account on November 19, used it to read private source repositories, and — critically — pushed malicious code into backend services, which then exfiltrated administrative customer records. The stolen data was explicitly non-secret: names, sign-in email addresses, account and user identifiers, creation and last-sign-in timestamps, public keys, SRP protocol parameters, and provisioning/invitation/recovery tokens embedded in emailed links. Containment included disabling the GitHub account, revoking the token, rotating all potentially exposed internal and CI/CD credentials, restoring clean service versions, and lengthening the alphanumeric code used in invite and recovery flows from six digits to ten to defeat brute forcing. 1Password's zero-knowledge architecture held: vault contents and the Secret Key/master-password material that decrypts them were never in the vendor's custody, so a total backend compromise still did not yield plaintext secrets.

The community's analysis quickly moved past the reassuring headline to the mechanics. Thomas Ptacek framed the incident as the canonical SaaS breach pattern — "as the number of employees grow, the likelihood that one of their laptops will get compromised approaches 1" — after which code pushed to GitHub and deployed becomes total compromise. Commenters pressed on the unanswered operational questions: was push-to-main blocked, were branch protection rules present or bypassable, did CI/CD hold long-lived static credentials rather than OIDC-scoped, short-lived tokens, and did any human approve the malicious merge? A second, sharper thread argued that end-to-end encryption is cold comfort when the vendor also ships the decrypting client: a malicious web-vault bundle or Electron update could capture the master password at the moment of unlock. Readers reported a wave of convincing phishing citing shared-vault items, and long-time users resurrected the local-vault debate (1Password 7, KeePassXC) that has shadowed the product since version 8.

The breach did not require breaking 1Password's encryption at all — an employee's GitHub account with push access to deployable backend code was enough to exfiltrate customer records, which commenters noted is the standard fact pattern for essentially every modern SaaS compromise.

Key Highlights
  • An employee's corporate GitHub account was compromised; the attacker read private repos and pushed malicious code to backend services that harvested customer account metadata.
  • Exposed data was non-secret: names, emails, account IDs, timestamps, public keys, SRP parameters, and emailed invitation/recovery tokens.
  • Invite and recovery codes were lengthened from six numeric digits to ten alphanumeric digits to make brute-force guessing impractical.
  • All potentially exposed internal and CI/CD credentials were rotated; the affected GitHub account was disabled and attacker-created access removed.
  • Vault contents, vault encryption keys, account passwords, and Secret Keys were not affected because 1Password never holds them.

#4
Slow Ubuntu security response times
⬆ 391 pts 💬 230 HN comments

Security researcher Hanno Böck used the oss-security list to document a pattern of slow Ubuntu kernel patching for severe remote flaws. The headline case is CVE-2026-99288 ('NoisyTCP'), a remote memory corruption bug in the Linux kernel TCP stack published on November 16th; nine days later Ubuntu still had no published fix, while several other distributions shipped one the day details went public. A second case, CVE-2026-99312, a KVM host escape affecting AMD virtualization disclosed November 18th, also remained unpatched, and a third remote TCP corruption (CVE-2026-98432) had previously lingered for weeks. Böck pinned the root cause on strategy rather than effort: Ubuntu LTS ships kernel 7.0.0-44, a heavily backported fork of an old base, whereas Debian stable tracks 6.12.118+deb13, a current kernel.org longterm release. Backporting thousands of patches onto a divergent tree, he argues, is 'hardly viable' versus rebasing on longterm kernels the upstream maintainers actually support.

The thread drew 391 points and 230 comments, and the practitioner anecdotes are the real payload. One commenter reported moving 'all of our server images to Debian from Ubuntu because of this'; another described manually compiling kernel fixes as a stopgap before rolling off Ubuntu entirely. A frequently quoted line from a stable-kernel maintainer warns that cherry-picking patches yields 'a potentially more insecure system, and one that contains known bugs' — precisely the model Ubuntu uses. Counterweights exist: Red Hat had CVE-2026-99288 patched only on November 23rd and CVE-2026-99312 still open, Amazon Linux 2023 lagged Debian by over two weeks on the earlier CVE, and defenders note that regression-tested backports occasionally break things too. The debate also exposes Canonical's structural constraints, with commenters citing a 'tiny security team,' a notoriously selective hiring process, and the reputation tax of Snap.

Nine days after a remote Linux kernel TCP memory-corruption bug (CVE-2026-99288) was publicly disclosed, Ubuntu had still shipped no fix — while Debian, tracking a current kernel.org longterm release, had one available the day details went public.

Key Highlights
  • CVE-2026-99288 (NoisyTCP), a remote kernel TCP stack memory corruption, was public on Nov 16 with no Ubuntu fix nine days later; CVE-2026-99312 (AMD KVM host escape) is also unpatched.
  • Böck attributes the lag to Ubuntu's backporting model — kernel 7.0.0-44 is a divergent fork of an old base, versus Debian's 6.12.118+deb13 which tracks a current kernel.org longterm release.
  • A quoted stable-kernel maintainer warns that cherry-picking patches instead of taking full stable releases produces 'a potentially more insecure system' with known bugs — undermining the enterprise LTS premise.
  • Practitioners report concrete migrations: server images moved to Debian, containers to Alpine, and at least one team manually patching kernels while planning an exit from Ubuntu.
  • Counter-evidence: Red Hat fixed CVE-2026-99288 only on Nov 23 and left CVE-2026-99312 open, while Amazon Linux 2023 trailed Debian by over two weeks on CVE-2026-98432 — the problem is industry-wide, not unique to Canonical.

#5
Nfs2root: A 12-year-old pre-auth remote root in the Linux kernel's NFS server
⬆ 201 pts 💬 85 HN comments

CVE-2026-99362 is a pre-auth heap overflow in the Linux kernel's in-tree NFS server, and its mechanism is an unusually clean example of state-machine reasoning failure rather than a dumb memcpy bug. Each NFSv4.1/4.2 session slot caches its last reply so retried requests are answered exactly once, and the client dictates that cache's size. Set the cache limit to zero, and every slot buffer is zero bytes; nfsd4_sequence() then shrinks the reply buffer down to that limit before accepting the slot. Pad the request's tag so the buffer fills immediately after the SEQUENCE opcode, and the compound encoder bails out without setting a failing status — so the server believes SEQUENCE succeeded and copies the full reply, tag and headers included, into a zero-capacity object. The KASAN report for the upstream fix shows an 80-byte write with 61 bytes past the slab object, 40 of them attacker-chosen. The bug dates to commit 47ee52986472, shipped in Linux 3.16 in March 2014.

The escalation path is a textbook modern kernel chain, run against a remote target over a single unauthenticated TCP connection to port 2049: corrupt the adjacent slot's bookkeeping, replay to leak 3.8 KB of heap and the KASLR slide, forge a pointer to free an object of the attacker's choosing, reclaim that memory with a fake callback assembled from NFS client-supplied names, then hang up so nfsd invokes the callback via the usermode-helper path and spawns /bin/sh as root. Fixes landed in 6.12.117, 6.18.61, 7.3.2 and 7.4-rc1 after Jérémy Jean of ANSSI reported it upstream on 17 August 2026; OpenSec claims its Antara harness independently rediscovered and weaponized it. Detection is poor by design — the attack is valid NFS traffic, and nfsd4_check_resp_size only warns after the copy has already happened. The practical mitigations are unglamorous: patch and reboot, firewall tcp/2049, or disable vers4.1/vers4.2 entirely, at the cost of pNFS and some 4.2 features.

"One TCP connection writes 61 bytes past a kernel heap object" — of which 40 are chosen by the attacker, which is all it takes to go from an anonymous packet to uid=0(root) on any host serving NFSv4.1/4.2.

Key Highlights
  • Client-controlled reply-cache size collapses session-slot buffers to zero bytes, so nfsd4_sequence() accepts a slot whose reply cannot fit; the encoder silently truncates instead of erroring.
  • Bug present since Linux 3.16 (2014); fixed in 6.12.117, 6.18.61, 7.3.2 and 7.4-rc1 via patches from Jérémy Jean (ANSSI), disclosed 20 Nov 2026.
  • Full chain: heap overflow → 3.8 KB replay leak for KASLR → forged-pointer arbitrary free → callback reclaim → usermode-helper root shell.
  • No network signature exists since the traffic is valid NFS; only post-hoc nfsd4_check_resp_size warnings and nfsd4_*/svc_* oops frames are observable.
  • Interim mitigations are network- or protocol-level: restrict tcp/2049 to a storage subnet, or set vers4.1=n / vers4.2=n, accepting loss of pNFS features.
