Benchmarking Opus 5 on SlopCodeBench
⬆ 299 pts 💬 68 HN comments

SlopCodeBench, a new benchmark from UW Madison, evaluates AI coding agents on long-horizon tasks by sequentially revealing new requirements across multiple checkpoints, mirroring real-world software evolution. Unlike single-shot benchmarks, it measures a model's ability to maintain code quality over time—tracking complexity, duplication, verbosity, and structural decay. The author ran three Claude models (Opus 4.8, Sonnet 5, Opus 5) on a subset of 3 problems with 17 checkpoints, using a strict pass criterion where all historical tests must pass. The results starkly illustrate that even frontier models degrade codebases: none completed any challenge without accumulating defects, and code quality metrics worsened monotonically across checkpoints. This highlights a critical gap between impressive one-shot coding and sustained maintainability.

Opus 5 achieved a 24% strict pass rate (4/17 checkpoints) versus Opus 4.8 and Sonnet 5 at 6% (1/17 each). Despite generating 5× more functions than Opus 4.8, the extra code did not translate to correctness—most production volume increased only 1.8×. Across all models, 89–98% of lines triggered at least one slop rule, with verbosity flags rising from 65% to 80% over checkpoints. The author notes that while Opus 5's mean complexity stayed lower, its sheer volume of functions (2000) suggests a trade-off. The benchmark remains unsaturated, offering a robust signal for future model progress. As one commenter put it, 'every dollar bought correctness. nobody bought enough of it.'

Opus 5 got a 24% strict pass rate on a small subset of SlopCodeBench—only marginally better than Opus 4.6's 17% in the original paper—and failed all three problems before the final checkpoint.

Key Highlights
  • SlopCodeBench tests models over multiple checkpoints with incrementally revealed requirements, simulating real software evolution.
  • Opus 5 scored 24% strict pass rate vs. 6% for Opus 4.8 and Sonnet 5 on the subset; none completed any problem without defects.
  • Models generated increasingly complex, verbose, and duplicated code; Opus 5 wrote 5× more functions than Opus 4.8.
  • Over 89% of code lines tripped slop rules; verbosity flags grew from 65% to 80% across checkpoints.
  • The benchmark is unsaturated and offers a more meaningful signal for long-term code quality than single-turn evals.

Self-contained highly-portable Python distributions
⬆ 146 pts 💬 32 HN comments

Python Standalone Builds (python-build-standalone) is an open-source project that produces self-contained, highly-portable Python distributions. These distributions bundle a fully-functional Python interpreter with most standard library modules, statically linking library dependencies to minimize runtime requirements. The project aims to create binaries that work on any system for a given architecture, limiting CPU instructions and shared library dependencies. Notably, these builds are used by popular tools like uv, pipx, Hatch, and Poetry to install Python itself, thanks to Astral's maintenance (now under OpenAI). The distributions also ship build artifacts and metadata for downstream repackaging, enabling custom embedded Python instances via PyOxidizer.

A key technical detail is that these builds are not truly single-file executables; they still depend on system libraries like glibc and CPU features, which can cause surprises in production. However, they offer a reproducible Python base without requiring a system Python. The distributions are remarkably small—15-20MB per version—making them ideal for containerized environments. Comments highlight two competing approaches: Cosmopolitan's APE binaries run natively across OSes including a ~40MB Python, sparking debate about the trade-offs. Astral’s maintenance ensures ongoing compatibility with CPython releases, though some quirks remain. The community values these builds for simplifying Python distribution, but notes limitations with native extension compatibility on musl-based builds.

Python Standalone Builds produce fully-usable Python installations in just 15-20MB, enabling reproducible Python environments across platforms.

Key Highlights
  • Self-contained Python distributions that work on any system for a given architecture.
  • Used by uv, pipx, Hatch, Poetry, and Bazel for installing Python.
  • Build artifacts allow custom repackaging for embedding Python.
  • Astral (now under OpenAI) maintains the project, ensuring CPython compatibility.
  • Distributions are 15-20MB, significantly smaller than typical Python installations.

How real are real numbers? (2004)
⬆ 81 pts 💬 60 HN comments

Gregory Chaitin's 2004 paper 'How real are real numbers?' is a provocative polemic against the mathematical Platonism that grants full existence to the uncountable continuum of real numbers. Drawing on algorithmic information theory and the constructivist tradition of Émile Borel, Chaitin argues that only numbers with finite descriptions—those that are computable or definable—should be considered 'real' in any meaningful sense. He presents the halting probability Ω, an uncomputable but definable real, as an example of a number that is logically irreducible, meaning its digits cannot be compressed into a finite set of axioms. This aligns with his broader 'quasi-empirical' view that mathematical truth is not absolute but emerges from the success of theories. The paper synthesizes ideas from Gödel, Turing, and Borel to challenge the necessity of the continuum for physics and mathematics.

The HN discussion reflects deep engagement with these foundational issues. Several commenters defend the classical view, noting that quantum mechanics and mathematical physics rely on continuous functions and that constructive mathematics has not replaced standard analysis. Others embrace Chaitin's skepticism, arguing that uncomputable numbers have no physical instantiation in a finite or quantized universe. A notable technical critique comes from francisdavey, who points out a flaw in Chaitin's measure-theoretic argument for uncountability, observing that it would also apply to the rationals. The conversation also touches on the naming of 'real' vs. 'imaginary' numbers, with Nevermark suggesting that 'nameable' or 'computable' would be more descriptive. Overall, the thread exemplifies the enduring tension between mathematical beauty and physical relevance.

Chaitin claims that Ω is 'computationally and therefore logically irreducible,' requiring his theory of program-size complexity to prove its irreducibility.

The project has already packaged over 100 repositories, including notable libraries like libxml2, Wayland, boringssl, and ffmpeg. The organization encourages upstreaming these build scripts, with the condition that they must not introduce more system dependencies than the Zig-packaged version. Community reactions are mixed: some praise the convenience and cross-compilation benefits, while others fear fragmentation, noting parallels with Meson's WrapDB and Bazel's ecosystem.
