What Is a Harness?
⬆ 27 pts 💬 15 HN comments

Earendil's post demystifies the term "agent harness" with a climbing analogy: just as a climbing harness connects a person to ropes and tools, an agent harness connects an AI model to instructions, tools, a control loop, and external models. The article breaks a harness into four pillars: a system prompt that shapes model behavior; a toolset (web search, code execution, email composition) exposed via function calling; the agentic loop, where the model iteratively evaluates results and calls tools again until the task is complete; and a translation layer that lets one harness drive Anthropic, OpenAI, or open-weight models interchangeably. The concrete example of an email agent researching schools shows how re-searching and spreadsheet generation create a loop. This framing reframes "agent = model + harness," making the harness the real product surface for user ownership and agency, with Pi (Earendil's own open-source harness) positioned as minimal, neutral, and user-owned.

HN's mostly technical commenters broadly accept the four-component definition but split on its significance. Some, like tosh and lebek, emphasize minimalism: "the bigger your backpack the slower you walk" applies to context and tool bloat. Others, like rurban, connect the term to Perl test harnesses and CI, arguing a good harness is a fast feedback loop between model and environment. Skeptics like amelius call harnesses a commodity and highlight model/hardware value, while jascha_eng dismisses the term as "the AI hype word for 2026." Practical builders like ChicagoDave report 20x productivity gains, and Syntaf details the pitfalls of over-prescriptive skills. The thread demonstrates both clarity and friction: alexjurkiewicz sees near-unanimous consensus on what a harness is, but profsummergig calls it "a placeholder for desire." The underlying tension—how much scaffolding is enough, and where real value accrues—remains the actual frontier.

A harness is the complement to the model: the better the model, the more minimal the harness can be.

Key Highlights
  • Agent harnesses provide the scaffolding: system prompt, tool registry, agentic loop, and translation layer.
  • The agentic loop is the mechanism by which a model iteratively calls tools, evaluates results, and re-calls until task completion.
  • A translation layer lets users swap between Anthropic, OpenAI, and open-weight models, reducing lock-in to AI labs.
  • Earendil's Pi is an open-source, minimal, locally-runnable harness with more than 5,000 user-built extensions.
  • Commenters debate whether harnesses are a new frontier or just the latest hype term, with some linking it back to classical test harnesses and CI systems.

I gave Qwen 3.8 27B a reverse-engineering job and it finished in 30 minutes
⬆ 159 pts 💬 80 HN comments

The article describes an experiment by XDA Lead Technical Editor Adam Conway in which Qwen 3.8 27B, a locally hosted 27B-parameter open-weights model, reverse-engineered the license verification scheme of a commercial application in about 30 minutes. Running on a Lenovo ThinkStation PGX (Nvidia GB10 Grace Blackwell, 128 GB unified memory, ~50 tok/s with SGLang/NVFP4/DFlash2 speculative decoding), the model refused an initial jailbreak prompt, identified from the binary's signing certificate that Conway was not the developer, then performed static analysis of thousands of lines of arm64. It mapped security functions to call sites, located a deliberately obscured RSA public key, and produced a working authentication bypass. Crucially, when its first reconstructed key passed signature verification but failed a hash integrity check, the model detected the discrepancy, debugged itself, and corrected the output byte-for-byte without human intervention.

The result is significant not because it is a frontier-level achievement, but because it happened entirely on a desktop-class machine with no cloud component: the binary, license, and analysis never left the device. Conway argues this flips assumptions about where advanced reverse-engineering capability resides. The same properties that make local models appealing for analyzing proprietary code or malware also make them a more credible threat vector: a locally running model has no remote oversight and can be pointed at any target by whoever controls the keyboard. Commenters pushed back that license checks are a testable, 'done/not-done' task and that static-only analysis is not the hardest RE workload, while others noted the model's persistence and self-verification are the real breakthrough. The broader debate centers on whether refusal training is meaningful when unrestricted versions are easily obtainable, and whether local AI will disrupt both software business models and the economic logic of cloud AI.

A 27B-parameter model that fits in 17 GB of VRAM recovered a deliberately obscured RSA public key from a commercial binary and built a working auth bypass - entirely offline, in about 30 minutes.

Key Highlights
  • Qwen 3.8 27B reverse-engineered a commercial app's license check in 30 minutes on a single workstation, with no cloud APIs involved.
  • The model refused a jailbreak prompt, correctly identified the real developer via signing certificate, then still produced an audit and a working bypass.
  • It used static analysis only, disassembling arm64 and recovering a deliberately hidden RSA public key, and self-corrected a hash mismatch without human help.
  • The same local, private, and unstoppable properties that make this great for researchers are also threat-model concerns.
  • Community debate suggests testable tasks with clear oracles are where local models shine, while guardrails on open models are largely seen as ineffective against determined users.

JIT Compiling Code in 5μs
⬆ 123 pts 💬 78 HN comments

This article, from the creator of pgrust, details how a JIT compiler can be built to compile code in about 5µs, making it feasible to JIT-compile every SQL query rather than only a subset. The key technique is copy-and-patch: pre-designed ARM64 assembly stencils are filled in with runtime-specific immediates and branch offsets, then concatenated into executable memory. The author walks through a tiny regex engine that compiles b(an)* into bare-metal ARM64, using a backtracking stack and null-terminated input to avoid bounds checks. The generated code performs on par with a handwritten implementation, achieving 10–20x speedups over a tree-walking interpreter. The author also credits AI for lowering the barrier to writing assembly, arguing that LLMs make formerly esoteric systems programming more accessible.

The performance table shows JIT and handwritten versions essentially tied: for a 2,049-byte input, JIT takes 470ns vs 393ns handwritten, both dwarfed by the interpreter's 8,301ns. The author uses this as evidence that template-based JIT via AI can match hand-optimized code, a claim that stirs debate in the comments. Some commenters counter that using LLVM or Cranelift is the standard path and that template-based compilers sacrifice optimization quality, while others defend copy-and-patch as a legitimate, real JIT. The write-up also touches on Apple's W^X requirements and the use of mmap with MAP_JIT, showing the low-level systems details involved. The broader thesis is that AI can revive ambitious database engineering, a position that receives both enthusiasm and skepticism.

'The pgrust JIT compiler compiles code in around 5μs, which enables us to JIT compile every SQL query, not just a subset of them.'

Key Highlights
  • Copy-and-patch JIT compiles ARM64 stencils with substituted values, achieving ~5µs compile times.
  • JIT performance matches handwritten code, delivering 10–20x speedups over an interpreter.
  • The author positions AI as the enabler that makes JIT compiler implementation practical.
  • Commenters debate LLVM/Cranelift vs template-based approaches, with some calling template JIT 'not real JIT'.
  • Security concerns about JIT and W^X policies appear in the comments, countered by arguments that JIT doesn't add new capabilities.

Fast and Hard Code
⬆ 81 pts 💬 44 HN comments

Armin Ronacher's 'Fast and Hard Code' argues that LLMs have fundamentally changed the economics of programming-language choice. Because agents can generate, optimize, and even rewrite code in unfamiliar languages, developers increasingly pick 'hard languages' like Rust or Zig based on performance and community 'vibe' rather than personal familiarity. He cites Cloudflare's Artifacts service, which ships a pure-Zig Git-protocol engine in a ~100 KB WebAssembly module, and Vercel's fx, a Zig coding agent. The same dynamic is pushing programmers into previously inaccessible domains such as DWARF debugging, eBPF, custom network drivers, and old hardware. While some of this is gatekeeping falling away, Ronacher acknowledges the potential for 'slop' – but believes more developers may now aim for fast, small software.

The Hacker News discussion splits sharply. Supporters point to concrete examples: one user vibe-coded a Cargo workspace linter that used rustc's name-resolution internals rather than a parser, 'something I would never have done myself.' Others warn that skipping language acquisition leaves developers unable to review agent output – as one commenter asks, 'How do you check the code if you don't know the language?' Cryptographic code becomes a flashpoint: one commenter claims AI can 'roll you crypto far better than what humans have built by hand,' while veteran engineers caution that careful review and conservatism are non-negotiable. A further thread questions authorship: 'Is it really building your own if it's just rephrasing training data? Or is it license laundering?'

"So maybe the world will have more slop, but it might also have more developers in it, that want things to be fast and small."

Key Highlights
  • LLMs lower the cost of using unfamiliar or historically 'hard' languages, shifting language choice to performance and marketing.
  • Cloudflare's Artifacts uses a pure-Zig Git engine in ~100 KB Wasm; Vercel's fx is a fast, small Zig coding agent.
  • Developers are now exploring DWARF, eBPF, custom crypto, and old hardware with AI assistance.
  • Critics argue code review requires language familiarity, or the developer cannot verify or guide agent output.
  • Originality and 'slop' debates persist: is an AI-generated project truly 'yours' if it rephrases training data?

MartyPC is a cross-platform emulator of early PCs written in Rust
⬆ 154 pts 💬 55 HN comments

MartyPC is a cross-platform emulator of early IBM-compatible PCs, written in Rust and available as a web edition. It emulates the IBM 5150/5160 with support for multiple video standards (MDA, Hercules, CGA, EGA, VGA), an AdLib sound card, and a configured memory sidecar. The developer, GloriousCow, has spent over four years on the project and emphasizes accuracy rather than breadth. A notable engineering achievement is the use of physical harnesses for real early CPUs, allowing test suites to be run against genuine hardware to validate emulation correctness down to timings and quirks. The project also provides an interactive debugger built on the egui immediate-mode GUI framework, which the developer says made advanced debugging possible in Rust. While only a subset of hardware is supported, the emulator aims for '100% correct' behavior, making it a serious tool for retrocomputing enthusiasts.

On Hacker News, the community response mixes admiration for the technical rigor with a familiar debate over the 'written in Rust' framing. Commenters like tensor and aw1621107 point to the hardware validation and accompanying blog posts, while wiz21c finds Rust 'a really nice language to write emulators.' However, many feel the title needlessly highlights Rust; szundi asks why we never see 'written in C,' and teiferer sarcastically dismisses it. The developer responds to feedback, noting that when he started in 2020, a Rust PC emulator was novel. Other threads discuss keyboard layout support (with a remapping system in development) and nostalgic requests for authentic hard disk sounds, which GloriousCow plans to record from real MFM drives. Overall, the project is seen as an impressive, accuracy-focused emulator, even if the language choice distracts some.

The author built physical harnesses for real early CPUs so that he could build test suites against the real hardware and ensure the emulation is 100% correct, down to every timing and quirk of the original hardware.

The End of an Athlon
⬆ 143 pts 💬 57 HN comments

The article, published on OS/2 Museum, documents a striking failure mode of early 2000s AMD Athlon XP processors: pulling off a heatsink sheared a large chunk out of the exposed CPU die. The author notes the CPU had worked fine until the chunk detached, and suspects a long, straight micro-crack silently weakened the silicon. This era of flip-chip PGA packaging left the bare die directly against the heatsink, a compromise driven by rapidly rising TDPs that exceeded 50W and approached 80W. Intel abandoned the approach with the Pentium 4 and PIII-S, while AMD kept exposed dies on Socket A Athlons. The result was a well-known fragility: uneven mounting pressure could crack the silicon, and many vintage CPUs survive today only with chipped corners.

Hacker News commenters respond with decades-old builder trauma and technical corroboration. Several recount killing their own Athlon XP or Thunderbird during heatsink installation, describing it as 'nerve wracking as hell' and a 'mini panic attack.' Others note the market for copper shims specifically for Athlon/Duron, while claiming Intel's Coppermine dies were noticeably tougher. A separate thread explores why silicon substrates are about 0.8mm thick: the active layer is microscopically thin, but bulk silicon is needed for epitaxial growth and structural integrity. The post also surfaces modern analogies, from delidding with liquid metal to Intel's LGA sockets moving mechanical risk from the die to the motherboard, showing how packaging engineering remains a balance between cooling, durability, and user error.

The CPU worked just fine until a good chunk of it came off.

Key Highlights
  • Heatsink removal from an Athlon XP tore away a large piece of the exposed silicon die, likely along a pre-existing micro-crack.
  • Early 2000s flip-chip PGA designs exposed the bare die; both AMD and Intel struggled with rising TDPs, but Intel moved to lidded packages sooner.
  • Bare-die fragility led to a market for copper shims and a culture of extreme care when mounting heatsinks on Socket A CPUs.
  • Community experience generally rated Intel's Coppermine cores as more durable than AMD's Athlon/Duron silicon.
  • Modern lidded processors shift mechanical vulnerability from the die to the socket, and delidding remains a risky enthusiast modification.
