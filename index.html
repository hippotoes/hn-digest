Running local models is good now
⬆ 1386 pts 💬 535 HN comments

In her blog post 'Running local models is good now', Vicki Boykis provides a deeply technical account of how local language models have matured to the point of being viable for real development work. Using a 2022 M2 Mac with 64GB RAM, she reports achieving roughly 75% of frontier model accuracy and speed for agentic coding tasks, such as refactoring a Python notebook into a modular repo or bootstrapping a recommendation system. Her setup relies on LM Studio as an inference server and Pi as the agent harness, with all agentic workflows sandboxed in Docker containers for security. She emphasizes the ability to introspect token processing, adjust context windows, and experiment with quantizations—capabilities that cloud APIs simply don't offer. While acknowledging ongoing issues like slow inference and limited context windows, Boykis argues that the ecosystem has crossed a critical threshold where local models are not just tinkerer's curiosities but practical tools for daily engineering.

The Hacker News community reaction was intense, with 535 comments reflecting a polarized but passionate audience. Many commenters echoed Boykis's enthusiasm, with hypfer calling Qwen3.6-27B 'very capable' and preferring it over Claude Sonnet for coding, while segmondy declared local models 'more than good' and listed numerous SOTA-competitive models like KimiK2.7 and DeepSeekV4. However, a strong skeptical contingent pushed back, arguing that local models still require expensive hardware (e.g., 64GB+ VRAM), suffer from quantization trade-offs, and fall short in complex agentic workflows. c0rruptbytes detailed the pain of dense vs. MoE compromises, and Tharre reported models 'hard stuck' on simple problems. A recurring theme was the economic debate: whether owning hardware is cheaper than renting frontier models, amplified by geopolitical concerns about reliance on US/Chinese cloud providers. This tension—between the dream of local sovereignty and the reality of hardware costs—dominated the discussion, signaling that while local models have improved dramatically, the field remains in flux.

"For agentic coding locally, I’ve finally been able to have loops work at about ~75% the accuracy/speed of frontier models, which is incredible."

Key Highlights
  • Local models now reach ~75% of frontier model performance for agentic coding tasks.
  • Hardware requirements remain a major barrier, with 96GB+ VRAM recommended for serious use.
  • Quantization trade-offs (e.g., 4-bit vs 6-bit) significantly impact tool-calling reliability.
  • Hybrid workflows (cloud for planning, local for execution) are gaining traction among practitioners.
  • Geopolitical and economic arguments for local models are intensifying, especially outside the US/China.

TIL: You can make HTTP requests without curl using Bash /dev/TCP
⬆ 452 pts 💬 206 HN comments

Bash's /dev/tcp redirection, a built-in compile-time feature, opens raw TCP sockets without needing external tools like curl or wget. The article demonstrates crafting HTTP/1.1 requests manually by writing a GET line with headers and a blank line via printf to file descriptor 3, then reading the response with cat. The author discovered this while checking container connectivity in a minimal Docker image stripped of networking utilities. This technique is not a full HTTP client; it lacks parsing, redirect handling, TLS, and may hang without the Connection: close header. It works only with bash (not dash or zsh) and depends on bash being compiled with --enable-net-redirections, which most mainstream builds include but older Debian systems disabled.

The HN comments reveal a collective memory of direct socket interactions: users recall telnetting to port 80 and 25 in the 90s, with one commenter noting 'it's all just text files.' Another highlights that zsh has its own zsh/net/tcp module, while Plan 9 offered real /net filesystems for network access. Some share practical workarounds—like using nsenter to invoke curl from the host namespace—and caution that this trick is fine for ad-hoc checks but not production. The dichotomy between nostalgic appreciation and rigorous engineering discipline underscores the community's depth: the feature is celebrated as a clever hack yet firmly relegated to debugging, with repeated warnings that manual HTTP handling will break under real-world conditions.

It’s a redirection that bash handles internally. From the Bash manual: /dev/tcp/host/port – If host is a valid hostname or Internet address, and port is an integer port number or service name, bash attempts to open the corresponding TCP socket.

Key Highlights
  • Bash can open TCP sockets via /dev/tcp/host/port, enabling raw HTTP requests without curl.
  • The technique requires the Connection: close header to avoid hanging on persistent connections.
  • No TLS support; only plaintext HTTP works without additional tools like openssl s_client.
  • It is a bash-specific feature, not POSIX, and may be disabled in some builds (e.g., older Debian).
  • Best suited for quick connectivity tests in minimal containers, not for production HTTP clients.

Stop Using JWTs
⬆ 420 pts 💬 251 HN comments

The gist 'Stop Using JWTs' argues that JSON Web Tokens are fundamentally misapplied in web authentication, especially for maintaining user sessions. The author contends that JWT was designed for short-lived tokens (~5 minutes) and that 'stateless' authentication is a myth: any secure system requires state for revocation, and once you have a data store, traditional session cookies are simpler, more secure, and more flexible. The article points to a history of insecure JWT libraries, the inability to revoke individual tokens without building stateful infrastructure, and the lack of trust among security experts. It recommends PASETO as a superior alternative for signed tokens and emphasizes that major players like Google use cookie sessions, not JWTs, for user login.

The debate is far from settled. Commenters highlight legitimate use cases: service-to-service communication, single sign-on transport, and short-lived access tokens in microservices architectures. Many argue that JWT insecurity stems from poor implementations rather than the spec itself, and that modern libraries have addressed earlier flaws. The core tension is between statelessness (no DB lookup) and controllability (revocation). Solutions like revocation lists, token version fields, and short lifetimes with refresh tokens are proposed. The community remains divided: some see JWT as a pragmatic tool when used correctly, while others insist on session cookies as the only truly secure approach for browser-based sessions.

"JWTs should not be used for keeping your user logged in. They are not designed for this purpose, they are not secure, and there is a much better tool which is designed for it: regular cookie sessions."

Key Highlights
  • JWTs are unsuitable for long-lived user sessions; session cookies with server-side storage are preferred.
  • Stateless authentication is not truly stateless when revocation is required, negating the main benefit.
  • JWT libraries historically had security flaws (e.g., alg=none attacks) but modern defaults are safer.
  • JWTs are valid for service-to-service, short-lived tokens, and single sign-on transport.
  • Alternatives like PASETO or opaque session tokens should be considered for authentication.
