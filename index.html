#6
Harnessing the Universal Geometry of Embeddings
⬆ 98 pts 💬 31 HN comments

Rishi Jha and colleagues extend the Platonic Representation Hypothesis from a philosophical conjecture to a workable translation primitive: they show, for the first time, that text-embedding vector spaces from differently trained models can be mutually translated with no paired data, no encoder access, and no predefined correspondence sets. The key assumption is that embedding geometry is universal — semantic similarity is encoded in the metric structure of latent space, not in arbitrary coordinate axes. A translator is learned by mapping arbitrary embeddings into an intermediate “universal” latent representation, allowing high-cosine-similarity transfer across architectures, parameter scales, and training datasets. In doing so they also formalize a metric-space/isometry view of representation spaces. For machine learning researchers, this provides striking evidence for the universality conjecture; for security engineers, it reclassifies a vector database from an opaque index into a recoverable representation of source documents.

Commenters quickly split. One HN practitioner cautions “similarity != executability”: geometry may be preserved for embedding models tuned for similarity, but the residual variance lost in translation might be exactly what makes hidden states executable inside an LLM. Another thread stresses that the serious consequence is privacy: “vectorized outputs from an unknown embedder on an unknown dataset is in no way private.” The paper demonstrates classification and attribute inference from vectors alone; as one reply clarifies, attackers do not even need to know the generating model. Code is linked via a GitHub repository (vec2vec), and the paper is now at v4 after a NeurIPS cycle. The discussion oscillates between fascination and defensive framing, with many users asking how practical and how broad this geometric translatability is beyond the discriminative embedding models used in the paper.

The paper shows that embeddings carry a recoverable universal geometry that is model-agnostic — and the authors warn that “an adversary with access only to embedding vectors can extract sensitive information about the underlying documents, sufficient for classification and attribute inference.”

Key Highlights
  • First unsupervised embedding-to-embedding translation without paired data, encoder access, or predefined matches.
  • Works by routing embeddings through a learned universal latent space predicted by the Platonic Representation Hypothesis.
  • Achieves high cosine similarity across different architectures, parameter sizes, and training datasets.
  • Demonstrates vector-only attacks for document classification and attribute inference.
  • Code is available; multiple HN users debate generality and whether the approach works for generative LLM states.

Ask HN: How do you manage skills files?
⬆ 192 pts 💬 176 HN comments

The Ask HN thread 'How do you manage skills files?' surfaces a sharp operational question from AI-assisted software workflows: as coding agents like Claude Code and Codex increasingly read 'skills'—bundled prompts, macros, and procedural runbooks—developers need lifecycle management beyond storing docs in a README. Commenters describe a variety of harness-specific folders, plugin marketplaces, and subagent delegation patterns. The dominant engineering instinct is to treat skills like dotfiles or internal libraries: keep them in Git, install them via symlinks or marketplace add-ons, version-control changes, and consume them through progressive disclosure. Others are skeptical, arguing that generic downloaded skills are snake oil and that modern models can infer context from a good repository. The thread also reveals emerging tooling from Tencent, Vercel Labs, Anthropic's skill-creator, and independent utilities like capshelf and dynobox.

Several concrete practices recur: one repo per personal or team skill set with an 'installer script that symlinks' (gregwebs), plugin-marketplace commands for Codex and Claude (mceachen, jve), and iCloud or Guix Home sync across Macs and VPSs (mark_l_watson, ssivark). Defenders of skills stress that high-leverage workflows are better framed as 'how to do X' than as generic expertise. A much-quoted line from bastawhiz: 'Treat skills as runbooks, not as a way to turn your agent into an expert.' Verification remains immature—commenters use deterministic file-touch tests, AI evals, and periodic pruning or audits. Community sentiment divides between viewing skill-file proliferation as a code smell and seeing it as an infrastructure layer that lets agents operate autonomously in proprietary codebases. No dominant tool has emerged; Git remains the only shared substrate.

“Treat skills as runbooks, not as a way to turn your agent into an expert.” — bastawhiz, summarizing the most practical path forward in the thread.

Key Highlights
  • Skills files are contextual guidance for AI coding agents; they are emerging as a new asset class beyond README and AGENTS.md.
  • A dominant pattern is to keep one Git repo as the source of truth and use installer scripts/symlinks to sync into harnesses.
  • The community is split between authoring skills for your own stack and downloading from marketplaces or skill-sharing sites.
  • High-value skills tend to encode workflow/runbook knowledge: how to deploy, how to query test DBs, how to migrate data safely.
  • A growing minority treats skills as code with integration tests, evals, and periodic pruning to prevent rot and context bloat.

Is mathematics about to enter the conservatory?
⬆ 86 pts 💬 98 HN comments

Mike McCoy's essay frames a quiet inflection point for pure mathematics: the same week Anthropic's Claude reportedly completed a formal Lean proof of Fermat's Last Theorem, an AI-assisted preprint by Wang and Wu claimed the long-open Spherical Hadwiger Theorem, a specialist piece of integral geometry. The author, who once attempted the conjecture in grad school, traces how automated theorem proving has moved from toy examples to research-grade work. He cites OpenAI's post-GPT-4 labor-impact analysis, which estimated 100% of a mathematician's job was exposed to LLMs—higher than writers or artists. Instead of triumphalism, McCoy asks whether mathematics is entering a classical-music-like state: institutionally preserved, enjoyed by a small educated audience, but no longer economically necessary to produce.

The Wang-Wu preprint's ethics statement says OpenAI Codex was used to develop proof details, identify gaps, organize and typeset the manuscript, and edit English; the authors reviewed all AI content. McCoy admits he has not fully verified the argument, only that it passes the 'sniff test' after working through it with Claude Fable. He places the result beside the Leiden Declaration's AI-use principles and warns that academia's fragile incentives—funding, tenure, fame—are poorly adapted to a landscape where no human can compete with machines at generating arguments. HN commenters split on the implications: one camp says humans remain essential as verifiers and storytellers, another argues the math itself can be generated and read by models.

OpenAI's analysis estimated that 100% of a mathematician's job was exposed to LLMs—higher than writers, translators, artists, and graphic designers.

Key Highlights
  • Wang and Wu's AI-assisted proof of the Spherical Hadwiger Theorem uses OpenAI Codex for proof details, gap-finding, and editing.
  • Claude's reported formalization of Fermat's Last Theorem in Lean signals that AI tools can now engage with landmark mathematical arguments.
  • The author argues pure mathematics already resembles a conservatory: the academy shelters it even as economic demand and public comprehension narrow.
  • A major open problem is not proof generation but proof verification and the allocation of funding, tenure, and fame when AI is involved.
  • Commenters disagree over whether AI results matter if no human can fully understand them, comparing the situation to chess spectatorship and live-music economics.

Nitter and XCancel resume service after legal advice
⬆ 821 pts 💬 352 HN comments

Nitter, the free and open-source privacy front-end for X/Twitter written in Nim, has announced it will continue operating after receiving what it calls legal advice. The project was hit with cease-and-desist letters from X Corp. on 24 August 2026, demanding permanent takedown of instances and its repository. The latest commit to zedeus/nitter modifies the README: 'Following legal advice, the Nitter project will continue. More details will be announced soon.' XCancel is also said to be resuming. Technically, Nitter distinguishes itself by proxying all requests server-side: clients never talk to twitter.com, no JavaScript is required, and ads/trackers are stripped out. For example, a @nim_lang timeline weighs ~60KB versus 784KB via the official site, and it supports RSS, themes, and mobile layouts. The GitHub diff also adds a Ko-fi badge, indicating renewed community support.

The legal context is more nuanced than 'Nitter is back.' Many commenters immediately separated the repository from third-party instances. The repo itself is arguably protected as software code, whereas instances that used X accounts to scrape content may violate X's ToS and invite CFAA claims. Nitter had to shift from guest accounts to authenticated scraping after X removed guest access, increasing legal exposure. The README now lists legal@poast.org for DMCA requests. Commenters on HN debate whether legal advice was actually obtained or whether this is a calculated YOLO move; some compare X's action to LinkedIn v. hiQ precedent, while others note that jurisdictions matter. The resilience has broader implications for archiving government posts, avoiding rage-optimized algorithms, and the 'agent-first' future where AI tools scrape social platforms—raising awkward questions about xAI's own data-sourcing practices.

'Following legal advice, the Nitter project will continue.' — the README line that reversed a total shut-down order from X Corp.

GrapheneOS Overhauled Default Apps and Secure Clipboard
⬆ 342 pts 💬 222 HN comments

GrapheneOS, the hardened Android distribution, is systematically replacing the stock AOSP application suite rather than patching Google's increasingly abandoned code. The immediate focus is a fully rewritten Messaging app—its first Alpha release arrived shortly after the announcement, deliberately gated through Alpha/Beta/Stable channels to manage quality expectations. The team's roadmap includes eventual RCS support with standard end-to-end encryption via Messaging Layer Security (MLS), explicitly aiming to remove the dependency on Google Messages and its proprietary Jibe infrastructure. The effort extends to replacing the outdated AOSP Gallery by forking ReFra (chosen for its Apache-2.0 license, since GPLv3 would conflict with GrapheneOS's own permissive licensing), and likely replacing the AOSP keyboard. Separately, the project announced a secure clipboard feature, which drew attention because the original title combined two distinct developments.

The Hacker News discussion reveals a sophisticated split over whether RCS is worth pursuing at all. Several commenters argue that RCS remains a carrier- and Google-controlled protocol with no real open ecosystem, with one calling it 'DOA' and another asserting it is 'strictly inferior to Signal.' Others defend RCS as the only practical bridge to iOS and legacy Android users, so GrapheneOS supporting it natively is considered a major privacy win. GrapheneOS team members pushed back on assumptions that AI generated the new code: 'We spent months working on this and certainly didn't vibe code it,' adding that LLMs are used mostly for code review and boilerplate while tests have increased. Commenters also shared alternative keyboard and gallery preferences, noting FUTO's licensing and praising Heliboard and ReFra. The overall sentiment is strong community support, tempered by technical skepticism about RCS and concern about AI-assisted development in a security-critical project.

It took a year to ship WebAssembly in Anubis
⬆ 308 pts 💬 149 HN comments

Anubis, an anti-bot service by Xe, uses proof-of-work challenges to make mass scraping by AI companies economically unappealing. The article chronicles a year-long effort to move that challenge solver into WebAssembly (WASM). The hard part was not writing WASM but holding Rust to a true WASM 1.0 baseline. As commenter adrian17 points out, the wasm32-unknown-unknown target silently gained non-MVP features later, effectively becoming a breaking change on stable. Other technical threads recommend wasm32v1-none for strict MVP or build-std to recompile the standard library. For clients with WASM disabled, the author transpiles the optimized binary back into JavaScript as a fallback, preserving access for legacy browsers, policy-blockers, and even smart TVs.

Compatibility work reportedly extended all the way back to Chrome 66-era browsers, and the shipped WASM flow is described as “ridiculously performant,” so much so that the post warns difficulty may need to be adjusted upward. Anubis is framed as an economic deterrent rather than a perfect bot filter: commenters quote the idea that you only need to make scraping expensive enough that abusive traffic stops being profitable. The discussion also raises the environmental waste of proof-of-work, the possibility of GPU/WebGPU accelerated solvers, and future plans for Service Worker-based pre-computed challenge tokens. This is a revealing case study in anti-bot strategy, browser compatibility, and the tensions between accessibility and abuse prevention.

The real challenge wasn't writing WebAssembly—it was keeping Rust's wasm32-unknown-unknown target from silently drifting past the true WebAssembly 1.0 MVP, turning a one-week compile into a year-long compatibility battle.

Key Highlights
  • Anubis uses proof-of-work to make mass AI scraping expensive rather than impossible.
  • Rust's wasm32-unknown-unknown target gained post-MVP features, breaking strict WASM 1.0-compatible builds.
  • No-WASM clients get a transpiled JavaScript fallback for compatibility with old or restricted browsers.
  • The WASM solver is extremely fast, so difficulty settings may need to be raised to keep it effective.
  • The author is testing Service Worker-based challenge renewal tokens for reduced per-page overhead.

Making a Python interpreter in 1024 bytes
⬆ 266 pts 💬 96 HN comments

Austin Z. Henley's 'Making a Python interpreter in 1024 bytes' details a weekend constraint exercise in C. It does not implement real CPython semantics; instead it recognizes just enough Python-like syntax—single-letter lowercase variable names, integer literals, + - * % expressions, comparisons, if/while/for range blocks with else, function definitions/calls, and print—to run a FizzBuzz program. The implementation compiles to nothing: after stripping spaces except inside strings, source text lives in a fixed 999-byte buffer; recursive-descent functions interpret expressions as they parse; and indentation is handled by measuring spaces before each line, using the C call stack for block recursion. Loops and function calls are implemented by recording a location in the source and jumping the parser back to that position, re-running logic until conditions fail. The unreadable golfed version is exactly 1024 bytes and required cutting comparison expressions, multi-character identifiers, and all error checking.

The post generates an unusually rich HN response because it sits at the intersection of code golf, language design, and retro-computing craft. Commenters invoke C4, SectorLISP, sectorC, DOS batch reparsing, and 8-bit micro BASIC interpreters as antecedents; userbinator notes that jumping back in the source was standard practice on micros with 64K address spaces, not merely golf. Others dispute the title: Scubabear68 says it is not Python 'within three orders of magnitude', while jrdres catalogs the keyword assumptions, where any 'w' means while and any 'd' means def. The article's key implementation insight is that readable code over 4800 bytes was shrunk using ASCII comparisons, implicit-int C89 declarations, comma/ternary operators, and recursion. The thread also contains meta arguments about whether source-size or binary-size matters, and whether dropping error handling makes it a 'proper self-contained interpreter' or just a human-checked demo.

'After everything, the golfed version is 1024 bytes! The final readable version is over 4800 bytes.' — Austin Z. Henley

Key Highlights
  • The 1024-byte C interpreter supports a tiny Python-like subset: single-letter integer variables, arithmetic/comparisons, if/while/for range blocks, recursive functions, and indentation-based control flow.
  • Source code is treated as its own AST: loops and function calls reparse the original source position each iteration or invocation, using the C call stack for nesting.
  • Golfing techniques include ASCII value comparisons, implicit-int C89 declarations, global variables as temporaries, recursion, and comma/ternary operators.
  • Only lowercase single-character variable names are supported; keywords are detected by first letter, e.g. any 'f' is treated as 'for', making even 'w = 4' invalid.
  • The readable version is over 4800 bytes, and both versions are on GitHub; commenters compare it to C4, SectorLISP, DOS batch behavior, and 8-bit BASIC interpreters.

Not real PythonA strongly voiced counterpoint is that this 1024-byte interpreter is only skin-deep. Scubabear68 says bluntly: it is 'not Python, or even within three orders of magnitude of Python'; SPBS adds the title 'should have said Python-like'. stingraycharles estimates that the amount of real Python that works is 'probably not a lot more than this specific FizzBuzz example'. shmoil wonders why long integers or power are absent, and Liquid_Fire replies that toy interpreters can reasonably omit such features. The debate is not that small subsets are useless, but that calling it Python overstates fidelity and may mislead readers about Python's breadth and semantics.~15 users
Historical hacking traditionThe HN audience embeds the project in a longer tradition of tiny interpreters. userbinator compares it with DOS .bat processing and says interpreting from source directly was 'standard practice on interpreters for 8-bit microcomputers' when 64K made ASTs wasteful. jeanmichelselli fondly recalls complete BASIC interpreters smaller than 32KB. tempodox links SectorLISP, and gabrielsroka wonders if sectorC could compile python1024. forgotpwd16 adds a sharp distinction: SectorLISP deliberately strips Lisp down until only its essence remains, while python1024 appears to imitate Python's surface syntax without a similarly principled core. This context enriches the article even while underscoring how far Henley's creation is from a production language.~12 users
Metric and self-contained critiqueA less whimsical branch criticizes the exercise's framing. galkk says 'I hate when they measure the size of source code instead of the size of a binary', pointing at .kkrieger as a genuine size demonstration. userbinator notes that 1,024 bytes of C compiles to a binary 'many times larger'. Critics see such assumptions as turning the project into a fragile FizzBuzz demonstrator rather than a dependable interpreter.~8 users
