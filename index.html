Show HN: Lathe – Use LLMs to learn a new domain, not skip past it
⬆ 337 pts 💬 61 HN comments

Lathe is a Go CLI paired with LLM skills (Claude Code, Cursor, Codex) that generates multi-part, hands-on technical tutorials on demand. Unlike typical LLM workflows that automate tasks, Lathe forces the user to manually type out code examples, aiming to preserve the cognitive effort required for deep learning. The tool stores tutorials locally in ~/.lathe/tutorials/, serves them via a purpose-built web UI at localhost:4242, and includes a verification skill that tests whether the tutorial actually compiles. It also features configurable “voices” that control prose style without altering structure or accuracy. The creator, devenjarvis, built Lathe to fill gaps where human-written resources are scarce—for example, writing a 3D slicer from scratch or learning embedded Zig. The architecture (CLI for deterministic tasks, skills for agent harness) is inspired by patterns from Simon Willison and other developer tooling.

Lathe has garnered 337 points and 61 comments on Hacker News, indicating strong interest. The repository includes 874 stars, and the README explicitly acknowledges it is “vibecoded” and experimental. Key implementation details include: skills installed via `lathe skills install` into Claude Code's directory, a metadata.json per tutorial tracking sources, model, voice, and verification status, and a client-side search on the web list page. The verification skill works through every step in a fresh temp directory and records results. The creator notes that Lathe is best used with large “thinking” models (Opus, GPT-5) and that human-written tutorials should be preferred. The highlight: “Lathe is an experiment in using LLMs to teach me, rather than think for me.” This reflects a broader community debate about whether LLMs can be effective educators or merely produce polished slop.

“Lathe is an experiment in using LLMs to teach me, rather than think for me.”

Key Highlights
  • Lathe generates multi-part, hands-on tutorials that users must type out themselves, reversing the typical LLM 'do it for you' pattern.
  • Tutorials are stored locally with metadata tracking sources, model, voice, and verification status.
  • The CLI manages state and serves a web UI; LLM skills handle generation, extension, verification, and Q&A.
  • Voices control prose style without affecting structure; two ship by default, and custom voices can be authored.
  • Verification is opt-in and runs in the LLM session, testing all steps in a scratch directory.

How's Linear so fast? A technical breakdown
⬆ 434 pts 💬 200 HN comments

The article offers a deep technical analysis of Linear’s performance architecture, centering on a local-first approach that inverts traditional client-server dynamics. By treating the browser’s IndexedDB as the primary data store and applying mutations optimistically before syncing via WebSockets, Linear eliminates network latency from critical user interactions. The author, Dennis Brotzky, reverse-engineers observable behaviors to describe a custom sync engine that batches and flushes transactions asynchronously. Key decisions—such as maintaining a MobX-observable in-memory state, using GraphQL for transport, and aggressive code splitting into hundreds of route-level chunks—collectively reduce perceived wait times to milliseconds. The piece also examines Linear’s build pipeline evolution (Parcel → Rollup → Vite → Rolldown), which halved shipped JavaScript and cut time-to-first-paint by 59% on Safari by dropping legacy browser support, aggressive dead-code elimination, and per-package vendor chunking.

Beyond the sync engine, the article details a holistic optimization stack: modulepreload tags flatten the initial load waterfall, a service worker precaches 1,200 assets for instant offline-capable navigation, and inline CSS/JS in the index.html renders a themed shell before authentication even begins. The 'render first, authenticate second' strategy checks localStorage for a cached workspace token and immediately paints the full UI, avoiding spinner-driven auth flows. However, Hacker News comments reveal a stark divide between architectural admiration and real-world experience. Many engineers applaud the rigour ('There’s nothing really new tech-wise… but it takes huge determination'), but longtime users report search slowness, sync inconsistencies (e.g., 'repeated writes sometimes overwrite themselves'), high memory usage in Firefox, and creeping complexity ('Linear has become the thing it sought to kill - complex'). The debate underscores that even the most technically elegant local-first design can introduce new failure modes—optimistic updates handle the happy path, but network partitions and concurrent edits remain hard to resolve without user-visible glitches.

Linear’s secret is treating the browser as the database: 'A few milliseconds is all it takes to update an issue… The actual database the UI reads from is in IndexedDB.'

Key Highlights
  • Local-first architecture: browser IndexedDB as primary store, optimistic mutations, async sync via WebSocket.
  • Aggressive code splitting (per-package chunks) and modulepreload flatten the initial load waterfall.
  • Service worker precaches 1,200 assets for instant navigations and offline functionality.
  • Inline critical CSS/JS in index.html renders a themed shell before authentication completes.
  • Renderer-first auth: checks localStorage for workspace token, avoids spinner-driven auth flows.
