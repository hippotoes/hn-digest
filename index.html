Claude Code sends 33k tokens before reading the prompt; OpenCode sends 7k
⬆ 605 pts 💬 327 HN comments

A rigorous benchmarking study by Systima reveals that Claude Code's agentic coding harness carries significantly higher token overhead than OpenCode before even processing a user's prompt. When asked to reply with a simple "OK", Claude Code sent roughly 33,000 tokens in system prompts, tool schemas, and scaffolding, compared to OpenCode's 7,000. The dominant contributor is tool schema definitions: Claude Code's 27 tools contribute ~24,000 tokens, while OpenCode's 10 tools add ~4,800. Even with tools stripped, Claude Code's system prompt is 6.5k tokens—over three times OpenCode's—due to extensive behavioral doctrine, skill catalogs, and environment descriptions. The overhead shrinks with newer models (from 4.7x to 3.3x on Claude Fable 5) but remains substantial. Critically, the study also finds that while Claude Code's aggressive batching can close the gap on multi-step tasks, this advantage is model-dependent and does not hold across all conditions.

The study identifies several multipliers that compound token usage in production. A 72KB instruction file adds ~20,000 tokens per request; five MCP servers add 5,000–7,000 more. Subagents are the largest multiplier, with a 4.2x cost increase for a simple fan-out (from 121k to 513k tokens) due to each subagent bootstrapping its own context and the parent consuming full transcripts. Cache behavior is a decisive differentiator: OpenCode emits byte-identical prefixes across sessions, enabling near-total cache read hits, while Claude Code repeatedly rewrites its cache mid-session—writing up to 54x more cache tokens on identical tasks. Cache writes are billed at a premium, further inflating costs. The commenters echo these findings, with many reporting unexpectedly high token consumption from subagents and expressing frustration over perceived incentives for Anthropic to maximize token usage. The broader implication is that harness design—not just model choice—dramatically impacts the economics and efficiency of agentic coding.

Claude Code's first-turn token overhead of ~33,000 is 4.7x larger than OpenCode's, but on multi-step tasks, its aggressive batching can invert the comparison—yet this advantage vanishes on newer models.

Key Highlights
  • Claude Code sends ~33k tokens before reading the prompt, vs. ~7k for OpenCode, driven mainly by tool schemas (24k vs 4.8k).
  • Subagents multiply token costs dramatically: a 121k-token direct task cost 513k when fanned out to two subagents.
  • Cache inefficiency plagues Claude Code: up to 54x more cache writes than OpenCode on identical tasks, incurring premium billing.
  • Configuration multipliers (instruction files, MCP servers, frameworks) can push first-request tokens to 75k-85k.
  • Claude Code's multi-step batching advantage is model-dependent; on newer models it disappears, costing 2.2x more than OpenCode.

What xAI's Grok build CLI sends to xAI: A wire-level analysis
⬆ 479 pts 💬 173 HN comments

A detailed wire-level analysis of xAI's Grok Build CLI (v0.2.93) reveals that the tool surreptitiously uploads the entire working repository—including git history and files the agent was explicitly told not to read—to a Google Cloud Storage bucket named grok-code-session-traces, regardless of the 'Improve the model' privacy toggle. Using mitmproxy, the researcher captured and decrypted traffic showing that file contents, including a .env secrets file containing API keys and passwords, are transmitted verbatim both in the model-turn endpoint (POST /v1/responses) and in a separate session_state archive uploaded via POST /v1/storage. Notably, a control run with a never-read canary file proved that unread files are absent from the model-turn channel but present in the storage uploads. The most damning evidence came from a 12 GB repository of random files that the agent never read: the storage channel moved 5.10 GiB in 73 ~75 MB chunks (all HTTP 200), while the model-turn channel consumed only 192 KB—a ~27,800× ratio. This demonstrates a dedicated whole-repo snapshot mechanism independent of the agent's actual tool calls.

The uploads are packaged as git bundles, allowing complete reconstruction of the repository, including files the agent was told not to open. In one test, a canary marker in a never-read file was recovered verbatim from a captured bundle after the prompt 'Reply exactly OK, do not read any files.' The analysis also found that disabling 'Improve the model' in settings had no effect: the trace_upload_enabled flag remained true. The binary strings confirm the upload machinery is a first-party Rust crate (xai-data-collector) and that the destination is a GCS bucket, not AWS S3. While cloud coding agents necessarily transmit context, this exfiltration of the entire codebase—without user consent or clear documentation—raises severe privacy concerns and undermines trust in AI coding tools. The HN community reacted with shock, proposing mitigations like environment variables (GROK_TELEMETRY_TRACE_UPLOAD=0) and sandboxing with bubblewrap, while others debated whether this is standard behavior or an unforgivable overreach.

How we can reduce traffic congestion
⬆ 140 pts 💬 206 HN comments

Google Research published a large-scale real-world experiment in Nature Cities demonstrating that network-aware routing modifications can reduce traffic congestion even when applied to a tiny fraction of trips. Over six months in ten U.S. cities, Google Maps algorithm was tweaked to gently guide vehicles away from pre-identified congested segments toward alternative routes with similar travel times. Only 2% of trips were rerouted, yet the intervention yielded a median 2% speed increase on targeted segments and ~0.5-1% fuel consumption reduction network-wide. The experiment used a city-wide switchback design, alternating treatment and control days, and a hierarchical Bayesian model to estimate outcomes. This work is the first empirical validation that coordinated, albeit minimal, routing changes can improve overall traffic efficiency, analogous to load balancing in computer networks.

The study draws on concepts from network theory—specifically Braess's paradox, where adding options can worsen congestion—and applies them to real roads. While the median speed gain is modest (~0.35% over all affected segments), during peak hours it rises to 0.5%, translating to thousands of tons of CO2 savings per city per year. However, the article also highlights that these benefits come with trade-offs: rerouting traffic to peripheral roads not designed for high volumes can cause wear, safety issues, and community pushback—a point echoed in HN comments. The research establishes a framework for evolving from individual trip optimization to cooperative routing, but critics argue that such micro-optimizations pale in comparison to structural changes like public transit, remote work, or congestion pricing. Google's approach is a technically elegant step, but its real-world impact remains bounded by the fundamental geometry of car-centric infrastructure.

Even rerouting just 2% of trips yielded a median 2% speed gain on congested segments and potential savings of thousands of tons of CO2 per city per year.

Key Highlights
  • First large-scale empirical study on network-level routing optimization for traffic
  • City-wide switchback experiment in 10 US cities over 6 months
  • Only 2% of trips rerouted, yet measurable improvements in speed and emissions
  • Hierarchical Bayesian model used for causal inference
  • Benefits and limitations: modest gains vs. externalities like road wear and community disruption

Tiny Emulators
⬆ 272 pts 💬 23 HN comments

Tiny Emulators is a web-based collection of cycle-accurate emulators for dozens of retro computers and consoles, from the ZX Spectrum and Commodore 64 to obscure East German machines like the KC85. The project's key innovation is its 'cycle-stepped' CPU emulation: rather than treating the CPU as a privileged controller that runs ahead of other components, each chip—CPU, video controller, sound chip—is advanced one clock cycle at a time in lockstep. This approach, combined with pin-level I/O modeling (literally emulating the electrical state of every pin on each chip), enables unprecedented accuracy and modularity. The emulator is written in C and compiled to WebAssembly via Emscripten, running entirely in the browser with no server-side processing. The author, flohofwoe, has also open-sourced the chip emulation library ('chips') on GitHub, allowing other developers to reuse these modular, conformance-tested components in their own projects.

The article itself is essentially a giant list of preconfigured system ROMs and games that boot instantly—a stark contrast to the original tape-loading experiences that could take minutes. This instant-on capability is a direct emotional hook for many commenters, who recall the agonizing wait times of their youth. Technically, the emulator's modular design is its standout feature: each chip (e.g., Z80, 6502, CRTC, AY-3-8912) is a self-contained black box with explicit interface pins, making it possible to mix and match components from different systems. As commenter Lerc notes, 'extremely thin but explicitly defined interfaces are an under-explored domain for interoperability,' and this approach could serve as a model for conformance testing in broader software engineering. However, some users noted UI issues, particularly the absence of per-emulator volume controls, and the linked URL was outdated (the correct, up-to-date site is at floooh.github.io/tiny8bit/). The project last saw major updates in 2021, but remains a beloved reference for cycle-accurate emulation enthusiasts.

The CPUs are 'cycle stepped'—ticked along with all other chips, no longer having a special controller role—enabling pin-level accuracy and modular component reuse.

Key Highlights
  • Cycle-stepped CPU emulation advances all chips in lockstep, eliminating the CPU's privileged controller role.
  • Pin-level I/O modeling emulates the electrical state of every chip pin for maximum accuracy.
  • The emulator runs in-browser via Wasm with no server-side processing.
  • Modular chip components (e.g., Z80, CRTC) are designed as self-contained black boxes with explicit interfaces.
  • The article lists over 100 preconfigured games and demos spanning multiple retro platforms.
