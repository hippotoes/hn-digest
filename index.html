Gemini 3.5 Flash
⬆ 809 pts 💬 562 HN comments

Google's Gemini 3.5 Flash release marks a strategic pivot toward agentic AI, combining frontier-level intelligence with action-oriented capabilities. Built for complex long-horizon tasks, the model achieves a 76.2% score on Terminal-Bench 2.1 and 84.2% on CharXiv Reasoning, outperforming its predecessor Gemini 3.1 Pro on multiple coding and agentic benchmarks. Its 4x speed advantage over other frontier models stems from serving on TPU 8i infrastructure, enabling rapid planning and iteration for real-world applications like codebase maintenance, financial document preparation, and dynamic UI generation. The model powers Google's new Antigravity platform for multi-agent orchestration, allowing collaborative subagents to tackle problems at scale. However, the lack of disclosed parameter counts has sparked community speculation, with inferences placing it in the 200-300B parameter range based on memory and compute constraints from the TPU hardware.

The pricing direction has drawn sharp criticism: per-million-token costs have tripled from Gemini 2.5 Flash ($0.30/$2.50) to $1.50/$9.00, with total evaluation costs rising over 5x in some benchmarks. This contradicts the narrative of decreasing AI costs and threatens unit economics for API-dependent applications. Performance data shows regression in tool-use efficiency compared to earlier models, and agentic SQL benchmarks place it below Gemini 3.1 Flash Lite Preview in both cost and accuracy. Nevertheless, early enterprise partners like Shopify and Macquarie Bank report meaningful workflow automation gains. The community remains divided: while some hail the speed and frontier capabilities as a breakthrough for personal AI agents like Gemini Spark, others question whether the price-performance trade-off makes economic sense versus open-weight alternatives from China, which continue to push the Pareto frontier downward.

3.5 Flash delivers frontier-level intelligence at exceptional speed — 4x faster than other frontier models — but at triple the price of its predecessor.

OpenAI Adopts Google's SynthID Watermark for AI Images with Verification Tool
⬆ 286 pts 💬 155 HN comments

OpenAI has announced the integration of Google DeepMind's SynthID invisible watermark into images generated by ChatGPT, Codex, and the OpenAI API, marking a significant step in content provenance. This multi-layered approach combines C2PA metadata—an open standard for cryptographic content credentials—with SynthID's durable watermarking, which is designed to survive common transformations like screenshots, resizing, and format changes. The company also previews a public verification tool that checks for both C2PA metadata and SynthID signals, though it initially only supports OpenAI-generated content. This move follows OpenAI's recent achievement of C2PA Conforming Generator status, giving platforms a standardized way to read and preserve provenance metadata. The announcement underscores the industry's shift toward ecosystem-wide solutions to combat AI-generated disinformation, acknowledging that no single technique is foolproof.

The technical debate is already evident in Hacker News comments. Some users claim to have developed removal methods, such as masking every second pixel and inpainting (himata4113), or using spectral analysis (aloshdenny's reverse-SynthID repo). However, others argue that no publicly available repository reliably removes production SynthID watermarks from OpenAI or Google's latest models (Tiberium, amazingamazing). Critics like WhatIsDukkha dismiss the effort as 'performative nonsense' and 'DRM glorp', while others worry about closed-source implementation enabling eventual copying or surveillance (minimaxir, bsder). A positive note comes from ericpruitt, who saw falsified posts debunked via SynthID checks. The societal impact is double-edged: while provenance tools can help verify authenticity, they also raise privacy concerns and may be circumvented by sophisticated actors. OpenAI plans to expand verification across platforms, aiming for a more interoperable trust ecosystem.

"No single provenance technique is enough on its own. We believe a strong approach combines shared standards, durable watermarking signals, and public verification." — OpenAI, 2026

Key Highlights
  • OpenAI integrates SynthID invisible watermark into ChatGPT, Codex, and API images.
  • Multi-layered provenance uses C2PA metadata and SynthID for resilience.
  • Public verification tool previewed, initially only for OpenAI content.
  • Debate in comments: some claim removal methods exist, others say they are ineffective.
  • Critics cite closed-source nature, potential for DRM-like control, and privacy risks.

⬆ 680 pts 💬 350 HN comments

Apple's latest accessibility announcement leverages Apple Intelligence to inject natural language understanding and on-device AI into core assistive tools like VoiceOver, Magnifier, Voice Control, and Accessibility Reader. The move also extends the Vision Pro’s utility with eye-controlled wheelchair navigation and introduces systemwide generated subtitles for uncaptioned video, hinting at a broader push to make every Apple device more autonomously assistive.

Outside the software stack, the Hikawa adaptive MagSafe grip launches globally in new colors, and Apple Vision Pro’s wheelchair control—built with Tolt and LUCI—offers recalibration-free eye tracking for users with ALS or severe mobility impairments. The generated subtitles feature, rolling out across iPhone, iPad, Mac, and TV, promises to fill a gap in personal and streaming content. As Tim Cook noted, Apple’s approach combines powerful capabilities with 'privacy by design,' aiming to set a new bar for inclusive technology.

“The option to control my power wheelchair on my own is gold to me,” said Pat Dolan, founder of GeoALS and member of Team Gleason’s patient advisory board.

Show HN: Forge – Guardrails take an 8B model from 53% to 99% on agentic tasks
⬆ 505 pts 💬 176 HN comments

Forge is a Python framework that dramatically boosts the reliability of local LLMs on multi-step tool-calling tasks through a layered guardrail system. The core insight is that small models (8B) can achieve near-frontier performance when their outputs are mechanically validated and corrected. Forge implements rescue parsing for malformed tool calls, retry nudges that gently steer the model back on track, and step enforcement to ensure required actions aren't skipped. Context management prevents VRAM overflow via tiered compaction and token budgets. The project emerges from a growing recognition that model intelligence is only part of the equation—the harness around the model often matters more, especially for open-source, self-hosted stacks. By providing a reliability layer as a proxy or middleware, Forge makes local models viable for production agentic workflows without requiring fine-tuning or cloud APIs.

The numbers are striking: an 8B model jumps from 53% to 99% on agentic tasks when wrapped in Forge's guardrails. In their 26-scenario eval suite, the best self-hosted config (Ministral-3 8B Instruct on llama-server) scores 86.5% overall and 76% on the hardest tier. The author notes that the serving backend itself produces wild variance—same weights can yield 7% accuracy on one backend and 83% on another due to function calling template differences. HN comments reflect both enthusiasm and caution: users report similar gains with small models but flag that raw speed and parallelism remain under-addressed. Others question whether this duplicates existing harness retry logic, while the author clarifies Forge operates at a lower, more generic level. The project includes a proxy server that transparently injects a synthetic 'respond' tool to keep models in tool-calling mode, a critical design choice for small models that cannot reliably choose between text and tools.

An 8B model jumps from 53% to 99% on agentic tasks—not by fine-tuning, but by mechanically enforcing reliable tool-calling through guardrails.

Key Highlights
  • Forge uses guardrails (rescue parsing, retry nudges, step enforcement) to lift 8B local models to ~99% reliability on tool-calling tasks.
  • The serving backend dramatically affects performance: same weights can differ by 76+ percentage points depending on function calling template support.
  • A proxy mode allows transparent integration with existing tools (OpenAI-compatible clients) by injecting a synthetic respond tool to keep the model in tool-calling mode.
  • Community feedback highlights the need for speed benchmarking and parallel retry strategies, as well as clarification on how Forge differs from existing harness retry mechanisms.
  • The project demonstrates that with a proper harness, small local models can be viable for production agentic workflows, reducing dependency on cloud APIs.

#12
CopyFail: From Pod to Host
⬆ 22 pts 💬 3 HN comments

Copy Fail (CVE-2026-31431) is a novel Linux kernel vulnerability that enables a deterministic, controlled 4-byte write into the page cache of any readable file, bypassing standard write accounting. It exploits the authencesn code path in the kernel's IPSec ESP Extended Sequence Number handling, accessible to unprivileged users via AF_ALG sockets and splice(2) zero-length copies. Because the page cache is shared across containers through the underlying inode's address_space, two containers on the same host that access the same lower-layer file (e.g., from a shared container image layer) will see the mutated cached folios. This allows an attacker in one pod to poison files in another pod's mount namespace without altering on-disk bytes, making it invisible to conventional disk-based scanners. The primitive is exceptionally portable, working from the 2017 in-place commit through the 2026 fix, and does not require kernel code execution.

The article outlines two primary attack scenarios: cross-container poisoning and container escape. In the first, an attacker in a compromised pod (or one that only needs pods/create rights) can modify a shared library or Python module in a commonly used base layer (e.g., python:3.12-slim), affecting all co-located pods that import it. The second scenario follows the Dirty Pipe pattern: by forcing runc to exec a process (e.g., via kubectl exec), overwriting /bin/sh with a shebang pointing to /proc/self/exe, and then poisoning the runc binary through its page cache, the attacker gains a root shell on the host. Mitigations include patching the kernel (commit a664bf3d603d), blocking AF_ALG via seccomp, and adopting microVM-based isolation like gVisor or Kata Containers. The researchers note that agent-less disk scanners and image registry scans are ineffective because the compromise lives only in the kernel's page cache.

Copy Fail gives attackers a repeatable, controlled 4-byte write into the Linux page cache backing any readable file, enabling deterministic container escape without kernel code execution.

Key Highlights
  • Copy Fail exploits the authencesn code path for IPSec ESP Extended Sequence Numbers via AF_ALG sockets and splice(2) to achieve a controlled 4-byte page cache write.
  • The page cache is shared across containers because it is backed by the host inode's address_space, not namespaced; any file descriptor pointing to the same underlying inode sees the modified cached data.
  • Cross-container poisoning occurs when containers share a lower overlayfs layer (e.g., same base image hash): attackers can modify files like Python modules or shared libraries, affecting co-located pods.
  • Container escape is achieved by poisoning the runc binary via /proc/<runc_pid>/exe after forcing runc to exec, granting a root shell on the host; the method mirrors Dirty Pipe but works on more kernel versions.
  • Effective mitigations include kernel patching, blocking AF_ALG with seccomp, and using per-pod microVMs or sandboxes (gVisor, Kata) that provide separate kernels and page caches.
