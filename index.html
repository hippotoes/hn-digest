We have proof automation now
⬆ 181 pts 💬 69 HN comments

The article 'We have proof automation now' by Adam Langley (ImperialViolet) argues that large language models (LLMs) are on the verge of making dependently-typed programming languages like Lean dramatically more practical for real-world software engineering. Traditionally, languages with powerful type systems that can encode arbitrary invariants (e.g., Lean, Coq) impose a huge proof burden—the seL4 project spent 10× more effort on proofs than on design and implementation. Langley demonstrates the potential by building a Zstandard decompressor in Lean, where an LLM automatically generated machine-checked proofs for subtle properties of the FSE entropy decoder's table construction algorithm. He emphasizes that because proofs are irrelevant to execution (only their existence matters), LLMs can cheaply produce correct proofs, reducing the overhead from a 10× factor to a matter of minutes and pennies. The author confirms that the LLM-generated proofs type-check and contain no 'sorry' placeholders, marking a practical breakthrough in proof automation.

Langley details how Zstandard's entropy coding works—using a finite state entropy (FSE) coder that approximates fractional bit costs by giving multiple states to common symbols—and how Lean's strict evaluation, imperative do-notation, and reference-counting optimizations make it suitable for performant systems programming. He reports that his toy decoder is 10× slower than the reference implementation, but expects parity with further LLM assistance. The article also touches on verified assembly, noting that AWS's LNSym could let LLMs safely optimize critical routines. The HN comments reflect a divided community: some are bullish on formal specs becoming the programmer's primary skill (gz09: 'writing formal specs is probably the main skill a programmer in the future will need'), while others worry about specification correctness (davemp: 'Now we can write bugs in our theorem descriptions instead of source code') and maintenance scalability (el_pollo_diablo: 'dependent types and total functions do not scale'). Overall, the piece ignited a deep debate on whether LLM-driven formal methods will finally bridge the gap between academic rigor and industrial practice.

LLMs can now generate complete, machine-checked proofs for complex algorithmic properties in about 20 minutes, using a fraction of a subscription quota — turning a 10x overhead into a manageable cost.

Key Highlights
  • LLMs combined with proof irrelevance dramatically reduce proof effort.
  • Author built a Zstandard decompressor in Lean with LLM-generated proofs.
  • FSE entropy encoder uses a state machine with fractional bits per symbol.
  • Lean's strict evaluation, imperative sugar, and reference-counting optimization make it practical.
  • Verified assembly (AWS LNSym) could enable safe optimization with LLMs.

⬆ 324 pts 💬 75 HN comments

It supports sound, images, hypertext, and scripted behavior, exporting to self-executing .html files that run anywhere. Key technical innovations include deep undo history, scroll wheel/touchscreen support, bulk editing, and a line-oriented text format compatible with Git. Decker also offers a headless interpreter (Lilt) for command-line usage, and even a Lil interpreter in POSIX AWK. The platform deliberately excludes advertising, telemetry, and generative AI integration, emphasizing user autonomy.

The HN community response is deeply nostalgic but also critically examines Decker's practical relevance. Commenters recall HyperCard's extraordinary ease of use—'as easy as writing in a notebook'—and note that it empowered non-programmers to build real applications. Others celebrate Decker's exportability for web zines and indie games, and the novel Lil language for introducing APL family concepts to new audiences. The project has sparked prior discussions across multiple HN submissions, indicating sustained interest.

Lil, Decker's scripting language, combines Lua's imperative familiarity with Q's functional vector operations, enabling 'a few lines of Lil go a long way.'

Key Highlights
  • Decker exports to standalone self-executing HTML documents, shareable anywhere.
  • Lil language mixes Lua-like syntax with APL/Q-style implicit scalar-vector arithmetic and SQL-like queries.
  • Headless interpreter Lilt allows scripted deck manipulation from command line.
  • Deck format is line-oriented text, compliant with Git and SVN for version control.
  • The platform has no telemetry, advertising, or generative AI features, prioritizing user privacy.

However, some faced confusion over the reverse concept, accidental double-click placement, and mobile layout issues. The author actively addresses feedback, highlighting a dark mode hidden in settings and explaining the hint system for stuck players.

The game’s solver classifies puzzles into five tiers (Easy–Insane) by the hardest deduction technique required, with what-if chains up to 4+ steps for Insane grids.

Go Analysis Framework: modular static analysis by go team
⬆ 212 pts 💬 77 HN comments

The Go team's `analysis` package, part of `golang.org/x/tools/go/analysis`, provides a standardized framework for building modular static analysis tools. It defines an `Analyzer` type that encapsulates name, documentation, flags, and a `Run` function operating on a `Pass` (representing a single package). Key design elements include dependency management via `Requires` (acyclic graph), a `Fact` mechanism for inter-package communication (e.g., recording that a function is a printf wrapper), and optional result types (e.g., control-flow graphs). The framework is used by `go vet` and hundreds of community linters, with over 6,500 importers. It supports separate compilation-like analysis: facts are serialized via `gob` for cross-package propagation, enabling scalable, modular checks. The package also provides `Validate` for sanity-checking analyzers and `analysistest` for testing with `// want` annotations.

This HN submission resurfaces the framework in response to a comment on a Ruff (Python linter) thread, where a user expressed envy for similar Go tooling. Commenters highlight practical applications: SpiceDB uses custom analyzers for code review efficiency, and others use them for 'adversarial anti-slop' pre-commit checks. Despite the framework being mature (v0.48.0, published July 2026), several commenters note its lack of visibility. Sentiments range from strong advocacy for Go's tooling (citing readability and community standards) to criticism of verbosity (e.g., manual `if err != nil`). The discussion underscores the gap between Go's powerful but under-advertised analysis infrastructure and the desire for more ergonomic static analysis in other languages.

The `analysis` framework is imported by over 6,564 packages and powers `go vet`, making it the backbone of Go's modern static analysis ecosystem.

Key Highlights
  • Defines the `Analyzer` type with `Run`, `Requires`, `FactTypes`, and optional `ResultType`.
  • Supports modular, cross-package analysis through serializable `Facts` (gob-encoded).
  • Pass provides access to syntax trees, type info, and reporting functions (`Reportf`, `ReportRangef`).
  • Includes utilities: `Validate` for analyzer sanity checks, `analysistest` for testing, `singlechecker` and `multichecker` for standalone commands.
  • Used extensively by `go vet` and third-party linters; enables efficient static analysis comparable to separate compilation.

Scriptc by Vercel: TypeScript-to-Native compiler, no JavaScript engine in binary
⬆ 205 pts 💬 105 HN comments

Vercel Labs has released Scriptc, a compiler that transforms ordinary TypeScript into small, fast native executables without requiring Node.js, V8, or any JavaScript runtime in the binary. The project claims to compile the majority of TypeScript constructs—including classes with inheritance, closures, async/await via stackful fibers, and a large portion of the Node.js standard library (fs, http, net, crypto, etc.)—directly to native code via an LLVM or C backend. For code that cannot be statically compiled (e.g., dynamic npm dependencies), Scriptc optionally embeds a 620KB QuickJS engine. The compiler enforces correctness through differential testing against Node and memory-safety audits with AddressSanitizer. Benchmarks on Apple M-series show startup times of ~2.4ms and binary sizes around 178KB for static builds, rivaling Go and Zig while maintaining byte-exact JavaScript semantics.

However, the community reaction is deeply skeptical. Many commenters note the project's 918,000 lines of code landed in a single week, attributing it to AI coding agents rather than human engineering. Others point to Vercel's pattern of launching ambitious projects (e.g., Zerolang) that are quickly abandoned after generating buzz. Technical concerns include the practical need for npm dependencies (which would force embedding the JS engine, bloating binaries to ~3MB) and the limited platform support (macOS arm64 primary, others via cross-compilation). Hacker News commenters also question Scriptc's value compared to existing solutions like Bun, Node.js single-executable applications, or truly native languages like Go and Rust. The project's heavy reliance on vibecoding has led many to view it as a growth hack rather than a serious tool, undermining its credibility despite its technically impressive claims.

Scriptc compiles 99% of TypeScript statements to native code, producing a 178KB binary with ~2.4ms startup—no JavaScript engine required.

Key Highlights
  • Scriptc compiles TypeScript directly to native executables without any JavaScript runtime, achieving ~178KB binary sizes and ~2.4ms startup times.
  • It uses differential testing against Node and memory-safety checks to ensure correctness and avoid silent miscompilation.
  • Nearly 1 million lines of code were committed in a single week, leading to widespread suspicion that AI coding agents generated most of the codebase.
  • Vercel has a pattern of launching ambitious projects (e.g., Zerolang) and then abandoning them, eroding trust in Scriptc's long-term viability.
  • While technically impressive, practical limitations (npm dependency handling, platform support) and ecosystem challenges limit its immediate utility for most developers.

Introduction to Data-Oriented Design [pdf]
⬆ 186 pts 💬 51 HN comments

Data-Oriented Design (DoD) is a programming paradigm that prioritizes data layout and access patterns over traditional object-oriented abstractions, aiming to maximize hardware efficiency. Popularized by Mike Acton's talks and the game development community, DoD challenges developers to think about how data is stored in memory, accessed by the CPU, and moved through caches. The linked PDF is a seminal introduction to this mindset, emphasizing that optimal performance comes from understanding the 'shape' of data and designing algorithms around it. DoD is not just about cache optimization; it's a holistic approach that influences everything from data structure selection to parallel processing strategies. The Hacker News discussion reveals a community deeply engaged with these concepts, yet divided on practical applicability and philosophical implications.

Comments on the story highlight both enthusiasm and skepticism. Advocates point to languages like Odin that embed DoD as a central paradigm, and to ECS (Entity Component System) architectures that naturally follow DoD principles without heavyweight frameworks. Others argue that DoD's rigidity clashes with evolving requirements in complex systems, and that its benefits are most pronounced in domains like game engines or high-frequency trading. A notable sub-thread compares DoD to relational database design, suggesting that normalized data layouts and index-based access patterns are a form of DoD. The conversation also touches on whether DoD is essentially 'array programming' or 'cache-aware algorithms,' with some insisting it is a distinct philosophy that extends beyond mere performance to a fundamental way of reasoning about software.

The essence of Data-Oriented Design is thinking about data layout and access patterns first, before algorithms, to maximize hardware utilization.

Key Highlights
  • DoD prioritizes data layout and memory access patterns over traditional OOP abstractions.
  • The paradigm is heavily used in game development and other performance-critical applications.
  • Advocates cite ECS and languages like Odin as natural fits for DoD.
  • Critics note DoD's rigidity in face of changing requirements and potential for dogma.
  • DoD shares principles with relational database normalization, emphasizing data-centric design.
