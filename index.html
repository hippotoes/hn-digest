#1
LLMs reward expertise
⬆ 980 pts 💬 414 HN comments

Sean Goedecke's essay argues that the most valuable skill in working with LLMs is domain expertise, not prompt craft. Using Terence Tao's ChatGPT session on the Jacobian Conjecture counterexample as a case study, he observes that Tao's prompts are terse, signal expertise, and push back against questionable model outputs without dictating. The model responds by entering a 'talking-to-mathematicians' mode, producing concise, high-level reasoning. Goedecke contends that the same LLM yields dramatically different value depending on the user's ability to recognize what 'looks weird,' propose alternatives, and steer the conversation. This reframes the bottleneck: the model often already contains the information, but extracting it requires a knowledgeable human. The thesis extends to software engineering, where familiarity with a specific codebase matters more than general system design theory, echoing his earlier argument that concrete specifics dominate.

The HN thread largely validates the core claim with personal anecdotes and sharp counterpoints. One commenter with BLE and scripting experience found a three-hour 'bot sitting' session straightforward, and another uses ChatGPT as a 'coding partner' for subtle memory bugs. Several note that adding just a few expert terms to a prompt dramatically changes output quality. But a contingent invokes the 'bitter lesson': tasks progress from impossible to expert-prompted to one-shot, so this advantage may be temporary. Others worry that juniors who rely on LLMs never build the hands-on familiarity needed to become experts. The discussion also surfaces the chat interface's shortcomings for novices, comparing query- vs browse-style access, and one commenter likens prompting to conditioning a Gaussian process into one's knowledge space. Overall, the thread affirms that today, expertise compounds LLM capability, while arguing about how durable that edge will be.

By signalling expertise, Tao shunts the model into 'talking-to-mathematicians' mode, not 'explaining-to-amateurs' mode — and 'it takes a very smart human to pull it out.'

Key Highlights
  • Terence Tao's short, expert-signalled prompts elicit concise, high-level model responses, unlike verbose amateur-mode output.
  • Domain knowledge lets users recognize 'weird' outputs, push back, and propose alternative directions the model misses.
  • The human is often the bottleneck: communicating exactly what kind of solution is desired is harder than generating it.
  • LLMs raise the floor for generalists, but the ceiling is far higher for those with deep codebase or domain familiarity.
  • Commenters debate whether this expertise premium is permanent or a transient phase before models one-shot all tasks.

#9
Smaller, faster, safer: running Kimi and GLM at scale
⬆ 221 pts 💬 58 HN comments

Cloudflare's Workers AI team details how it serves Moonshot's Kimi K2.6 and Z.ai's GLM 5.2 on GPU clusters using SGLang, leaning on disaggregated prefill/decode to apply different optimizations to each phase. Quantizing the KV cache from BF16 to FP8 halves its memory footprint, raising Kimi's resident context from ~686K to ~1.37M tokens. BF16 runs out of memory at 32 concurrent requests, while FP8 sustains 64, delivering 2,192 tok/s vs. 1,558 peak BF16 — a 41% throughput gain at ~30% lower cost per token. Weight compression drops GLM 5.2 from 705GB to 421GB, making decode faster by reducing memory-bandwidth pressure, though prefill slows slightly, so they run FP8 prefill and INT4 decode. Cloudflare reports benchmark parity and says these efficiency gains reduce cost without changing model accuracy.

The post emphasizes that 'none of this would matter if it changed the model's answers,' and tables across GSM8K, ARC, MMLU, and an internal benchmark show differences well below one point. But HN engineers immediately push back: the suite lacks coding benchmarks, tool-call validity is only lightly tested, and aggregate scores can hide per-example degradation. To protect the denser shared KV cache, Cloudflare adds page tags and integrity checks that abort mismatched requests, with measured overhead under 1% on throughput and p95 latency. The larger conversation is about transparency — whether providers should label quantized models, whether data is tampered with, and whether Cloudflare's AI-generated prose style itself erodes trust. The efficiency work is real, but the community wants stronger evaluation methodology and clearer disclosure.

FP8 KV cache lets Kimi K2.6 serve 64 concurrent requests at 2,192 tok/s — 41% faster and 30% cheaper per token than BF16's peak at 32 requests.

Key Highlights
  • FP8 KV cache halves memory footprint, doubling context capacity from ~686K to ~1.37M tokens.
  • INT4 weight compression shrinks GLM 5.2 from 705GB to 421GB and speeds decode up to 55% at low concurrency.
  • Cloudflare runs FP8 prefill and INT4 decode to get the best of both: prefill is compute-bound, decode is memory-bound.
  • KV cache integrity checking adds page tags and abort-on-mismatch, with measured overhead under 1%.
  • Community pushback focuses on missing coding benchmarks, lack of pricing transparency, and trust concerns around cloud inference.

Devtools must be open source
⬆ 620 pts 💬 206 HN comments

In 'Devtools Must Be Open Source,' David Crawshaw argues that LLM agents are fundamentally transforming the economics of software personalization. His thesis is direct: if an agent can download source, patch it for a single user, and maintain the fork through a nightly 'fetch upstream and rebase' cron, then config files and plugin APIs become obsolete. The source itself is the extension point. Crawshaw demonstrates with meat.dev, a diff-minimizing tool he integrated into Shelley via one natural-language prompt, including background preprocessing of commits and a toggle in the UI. He credits this to the skill-based agent architecture, not extension hooks. The broader claim is that closed-source devtools—specifically Claude Code—will be left behind because users cannot instruct an agent to change their internals. Thus, devtools must be open source to realize what he calls 'the age of personalized software.'

The Hacker News thread (620 points, 206 comments) is sharply divided. Simon Willison agrees: 'LLMs have changed that equation in a way that makes the original dream much more feasible.' Yet resistance is strong. One top commenter calls the nightly rebase setup 'hell,' warning that AI executes the letter, not the spirit, so 'check that the software works as intended' is insufficient. Others defend configuration and plugins on efficiency grounds, arguing constant rebuilding burns electricity when a parser could be written once. Maintainers note forks create permanent upgrade tax, and business-focused commenters invoke Sendmail's failure to monetize as a cautionary tale. The author's affiliation with exe.dev—a company selling cloud VMs—also draws cynicism. The debate centers on whether LLMs truly eliminate the hidden costs of forking or merely shift them.

"The source code is the extension system."

Key Highlights
  • LLM agents lower the cost of personalizing open-source software by directly editing and rebasing on upstream.
  • The author proposes nightly cron jobs to fetch upstream and rebase local changes, making maintenance autonomous.
  • Demonstration: author added meat.dev diff-minimizer to Shelley with one prompt, including background preprocessing and a UI toggle.
  • Crawshaw argues plugin/config systems become unnecessary; the source code is the extension system.
  • Closed-source agents like Claude Code cannot offer this personalization; therefore devtools must be open source.

Show HN: Run an 80B Qwen in 4.3 GB of RAM on a Mac, and a 35B on an iPhone
⬆ 190 pts 💬 84 HN comments

Swiftlet is a from-scratch Swift + Metal runtime that proves hybrid MoE models can run on ordinary Apple hardware by streaming expert weights from SSD instead of holding them in RAM. For Qwen3-Next-80B-A3B, peak memory drops to ~4.3 GB (42 GB on disk) while generating at 4.5–5 tok/s on an M5; the 35B variant needs only 2.6 GB and reaches 7–11 tok/s. The trick exploits Qwen's high MoE sparsity: only ~3B of the model's parameters are active per token, so Swiftlet keeps the dense attention/routing layers resident and fetches each token's 8–10 experts with a single pread from a purpose-built .qpack container. A bounded pool with LFU-plus-recency eviction and fixed-stride blob layout keeps cache misses cheap, while Metal kernels are runtime-compiled to ship identical code on macOS and iOS.

The project is already validated end to end: per-layer fixtures compare against mlx-lm, incremental decoding matches whole-sequence processing, and the 35B model runs on an iPhone 17 in ~2.5 GB RAM at ~1 tok/s—claimed as a first for this model class. The author is honest about trade-offs: 'these models chat and write like large models but recall facts like small ones.' Built with Claude Code and inspired by TurboFieldfare, Swiftlet is Apache-2.0 and also powers an open-source iOS app. HN commenters recognize this as a stepping stone toward commodity local AI—one even dreams of a 1T-parameter model on a $200 SSD—while others worry about SSD endurance, prefill latency, and whether the 'first on iPhone' claim is unique given prior work like Anemll's 400B demo.

An 80B Qwen runs in 4.3 GB of RAM by streaming only ~3B active parameters per token—yet 'these models chat and write like large models but recall facts like small ones.'

  • 80B model: 42 GB disk, ~4.3 GB peak RAM, 4.5–5 tok/s on M5; 35B model: 18 GB disk, ~2.6 GB RAM, 7–11 tok/s.
