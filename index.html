Memory has grown to nearly two-thirds of AI chip component costs
⬆ 400 pts 💬 420 HN comments

A new analysis from Epoch AI reveals that high-bandwidth memory (HBM) now accounts for 63% of the total component cost of AI chips, up from 52% in Q1 2024. The study, covering designs from Nvidia, AMD, Google, and Amazon, breaks down costs into memory, logic dies, advanced packaging (CoWoS), and auxiliary components. Over the period, logic die share remained flat at ~13%, while packaging fell from 19% to 15% and auxiliary components from 15% to 9%. In absolute terms, HBM spend surged from roughly $12 billion in 2024 to $32 billion in 2025, driven by tight supply and rising prices. Epoch AI's methodology models per-chip costs with 90% confidence intervals, highlighting the shifting cost structure as memory becomes the dominant bottleneck.

The trend has significant implications for AI infrastructure costs. Hyperscalers are already factoring higher component prices into capex: Microsoft's $190 billion FY2026 outlook includes ~$25 billion from higher component costs, while Meta raised its 2026 guidance by $10 billion. The article notes that AI inference and training could see ~3x hardware cost reduction if memory supply catches up, as memory makers have historically oscillated between undersupply and oversupply. However, comments on Hacker News express deep skepticism about near-term relief, citing patent thickets, fab complexity, and strategic supply management by the three dominant DRAM manufacturers. This cost pressure is already cascading to consumer markets, with DDR5 prices skyrocketing and hobbyists facing unprecedented barriers to building or upgrading systems.

HBM spend grew from $12B in 2024 to $32B in 2025, now accounting for 63% of AI chip component costs, up from 52% in Q1 2024.

Key Highlights
  • HBM cost share rose from 52% to 63% in under two years, becoming the dominant AI chip component cost.
  • Absolute HBM spend tripled from $12B to $32B, outpacing growth in logic, packaging, and auxiliary components.
  • Hyperscaler capex guidance explicitly factors in higher component prices, indicating persistent cost inflation.
  • Comments highlight consumer pain: DDR5 prices have doubled or tripled, and PC hobbyist markets are squeezed.
  • Debate centers on whether memory makers will expand capacity or maintain tight supply, with geopolitical and patent barriers complicating new entry.

This is particularly important because DeepSeek's API charges significantly less for cached tokens (as low as $0.01 per million cached vs. $0.40 per million missed). The agent is open-source, built with Node.js, and supports self-hosted endpoints. However, critics argue that similar cache efficiency can be achieved with simple API wrappers or by using DeepSeek via existing agents like Claude Code, raising questions about the necessity of a purpose-built harness.

Skeptics counter that DeepSeek's caching works 'magically' regardless of client, with user m00dy sharing: 'using claude code on deepseekv4. just burnt 24.1M input hit and 170k cache miss.' A significant thread debates the append-only vs. partial compaction tradeoff: user jbellis notes that 'when they decide to break the prefix cache... it's always because they've tested it and it gives better results overall.' Meanwhile, several commenters deride the project's marketing page for poor UX—especially the animated code example that shifts content on scroll—calling it 'AI slop.' The tool's npm dependency and lack of a compiled binary also drew criticism from users preferring Rust or Golang solutions.

DeepSeek Reasonix claims to achieve >99% cache hit rates, potentially reducing API costs to less than $0.05 for an entire day of heavy coding agent usage.

Constraint Decay: The Fragility of LLM Agents in Back End Code Generation
⬆ 246 pts 💬 142 HN comments

This paper from Dente et al. introduces the concept of 'constraint decay' in LLM-based code generation agents, highlighting a critical fragility when moving from unconstrained prototyping to production-grade backend development. The authors systematically evaluate GPT-5.2 (and other models) across 80 greenfield generation tasks and 20 feature-implementation tasks spanning eight web frameworks (Flask, FastAPI, Django, etc.), using a dual evaluation of behavioral tests and static verifiers. Their core finding: as structural constraints accumulate—architectural patterns, ORM mappings, database schemas—agent performance degrades substantially. Capable configurations lose an average of 30 points in assertion pass rates from baseline to fully specified tasks, with weaker approaches near zero. The study isolates framework sensitivity: agents succeed in explicit, minimal frameworks like Flask but struggle in convention-heavy environments like FastAPI and Django. Root cause analysis identifies data-layer defects (incorrect query composition, ORM runtime violations) as the leading failure mode, suggesting that functional correctness alone is insufficient; structural fidelity remains an open challenge for coding agents.

The community reaction in the Hacker News thread reveals a split between practitioners who have observed similar degradation and those who have found effective workarounds. Multiple commenters echo the paper's findings: 'guhcampos' notes that as specifications grow more detailed, the agent loses coherence, while 'sdevonoes' warns of 'moving complexity from the deterministic world of programming to the informal world of natural language.' Conversely, commenters like 'bob1029' report inverse findings when using a recursive harness that queries existing code and git history, achieving high accuracy even on legacy codebases. This aligns with 'dalemhurley''s assertion that the ecosystem of linting, testing, and agentic loops is more important than the model itself. The debate underscores a fundamental tension: LLMs excel at unconstrained generation but require robust external scaffolding to respect architectural constraints. Some commenters, like 'spacedoutman', dismiss the research as outdated, arguing that frontier models (e.g., GPT-5.5-codex) have largely mitigated these issues, while others like 'maxbond' connect it to broader phenomena of error accumulation in long-horizon tasks. The consensus is that while LLM agents are powerful for rapid prototyping, production readiness demands sophisticated constraint enforcement mechanisms.

Capable configurations lose 30 points on average in assertion pass rates from baseline to fully specified tasks, with some weaker approaches near zero.

Key Highlights
  • Constraint decay: LLM agent performance declines as structural requirements accumulate.
  • Framework sensitivity: minimal frameworks (Flask) outperform convention-heavy ones (Django, FastAPI).
  • Data-layer defects are the primary root cause of failures in constrained generation.
  • Workarounds like recursive harnesses and static analysis tools can mitigate decay.
  • The study used GPT-5.2; some commenters argue newer models may have largely solved these issues.

#13
Building Pi with Pi
⬆ 115 pts 💬 85 HN comments

Armin Ronacher's post, "Building Pi with Pi," reflects on the challenges of using AI agents (which he terms "clankers") to maintain Pi, an open-source project integrated into Earendil. The core dogfooding loop—using Pi's agent harness to develop Pi itself—exposes a critical tension: AI-generated issues and pull requests are often voluminous but low-quality, filled with confident but incorrect diagnoses. Ronacher argues that the worst issues are those where users ran their own observations through an LLM, expanding narrow facts into a mess of plausible-sounding speculation. The agent then treats this speculation as evidence, leading it down wrong paths. To counter this, Pi uses custom slash commands like /is to instruct the agent to ignore the issue's analysis and independently verify. Yet the slop remains a burden, as agents over-engineer fixes by adding permissive readers and fallbacks instead of preserving the system's invariants. Ronacher laments that this local working-around mentality erodes the collaborative foundation of open source, where problems should be solved upstream through human coordination, not isolated work with a machine.

The volume of AI-assisted contributions is staggering: over 90 days, Pi's tracker saw 3,145 external issues and PRs, with 2,504 auto-closed from non-approved contributors. Only 8% of auto-closed PRs were ultimately merged, and 26% of issues were eventually fixed (some referenced by commits without reopening). Ronacher notes that many submitters didn't even realize they created an issue, pointing to OpenClaw instances and skill-sets that encourage spam. To manage this, Pi employs careful parallelism: agents run independent reproduction sessions for multiple issues, visually distinguished in the UI, with prompts that enforce distrust of the issue's analysis. The highlight of the piece is Ronacher's call to preserve open source's human-centric value: "Open Source needs more collaboration, not more isolated work with a machine." He advocates for stronger foundations and discipline—like refusing to paper over every misconfigured gateway—to avoid fragmenting effort. The post is a sobering look at how AI is transforming maintainer workloads, demanding new tools and norms to filter signal from slop.

"Slop Begets Slop" – AI-generated issues and PRs, full of confident but inaccurate analysis, mislead both human maintainers and automated agents, creating a feedback loop of increasingly complex and unnecessary defenses.

Key Highlights
  • Pi uses AI agents (clankers) to develop itself, but AI-generated issues often contain confident but wrong diagnoses that mislead both humans and agents.
  • The project employs custom slash commands (/is, /wr) to instruct agents to ignore issue analysis and independently verify behavior.
  • Over 90 days, only 8% of auto-closed PRs from non-approved contributors were ultimately merged, illustrating the low quality of AI-assisted contributions.
  • Agents tend to over-engineer fixes by adding permissive readers and defenses against bad state, rather than preserving the system's invariants.
  • Ronacher argues that open source's value lies in human collaboration, not isolated work with machines, and urges maintainers to refuse local workarounds that fragment effort.

Microsoft open-sources “the earliest DOS source code discovered to date”
⬆ 483 pts 💬 170 HN comments

Microsoft has open-sourced what it describes as 'the earliest DOS source code discovered to date' — the 86-DOS 1.00 kernel, along with development snapshots of PC-DOS 1.00 and utilities like CHKDSK. This code predates MS-DOS branding and was painstakingly transcribed from paper printouts by a team of historians led by Yufeng Gao and Rich Cini, as modern OCR software struggled with the decades-old dot-matrix output. The release provides an unprecedented glimpse into the pre-IBM PC era, when Tim Paterson’s 'quick and dirty operating system' was written for the Intel 8086-based Seattle Computer Products kit. Microsoft later licensed and bought the rights, leading to PC-DOS and the MS-DOS that powered the PC revolution.

The open-sourcing continues Microsoft’s pattern of releasing early software, following MS-DOS 1.25/2.0 in 2014/2018 and the oddball MS-DOS 4.0 in 2024. The code is now available in the same GitHub repository as those prior releases. Commenters on Hacker News largely celebrated the preservation effort, with one noting that 'text printed on paper outlived any digital storage.' Others drew comparisons to modern software complexity, with one user remarking that 'a few thousand lines of assembly was what it took to launch a successful software company.' The release also reignited discussion about the IBM PC deal, Digital Research’s misstep, and the enduring influence of early x86 architecture decisions.

"This source code is old enough that it hadn’t been stored digitally. A dedicated team of historians and preservationists painstakingly transcribed and scanned in code from paper printouts provided by Paterson."

Key Highlights
  • Earliest DOS source (86-DOS 1.00) now open-sourced, transcribed from paper printouts.
  • Code includes kernel and classic utilities like CHKDSK.
  • Microsoft has released prior versions (1.25, 2.0, 4.0) but this is the oldest.
