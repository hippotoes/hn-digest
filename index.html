An OpenAI model has disproved a central conjecture in discrete geometry
⬆ 1210 pts 💬 887 HN comments

OpenAI has announced that an internal general-purpose reasoning model has disproved a central conjecture in discrete geometry—the planar unit distance problem—first posed by Paul Erdős in 1946. The conjecture held that the maximum number of unit-distance pairs among n points grows only slightly faster than linearly (n^{1+o(1)}). The AI constructed an infinite family of configurations achieving at least n^{1+δ} pairs for a fixed δ>0, with a refinement later yielding δ=0.014. The proof leverages deep algebraic number theory, specifically Golod-Shafarevich theory and infinite class field towers, to create point sets with many unit distances. This marks the first time an AI has autonomously solved a prominent, long-standing open problem central to a subfield of mathematics, verified by external mathematicians including Tim Gowers and Noga Alon, who called it a milestone.

The result is notable not only for its impact on discrete geometry but also for the method of discovery. The model was not fine-tuned on mathematics or given problem-specific scaffolding; it was a general reasoning system prompted to explore Erdős problems. The chain of thought spanned 125 pages, revealing the model's ability to explore unconventional approaches—it spent most of its effort constructing counterexamples rather than proving the conjecture. This suggests a capacity for creative intuition and cross-domain transfer. The companion paper by mathematicians enriches the solution, noting that the proof reveals unexpected connections between number theory and geometry. While some commentators express skepticism about attribution and training data, the consensus among experts is that this represents a genuine breakthrough, though questions remain about compute cost and reproducibility.

The proof used sophisticated algebraic number theory to construct counterexamples, leading to a exponent improvement δ=0.014, and the model's chain of thought ran 125 pages long.

⬆ 881 pts 💬 367 HN comments

GitHub confirmed a breach of approximately 3,800 internal repositories after an employee installed a malicious VS Code extension. The trojanized extension, removed from the marketplace, exfiltrated source code to a threat actor. This incident underscores the longstanding security risks of VS Code's extension model, which lacks sandboxing and explicit permission systems—a flaw flagged since 2018. The breach is attributed to TeamPCP, the same group behind the TanStack npm supply-chain attack, illustrating a recurring exploitation of developer tools to compromise high-value targets. The attack vector—a poisoned IDE extension—highlights the tension between developer productivity and security, as extensions provide essential functionality but can execute arbitrary code with minimal oversight.

GitHub's investigation found that the attacker's claim of ~3,800 repos aligns with their findings, though no customer data outside internal repos is believed affected. The stolen data is offered for at least $50,000 on Breached forums, with threats of public release if not purchased. The incident is part of a larger pattern: previous malicious VS Code extensions have stolen credentials, deployed cryptominers, and exfiltrated data to servers in China. Commenters note that the breach originated from the widely-used Nx Console extension, suggesting a supply-chain compromise. This event reignites debate over IDE security, with many calling for Microsoft to prioritize extension sandboxing over features like Copilot, while others advocate for editors such as Zed or Sublime Text, despite their own security limitations.

Saying goodbye to asm.js
⬆ 390 pts 💬 150 HN comments

Mozilla's SpiderMonkey team has announced the deprecation of asm.js optimizations in Firefox, marking the end of an era for the pioneering compilation target that enabled near-native performance for C/C++ codebases on the web. Starting with Firefox 148, the dedicated asm.js compiler (OdinMonkey) is disabled by default, with complete removal planned in a future release. Asm.js was originally conceived as a statically-typed subset of JavaScript, allowing engines to recognize and compile code ahead of time, bypassing traditional JIT limitations. It debuted in Firefox 22 (2013) and proved the viability of web-based native code execution, directly paving the way for WebAssembly. The decision to sunset asm.js reflects WebAssembly's widespread adoption and the diminishing need for a dual optimization path that adds maintenance burden and attack surface. Notably, existing asm.js code will continue to run as standard JavaScript through the regular JIT, ensuring no breakage for users.

The removal of asm.js optimizations represents a significant milestone in web platform evolution, with the team invoking Norse mythology—OdinMonkey meets its fate at Ragnarök, while BaldrMonkey (the WebAssembly optimizing compiler) rises. WebAssembly's more advanced pipeline now offers better performance and smaller binaries than asm.js ever could. However, the transition is not without friction, as highlighted by commenters: some note that asm.js's seamless integration with JavaScript APIs and zero-copy semantics offered advantages for certain use cases. One developer reported that their asm.js SHA-256 implementation outperformed WASM on Chrome, though this may be an outlier. Others lament the loss of asm.js's simplicity for runtime code generation, as WASM requires explicit module loading. The tech community broadly acknowledges asm.js's pivotal role, with many citing unreal engine demos and Figma's early adoption as proof of concept. The move signals a full commitment to WebAssembly as the standard for high-performance web code.

“Without asm.js, we likely wouldn’t have WebAssembly.” — SpiderMonkey blog post, acknowledging asm.js as the key precursor that unlocked near-native web performance.

Key Highlights
  • Asm.js optimizations disabled by default in Firefox 148; full removal planned.
  • Existing asm.js code remains functional through standard JavaScript JIT.
  • WebAssembly is the intended replacement, offering faster execution and smaller sizes.
  • Asm.js's historical significance includes proving the web could run near-native code, leading to WASM.
  • Some developers report cases where asm.js still outperforms WASM, particularly in JIT compilation scenarios.

Show HN: I reverse engineered Apple's video wallpapers
⬆ 308 pts 💬 71 HN comments

Phosphene is a macOS Tahoe video wallpaper engine that reverse engineers Apple's private WallpaperExtensionKit framework to let users play their own video files as desktop and lock-screen wallpapers. The project has garnered 308 points and 71 comments on Hacker News, reflecting strong interest from developers who have long wanted customizable video wallpapers on macOS. While many praise the implementation's elegance, concerns about reliance on private APIs and potential breakage with future macOS updates temper the enthusiasm. The project's MIT license and availability of pre-built variants aim to lower adoption barriers.

Phosphene achieves frame-accurate gapless looping by offsetting PTS/DTS across loop boundaries—no flush, no stutter—and integrates with macOS's native wallpaper picker so videos appear alongside Apple's built-in Aerials.
