#3
Terence Tao: Math 2.0 [pdf]
⬆ 484 pts 💬 477 HN comments

Terence Tao's Caltech 2026 deck, 'Math 2.0', is the most consequential public framing yet of what happens to a formal discipline when AI systems begin producing results the discipline's own practitioners cannot yet explain. Tao's central claim is structural rather than futuristic: open problems function as 'lighthouses, not destinations' — they are reconnaissance devices that reveal which theories, definitions, and proof techniques need to be built. When automated tools resolve a lighthouse prematurely, they can 'disrupt the exploration of the paths not taken, and sterilize the surrounding field.' Math 1.0, in this framing, is not being extended but forked — a forced upgrade that breaks plug-ins, with the community left to triage the compatibility bugs.

The comment thread (484 points, 477 comments) shows the argument being stress-tested on two fronts. First, empirics: after an October 8 release of solutions to 100-plus problems, mathematicians reportedly scrapped freshly submitted grant requests and described the loss of long-worked problems as 'losing an old friend.' Second, epistemology: Tao's slide imagining an AI-designed cancer cocktail nobody understands drew sustained fire from drug-discovery practitioners, who note that anesthesia, Tylenol, and SPICE transistor models already run on curve fits, not first principles. The unifying concern is less about capability than about externalities — that AI is 'astounding in some directions, while inadequate in others,' and will exploit weaknesses in institutions built around human cognition.

'Reaching these lighthouses prematurely by automated tools can disrupt the exploration of the paths not taken, and sterilize the surrounding field.' — Tao's slide, which several commenters argue is the actual argument the cancer-cocktail slide obscured.

Key Highlights
  • Tao reframes open problems as navigational lighthouses rather than goals: solving them early can sterilize unexplored territory around them.
  • AI currently produces proofs but not proof techniques — mechanical verification without the conceptual compression that mathematics values.
  • The cancer-cocktail slide misfired: practitioners note anesthesia, Tylenol, and even SPICE transistor models rely on semi-empirical fits rather than understood mechanisms.
  • Community-level damage is real: lost problems, rewritten grant proposals, disrupted mentorship and collaboration pathways for juniors.
  • Institutional questions dominate — how to assign credit, evaluate mathematicians, and prevent capability consolidation inside a few frontier labs.

Total Annihilation, rebuilt for modern computers
⬆ 630 pts 💬 239 HN comments

Nanolathe is an MIT-licensed, clean-room reimplementation of the Total Annihilation engine, released as a public beta with a browser demo and native Windows/macOS/Linux builds that consume the user's own GOG/Steam/CD game data. What makes it more than a nostalgia port is the engineering: the team reverse-engineered and documented Cavedog's proprietary data formats (the /docs section drew specific praise), then rebuilt the renderer as a modern GPU path with lighting, glow, supersampling and synthesized 2× terrain tiles generated from the original 32×32 tiles — with a Classic CPU renderer retained as a fallback for fidelity comparison. The demo ships three original campaign missions that run entirely client-side, no game folder required, and multiplayer uses host-selected Modern, Community 3.9 or Strict 3.1 rule sets across 2–10 player skirmish and Survival, with every battle auto-recorded as a replay.

The 630-point, 239-comment thread exposed an old fault line in the TA lineage. Commenters repeatedly redirected to Beyond All Reason, itself a descendant of the two-decade-old Spring/Recoil engine (recoilengine.org) — 'BAR is a technical marvel… it doesn't even have unit caps' — and to Zero-K, Planetary Annihilation and Supreme Commander's Forged Alliance Forever. The distinction matters legally and technically: BAR deliberately became 'legally distinct,' while Nanolathe preserves the 1997 balance and feel. A parallel thread dissected Spring's multiplayer determinism — 'they implemented the game with deterministic, lockstep multiplayer… but used native floats, compiler fastmath flags, and stdlib math functions' — a classic desync source that clean-room engines can avoid. Meanwhile, a large cohort spent the thread mocking the site itself as 'AIslop,' citing the numbered 01/02/03 card layout as an AI-generated-website tell. Others noted the engine's Go/Ebiten implementation and unresolved questions about multicore scheduling.

Nanolathe's Modern renderer synthesizes genuine 2× terrain tiles from the installed game's original 32×32 tiles, then supersamples and adds light and glow — 'the same explosion, a different atmosphere,' rendered from the same committed simulation tick.

Key Highlights
  • MIT-licensed clean-room reimplementation of Total Annihilation, using original game data supplied separately; browser demo needs no game folder.
  • Modern GPU renderer with 2× synthesized terrain and sprites, supersampling, light and glow, plus a Classic CPU renderer for pixel-faithful comparison.
  • Multiplayer supports 2–10 player skirmish and Survival under Modern, Community 3.9, or Strict 3.1 rule sets, with automatic replay recording.
  • Commenters overwhelmingly point to Beyond All Reason (Spring/Recoil engine lineage) and Zero-K as the mature alternatives, praising BAR's 150-player matches and lack of unit caps.
  • Technical debate centers on Spring's lockstep determinism built on native floats and fastmath flags, and on longstanding multicore/busy-cpu0 complaints in the original engine.

#2
Fingerprints are the new cookies
⬆ 618 pts 💬 302 HN comments

The piece is less a primer than an indictment: it frames Google's decade-long cookie saga as a three-act play — "PRIVACY IS PARAMOUNT TO US" (2019's deprecation pledge), the Privacy Sandbox as five-year distraction that "kinda sucks and raised antitrust concerns so nobody uses them," and finally ACT III, where device fingerprinting is quietly admitted into Google's ad products. Technically it draws the line regulators keep blurring: cookies are client-side state you can clear; fingerprinting is passive measurement you cannot. Data arrives from two strata — the network request (IP, User-Agent, Accept-Language: all fragile or generic) and the code environment, where JavaScript silently reads GPU strings via WEBGL_debug_renderer_info, canvas anti-aliasing artifacts, OfflineAudioContext float rounding, Intl timezone/calendar fields, and navigator.hardwareConcurrency. Individually common, jointly unique — the author's Akinator analogy reduces identification to information entropy and surprisal: log₂ of the ratio by which each answer shrinks the candidate pool.

Two remedies exist, and only two: farbling (per-site noise, as Brave ships) or uniformity (Tor and Mullvad Browser force every user to render identically). The article flags the counterintuitive trap — "privacy extensions make you more unique, since fewer people have them" — and insists no extension equals engine-level defense, since trackers can simply detect and ignore the disrupted signals. Commenters supply hard numbers. brainwad measured that "just my HTTP headers leak 18.46 bits" on coveryourtracks.eff.org, mostly from de-CH/en-AU Accept-Language quality values; the author notes ZIP code plus birth date plus sex uniquely identifies over 60% of Americans, and that roughly 20 bits singles out one person in a city of a million. legitster counters that commercial reality is messier: "90% of commercial fingerprinting services still rely mostly on the IP address," leaving configurations with "a very short half life."

"A ZIP code (inferred from IP), a birth date (you've given away on some platform) and sex (you fill it in everywhere) together are enough to uniquely identify over 60% of Americans" — and the fingerprint need not be globally unique, only unique enough within the tracker's sample size.

Key Highlights
  • Browsers expose high-entropy signals without consent: WebGL GPU strings, canvas rendering artifacts, OfflineAudioContext float rounding, Intl locale/timezone, and CPU-core counts combine into near-unique hashes.
  • Fingerprints bypass cookie controls entirely — deleting cookies, switching to incognito, or using a VPN leaves the hardware and software fingerprint intact across sessions and devices.
  • Google's 2019 cookie-deprecation pledge ended in a reversal; fingerprinting is now reportedly permitted in its ad products, validating the article's three-act framing.
  • Defenses bifurcate into farbling (Brave adds per-site noise) and uniformity (Tor/Mullvad make all users identical); extensions like JShelter break sites and ironically increase uniqueness.
  • Entropy math grounds the argument: header-only leakage measured at 18.46 bits on coveryourtracks.eff.org, and ~20 bits suffices to isolate one individual in a million-person city.

Cartographers of North Korea (2019)
⬆ 306 pts 💬 62 HN comments

The 2019 interactive piece "Cartographers of North Korea" explores how OpenStreetMap contributors have built unusually detailed coverage of a country with almost no commercial mapping presence. Because the app requires JavaScript, the article text itself is minimal, but the HN discussion reveals the substantive material: a data-driven analysis of OSM edits, contributor interviews, and maps of roads, fences, towns, and rivers—especially along the Tumen River and Phungso-ri. Technically, this is crowdsourced geospatial intelligence: volunteered geographic information (VGI) assembled from GPS traces, satellite imagery, local knowledge, and hobbyist effort. The top contributor has 75,583 contributions, and the site anonymizes names while exposing editing patterns. The project illustrates how OSM functions as critical public infrastructure, albeit one where data provenance, verification, and geopolitical sensitivity are inseparable from the map itself.

The comments add strong context and tension. One mapper, P791, says: "I map North Korea to help North Koreans. I select areas that look like they might be good points to escape… It is important to map the fences, roads, and towns on the Chinese side." Others push back on outsider narratives: tourism videos are "not life in NK" but "propaganda," and only Russians may currently tour. The community also debates OSM's opacity: voidUpdate notes anonymization is cosmetic because edit histories are public; lucb1e says vandalism is usually caught quickly. UX criticism is sharp: "It's a blank blue page," "tedious to read on mobile," and a "regular article with static images" would be better. Yet many celebrate OSM as "one of my personal 7 Wonders of the Internet," and the 2019 data still points to a living, imperfect map.

P791's stated motive is the most striking data point: "I map North Korea to help North Koreans. I select areas that look like they might be good points to escape… It is important to map the fences, roads, and towns on the Chinese side."

Ask HN: Do you want a router that has DD-WRT pre-installed?
⬆ 113 pts 💬 125 HN comments

An Ask HN post poses a deceptively simple business question: is there demand for a router shipped with DD-WRT pre-installed, the way Dropbox once bundled rsync into something non-hackers would actually use? The framing invites the classic HN teardown of a 'just do X' pitch. Technically, DD-WRT occupies a shrinking niche: several commenters note it deliberately freezes the Linux kernel to keep closed-source vendor drivers (typically Broadcom's) working, meaning a flashed device is often more stable and performant than stock firmware but not necessarily more secure or more feature-current. Meanwhile OpenWrt has become the de facto standard, and pre-flashed OpenWrt hardware already exists — GL.iNet devices ship it with LuCI one toggle away, plus ThinkPenguin, Turris, Firewalla, Ubiquiti and community ASUS-Merlin builds. The technical premise is thus already served, imperfectly, by an existing supply chain.

The thread's 113 points and 125 comments cluster around market structure rather than firmware merit. '99.99% of people don't even buy routers, they just use the free one that comes with the connection,' writes MisterMunchkin, a claim corrected to roughly 80% by functionmouse. dpark asserts the target audience 'is functionally nonexistent... people who won't actually tinker with it but want to imagine they would,' answered by _tk_: 'I own a RaspberryPi and have never once used it. In fact, I know several people who own several RaspberryPis and don't use them!' mushufasa's lived data point — a FlashRouters device that lasted four years, soured by an auto-enrolled support subscription — illustrates the margin problem. lobster2342 offers the counter-position: willing to pay a flash fee to save time, envisaging 'a shop for wealthy nerds.' Others skip consumer routers entirely for x86 appliances running OPNsense.

dpark: "The set of humans who want a turnkey DD-WRT-type solution is functionally nonexistent... people who won't actually tinker with it but want to imagine they would" — answered by _tk_: "I own a RaspberryPi and have never once used it. In fact, I know several people who own several RaspberryPis and don't use them!"

Key Highlights
  • DD-WRT's kernel-freezing design preserves closed Broadcom driver support but delivers neither newer security patches nor modern kernel features — OpenWrt is widely called the more significant project today.
  • Pre-flashed alternatives already exist (GL.iNet, ThinkPenguin, Turris, Firewalla, Deciso, ASUS-Merlin), so the proposed product lacks differentiation.
  • The addressable market is a fraction of a fraction: most users take ISP-supplied gateways, and non-enthusiasts who do buy are steered to Eero/Orbi/Fritz!Box.
  • Commenters who do want the product describe a 'wealthy nerd' niche shop model — profitable for one person, but explicitly non-scaling and best bootstrapped without debt.
  • A significant cohort has abandoned consumer routers altogether for dual-NIC x86 boxes or old servers running OPNsense/OpenWrt, with commercial Wi-Fi hardware demoted to dumb access points.

#6
Running the unmodified Linux amdgpu driver on an iPad
⬆ 72 pts 💬 19 HN comments

LemonSeed Studio is a single iPadOS app that sidesteps the total absence of a public GPU-driver API on iPad by shipping the unmodified upstream Linux amdgpu and amdkfd drivers as a PCIDriverKit extension, giving userspace code DMA and MMIO access to an AMD GPU sitting in a Thunderbolt enclosure. Because DriverKit runs drivers outside the kernel, the port keeps Linux's PCI probe and command-submission paths largely intact, while the app — an editor plus a SwiftUI shell — reaches the GPU through an HSA runtime (HRX/Loom) in the bundled LemonSeed Engine, with amdgpu_mtopg providing live telemetry. Three git submodules (mac_linuxgpu, LSE, amdgpu_mtopg) carry the moving parts; mac_linuxgpu fetches its pinned kernel sources sparsely on first build, and the original code is dual-licensed MIT or GPL-2.0-only. In practice it is a userspace Linux driver stack grafted onto a locked-down tablet.

The headline ambiguity is that "on-device" inference actually happens beside the device: the model runs on an eGPU, not the M-series silicon, a distinction HN compressed into "beside-device inference." The repo shows 43 stars, 154 commits, and three submodule components, and at 72 points/19 comments the thread skewed toward architecture questions rather than benchmarks. skavi asked whether the IDE coupling is "the psychosis enabled bikeshed" of the driver; haunter replied that this is precisely DriverKit's intended use, with drivers as app extensions. Karliss added the sharper systems point: since Apple exposes no kernel APIs for custom GPU drivers on iPad, userspace embedding is effectively the only legal path — and he was "a bit surprised Apple allows enough low level thunderbolt access to implement this at all."

The unmodified upstream Linux amdgpu + amdkfd driver runs as a userspace DriverKit app extension on iPadOS — turning "on-device inference" into what one commenter wryly called "beside-device inference."

Key Highlights
  • The entire upstream Linux amdgpu + amdkfd driver is embedded unmodified as a PCIDriverKit extension, running in userspace rather than as a kernel extension.
  • Inference is offloaded to an AMD GPU in a Thunderbolt enclosure via an HSA runtime (HRX/Loom) inside the bundled LemonSeed Engine; amdgpu_mtopg supplies live GPU telemetry.
  • Three git submodules (mac_linuxgpu, LSE, amdgpu_mtopg) constitute the stack; kernel sources are fetched sparsely and pinned on first build; original code is MIT/GPL-2.0-only dual-licensed.
  • Commenters note DriverKit is the only viable mechanism because Apple provides no kernel-level API for custom GPU drivers on iPadOS — and the level of Thunderbolt PCI access Apple permits here is itself surprising.
  • The thread's dominant objection is teleological, not technical: an eGPU enclosure is non-portable, so skeptics ask why an iPad rather than a Linux mini-PC, while defenders invoke hacker ethos and touchscreen-first agentic workflows.

#7
Choreographic Programming in Rust
⬆ 44 pts 💬 30 HN comments

Hibana is a Rust crate that lets a finite multiparty protocol be written once as a global choreography and then projected into a compact per-role program, with every send, receive, or route step enforced against that projection before progress is allowed to commit. The design targets a narrow but demanding niche: it is unconditionally no_std, requires no allocator, and takes caller-provided storage, so the same public API works on hosted and embedded targets. Rather than generating a distinct Rust continuation type per protocol state — the approach that makes endpoint typing grow combinatorially — Hibana keeps protocol state in compact descriptors: 256 roles (the full u8 domain), 65,535 event identities, 65,535-byte program images, binary routes, affine endpoints that may be dropped but cannot publish progress twice, and a five-operation Transport trait for carrier neutrality.

The engineering evidence is unusually formal for a GitHub release. Lean proves must-facts for every selected-arm execution and derives receive-before-send ordering; Kani checks the packed count domain; a const fixture emits a full 7,281-event atom-only image; and a Pico-target compile gate projects 256 cyclic sender handoffs within bounded compiler time and memory. Crucially, the README is honest about its guarantee boundary: Hibana does not implement a network stack or a distributed algorithm, and splitting a protocol across sessions means each session is checked rather than the original global choreography. HN reaction split sharply between researchers who wanted endpoint-projection and Knowledge-of-Choice details and a large cohort that found the README itself impenetrable, with one commenter invoking Tolkien to call it 'that of Opus 5.'

Hibana enforces a whole multiparty protocol in a no_std, allocator-free runtime whose entire global program image must fit in 65,535 bytes — with 256 roles, 65,535 event identities, and Lean-checked receive-before-send ordering as the safety argument.

Key Highlights
  • Choreography-derived runtime enforcement: one global choreography is projected per role, and each send/recv/route must match the projected RoleProgram before progress commits.
  • Compact descriptors replace per-state Rust continuation types, so protocol growth does not become endpoint type growth; state lives in u16-indexed descriptor rows.
  • Explicit hard limits: 256 roles, 65,535 event identities, 65,535-byte program and role images, binary routes, 256 physical lanes, 256 inbound frame colors.
  • Formal backing spans Lean proofs of sibling exclusion and lane-head preservation, Kani checks on the packed count domain, and finite Rust/Lean correspondence fixtures.
  • Stated guarantee boundary: Hibana is endpoint-local enforcement, not a network stack — lifting local results to a distributed guarantee requires explicit carrier, codec, and scheduling premises.
