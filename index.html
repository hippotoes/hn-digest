#5
Apple ML Research: Muse Spark Open with MLX on Mac Studio
⬆ 327 pts 💬 164 HN comments

Apple's MLX team published a systems-level result that reads like a hardware thesis: an 816B-parameter mixture-of-experts model (Muse Spark Open, 42B active parameters, ~493GB in NVFP4) running across a cluster of Mac Studios with M5 Ultra SoCs. The technical foundation is three stacked advances — GPU Neural Accelerators in the M5 family that add dedicated matrix-multiply hardware, 1.2 TB/s of unified memory bandwidth (up from 819 GB/s on M3 Ultra), and macOS 26.2's low-latency RDMA-over-Thunderbolt 5 driver, which MLX v0.30.1 wraps in new communication collectives named jaccl and exposes through an mlx.launch helper. The performance model is cleanly split, and Apple knows it: time-to-first-token is compute-bound and therefore neural-accelerator-bound (up to 4.6× over M3 Ultra), while decode is memory-bandwidth-bound (1.6× faster). Everything else in the post follows from that distinction.

The benchmarks quantify it: Mistral Medium 3.5 (128B dense, FP8) drops TTFT from 95.9s on M3 Ultra to 24.6s on M5 Ultra at 8,192 tokens, and Qwen 3.8 hits 50.89 tok/s decode on four tensor-parallel M5 Ultras. Muse Spark Open does not fit on a single machine, so it becomes the parallelization showcase — 8.4s TTFT under two-node pipeline parallelism, 4.8s under four-node tensor parallelism at 65,536-token context, and 36.73 tok/s decode, roughly twice human reading speed. Notably, pipeline parallelism beats a single node on large-context prefill by up to ~1.8× because MLX chunks the context (--prefill-step-size 8192) and overlaps chunk k's later layers with chunk k+1's earlier ones; a second Thunderbolt cable cuts TTFT from 50.5s to 40.6s. Peak power is 200–300W per machine, though the 256GB Mac Studio starts at $9,499.

Four M5 Ultra Mac Studios sustain 36.7 tokens/sec decoding an 816B-parameter MoE — with 4.8s to first token at a 65,536-token context — while drawing roughly 300W each.

Key Highlights
  • Muse Spark Open (816B total / 42B active, NVFP4 at ~493GB) exceeds single-machine memory, making multi-Mac parallelization mandatory rather than optional
  • M5 Ultra's GPU Neural Accelerators target compute-bound prefill, yielding up to 4.6× TTFT speedup over M3 Ultra; 1.2 TB/s bandwidth yields 1.6× decode
  • macOS 26.2 RDMA-over-Thunderbolt 5 plus MLX's jaccl collectives and mlx.launch make two- and four-node tensor/pipeline parallelism a flag change
  • Pipeline parallelism beats a single node on long-context prefill (~1.8×) via 8,192-token chunk overlap, while tensor parallelism scales decode better with more nodes
  • Practical deployment remains gated by cost and configuration friction — 256GB Mac Studio starts at $9,499, and mlx_lm.server/OpenCode integration is still DIY

#6
You could have invented transformers from memory
⬆ 323 pts 💬 76 HN comments

Alex Wang's post reverse-engineers the transformer from a single primitive: the associative memory. A linear layer is nothing more than an outer-product accumulator, W = Σ vᵢkᵢᵀ = VᵀK, so recall is f(x) = Σ vᵢ(kᵢᵀx) — a similarity-weighted sum over stored values. The analytical move is to normalize keys and decompose f(kⱼ) into the target value plus interference from every non-orthogonal neighbour, then bound that interference as a random walk: ‖interference‖/‖signal‖ ~ √(M/d_k), so capacity collapses to roughly M ≈ d_k. Since ℝ^{d_k} only has d_k orthogonal directions, exact recall is structurally impossible past the key dimension — a clean, quantitative statement of why a single linear layer is a lossy, capacity-starved memory.

From there the post climbs a ladder: an MLP as a nonlinear store (≈2,700 memories at d=64), then self-attention as a non-parametric store that keeps keys and values in the context window, pushing capacity past a million and effectively unbounded. It also frames a gradient step as a memory write with key x and value −ηȳ, tying training to recall. Commenters sharpened the picture: vatsachak noted transformers behave like Hopfield networks that converge in one step, femto mapped the terminology onto channel capacity, and dullcrisp asked the practical question the post leaves implicit — in a real attention layer, keys and values are all runtime projections of the residual stream, not literal tokens.

With 64-dimensional keys, the capacity ladder runs from roughly 64 memories (linear layer) to about 2,700 (MLP) to over a million (self-attention) — a concrete, order-of-magnitude account of why attention beats feedforward storage.

Key Highlights
  • Associative memory framing: a linear layer stores key-value pairs via W = VᵀK and recalls by similarity f(x) = Σ vᵢ(kᵢᵀx)
  • Interference-to-signal ratio scales as √(M/d_k), giving linear-layer capacity of roughly M ≈ d_k memories
  • MLP acts as a nonlinear memory store raising capacity to ~2,700 at d=64
  • Self-attention is a non-parametric store with near-unbounded capacity (>1M) and one-step recall
  • A gradient descent step itself is a memory write: key x, value −ηȳ, linking training dynamics to recall

#2
Claude reveals ECDSA curve origins
⬆ 898 pts 💬 335 HN comments

For a quarter century, the 'seeds' published alongside NIST's prime and binary elliptic curves in FIPS 186-2 occupied the same uneasy space as the constants in DES S-boxes or the P-256 coefficients themselves: officially unexplained, and therefore suspect. The received folklore — sourced from Jerry Solinas himself in a 2015 email to Dan Bernstein — was that the seeds were hashes of a jokey passphrase ('Give Bob and Jerry a raise'), which made the provenance both charming and unverifiable. Koblitz and Menezes canonised the discomfort in 'A Riddle Wrapped in an Enigma.' Anthropic's account overturns that: an internal research model, given no hint, found in under thirty minutes that the seeds are raw output from the 1990s C library PRNG lrand48, seeded by srand48 with a Unix timestamp. The give-away was structural — the top bits of several seeds were uniformly zero, a 1-in-5810 signature of a generator that returns only the top 31 bits of a 48-bit LCG state. Claude brute-forced the 17 hidden bits for four seeds, then used LLL lattice reduction to recover internal state from truncated output (lrand48() >> 23) for the ten prime-curve seeds, stepping the state backwards until it hit the srand48 initialisation form (low 16 bits 0x330E) and reading off dates between May 1997 and April 1998.

The follow-on finding is arguably more interesting than the seeds: six base points trace to zrandom in FreeLIP, Arjen Lenstra's long-integer package (later shipped in early NTL), where state advances as state * 3^121 mod (2^107 − 1), seven single-limb draws are discarded, and 26-bit limbs are concatenated and reduced mod p until the candidate lands on the curve — with seeds 20000, 20420, 20507, 20509, 20512 and 20517 reproducing published Gx exactly. The work is deliberately understated in its security implications: revealing a weak-but-reproducible generation method makes deliberate subversion less plausible, not more, but it does not close the question, since skipped viable candidates (P-256's 876th) and unexplained cases (B-163, and the base points of P-224/P-256/P-384/P-521) remain. The $36,864 bounty goes to the Internet Security Research Group, and CC0 reproduction code ships with the write-up.

Four of ten curve seeds had a zero in the top bit of all 20 32-bit words — a 1/5810 coincidence that fingerprints lrand48's 31-bit output and, per sweis, collapses '13 years of tinfoil hats for srand48(time(NULL))'.

Key Highlights
  • NIST/ANSI prime-curve seeds are consecutive lrand48 outputs from srand48(t) with t a Unix timestamp between May 1997 and April 1998; binary-curve seeds use the same generator with the clock halved (April 17, 1998).
  • Claude detected the generator from a statistical artefact (top-bit-always-zero, p≈1/5810), brute-forced 2^17 hidden bits, and used LLL lattice reduction to solve truncated-LCG state recovery for the >>23 outputs.
  • Six base points (P-192 and the five X9.62 example curves) come from FreeLIP/NTL's zrandom with small integer seeds and seven discarded draws — the first time any NIST base point provenance has been explained.
  • Residual gaps remain: skipped viable candidates, an unexplained B-163 binary seed, and unresolved base points for P-224/P-256/P-384/P-521.
  • The $36,864 bounty is donated to ISRG, and public-domain reproduction code lets anyone regenerate every recovered seed and Gx.
  • The framing is explicitly non-alarmist: this is evidence against intentional weakening, since a reproducible weak-PRNG story leaves little room for a hidden backdoor.

#3
90% of US working hours are spent on tasks not covered well by AI benchmarks
⬆ 521 pts 💬 442 HN comments

Mercor's Benchmark Map is an attempt to quantify a question the eval community has largely avoided: what fraction of actually-paid-for work do AI benchmarks measure? The method is a taxonomy crosswalk. They take O*NET's 923 occupations and 18,797 constituent tasks, curate 29 benchmarks (924 prompts in the index) selected for public availability, agentic framing, economic realism, per-job-family diversity, and non-saturation, then use an LLM judge to tag each prompt to as many O*NET tasks as it plausibly matches - a tagging approach borrowed from Wang et al. and validated against human expert tags on Mercor's own APEX suite. A task counts as 'covered' only when at least 5 prompts map to it. That threshold yields 208 of 923 occupations covered, six of 22 job families with essentially nothing, and - combining coverage with Hatgis-Kessell et al.'s LLM-derived estimates of working-time share per task - the headline claim that ~90% of US working hours sit on inadequately benchmarked tasks.

The distributional analysis is the more interesting artifact. Coverage is not random: tasks tagged 'exposed' by Eloundou et al. (2023) are ~6x more likely to appear in a benchmark, and even after controlling for exposure, tasks in occupations with larger annualized wage bills are significantly overrepresented, as are tasks rated high on O*NET's 1-5 importance scale (6-10x). So bench-marking has followed exposure, wage bill, and importance - a rational allocation of scarce effort that nonetheless produces blind spots: heavily covered AI-exposed lawyers, barely covered equally exposed legal secretaries and court clerks. Their own O*NET-reweighting experiment, scoring the APEX suite with each task equally weighted across investment banking, law, accounting, and SWE, moved scores by only a few points (e.g. Claude Opus 5.5 73.3% -> 70.2%), because under a third of relevant tasks have enough prompts to include - low statistical power, not weighting, is the binding constraint.

Only 208 of 923 O*NET occupations - and a task counts as 'covered' with as few as 5 benchmark prompts - contain any well-benchmarked task at all, yet benchmarks are ~6x more likely to cover AI-exposed tasks than unexposed ones and skew toward high-wage-bill occupations even after controlling for exposure.

Commenters largely accept the direction of the finding while disputing its precision, reframing it around bottlenecks (Doorman Fallacy, Baumol's cost disease, Amdahl's Law), O*NET's staleness, and the political economy of which jobs get automated first.

A task counts as 'covered' by just 5 benchmark prompts - yet by that generous bar only 208 of 923 US occupations clear it, and benchmarks are ~6x more likely to cover AI-exposed tasks than unexposed ones.

Key Highlights
  • Mercor crosswalks 29 curated benchmarks (924 prompts) onto O*NET's 923 occupations and 18,797 tasks via LLM-judge tagging, validated against human expert tags on APEX benchmarks
  • A task is 'covered' at ≥5 mapped prompts; only 208 of 923 occupations qualify and 6 of 22 job families have no qualifying occupation, implying ~90% of US working hours are unbenchmarked
  • Coverage tracks AI-exposure (~6x), occupational wage bill, and O*NET task-importance (6-10x), producing blind spots among mid-wage clerical/knowledge roles
  • O*NET-weighted scoring barely changes model rankings (e.g. 73.3% → 70.2%) because under a third of relevant tasks have ≥5 APEX prompts - statistical power, not reweighting, dominates
  • Authors concede four open gaps: low statistical power, no difficulty/fidelity weighting, automation-only evals that miss human augmentation, and Dingel-Neiman's finding that only ~37% of US jobs are fully remote-feasible

#4
How the Claude Code team does code review
⬆ 369 pts 💬 339 HN comments

Anthropic's Claude Code team published a detailed account of how it reviews code when roughly 90% of that code is written by Claude itself. The central argument is a reframing: "did a human read the diff?" is a poor proxy for "what could go wrong here, and which check — automated or human — is the right one to catch it?" Review therefore stops being a terminal gate and becomes a continuous, layered property of the pipeline. Seven layers are described: pre-PR verification (Claude runs tests, builds, linters and a fresh-context subagent reviews the diff before a PR even exists), an AI reviewer on every PR whose findings are themselves validated by voting verifier agents, a blocking security pass, conventional CI, a risk classifier that assigns zero, one, or two required human approvers based on the change rather than the author, a merge queue plus feature flags and channel-staged rollout, and finally fast detection and rollback. The stated optimization target is minimal human attention without raising reverts or incidents — measured via median and p95 human approvals per PR, comment counts, and time-waiting-on-a-person, with revert and incident rates as guardrails.

The numbers are the interesting part. Anthropic's monorepo went from ~2,500 changes per day in May to over 30,000 by September; Claude Code's merged PRs more than doubled from June to September while the share reverted fell more than 40%. Adding AI review moved the share of internal PRs receiving substantive comments from 16% to 54%. Incidents become evals: past PRs that caused incidents, expert-confirmed, are replayed daily against any change to the reviewer's prompts, tools, or model. But the team is candid about failure modes. Agent-vs-agent review can fail to converge — one CLI PR went through more than fifty rounds overnight — and git blame showed ~59% of what the reviewer kept flagging was pre-existing code. They added a three-round cap, diff-only re-review, bug-class flagging, and de-duplication, moving single-round pass rates from 65% to 78% and five-plus-round PRs from 8.9% to 1.5%.

"One CLI PR went through more than fifty rounds of review and fixes overnight before its author stopped it" — and git blame showed ~59% of what the reviewer kept flagging was code that had been there since its first pass. Review has to converge, or two agents will keep each other busy indefinitely.

Key Highlights
  • Review is decomposed into seven layers — pre-PR agent verification, AI review with verifier-agent voting, separate blocking security review, CI, risk-tiered human approval, merge queue plus flags, and fast rollback — rather than one human gate.
  • A classifier, not the author, assigns risk tier (0/1/2 human approvals); agent approvals never count as human ones, and approvals are commit-scoped so they must be re-earned after unattested pushes.
  • Incidents are converted into a daily regression eval for the reviewer, with noise measured by classifying how authors respond to each comment (fixed / wrong / intentional / irrelevant).
  • Convergence is the real bottleneck: the team added a three-round cap, diff-only re-review, bug-class flagging, and no-repeat findings, cutting mean reviews to pass from 2.08 to 1.32.
  • Humans are retained for five decisions — should we build it, risky code (billing, auto-updater, CI workflows), architecture, reading evidence, and owning the outcome — while codebase comprehension is outsourced to on-demand Claude explainers.

#7
Llama.cpp on a jailbroken PS5: run any GGUF model natively on the console
⬆ 302 pts 💬 75 HN comments

PS5LM is a homebrew port of llama.cpp to jailbroken PlayStation 5 consoles, running GGUF inference on the console's RDNA 2 GPU through llama.cpp's Vulkan backend, itself built on the PS5_Vulkan project's RADV/Mesa driver patches. The technical premise is straightforward but non-trivial: the PS5 exposes roughly 11.4 GB of unified GDDR6 memory to the GPU, enough to hold a quantized 27B model plus a 64k context, and the port supplies a memory planner that reads each GGUF's tensor layout and picks the longest context and KV-cache configuration that fits in free memory. On top of the inference engine sits a full appliance: an OpenAI-compatible /v1/chat/completions endpoint, an Anthropic-compatible /v1/messages endpoint that Claude Code can target, and a 'decision model' API (/v1/systemone) that answers typed, calibrated questions in a single forward pass with no token generation. Deployment requires firmware 7.00–13.60 with kstuff-lite, etaHEN, ShadowMountPlus, elfldr and ftpsrv payloads loaded — a reminder that the entire stack lives downstream of a kernel exploit.

The published throughput numbers frame the real argument: 207 tok/s for Qwen 3.5 0.8B at Q4_K_M, 55 tok/s for a 9B, and roughly 20 tok/s for a 27B at UD-Q2_K_XL. That last figure is the interesting one, because 2-bit quantization is where capability degrades fastest, and commenters immediately split on whether a 27B at 2 bits is a usable assistant or a benchmark curiosity. The economics are the counter-argument: a PS5 draws well under a hundred watts in this role, so a commenter's estimate of ~$0.70/day of electricity for ~2M output tokens reframes a games console as a fixed-cost, always-on inference node for background workloads — log monitoring, camera review, long-running agent tasks. The bigger implication is architectural: unified memory consoles and APU boards are becoming the cheapest source of VRAM-shaped memory on the consumer market, and projects like this demonstrate that the software stack (Vulkan, llama.cpp, OpenAI-compatible APIs) is now portable enough to make that memory useful.

The security findings are where this stops being a hardware war story.
