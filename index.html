SeaStore: Redesigning Ceph's Storage Back End for CPU-Efficient NVMe Performance
⬆ 52 pts 💬 2 HN comments

Ceph's performance problem has never been raw disk speed — it has been the software stack sitting between the NVMe device and the client. The original FileStore backend wrote every object twice (journal, then backing filesystem) and leaned on a POSIX filesystem that was never designed for object semantics; BlueStore fixed much of that by taking raw block devices, managing allocation itself, and pushing metadata into RocksDB with checksums and inline compression. But BlueStore still carries a hybrid cost model: an LSM-tree whose compaction consumes CPU and write amplification, thread pools that contend across NUMA boundaries, and the OSD's PG-level locking and messenger layers. SeaStore is the attempt to remove that tax structurally rather than tune around it — a sharded, share-nothing backend built on Seastar, where each core owns its own segment-managed log-structured storage, avoiding cross-core synchronisation and the RocksDB dependency entirely.

The framing matters: the target is CPU efficiency per I/O on fast NVMe, not throughput on spinning media. That inverts the bottleneck. When a device can serve millions of IOPS, per-operation CPU cycles — memcpy, checksum, lock acquisition, allocator metadata, cache-line bouncing between cores — become the binding constraint, and a design that amortises those costs across threads stops scaling. Segment cleaning and garbage collection replace LSM compaction as the background tax, with the same fundamental trade-off between space amplification and write amplification. The community reaction, though sparse, is telling: the top comment cites the standing joke that Ceph is 'the most efficient way to turn 1,000,000 IOPS into 1000 IOPS' and reports it tested 'rather close to accurate,' while a second commenter frames the seven-year wait for SeaStore to ship as the real story — and defends Ceph's recovery model as making 'permanent data destruction' genuinely hard.

Gnomon: Git for Postgres Data
⬆ 28 pts 💬 5 HN comments

Gnomon is a PostgreSQL extension that ports Git-style workflows — branches, history, diffs, three-way merges and undo — into the database itself. Rather than provisioning a second copy or separate database, it runs inside the existing Postgres instance; after `create extension gnomon` and `gnomon.track('orders')`, it begins capturing history for tracked tables. A branch reads unchanged rows from main and stores only the rows a session modifies, so `gnomon.create_branch()` is described as instant and copy-free regardless of database size. Sessions are redirected with `gnomon.use()` or a connection string, letting existing SQL and ORMs read and write a branch without application changes. Merges are type-aware, present conflicts as rows, and can be undone; a change feed can stream every change to Kafka, NATS, a webhook or a file.

The agent story is the wrapper: `gnomon agent create support-bot` yields a role, branch and connection string, with Postgres enforcing isolation and merge rules — row/table limits and checks — even if an agent asks for main. TypeScript and Python SDKs model tasks as 'runs'; bindings cover Node, Go, Ruby, Java, Elixir, .NET and PHP, plus an MCP server. On Hacker News the launch drew only 28 points and 5 comments, and reaction was split between comparison shopping and skepticism. Supporters pointed to Neon and Xata as existing Postgres branching options; critics dismissed self-hosting plus event sourcing as a '$5/month' alternative, questioned a project 'started 2 weeks ago and was vibecoded solo', and objected that 'for agents' marketing adds little beyond an 'unnecessary MCP server.' The technical premise is compelling; the thread shows HN demanding operational evidence and less AI framing.

“A branch reads everything from main and keeps only what it changes, so it opens instantly and copies nothing, however big your database is” — the core technical claim that makes instant Postgres branching plausible.

Key Highlights
  • Runs as a PostgreSQL extension inside the existing database, avoiding copies or a second database.
  • Copy-on-write-style branches read unchanged data from main and store only modifications, enabling instant branch creation.
  • SQL API covers track, branch creation, session switching, diffs, three-way type-aware merges, conflicts as rows, and undo.
  • Agent isolation is enforced by Postgres roles and merge rules, with SDKs, language bindings, MCP server, and change-feed integrations.
  • HN comments compared it with Neon and Xata, proposed DIY VPS/event-sourcing alternatives, and questioned maturity and AI-centric marketing.
